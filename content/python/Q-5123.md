## 题目

**题目**：

```python
counter = 0
def worker():
    global counter
    for _ in range(100000):
        counter += 1
# 开 4 个线程跑完，counter 是多少？
```

**问**：两个线程同时 `i += 1` 会丢更新吗？怎么保证线程安全？

## 口述答案

> **会丢**。`counter += 1` 在字节码层面是三步：`LOAD`（读）→ `ADD`（加）→ `STORE`（写）。线程可能在任意一步之间被切换，两个线程都读到旧值，写回时只加了一次。
> GIL 只保证**单条字节码原子**，不保证"读-改-写"这个序列原子。解决方法是加锁，或改用 `queue`/原子操作。

## 讲深一层

```python
import threading
lock = threading.Lock()
counter = 0

def worker():
    global counter
    for _ in range(100000):
        with lock:            # ✅ 保护整个读-改-写
            counter += 1
```

| 操作 | 线程安全 | 原因 |
|---|---|---|
| `lst.append(x)` | ✅ | 单条字节码 + C 实现 |
| `d[k] = v` | ✅（单个赋值） | 单条字节码 |
| `i += 1` | ❌ | 三步，可被打断 |
| `d[k] += 1` | ❌ | 读-改-写 |
| `if k not in d: d[k] = 1` | ❌ | 检查与设置之间有窗口 |

**更推荐的做法：不共享**。用 `queue.Queue` 传消息，或者用 `concurrent.futures` 收集结果——共享状态是 bug 的源头。

**`threading.local()`**：需要每线程独立状态时用它，避免加锁。

## 高频追问

1. **加锁会让程序变慢很多吗？** —— 临界区短的话影响很小；锁竞争激烈时会退化。
2. **有原子计数器吗？** —— 没有内置的，用 `Lock` 或 `itertools.count`（C 实现，`next` 是原子的）。
3. **多进程还需要锁吗？** —— 需要，但要用 `multiprocessing.Lock`。

## 易错点

- 以为 GIL 保证一切线程安全
- 只锁写不锁读
- 用 `+=` 在多个线程改同一个计数
