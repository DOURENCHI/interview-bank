## 题目

**场景**：面试官给出业务外壳——校园网环境下的即时通讯软件，要求现场设计。它不是考你背 TCP/UDP 定义，而是考把网络与后端知识装进业务里落地。

**问**：怎么设计？从网络限制分析到模块拆解，给出整体方案。

## 口述答案

> 先分析校园网这个环境的特殊性，再按"连接→消息→存储→可靠性"四步走。校园网特点：内网用户密度高、出口有 NAT/防火墙、宿舍与教学楼跨网段、高峰拥塞。连接层：IM 是双向实时通信，选 WebSocket 长连接（HTTP 升级而来，能穿校园网常见防火墙），网关做连接保持与心跳；同一校区内网可直连，跨网段经服务器中转。消息层：登录鉴权（校园统一身份+Token）、消息转发按"目标在线→直推，离线→落库待拉"；群聊写扩散/读扩散按群规模选。存储层：离线消息表、会话索引、未读数；热点数据进 Redis。可靠性：断网重连后按序号补拉（客户端记 last_seq）、消息幂等去重（客户端生成 msg_id）、弱网下重试与退避。最后主动报瓶颈与延伸：万人群广播的写扩散放大、文件传输走对象存储+断点续传、接口设计与消息表结构可以继续展开。

## 讲深一层

```text
分层作答模板（场景题通用）：
1. 澄清需求：单聊/群聊？消息类型？量级？（先问再答，别闷头设计）
2. 环境约束：校园网 NAT/防火墙/拥塞 → 决定长连接选型
3. 核心链路：连接保持 → 消息转发 → 离线存储 → 同步补拉
4. 关键设计点各自一小段：鉴权 / msg_id 幂等 / last_seq 补拉
5. 主动报瓶颈：写扩散放大、热群、弱网；再报延伸：接口/表结构
```

| 子问题 | 决策 | 理由 |
|---|---|---|
| 长连接选型 | WebSocket | HTTP 80/443 可穿防火墙；全双工；校园网 NAT 友好 |
| 在线判定 | 网关心跳 + 状态表 | 断线半开连接靠心跳超时清理 |
| 离线消息 | 服务端落库 + seq 拉取 | 客户端掉线期间的消息不丢 |
| 消息幂等 | 客户端 msg_id 去重 | 重试导致重复发送是必然，去重放服务端 |

记忆锚点：**场景题=业务外壳+基础内核，先拆外壳拿约束，再拿内核知识填模块。**

## 高频追问

1. **为什么不用 HTTP 轮询？** —— 轮询延迟高且空轮询浪费；长轮询服务端 hold 住请求占用连接；WebSocket 一条连接双向推，校园网高密度下连接数与延迟都更优。
2. **NAT 环境下 P2P 直连可行吗？** —— 同内网可以；跨 NAT 要打洞（STUN/TURN），成本高，校园 IM 规模下服务器中转更稳。
3. **消息顺序怎么保证？** —— 单会话内服务端分配单调 seq，客户端按 seq 渲染与补拉；跨会话不承诺全局有序。

## 易错点

- 上来就画架构图，不先澄清需求与环境——场景题一半分在"问对问题"
- 只答"用 WebSocket"三个字，说不出穿透 NAT、心跳保活、断线补拉
- 忘了幂等：网络重试必然产生重复消息，服务端必须去重
- 不主动讲瓶颈与延伸，等面试官追问就被动
