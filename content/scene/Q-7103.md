## 题目

**场景**：现场有几十台户外设备（传感器 + MCU/SoC），要求把数据实时采上来、能在平台上远程监控，设备还分布在 4G 信号不稳的区域。

**问**：端侧采集、网络传输、云端监控三层怎么设计？重点讲弱网可靠性与远程运维。

## 口述答案

> 按"端—管—云"三层走，弱网可靠性和远程运维是这道题的题眼。端侧：MCU 采集传感器做本地缓存（环形缓冲+Flash 掉电保存），数据打上设备号+单调 seq+时间戳；采样、打包、上报节奏按低功耗要求分档（常态小包心跳、事件触发加密上报）。管侧：MQTT over 4G，QoS1 保证至少一次到达；弱网下断点续传靠"云端确认到哪个 seq、端侧从确认点重发"，配合指数退避重连；流量敏感则二进制协议（protobuf/自定义帧）而不是 JSON。云侧：接入网关做设备鉴权（一机一密）与消息入队（Kafka/EMQX），规则引擎分发到时序库（设备数据天然是时序数据，别塞进 MySQL 行存）；监控平台做实时仪表、阈值告警、设备影子（设备离线时平台仍持有最后状态）。远程运维：OTA 分批灰度升级（参考 A/B 双分区）、远程日志拉取、远程重启；安全上 TLS+密钥不落明文。

## 讲深一层

```text
数据流主干：
传感器 → MCU(缓存+seq) → MQTT(QoS1) → 接入网关(鉴权) → 消息队列
  → 时序库 ← 监控/告警
  → 指令下行通道(影子/OTA/日志)
```

| 设计点 | 决策 | 为什么 |
|---|---|---|
| 传输协议 | MQTT QoS1 + 二进制载荷 | 弱网重传内建；流量省 3-10 倍 |
| 断网续传 | 云端 ack 最大连续 seq | 端侧只缓存未确认段，Flash 压力可控 |
| 存储 | 时序库（TDengine/InfluxDB） | 按时间分区+降采样，行存库扛不住设备规模 |
| 远程状态 | 设备影子 | 设备离线时 UI 与规则引擎仍有可用状态 |

记忆锚点：**seq 是端云之间的信任锚——有它，断网续传、幂等去重、顺序补拉全都顺理成章。**

## 高频追问

1. **QoS1 会重复投递怎么办？** —— 端侧 seq 唯一，云端按 (设备号, seq) 幂等去重；这正是"至少一次+幂等=恰好一次"的标准组合。
2. **设备侧 Flash 寿命怎么管？** —— 环形缓冲均匀磨损+写放大控制（攒批再写），关键索引双扇区备份。
3. **几十台和几十万台方案差在哪？** —— 接入层从单 EMQX 到集群+LB，时序库分片，OTA 从手动分批到灰度编排；端侧协议不变——这就是分层的好处。

## 易错点

- 只画框不谈弱网——这题的区分度全在断网续传与重连策略
- 数据塞 MySQL 行存，忘了设备数据的时序属性
- OTA 一笔带过，追一句"升级到一半断电怎么办"就露馅（见 Q-6117）
- 没有设备鉴权概念，"平台谁都能连"是安全硬伤
