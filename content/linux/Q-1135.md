## 题目

**背景**：掉电一致性的场景题，面试官假设"程序用缓冲区攒数据，攒满才写"，问异常断电时怎么办。

**问**：缓冲区攒满再写，突然掉电时缓存里的数据怎么办？

## 口述答案

> 默认就是丢了，内存不保电。所以要按数据等级分开处理。一，可丢数据（访问日志、统计计数）：接受丢失，靠缩短 flush 周期控制丢失窗口。二，不可丢数据（订单、账务、配置变更）：必须"先落盘再返回成功"，即 `write` 之后 `fsync`，而且 fsync 要真到介质——磁盘自身 write cache 要用 `O_DIRECT` 或关掉盘缓存，否则 fsync 返回了数据还在盘上内存里。三，折中方案是 WAL：先追加一条记录并 fsync，再改内存状态，掉电后重放日志恢复。硬件上可以加超级电容或掉电检测中断，给 flush 抢时间。

## 讲深一层

| 数据等级 | 策略 | 最坏丢失 |
|---|---|---|
| 可丢 | 定期 flush | 一个周期 |
| 关键 | 每条 fsync | 0（到介质） |
| 高频关键 | WAL + 批量提交 | 一个提交批次 |

`fdatasync` 只刷数据不刷 mtime，比 `fsync` 省一次元数据写；group commit 把多个事务的 fsync 合并，是数据库提升吞吐的常用手段。

## 高频追问

1. **fsync 很慢怎么办？** —— 用 group commit 把并发事务合并成一次 fsync，或者先写 WAL 再异步 checkpoint
2. **掉电检测怎么做？** —— 用 PMIC 的掉电中断或电压比较器，检测到就停止接收新请求、flush 缓冲区，靠电容撑几十毫秒
3. **文件系统层还能帮什么？** —— `O_SYNC`/`O_DSYNC` 打开写即同步，barrier 保证顺序，但都要确认硬件真的遵守

## 易错点

- 认为"write 返回就安全"——只进了内核 page cache，掉电全丢
- 用 fsync 但不关盘缓存——RAID 卡或磁盘的 write cache 会让 fsync 提前返回，硬件层必须确认
- 对所有数据都逐条 fsync——吞吐会掉一个数量级，要按数据等级分级
