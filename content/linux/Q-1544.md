## 题目

**背景**：候选人说"任务丢进线程池跑就行"，面试官追问异常和提交方式的差异。

**问**：线程池里任务抛出的异常最终去了哪里？`submit` 和 `execute` 在异常处理上有什么区别？

## 口述答案

> 结论：**异常不会自己冒出来，取决于提交方式**。`submit` 返回 Future，异常被捕获存进 Future，只有调用 `future.result()` 时才重新抛出；没人取结果就**静默丢失**，日志里什么都没有。`execute` 无返回值，未捕获异常交给线程的 `UncaughtExceptionHandler`，默认打到 stderr，线程随后被销毁并由池补建。生产上要么统一用 submit + 回调里读 `future.exception()`，要么任务体内自己 try/except 记日志。

## 讲深一层

```python
f = pool.submit(work, x)
f.add_done_callback(lambda fut: log.error("task failed", exc_info=fut.exception())
                    if fut.exception() else None)
```
| | submit | execute |
|---|---|---|
| 返回 | Future | void |
| 异常位置 | 封装在 Future | 抛给线程 |
| 默认可见性 | 不取则静默 | 打到 stderr |
| 能否取消/超时 | 能 | 不能 |

## 高频追问

1. **线程池任务卡死不返回怎么办？** —— `future.result(timeout=...)` 拿 `TimeoutError`，但线程本身不会停；要用可中断的任务（检查取消标志）或独立进程池。
2. **`map` 的异常行为？** —— 迭代到出错那个元素时才抛，之前的已执行完；`as_completed` 可逐个取，避免一个失败拖垮全批。
3. **异常会不会让线程池泄漏线程？** —— 不会，工作线程会被复用；但任务里吞掉 `BaseException`（如 `SystemExit`）会污染状态。

## 易错点

- 用 `submit` 却从不 `result()`，线上失败率永远是 0
- 在任务里 `except: pass`，把可观测性彻底掐断
- 以为 `future.cancel()` 能停掉已在跑的线程
