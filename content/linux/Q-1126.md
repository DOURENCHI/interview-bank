## 题目

**背景**：并发编程的底层追问，聊到内存模型和内存屏障时，面试官要求区分两类"乱序"的来源。

**问**：编译器乱序和 CPU 乱序有什么区别？

## 口述答案

> 两者发生在不同阶段、约束手段也不同。编译器乱序在编译期，编译器在不改变单线程可见行为的前提下重排指令，比如提前无关的读、外提循环不变量，它只看得到当前编译单元，跨函数优化受限。CPU 乱序在运行期，由乱序执行引擎动态调度，靠寄存器重命名、乱序发射、store buffer 和无效队列实现，还会叠加缓存一致性带来的可见性延迟。两者都保持单线程语义，所以多线程下都要约束：编译器屏障（`asm volatile("" ::: "memory")`）只挡编译器，CPU 屏障（`mfence`、ARM 的 `dmb`）才挡硬件；C++ 的 `std::atomic` 配 memory_order 是一次性把两者都处理掉。

## 讲深一层

| 维度 | 编译器乱序 | CPU 乱序 |
|---|---|---|
| 时机 | 编译期静态 | 运行期动态 |
| 可见范围 | 单编译单元 | 全局 |
| 约束 | `asm volatile` 内存屏障 | `mfence`/`dmb` |
| 典型重排 | 读提前、常量外提 | StoreLoad 等四种 |

x86 是 TSO，只允许 StoreLoad 重排；ARM/POWER 是弱内存模型，四种重排都可能，所以同一段无锁代码在 x86 上"看起来对"，换 ARM 就崩。

## 高频追问

1. **`volatile` 能解决乱序吗？** —— 在 Java 里能（有内存语义），在 C/C++ 里只保证不被优化掉、不保证顺序，别混用两套语义
2. **为什么单例的双检锁要加 volatile？** —— 对象引用赋值和构造可能被重排，别的线程会看到"非 null 但字段未初始化"的半成品
3. **四种重排是哪四种？** —— LoadLoad、StoreStore、LoadStore、StoreLoad，最后一种代价最高，`mfence` 主要就是挡它

## 易错点

- 认为"用了 volatile 就没有乱序"——C++ 的 volatile 只管可见性和不被优化，不管重排
- 把 x86 的经验套到 ARM——TSO 下很多无锁代码侥幸能跑，弱内存模型下必须显式屏障或 acquire/release
- 只答"CPU 会重排指令"——漏掉编译器这一层，而很多线上问题恰恰是 `-O2` 之后才出现
