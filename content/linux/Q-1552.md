## 题目

**背景**：前面聊到长任务会保存任务状态，面试官接着问检查点和幂等的关系。

**问**：检查点和幂等机制是什么关系？进程崩溃恢复时，怎样避免已经执行过的步骤被重复执行？

## 口述答案

> 结论：**检查点管"进度"，幂等管"安全"**。检查点记 offset、step，负责缩短重放距离；幂等保证同一操作做多次等于做一次。单靠检查点不够：写检查点和提交副作用不在同一事务，崩在中间就会重放最后一批。做法是让副作用本身幂等——按 `(task_id, step)` 唯一键 upsert；顺序必须是**先写数据、再推检查点**。即 at-least-once 投递 + 幂等消费 = 效果上的 exactly-once。

## 讲深一层

```
顺序：先写数据（幂等）→ 再推进 checkpoint
崩溃点 A：数据已写、cp 未推进 → 重放 → 被唯一键吸收 ✔
崩溃点 B：数据未写、cp 未推进 → 重放 → 正常补写 ✔
反序：先推 cp 再写数据 → 崩在中间 → 数据永久丢失 ✘
```
| 机制 | 解决 | 不解决 |
|---|---|---|
| checkpoint | 重放开销 | 重复执行 |
| 幂等键 | 重复执行 | 进度丢失 |

## 高频追问

1. **为什么不能把 checkpoint 和数据放一个事务？** —— 数据源往往是外部系统（Kafka offset、第三方 API），无法与本地库同事务；Kafka 事务性写出要求下游支持。
2. **流处理里怎么对应？** —— Flink 的 barrier 对齐 + 两阶段提交 sink，本质也是"状态快照 + 幂等/事务写"。
3. **检查点存什么？** —— 输入 offset、聚合中间态、待发消息队列；不要存能从源头重算的派生数据。

## 易错点

- 先推进 checkpoint 再写数据，崩溃即丢数据
- 认为"有检查点就不会重复"，忽略提交边界
- 检查点里存了巨大的中间态，写一次比重算还慢
