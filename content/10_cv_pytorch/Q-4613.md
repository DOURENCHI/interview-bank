## 题目

**背景**：字节 AI Agent 开发二面的推理服务题。考官要的是把 LLM 推理的两个阶段按「算力瓶颈还是带宽瓶颈」拆开讲，再落到长输入和长输出两类业务的优化差异——这是做推理服务的基本功。
**问**：先讨论模型服务：Prefill 和 Decode 的主要工作有什么不同？长资料输入和长脚本输出，优化重点一样吗？

## 口述答案

> 两个阶段干的事和瓶颈完全不同。Prefill 处理输入 prompt：把所有输入 token 一次性并行送进模型，算出每个位置的 KV，本质是一次大矩阵乘，算术强度高，是算力瓶颈，GPU 利用率上得去。Decode 是自回归生成：每步只算一个 token，但要读全部历史 KV 过一遍完整模型，本质是反复访存的小矩阵乘，算术强度极低，是带宽瓶颈——时间几乎都耗在搬 KV Cache 和权重上。
> 所以优化重点是反着来的。长输入场景（RAG、长文档总结）瓶颈在 Prefill 的计算量，思路是省计算：前缀 KV 复用——system prompt 和固定文档只算一次存下来，后续请求直接复用；Prompt Cache 和上下文压缩同理；在线服务里用 chunked prefill 把大 prefill 切块与 decode 混排，防止一个三万 token 的请求把整个 batch 的生成卡住几百毫秒。
> 长输出场景（长脚本生成）瓶颈在 Decode 的每步访存，思路是省访存和摊薄访存：KV Cache 管理是核心——PagedAttention 分页管理消碎片；KV 量化压缩体积；连续批处理让新请求即插即用提高利用率；投机解码用小模型起草、大模型并行验证，一次前向出多个 token，把串行的 Decode 部分并行化。
> 总结成一句：Prefill 优化算力，少算；Decode 优化带宽，少搬。工程上 SLA 也是分开定的——首 token 延迟 TTFT 看 Prefill，每 token 间隔 TPOT 看 Decode，两类业务对两者的敏感度不同：问答类在乎 TTFT，长文生成在乎 TPOT 稳定。

## 讲深一层

- compute-bound 与 memory-bound 的判据是算术强度（FLOPs 比访存字节数）：Prefill 大 GEMM 高强度、Decode GEMV 低强度，这决定了优化方向相反。
- KV Cache 体积公式：层数×2×kv_heads×head_dim×序列长×每元素字节数——128K 上下文单请求可占几十 GB，这是 PagedAttention、KV 量化、稀疏化共同的动机。
- chunked prefill 解决的是调度公平性而不是总吞吐：不切块的话长 prefill 会阻塞同 batch 所有 decode 请求，TPOT 抖动。
- 投机解码的前提是小模型与大模型分布足够接近，且验证用拒绝采样保证输出分布与大模型一致——加速是「白拿」的，不损失正确性。

## 高频追问

1. Decode 为什么不能像 Prefill 一样并行？——自回归每步依赖上一步输出，本质串行；只能靠投机解码猜多个再验证、或 beam 类结构换并行度
2. TTFT 和 TPOT 分别由什么决定？——TTFT 主要看 Prefill 时长（输入长度×算力×当前负载），TPOT 看 Decode 每步（KV 大小×带宽×batch 竞争），监控和优化分开做
3. 长上下文为什么常用滑动窗口或稀疏注意力？——全注意力 Prefill 计算 O(n²) 爆炸、KV 随长度线性膨胀；窗口和稀疏把两头都压下来，代价是长距离依赖的损失

## 易错点

- 把 Prefill 和 Decode 说成「前后两步没啥不同」——算力与访存的瓶颈差异就是这题的全部考点
- 长输入优化只会答「加卡」——Prefill 可并行可切分，先省算（前缀复用、压缩）再谈扩容
- 不提 TTFT/TPOT 分属两阶段——工程 SLA 就是这么定的，混在一起显得没做过推理服务
