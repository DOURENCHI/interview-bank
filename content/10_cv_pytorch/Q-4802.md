## 题目

**背景**：优化检索延迟时，面试官问"查询向量化前置"和"跨请求缓存"是不是一回事。

**问**：查询向量化前置与跨请求缓存有什么区别？

## 口述答案

> 前置是时间维度前移：在请求进入检索前就把 query embedding 算好（同步提前、与改写并行、或批量预热），每次请求仍然要算，只是不占关键路径，收益是降延迟。
> 跨请求缓存是请求维度复用：以归一化后的 query 文本 + 模型版本 + 参数为 key，存向量或检索结果，多个请求命中同一 key 就直接复用，收益是省算力也降延迟。
> 一个是"提前做"，一个是"不重复做"；前者不减少总计算量，后者才会。

## 讲深一层

缓存 key 必须包含 (model_version, normalize, query_prefix, text)，漏掉任一项都会读到脏向量。
| 方案 | 降延迟 | 降成本 | 风险 |
|---|---|---|---|
| 前置 | 是 | 否 | 链路复杂 |
| 精确缓存 | 是 | 是 | 命中率低 |
| 语义缓存 | 是 | 是 | 相似但不等价，答错 |

## 高频追问

1. **语义缓存什么时候危险？** —— 个性化、强时效、数字精确类查询，相似 query 的答案可能完全不同。
2. **缓存怎么失效？** —— 按模型版本和索引版本打 tag，升级时整批失效，不要逐条清。
3. **前置能省多少？** —— 通常几十毫秒，占检索链路的大头，但总延迟还受 rerank 和生成影响。

## 易错点

- 把两者混为一谈，以为做了前置就不需要缓存。
- 缓存 key 不带模型版本，换模型后读到旧向量。
- 语义缓存阈值设太松，把不同意图的 query 判成同一个。
