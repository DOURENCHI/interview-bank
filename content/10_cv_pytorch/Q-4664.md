## 题目

**背景**：面试官从分词聊到多语言文本处理，抓住"看起来是一个字符"这一点，问后端长度和前端位置为什么对不上。

**问**：既然文本会被转换，同样看起来是一个字符，Python 的长度和前端位置为什么可能对不上？

## 口述答案

> 因为三套计数单位不同。Python 3 的 str 长度按 Unicode code point 算，一个 emoji 通常是 1 个 code point，但带肤色修饰或家庭组合的 emoji 由多个 code point 加零宽连接符组成，len 会变成好几个。JavaScript 的字符串是 UTF-16，非 BMP 字符要占两个 code unit，所以 .length 又是另一个数。而用户眼里的"一个字符"是 grapheme cluster，也就是渲染出来的一个字形。三者不一致，后端用 code point 偏移去截前端传来的位置就会切错，典型表现是 emoji 被切成半个乱码，或者高亮位置偏一格。

## 讲深一层

以 "👨‍👩‍👧" 为例（4 个 emoji + 2 个 ZWJ）：

| 视角 | 计数 |
| --- | --- |
| Python `len()`（code point） | 多个，含 ZWJ |
| JS `.length`（UTF-16 unit） | 约为 code point 的 1–2 倍 |
| grapheme cluster | 1 |

解法是统一偏移语义：接口层约定用 code point 或 UTF-8 字节偏移，前端用 `Intl.Segmenter` 或 `Array.from` 转成 code point 数组再映射。跨语言时尤其容易出错，Java 的 String 也是 UTF-16，C++ 的 `std::string` 是字节，偏移单位不声明清楚，两边永远对不上。

## 高频追问

1. **后端怎么安全截断** —— 按 code point 切片，不要按字节；更严格按 grapheme 边界切
2. **高亮偏移怎么对齐** —— 让后端返回 code point 区间，前端做一次转换表，别让两边各算一套
3. **数据库排序和长度限制受影响吗** —— 会，varchar 长度在不同 DB 里可能按字节或按字符算，要实测

## 易错点

- 说"Python len 就是字符数" —— 是 code point 数，不等于用户感知字符
- 用字节长度当偏移 —— UTF-8 中文 3 字节，直接切会切碎
- 只处理 emoji 不处理组合字符 —— 泰文、天城文的组合元音同样是一个 grapheme 多个 code point
