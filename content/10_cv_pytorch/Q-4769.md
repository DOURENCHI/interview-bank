## 题目

**背景**：快手大模型算法岗一面的推理延迟量化题。考有没有真正理解 prefill 阶段的计算模型：首 token 延迟由什么决定、prompt 长度和它的关系是不是简单线性。判断点在于能否区分「计算量线性增长」和「延迟非线性响应」之间的差别。
**问**：Prompt 长度加倍，首 token 延迟是否也会加倍？

## 口述答案

> 先定位：首 token 延迟基本就是 prefill 时间——模型要对整段 prompt 做一次并行前向，算完最后一个位置才能吐第一个 token，之后就是逐 token 的 decode。prefill 的计算量正比于 prompt token 数，所以「理论趋势是近似线性」，但严格说不会精确加倍，有三个修正因素。
> 一是固定开销占比：kernel 启动、权重加载、调度这些不随 prompt 长度变的成本，在短 prompt 时占大头——prompt 从 100 token 加到 200，延迟可能几乎不变，因为都在底噪里；prompt 从 8K 加到 16K，才接近线性。二是算力饱和：GPU 是批量并行处理 prompt 的所有位置，prompt 短时算力没用满，加长 prompt 是「免费」并行；超过某个长度后算力打满，再翻倍就要排队等算力，延迟开始超线性。三是系统因素：KV Cache 写入翻倍、分页管理开销、长上下文时 attention 的 O(n²) 部分（prefill 里 token 之间的 attention 计算是平方项）会逐渐显现——短上下文被并行掩盖，长上下文里平方项会把增长推到超线性。
> 所以完整回答是：短 prompt 区间近似常数（固定开销主导），中段近似线性（并行消化计算量），长 prompt 区间趋向超线性（算力墙+attention 平方项）。工程上这就是为什么长上下文优化要靠 FlashAttention（压平方项的访存）、Chunked Prefill（把长 prompt 切块避免一次打满）、Prefix Cache（系统提示词重复利用，prefill 直接跳过公共前缀）。

## 讲深一层

- prefill 是 compute-bound、decode 是 memory-bound：prefill 一次算一批，算力打满；decode 逐 token 读全部权重，卡在带宽。所以 prompt 加长主要影响 prefill，回答里点出这个二分是深度信号。
- Attention 的平方项在 prefill 里为什么平时感觉不到：QK^T 是 n²但一次矩阵乘并行算完，n 不大时被算力吸收；n 上万后即使并行也压不住，FlashAttention 通过分块在线 softmax 避免物化 n²矩阵，省的是显存和访存而不是计算量。
- Prefix Cache/系统提示词缓存是生产环境降首 token 延迟最有效的一招：多轮对话里公共前缀占大头，命中后 prefill 只算增量部分，首 token 延迟能降一个量级。

## 高频追问

1. 那 decode 的延迟和什么成正比？——每步读全部权重+已有 KV，与已生成长度线性相关，与 batch 数也相关，所以长回答尾部越来越慢
2. Chunked Prefill 解决什么？——长 prompt 一次 prefill 会挤占在线 decode 请求的算力（ITL 尖刺），切块交错调度，牺牲一点 TTFT 换整体尾延迟平稳
3. 怎么实测验证线性关系？——固定其他条件，扫 prompt 长度画 TTFT 曲线，看拐点在哪，拐点即该卡的 prefill 算力饱和位置

## 易错点

- 直接答「会，线性加倍」——趋势对但丢掉了固定开销、算力饱和、平方项三个修正，面试官会追「真的严格线性吗」
- 把首 token 延迟归到 decode——首 token 是 prefill 产物，decode 是第二 token 开始的事，概念错位直接扣分
- 只谈理论不谈系统——生产里 Prefix Cache、Chunked Prefill、FlashAttention 才是控制 TTFT 的实际手段，能落到这些说明做过推理优化
