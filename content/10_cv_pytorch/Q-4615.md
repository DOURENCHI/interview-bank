## 题目

**背景**：对方给你一份线上出过问题的脚本，让你评估"能不能复现"。

**问**：要复现一份有问题的脚本，只记录模型名和提示词够吗？怎样区分"输入可追溯"和"输出可复现"？

## 口述答案

> 不够，"模型名 + 提示词"只记录了意图，没记录实际输入。要补三类：
> 1. 输入侧：模板版本、system prompt、few-shot、检索到的 chunk 及顺序、工具返回、渲染后的最终 prompt；
> 2. 解码侧：模型快照、temperature、top_p、top_k、max_tokens、stop、seed；
> 3. 链路侧：编排代码版本、后处理与安全过滤。
> "输入可追溯"是能还原喂进去的每个字节；"输出可复现"要求同输入同参数得同输出。但 GPU 浮点非结合、batch 变化、MoE 路由、供应商静默升级都会破坏它，通常只能做到分布可复现。

## 讲深一层

| 层级 | 记录内容 | 作用 |
|---|---|---|
| 可追溯 | prompt 全文 + 模板 hash + 检索文档 id | 事后归因、审计 |
| 可复现 | 模型快照、采样参数、seed、request id | 重跑对比 |
| 可回归 | 输出 + 判定结果 + 人工标注 | 建 badcase 集 |

即使 temperature=0 也不保证逐字一致：浮点归约顺序随 batch/显卡变化，MoE 的 token 路由也可能不同。可量化指标是"同输入重复 n 次的完全一致率"，工程上更常用语义一致率。

## 高频追问

1. **seed 固定了就一定可复现吗？** —— 不一定，seed 只固定采样随机数，固定不了 kernel 的非确定性归约和多卡通信顺序。
2. **线上不能存全量 prompt 怎么办？** —— 存 hash + 脱敏后的摘要，关键字段单独落库，出问题时用 hash 反查同批次样本。
3. **供应商升级模型怎么防？** —— 锁定带日期的快照版本，网关层记录实际路由到的版本号，升级走灰度而不是静默替换。

## 易错点

- 只记 prompt 文本，不记 chat template 与 system prompt，重跑必然不同。
- 把"重跑结果不一样"直接判成模型有 bug，忽略采样参数和 batch 非确定性。
- 复现时换了 RAG 索引版本，却以为输入没变。
