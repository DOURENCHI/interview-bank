## 题目

**背景**：阿里二面的大模型基础设施题，考你能不能把 KV Cache 从「听说过」讲到「会算显存账」，这是推理岗和 Agent 后端岗的分水岭题。
**问**：KV Cache 缓存的是什么？为什么能加速，显存占用怎么估算？

## 口述答案

> KV Cache 缓存的是自回归生成过程中，每层每个历史 token 的 Key 和 Value 投影。能加速的原理要从因果注意力说起：生成第 t 个 token 时，它的 Q 要和全部前缀的 K、V 做交互；而因果 mask 下历史 token 的 K/V 永远不随新 token 变化，所以每步只需计算新 token 自己的 Q/K/V 三个向量，再和缓存里的历史 K/V 做注意力——否则每生成一个 token 都要对全部前缀重新做一遍前向，复杂度是每步 O(t²·d)，缓存后降到 O(t·d)，这是一阶多项式对平方级的差距，长文本下是几十倍的速度差。显存估算公式：2（K 和 V 两份）× 层数 × KV 头数 × head_dim × 序列长度 × batch × 每元素字节数。拿 7B 级模型举例：32 层、32 头、head_dim 128、fp16、4096 上下文、batch 1，每 token 约 2×32×32×128×2B=512KB，4K 序列就是 2GB；如果用了 GQA、KV 头只有 8 个，直接除以 4 降到 512MB。这也是为什么长上下文服务都上 GQA/MQA——KV 头数是显存账里最值钱的杠杆。

## 讲深一层

- 为什么只缓存 K/V 不缓存 Q：注意力只需要「新 token 的 Q」去查历史，历史 token 的 Q 从未被再次使用。
- GQA/MQA 是显存与质量的折中：KV 头数从 32 降到 8/1，显存线性降，质量轻微损失；MHA→GQA 是当前主流默认。
- prefill 与 decode 两个阶段：prefill（吃 prompt）可以整段并行算好首批 KV，decode 逐 token 增量追加，首 token 延迟主要由 prefill 决定。
- 工程进化：PagedAttention（vLLM）把 KV 切页管理解决碎片、KV 量化（int8/fp8）再压一半、前缀缓存让多轮对话复用公共前缀。
- 估算时要盯三个容易漏的因子：batch（线性放大）、精度（fp16→int8 减半）、是否共享前缀（system prompt 只存一份）。

## 高频追问

1. batch 拉大时显存怎么变？——KV 显存随 batch 严格线性增长，这也是并发上限的主要约束，常先于模型权重成为瓶颈
2. 为什么长上下文贵？——KV 随序列长度线性涨，100K 上下文的 KV 可能超过权重本身，所以有滑窗、压缩、稀疏注意力这些省 KV 的路线
3. 多轮对话怎么复用？——历史轮的 KV 原样保留，新轮只算增量；若前缀相同可跨请求共享（前缀缓存/Radix 树管理）

## 易错点

- 把它说成「缓存模型计算结果」的通用缓存——它是注意力机制的结构性缓存，和 LRU 那种应用层缓存完全是两回事
- 显存估算漏掉 KV 头数或 batch——MHA 和 GQA 差 4 倍、batch 8 再差 8 倍，答不出公式直接露馅
- 以为 KV Cache 能省计算时间但不占显存——它是拿显存换计算，显存恰恰是它最大的代价
