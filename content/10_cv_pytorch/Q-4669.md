## 题目

**背景**：前面聊了输出结构，面试官把同样的思路推到工具入参上，考的是对 function calling schema 的理解。

**问**：刚才说的是输出结构。Function Calling 的输入参数怎么设计？必填、可选、有默认值是一回事吗？

## 口述答案

> 不是一回事。required 是"模型必须给"，optional 是"可以不给"，default 是"不给时服务端补什么"，三者语义不同，落在不同层。设计原则：能推断的参数不要让模型填，比如时区从会话上下文取，让模型填只会多一个出错点；有默认值的参数，默认值要放在服务端代码里，不要只写在 schema 描述里，因为模型不知道你的默认值，很可能自己编一个；必填项越少越好，每多一个必填就多一次编造机会。参数尽量用 enum 代替自由字符串，描述里写清单位和格式，比如时间用 ISO 8601。服务端必须做 schema 校验和业务校验，模型给的参数永远当不可信输入。

## 讲深一层

| 概念 | 语义 | 该放哪 |
| --- | --- | --- |
| required | 模型必须产出 | schema |
| optional | 模型可省略 | schema |
| default | 省略后的取值 | 服务端代码，不是 schema |

反模式：在 schema 里写 `"default": "Asia/Shanghai"` 就以为模型会照做——多数实现只是把它当描述文本，模型仍可能填别的值。真正生效要在服务端补默认值。

## 高频追问

1. **参数太多怎么办** —— 拆成多个工具，或者用一个粗粒度工具加受控的自由字段，别让模型一次填十几个
2. **怎么做参数纠错** —— 校验失败时把错误信息结构化回传给模型重试一次，还错就转澄清提问
3. **嵌套对象要注意什么** —— 层级越深模型越容易漏字段，能拍平就拍平

## 易错点

- 把 required 和 default 当成一回事 —— 一个约束模型，一个兜底服务端，混淆会导致参数大面积缺失
- 默认值只写在描述里 —— 模型不会执行你的默认值
- 完全信任模型给的参数 —— 直接拿去做写操作，是注入和越权的高发点
