## 题目

**背景**：面试官顺着提示词往下问容量：笔记、示例、历史对话一起塞，迟早会撞上下文上限。

**问**：沿着提示词继续问：笔记、示例和历史对话越来越长，超过上下文限制怎么办？直接截掉最后一部分行不行？

## 口述答案

> 不行，最后一部分往往是最新的指令和当前问题，截掉它等于把任务删了。我的做法是分层处理：system prompt 和输出 schema 永不压缩；当前任务和最近几轮对话保留原文；更早的轮次做摘要或抽取成结构化事实；长笔记不整体塞进去，而是切块建索引，按当前子任务检索相关片段。如果单个文档就必须整体处理，用 map-reduce，分块出题再合并去重。截断只能在语义边界上做，按段落或句子切，绝不能切在 JSON 或代码中间，否则模型收到的输入本身就是坏的。

## 讲深一层

| 内容 | 策略 | 原因 |
| --- | --- | --- |
| system + schema | 永不裁剪 | 决定行为边界 |
| 当前问题 + 近 N 轮 | 原文保留 | 指代和意图都在这里 |
| 更早轮次 | 摘要 / 结构化抽取 | 只要结论不要过程 |
| 长笔记 | 分块检索 | 相关性和成本 |
| 超长单文档 | map-reduce | 无法局部取舍 |

## 高频追问

1. **摘要会不会丢关键信息** —— 会，所以数值、否定约束、未决事项要抽成结构化字段单独保留
2. **怎么决定检索哪些块** —— 按当前子任务做 embedding 召回，再按 token 预算截断，别按文档顺序取
3. **怎么发现压缩导致的退化** —— 建一组需要跨段信息的长文档用例，专门测压缩前后的一致性

## 易错点

- 答"截掉最前面的历史" —— 会丢掉用户早期设定的约束，比截尾部更隐蔽
- 按字符数硬切 —— 切在 JSON 中间，模型直接解析失败
- 认为扩大上下文窗口就解决了 —— 成本和注意力稀释都随长度恶化，不是免费方案
