## 题目

**背景**：讨论 RAG 检索链路时，面试官问起 query 向量化放在哪一步。

**问**：Embedding 前置与否，对准确率和召回率分别有什么影响？

## 口述答案

> 先把"前置"拆成两种含义，结论完全不同。
> 如果指把 query 向量化从检索服务前移到请求入口做预计算：只要模型版本、归一化方式、query instruction 不变，向量逐位一致，准确率和召回率都不变，收益只在延迟。
> 如果指链路顺序（先向量召回再过滤，还是先规则过滤再向量召回）：影响很大。先过滤会缩小候选池，Recall@K 的上限被压死，长尾 query 掉得最明显；只走向量单路、丢掉 BM25，型号、编号这类精确匹配召回下降，准确率跟着掉。真正改变指标的是候选集与输入，不是"前置"这个动作。

## 讲深一层

Recall@K = 前 K 个结果中命中相关文档的比例；前置预计算的一致性依赖缓存 key 必须包含 `(model_version, normalize, query_prefix, text)`，漏掉 query prefix（如 e5/bge 要求 `query: `）会让向量整体偏移，召回静默下降几个点。

## 高频追问

1. **预计算能省多少延迟？** —— 一次 embedding 通常几十毫秒，占检索链路大头；命中缓存可把 P99 压到个位数毫秒。
2. **先过滤再向量召回什么时候是对的？** —— 有强约束（租户、权限、类目）时必须先过滤，否则会召回越权内容，代价是接受召回上限下降。
3. **怎么验证前置没伤召回？** —— 固定同一批 query，对比前置前后的 Recall@K 与 top-10 重合率，重合率低于 99% 就说明输入变了。

## 易错点

- 认为"把 embedding 提前算"能提升召回——它只影响延迟。
- 前置时换了模型或忘了加 query instruction，却把指标下降归因于链路顺序。
- 只保留向量召回，丢掉关键词通道，罕见实体直接召不回。
