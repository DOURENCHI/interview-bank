## 题目

**背景**：接着 Skill 的话题，面试官问能力该封装成 Skill 还是写在代码里。

**问**：Skill 的边界怎么定？什么该进 Skill，什么该留在代码里？

## 口述答案

> 按两个维度切：是否需要模型判断、是否稳定复用。需要语义理解、步骤不固定、要动态选工具的做成 Skill；规则明确、纯计算、强一致要求的留在代码里。有三类必须留代码：权限与风控判定、资金计算、事务边界。Skill 适合做编排和表达，不适合做最终裁决，因为它不确定也难单测。边界划错的信号是 Skill 里塞满 if-else，或代码里到处调模型。

## 讲深一层

|  | 稳定复用 | 一次性的 |
|---|---|---|
| 需模型判断 | Skill | 直接 prompt |
| 规则明确 | 代码/函数 | 代码 |

判断口诀：**能不能写出确定的单测**——能，就留代码；只能靠评测集，才考虑 Skill。

## 高频追问

1. **Skill 里能不能写代码？** —— 可以，Skill 可以调确定性工具，把计算交给工具而不是让模型算。
2. **边界错了有什么后果？** —— 权限判定放 Skill 里等于把风控交给模型，可被 prompt 注入绕过。
3. **怎么演进？** —— 先代码跑通，稳定后再抽成 Skill；不要把没跑通的流程提前 Skill 化。

## 易错点

- 什么都说成 Skill，包括纯 CRUD
- 让模型做金额计算和权限判断
- Skill 内部又是大段 if-else，等于用自然语言写代码
