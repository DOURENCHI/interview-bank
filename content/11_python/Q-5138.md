## 题目

**现象**：一个常驻的 Python 服务，内存每小时涨 20 MB，几天后 OOM。

**问**：Python 进程内存一直涨，怎么排查？

## 口述答案

> 先分清是**真泄漏**（对象没释放）还是**假泄漏**（缓存/arena 不归还）。用 `tracemalloc` 拍两次快照做差集，能直接定位到分配的代码行；再用 `gc.get_objects()` 看哪类对象在涨。
> 常见真凶：**全局缓存无上限**、**循环引用 + `__del__`**、**闭包持有大对象**、**matplotlib 图未 close**、**日志 handler 重复添加**。

## 讲深一层

```python
import tracemalloc, gc

tracemalloc.start(25)                    # 保留 25 帧
snap1 = tracemalloc.take_snapshot()
# ... 跑一段时间 ...
snap2 = tracemalloc.take_snapshot()

for stat in snap2.compare_to(snap1, 'lineno')[:10]:
    print(stat)                          # 涨得最多的代码行

print(len(gc.get_objects()))             # 对象总数是否持续增长
```

| 现象 | 可能原因 |
|---|---|
| 对象数持续涨 | 真泄漏（引用未释放） |
| 对象数稳定但 RSS 涨 | 内存碎片/arena 不归还（假泄漏） |
| 只在某接口后涨 | 该接口的缓存或临时对象 |
| 涨到某个值就稳 | 缓存达到上限，正常 |

**常见修复**：
1. `functools.lru_cache(maxsize=N)` 一定要设上限；
2. 用 `weakref.WeakValueDictionary` 做缓存，让对象可被回收；
3. `del` 掉不再用的大对象，并避免闭包意外持有；
4. 绘图后 `plt.close(fig)`。

**假泄漏的处理**：`MALLOC_ARENA_MAX=2` 限制 arena 数量，或定期重启 worker。

## 高频追问

1. **`gc.collect()` 能解决吗？** —— 只对循环引用有效，对"还有引用"的泄漏无效。
2. **`__del__` 有什么问题？** —— 有 `__del__` 的对象在循环引用里可能不被回收（3.4 起已改善）。
3. **怎么监控？** —— `psutil` 定期打 RSS，配告警。

## 易错点

- 无上限的 `lru_cache` / 全局 dict
- 用 `gc.collect()` 掩盖真实引用泄漏
- 只看 RSS 不看对象数
