## 题目

**题目**：面试官问"Python 多线程是假的多线程吗"，你会怎么回答？

**问**：GIL 是什么？它限制了 Python 的什么能力？

## 口述答案

> GIL 是 **CPython 解释器的全局锁**：保证同一时刻只有一个线程在执行 Python 字节码。所以多线程**不能并行跑 Python 计算**。
> 但它是**实现细节，不是语言规范**——Jython、IronPython 没有 GIL；CPython 3.13 起还提供了 free-threaded 的实验构建（PEP 703）。
> 关键在于：**GIL 在执行 I/O 和调用 C 扩展时会释放**，所以多线程对 I/O 密集任务依然有效。

## 讲深一层

| 场景 | 多线程有效吗 | 原因 |
|---|---|---|
| 网络请求、读写文件 | ✅ | I/O 时释放 GIL |
| 调用 numpy / OpenCV | ✅（部分） | C 扩展内部释放 GIL |
| 纯 Python 计算 | ❌ | 抢同一把锁，还有切换开销 |
| 需要真正并行 | 用多进程 | 各自独立解释器 |

```python
import sys
sys.getswitchinterval()      # 默认 0.005 秒，线程切换间隔
```

**为什么要有 GIL**：CPython 用引用计数管理内存，多线程同时改计数会崩溃；加锁最省事，也保护了大量 C 扩展的线程安全假设。

**代价**：多核机器上 CPU 密集任务无法加速，这是 Python 在高性能计算上的主要短板（靠 numpy/Cython/C 扩展绕过）。

## 高频追问

1. **GIL 会取消吗？** —— 3.13 起有 free-threaded 构建，但生态兼容需要时间，主流仍是带 GIL。
2. **多线程一定比单线程快吗？** —— 不一定，切换有开销；I/O 密集才有明显收益。
3. **GIL 能手动释放吗？** —— C 扩展里可以 `Py_BEGIN_ALLOW_THREADS`，纯 Python 不行。

## 易错点

- 说"Python 多线程是假的"（I/O 场景是真的有用）
- 认为 GIL 是语言特性
- 用多线程做 CPU 密集计算
