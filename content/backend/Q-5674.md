## 题目

**场景**：SHEIN 一面 MySQL 标配题（原题面含隔离级别枚举 + 三者区别 + MySQL 8 默认级别）。基础但必考：定义要准、级别矩阵要熟、能点出 InnoDB 默认 RR 下各自的防线。

**问**：脏读、不可重复读、幻读的区别是什么？四个隔离级别分别防住哪些？

## 口述答案

> 三个问题是「读到不该读的数据」的三种形态，关键区别在**数据是否提交、是否是同一行**：
> - **脏读**：读到了别人**还没提交**的数据，对方一回滚，我读到的就是从未存在过的数据——最严重。
> - **不可重复读**：同一事务内两次读**同一行**，结果不同——期间别人把它**更新并提交**了。矛盾在「更新」，对象是行内容。
> - **幻读**：同一事务内两次**范围查询**，第二次多出/少了**别的行**——期间别人**插入/删除**了范围内的行。矛盾在「插入」，对象是行数。
> 记法：脏读看**提交没提交**，不可重复读看**同一行的 UPDATE**，幻读看**范围内的 INSERT/DELETE**。
>
> 隔离级别逐级升级：**RU**（读未提交）什么都不防；**RC**（读已提交）防脏读——只让读已提交数据；**RR**（可重复读）再防不可重复读——事务内读到的是同一版本快照；**SERIALIZABLE** 全防，读也加锁，并发最差。MySQL InnoDB 默认 **RR**，靠 MVCC（快照读不加锁）+ 当前读时的 next-key lock（记录锁 + 间隙锁）基本防住幻读——注意是「基本」：先快照读再当前读混用仍可能看到新行，RR 并没有 100% 消灭幻读。

## 讲深一层

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现要点 |
|---|---|---|---|---|
| READ UNCOMMITTED | ✗ 会发生 | ✗ | ✗ | 直接读最新数据 |
| READ COMMITTED | ✓ 防 | ✗ | ✗ | 每条语句生成 ReadView |
| REPEATABLE READ（InnoDB 默认） | ✓ | ✓ 防 | 基本 ✓ | 首次查询定 ReadView；当前读加 next-key lock |
| SERIALIZABLE | ✓ | ✓ | ✓ | 读也加共享锁 |

InnoDB 在 RR 下其实把「不可重复读」和大部分「幻读」一起解决了：快照读靠 MVCC 版本链，当前读（FOR UPDATE/UPDATE）靠间隙锁挡住区间内插入。

**判断技巧**：三个现象各抓一个关键词——**提交**（脏读）、**更新**（不可重复读）、**插入**（幻读）；先判断现象再查级别矩阵，别把「同一行变了」和「多了一行」混为一谈。**记忆锚点**：「脏在未提交，误在更新行，幻在多出行」。

## 高频追问

1. **RR 彻底解决幻读了吗？** —— 没有。快照读看不到新行，但事务内先普通 SELECT 再 SELECT FOR UPDATE（当前读），别的事务刚提交的插入就会出现。
2. **RC 和 RR 在 MVCC 上的差别？** —— ReadView 生成时机：RC 每条语句一次（所以能看到别人新提交的值），RR 事务首次查询一次并复用（所以可重复读）。
3. **为什么互联网公司常改用 RC？** —— RC 无间隙锁，死锁更少、并发更好，且 binlog 用 ROW 格式后主从不乱了；Oracle/PG 默认也是 RC。

## 易错点

- 把不可重复读说成「读到别的行」——它是同一行被 UPDATE；对象搞错，级别矩阵就全乱。
- 背「RR 解决幻读」不提混用场景——主动说出「先快照读再当前读仍可能幻读」是区分度所在。
- 忘了 MySQL 默认级别——InnoDB 是 RR（PostgreSQL 是 RC），级别题几乎必带这一问。
