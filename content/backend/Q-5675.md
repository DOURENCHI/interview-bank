## 题目

**场景**：字节日常实习一面开场大题（原题面：秒杀抢购的整体逻辑）。考「分层削峰 + 原子扣减 + 异步落库」的完整链路，答成「加 Redis 就行」会被追问打穿。

**问**：秒杀抢购的整体逻辑怎么设计？从入口到落库每一层做什么？

## 口述答案

> 秒杀的本质矛盾：**瞬时百万级请求去抢有限库存**，任何一层直通 DB 都会崩。整体思路是**层层漏斗：把无效流量挡在前面，让真正有效的少量请求走到底**。
>
> **①入口层**：验证码/答题错峰，按钮置灰防连点，静态资源 CDN 化——先削掉机器流量和重复点击。**②网关层**：限流（令牌桶按容量配额，超了快速失败返回「已抢完」）、UID/IP 黑名单风控——宁可拒绝，不让请求堆进服务。**③服务层**：先查**本地缓存/活动信息**判断活动状态，再去 **Redis 预扣库存**——Lua 脚本把「判库存>0、扣减、记录用户购买标记」合成原子操作，防超卖 + 一人一单；扣减失败直接返回，成功才发消息。**④异步落库**：扣减成功发 MQ（RocketMQ/Kafka），下单服务**匀速消费**创建订单、扣 DB 库存，DB 用 `UPDATE stock SET n=n-1 WHERE id=? AND n>0` 兜底 + `(user_id, goods_id)` 唯一索引兜防重。**⑤支付/收尾**：超时未支付回补库存，前端轮询订单结果。
>
> 三个关键点主动说：①Redis 只是「资格预扣」，最终一致性靠 DB 兜底；②消息可能重复，消费侧要幂等（唯一索引天然兜底）；③Redis 挂了要能降级到 DB 原子扣减，宁可慢不可超卖。

## 讲深一层

| 层 | 手段 | 挡掉什么 |
|---|---|---|
| 入口 | 验证码、按钮置灰、CDN | 机器人、重复点击 |
| 网关 | 令牌桶限流、风控 | 超容量流量、黑产 |
| 服务 | Redis Lua 原子预扣 | 无库存请求、重复购买 |
| MQ | 异步削峰、匀速消费 | DB 瞬时写压力 |
| DB | 条件 UPDATE + 唯一索引 | 最终的超卖、重复订单 |

**判断技巧**：答题顺序固定「漏斗五层 + 两个兜底（DB 条件更新防超卖、唯一索引防重）」；被追问「Redis 和 DB 库存不一致怎么办」就答「以 DB 为准，异步对账 + 超时回补」。**记忆锚点**：「前端挡量、网关限流、Redis 定资格、MQ 缓节奏、DB 定生死」。

## 高频追问

1. **Redis 预扣和 DB 扣减不一致怎么办？** —— Redis 只是资格预扣，DB 条件 UPDATE 是最终约束；消费失败/超时回补 Redis 与 DB，定时对账兜底。
2. **消息队列积压怎么办？** —— 消费端水平扩容 + 批量拉取，必要时按库存量提前扩队列分区；积压本质是「消费速度 < 发放速度」，入口层提前限流才是根治。
3. **热点商品单 key 打满 Redis 带宽呢？** —— 库存分段（拆成 N 个 key 轮询扣）、本地内存预扣一部分再合并，或直接上 Redis cluster 分片。

## 易错点

- 只答「用 Redis 扣库存」——漏了入口削峰和 MQ 异步，链路不完整等于没扛过真实流量。
- 先 GET 再 DECR 判库存——check-then-act 并发下必超卖，必须 Lua/脚本原子。
- 忘了防重复下单——一人一单靠唯一索引或 SETNX 标记，只防超卖不防黄牛脚本。
