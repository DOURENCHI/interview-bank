## 题目

**背景**：Redis 内存管理的追问，面试官从"key 过期了会立刻删吗"切入，要求讲清删除策略的组合。

**问**：Redis 的过期删除策略有哪些？为什么不全用惰性删除？

## 口述答案

> 三种机制并存。一，惰性删除：访问 key 时才检查是否过期，过期就删并返回空——对 CPU 友好，但没人访问的 key 永远占着内存。二，定期删除：每秒若干次（`hz` 默认 10，约每 100 ms 一次）随机抽取一部分带过期时间的 key，删掉过期的；若这批里过期比例超过 25% 就继续抽，直到低于阈值或用完时间预算（默认不超过 25% CPU）。三，内存淘汰：`maxmemory` 到了按 `maxmemory-policy` 淘汰，这是兜底而不是过期机制。不全用惰性的原因很直接：冷 key 会永久堆积，内存只增不减，等于泄漏；而且删除成本被转嫁到请求路径上，大 key 过期会卡住那一次访问。

## 讲深一层

| 机制 | 触发 | 优点 | 缺点 |
|---|---|---|---|
| 惰性删除 | 访问时 | 不浪费 CPU | 冷 key 不释放 |
| 定期删除 | 周期采样 | 折中 | 采样不全，可能漏 |
| 内存淘汰 | 达 maxmemory | 兜底防 OOM | 会淘汰未过期数据 |

淘汰策略八种：`noeviction`、`allkeys-lru/lfu/random`、`volatile-lru/lfu/random/ttl`。缓存场景常用 `allkeys-lru`，混合存储用 `volatile-*` 保护无 TTL 的数据。

## 高频追问

1. **从库会自己删过期 key 吗？** —— 不会，从库等主库的 `DEL` 同步过来；但从库读到的过期 key 会返回空（逻辑上已过期）
2. **`hz` 调大有什么代价？** —— 定期删除更积极，但 CPU 占用上升、延迟抖动增加，默认 10 一般够用
3. **大 key 过期为什么卡？** —— 释放大对象是同步的，几百万元素的集合删除会阻塞主线程数百毫秒，要用 `UNLINK` 异步释放

## 易错点

- 以为设了 TTL 就会准点删除——到期只是"逻辑过期"，物理删除靠惰性加定期
- 用 `volatile-*` 策略但 key 没设 TTL——内存满了无法淘汰，直接报 OOM 错误
- 忽略 `DEL` 大 key 的阻塞——生产上应该用 `UNLINK` 或分批删
