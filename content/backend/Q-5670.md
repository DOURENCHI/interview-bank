## 题目

**场景**：得物一面集合第一题，基础八股但答法分层：结构 → 复杂度 → 场景，最后能补一句「为什么实际开发几乎总用 ArrayList」才算透。

**问**：ArrayList 和 LinkedList 有什么区别？各自适合什么场景？

## 口述答案

> 结构决定一切：**ArrayList 底层是 Object[] 动态数组，LinkedList 是双向链表**（JDK 6 之前是循环双向，7 起改成头尾两个指针的非循环双向）。
>
> 由此展开四个差异：①**随机访问**：ArrayList 支持，`get(i)` O(1) 直接算地址；LinkedList 要从头/尾数过去，O(n)。②**中间插删**：LinkedList 在**已定位位置**改 4 个指针引用 O(1)，但**找到那个位置本身要 O(n) 遍历**——所以「按下标插删」两者都是 O(n)，LinkedList 并没有优势；只有拿着迭代器/节点在当前位置插删才是真 O(1)。③**内存**：ArrayList 有扩容余量但连续、缓存友好；LinkedList 每个元素一个 Node 对象（前驱+后继+数据三个引用），同数据量内存大得多，且节点散落堆上、缓存命中率差。④**扩容**：ArrayList 扩 1.5 倍 + 整体复制；LinkedList 无需扩容但每插一个 new 一个节点。
>
> 场景结论：**90% 的业务代码无脑 ArrayList**——读多写少、按下标访问、遍历友好；LinkedList 的合理位置是「迭代中频繁插删」的队列/Deque 场景（配合它的 List + Deque 双接口），或者 LRU 这类要 O(1) 摘节点配合哈希表的结构。但纯队列用 ArrayDeque 更好（循环数组），这也是阿里巴巴规约建议默认 ArrayList、慎用 LinkedList 的原因。

## 讲深一层

| 操作 | ArrayList | LinkedList |
|---|---|---|
| get(i) 随机访问 | O(1) | O(n)（从近端数） |
| 尾部 add | 均摊 O(1) | O(1) |
| 头部插删 | O(n) 整体搬移 | O(1) |
| 已定位节点插删 | O(n) 搬移 | O(1)（但定位本身 O(n)） |
| 内存 | 连续数组，缓存友好 | 每 Node 3 引用，零散 |

**判断技巧**：面试被问「中间插入谁快」，先反问「位置怎么来的」——按下标两者都 O(n)（LinkedList 定位还要遍历），持迭代器才轮到 LinkedList 赢；这一问就是分水岭。**记忆锚点**：「数组赢在读，链表赢在断点接驳；定位成本是链表的隐形税」。

## 高频追问

1. **ArrayList 扩容机制？** —— 新容量 = 旧容量 × 1.5（`oldCap + (oldCap >> 1)`），Arrays.copyOf 整体复制；能预估就构造时指定 initialCapacity，避免反复扩容。
2. **ArrayList 删除元素后数组会缩容吗？** —— remove 只置 null 等 GC，不自动缩；trimToSize() 手动收缩。频繁增删大列表要留意内存驻留。
3. **线程安全版本？** —— 都不安全。并发读多写少用 CopyOnWriteArrayList，写多用 Collections.synchronizedList 或自己加锁；Vector 已过时。
4. **为什么规约建议 ArrayDeque 代替 Stack？** —— Stack 继承 Vector，所有方法 synchronized，单线程也有锁开销；栈/队列语义用 ArrayDeque（循环数组、无锁）更快（Q-0857 有完整对比）。

## 易错点

- 背「LinkedList 插入删除 O(1)」却不提定位成本——按下标插删它反而更慢，这是最经典的坑。
- 说「LinkedList 省内存」——每个元素多两个引用外加 Node 对象头，通常更费。
- 忽略 CPU 缓存局部性——链表节点散落堆上，实测遍历往往比复杂度数字更难看。
