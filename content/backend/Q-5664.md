## 题目

**场景**：滴滴日常实习一面真题，DB 排查的入门第一题——考的不是背参数，而是「线上 SQL 变慢了，你从哪下手」的完整动作链。

**问**：MySQL 怎么开启慢查询日志？抓到慢 SQL 之后怎么定位问题？

## 口述答案

> 开启三步：`SET GLOBAL slow_query_log = ON` 打开日志；`SET GLOBAL long_query_time = 1` 把阈值从默认 10 秒调到 1 秒（OLTP 一般 0.5~1 秒）；要连「没走索引但还没超时」的 SQL 一起抓，再开 `log_queries_not_using_indexes`。用 `SHOW VARIABLES LIKE 'slow_query%'` 确认；`SET GLOBAL` 重启会丢，永久生效要同步写进 my.cnf。
>
> 定位分两段。第一段看日志记录本身：每条慢查询带 **Query_time、Lock_time、Rows_examined、Rows_sent** 和 SQL 文本，重点看 **Rows_examined / Rows_sent 的比值**——返回 10 行却扫了 100 万行，基本就是索引问题。日志量大用 pt-query-digest 按指纹聚合出 Top SQL。第二段拿到嫌疑 SQL 后 `EXPLAIN` 看执行计划：`type=ALL` 是全表扫描，`key=NULL` 是索引没生效，`rows` 是预估扫描行数，`Extra` 出现 `Using filesort`/`Using temporary` 提示排序或临时表开销。MySQL 8.0 可以直接 `EXPLAIN ANALYZE` 看真实执行耗时，不用再猜估算值。

## 讲深一层

| 参数 | 作用 | 线上建议 |
|---|---|---|
| `slow_query_log` | 慢日志总开关 | ON，常开 |
| `long_query_time` | 超过该秒数记入日志 | 0.5~1（默认 10 等于没开） |
| `log_queries_not_using_indexes` | 没走索引也记录 | 配合 throttle 限流再开 |
| `slow_query_log_file` | 日志文件位置 | 放独立盘，避免和数据抢 IO |

EXPLAIN 速查：`type` 从好到差 system > const > eq_ref > ref > range > index > ALL；`Extra` 里 `Using index`（覆盖索引）是好消息，`Using filesort`/`Using temporary` 要警惕。

**判断技巧**：先看扫描放大率（Rows_examined/Rows_sent），再 EXPLAIN 定罪——九成慢 SQL 是「没走索引」或「走了但回表太多」；日志只负责抓嫌疑人，审判靠执行计划。**记忆锚点**：「开日志、定阈值、看放大率、EXPLAIN 定罪」四步动作。

## 高频追问

1. **`SET GLOBAL` 之后为什么有的会话没生效？** —— `long_query_time` 是会话级可覆盖变量，已建立的连接沿用旧值，新会话才用全局值；重要参数必须落配置文件。
2. **日志常开有性能影响吗？** —— 顺序写开销小可以常开；但开 `log_queries_not_using_indexes` 在低索引场景会刷爆日志，用 `log_throttle_queries_not_using_indexes` 限流，或把 `log_output` 指到 TABLE 方便 SQL 聚合。
3. **除了慢日志还有什么定位手段？** —— performance_schema 的 `events_statements_summary_by_digest`（按指纹聚合）、sys schema 的全表扫描视图、业务侧 APM 链路耗时；慢日志是第一入口不是唯一手段。
4. **`long_query_time` 设成 0 行不行？** —— 可以，等于全量记录，排查瞬时抖动时短开短关；长期全量会刷爆日志盘，配合采样或只开一两天。

## 易错点

- 只开 `slow_query_log` 不调 `long_query_time`——默认 10 秒的阈值，线上几乎抓不到东西。
- 只看 Query_time 不看 Rows_examined——耗时受缓存影响会波动，扫描行数才是索引问题的稳定信号。
- `SET GLOBAL` 不落 my.cnf——重启后配置丢失，排查当天正常、第二天复发。
- 只抓 SELECT 忘了 DML——UPDATE/DELETE 慢同样拖垮链路，慢日志不挑语句类型。
- 看到第一条日志就动手——先按总耗时/频次聚合找 Top SQL，单条偶发慢不一定是问题。
