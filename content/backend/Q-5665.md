## 题目

**场景**：滴滴一面连环追问的收口题：Error 和 Exception 的区别 → 怎么捕获 → 「可以捕获 error 吗？为什么可以捕获 error？」——考的是 Throwable 体系是不是真懂，而不是背一句「Error 不能捕获」。

**问**：Java 里可以捕获 Error 吗？为什么语言允许，实际该不该捕获？

## 口述答案

> **语法上完全可以捕获**。Error 和 Exception 是平级的，都继承 Throwable，而 catch 的匹配类型就是 Throwable——`catch (OutOfMemoryError e)`、`catch (Throwable t)` 都能编译通过，运行时也真能接住 OOM、StackOverflowError。
>
> **为什么语言允许**：JVM 只定义了「Throwable 都可抛可捕」，没有在语言层面禁止捕获 Error，因为确实存在正当的兜底场景——线程池里任务抛了 Error 不接住就静默丢失；框架层（Netty 的事件循环、Tomcat 的应用隔离）要捕 Throwable，保证单个请求或单个应用的致命错误不拖垮整个进程；还有资源清理需要先接住、处理完再决定去向。
>
> **该不该捕获**：业务代码原则上不捕。OOM/StackOverflow 发生时 JVM 状态往往已经不可靠，「接住继续跑」可能带着损坏的状态运行，还吞掉了本该触发进程重启的信号。正确姿势是：让 Error 传播到线程边界，交给 UncaughtExceptionHandler 记日志、打告警，配合 `-XX:+HeapDumpOnOutOfMemoryError` 留现场，再由进程级自愈（容器重启、K8s 拉起）恢复。资源清理用 finally 或 try-with-resources，而不是 catch Error。

## 讲深一层

```text
Throwable
├── Error（JVM 级严重错误：OutOfMemoryError、StackOverflowError、NoClassDefFoundError）
└── Exception
    ├── RuntimeException 及子类（非受检：NPE、数组越界……）
    └── 其他（受检：IOException、SQLException……编译器强制处理）
```

| 类型 | 语义 | 业务代码的处理 |
|---|---|---|
| Exception | 可预期、可恢复的异常 | 按类型 catch、降级或上报 |
| Error | JVM 级严重问题 | 不捕；线程边界兜底 + 进程重启 |
| Throwable | 两者总称 | 只在框架兜底层用，且要按类型重抛 |

**判断技巧**：catch 之前问自己「接住之后我能把系统恢复到一致状态吗」——能（重试/降级）才值得捕；不能就让它死，把恢复交给进程重启。**记忆锚点**：「Error 接得住 ≠ 救得活；兜底靠 UncaughtExceptionHandler + 重启」。

## 高频追问

1. **catch Throwable 和 catch Exception 的区别？** —— Throwable 多接住了 Error；业务兜底层用它时必须先记日志、再按类型重抛非预期部分，否则致命错误被静默吞掉。
2. **发生 OOM 后进程还能继续跑吗？** —— 多数不建议：OOM 可能打断框架的中间步骤留下损坏状态；主流做法是 HeapDumpOnOutOfMemoryError 留 dump + 主动退出触发重启。
3. **StackOverflowError 和 OutOfMemoryError 是一回事吗？** —— 不是：前者是线程栈深度超限（深递归、-Xss 太小），后者是堆/元空间申请不到内存，排查方向完全不同。

## 易错点

- 背「Error 不能被 catch」——语言层面能，规范是「不建议」，一字之差立场就错了。
- catch Error 后假装无事发生继续跑——状态可能已损坏，正确做法是留现场、快速失败、交给重启。
- 把资源清理写成 catch Error——该用 finally / try-with-resources，异常路径清理才不漏。
