## 题目

**场景**：SHEIN 一面的 HTTP 规范辩论题（原题面：GET 请求可不可以带请求体）。它不是背状态码，考的是「语义层 vs 实现层」的分层思维：RFC 怎么说、服务器怎么做、缓存/代理怎么受影响。

**问**：GET 请求可以带请求体吗？为什么实际中不该带？

## 口述答案

> 分两层答，先给结论：**语法上不禁止，语义上不该用**。
>
> **规范层**：RFC 7231 明确写道——GET 请求体「没有定义语义」（a payload within a GET request message has no defined semantics），RFC 7230 补了一句：服务器**可以**拒绝、可以忽略。注意措辞是「没有语义」，不是「必须拒绝」——所以带 body 的 GET 在语法上合法，只是规范不为它定义任何含义。
>
> **语义层**：GET 的定义是「安全 + 幂等的读取」，参数应该全部在 URL/头部里。往 body 里塞参数等于把「查询意图」藏进一个规范没定义语义的地方，工具、中间件、网关都不必然转发或解析它。
>
> **实现层**（为什么实践中别带）：①**缓存**——缓存键一般是「方法 + URL + 少数头部」，body 不参与，同 URL 不同 body 会命中同一条缓存，返回错数据；②**代理/网关**——可能剥掉或直接拒掉 GET body（Elasticsearch 早年间就见过网关转发不了 GET body 的案例，官方后来给 POST 加了 _source 参数）；③**服务端框架**——多数默认忽略 GET 的 body，Spring 的 @RequestBody 也不保证所有容器支持；④**日志/调试**——参数在 URL 里可见可复制，进 body 后 curl 重放、日志排查都麻烦。所以结论落在工程习惯：GET 用 query 参数；要带复杂负载就用 POST，并自己处理幂等。

## 讲深一层

| 层 | 规定/行为 | 一句话 |
|---|---|---|
| RFC 7231（语义） | GET body 无定义语义 | 合法但无意义 |
| RFC 7230（消息） | 服务器可拒绝/忽略 | 不保证被处理 |
| 缓存/CDN | 缓存键不含 body | 不同 body 撞同一缓存 |
| 代理/网关 | 可能剥离或拒绝 | 链路上不可靠 |
| 框架/容器 | 多数忽略 GET body | 服务端读不到 |

**判断技巧**：HTTP 辩论题的模板是「先问这是哪一层的问题」——语法层（能不能发出去）、语义层（RFC 定义了什么）、实现层（工具链会怎么对待它），三层分开答就不会被追问绕晕。**记忆锚点**：「GET body：发得出，没语义，不可靠」。

## 高频追问

1. **DELETE 带 body 呢？** —— 同样的处境：RFC 同样「无定义语义」，部分代理会拒；条件删除用查询参数或 If-Match 头更稳。
2. **那 Elasticsearch 为什么曾用 GET + body 查询？** —— 它把「查询 DSL」当资源描述而不是参数，早期很多客户端/网关支持 GET body，后来为兼容性补了 `POST /_search?source=`，官方文档明确推荐 POST。
3. **幂等和安全是硬性要求吗？** —— 是语义约定不是实现强制：客户端重复发 GET/DELETE 不会产生额外效果才算合格；PUT 幂等、POST 不幂等，这是选方法的第一判据。

## 易错点

- 一口咬死「GET 绝对不能带 body」——RFC 说的语义是无定义而非禁止，措辞不准确在规范题里是硬伤。
- 只答 RFC 不答工程影响——缓存撞键、代理剥包才是面试官要的落地层。
- 把「服务器不读」说成「协议禁止」——两层混着说，暴露没分清语义与实现。
