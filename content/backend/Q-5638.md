## 题目

**背景**：事务 ACID 的追问，面试官已经听完四大特性的定义，要求以 InnoDB 为例把"持久化"落到具体机制上。

**问**：以 InnoDB 为例，事务的持久性（Durability）是怎么保证的？

## 口述答案

> 靠 WAL、redo log、doublewrite、fsync 四件套。修改先改 Buffer Pool 里的页并写 redo log——redo 是顺序追加、代价远小于随机刷页；提交时按 `innodb_flush_log_at_trx_commit` 决定是否 fsync，取 1 时每次提交都刷盘，保证已提交事务不丢。脏页由后台线程异步刷回数据文件；为防止刷到一半掉电留下半页（torn page），刷之前先把页拷到 doublewrite buffer，恢复时用完整副本修复。重启后先用 redo 做前滚（按 LSN 推进），再用 undo 回滚未提交事务。核心思想是"随机写变顺序写，且始终有可修复的副本"。

## 讲深一层

| 参数 | 取值 | 语义 | 代价 |
|---|---|---|---|
| `innodb_flush_log_at_trx_commit` | 0 | 每秒刷，崩溃丢 1s | 最快 |
| | 1 | 每次提交 fsync | 最安全，默认 |
| | 2 | 写 OS cache 不 fsync | 宕机不丢，断电丢 |
| `sync_binlog` | 1 | 每次提交刷 binlog | 主从一致前提 |
| `innodb_flush_method` | O_DIRECT | 绕过 page cache | 避免双份缓存 |

LSN 单调递增，checkpoint 之前的 redo 可被覆盖，所以 redo 是环形复用而非无限增长。

## 高频追问

1. **`innodb_flush_log_at_trx_commit=2` 会丢什么？** —— 进程崩溃不丢（已进 OS cache），机器断电丢最近约 1 秒的已提交事务
2. **redo log 满了会怎样？** —— 触发强制 checkpoint，刷脏页跟不上就出现"抖"甚至写阻塞，这是突发写入卡顿的常见原因
3. **doublewrite 能关吗？** —— 可以，但只有文件系统能保证原子写（如某些 ZFS 配置）才安全，否则可能永久损坏页

## 易错点

- 说"提交就写数据文件"——那样每次提交都是随机 IO，InnoDB 实际只保证 redo 落盘，数据页是异步刷的
- 混淆 redo 与 binlog——redo 是存储引擎层物理逻辑日志用于崩溃恢复，binlog 是 server 层逻辑日志用于复制和归档
- 忽略 doublewrite——只讲 redo 讲不清 torn page，这是"为什么还需要额外一份拷贝"的关键
