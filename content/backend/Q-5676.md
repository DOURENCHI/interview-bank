## 题目

**场景**：字节日常实习一面 JVM 追问（原题面：类加载的双亲委派模型，为什么这么做、好处、怎么打破）。考模型本身 + 设计动机 + 反例，三段都要接得住。

**问**：类加载为什么采用双亲委派？有什么好处？什么场景需要打破它？

## 口述答案

> 模型先说清：类加载器收到加载请求，**先逐级上抛给父加载器**（Application → Platform/Extension → Bootstrap），父加载器反馈「加载不了」子加载器才自己加载——「能委托给父的一律委托」。
>
> 为什么这么设计，两个好处：①**安全**：核心类永远由 Bootstrap 加载，用户自己写个 `java.lang.String` 或 `java.lang.Object` 试图注入，最终到 Bootstrap 发现 rt.jar 里已有，直接用 JDK 的版本，恶意类没有机会顶替核心 API。②**唯一性/一致性**：同一个类只被同一个加载器加载一次，保证「类的同一性」——同一个 class 文件被两个加载器各加载一次就是两个不同的 Class，instanceof 都不相等；双亲委派让全 JVM 对核心类只有一份。
>
> 打破的场景是「父加载器管不到、子加载器必须先加载」或「需要隔离」：**SPI（JDBC 驱动）**——java.sql.DriverManager 在 Bootstrap 里，但驱动实现在应用 classpath，父加载器「够不着」，于是用线程上下文类加载器（TCCL）反向委托给 Application 加载器加载驱动；**Tomcat**——每个 webapp 独立加载器优先加载自己的类（实现多应用类隔离、同库不同版本共存），对委托顺序做了逆置；**热部署/OSGi**——模块化加载器按需替换类。打破的方式统一一句话：**重写 loadClass()（不委托或先自加载）**——重写 findClass() 只是扩展查找路径，委派模型还在。

## 讲深一层

| 加载器 | 职责 | 典型加载对象 |
|---|---|---|
| Bootstrap | JVM 核心库 | java.lang.*、rt.jar 核心 |
| Platform（8: Extension） | 平台扩展 | javax.* 等 |
| Application（系统） | classpath | 业务代码、三方库 |
| 自定义 | 隔离/热部署/加密 | 按需（Tomcat webapp、SPI） |

**判断技巧**：三段式答题——模型（上抛）→ 动机（安全 + 唯一性）→ 反例（SPI 用 TCCL 反向、Tomcat 隔离）；被问「怎么打破」必须说出 **loadClass vs findClass 的区别**，这是判断是否真写过自定义加载器的分水岭。**记忆锚点**：「向上安全，向下隔离；打破靠 loadClass，反向委托靠 TCCL」。

## 高频追问

1. **JDBC 加载驱动的完整链路？** —— DriverManager（Bootstrap 级）静态块里 `Class.forName(驱动类, true, TCCL)`，用线程上下文加载器拿到 classpath 里的驱动实现——父加载器借子加载器能力，这就是「反向委派」。
2. **同一个类被两个加载器加载会怎样？** —— 得到两个互不相干的 Class 对象，instanceof 为 false，强转抛 ClassCastException——Tomcat 多应用隔离正是利用这一点。
3. **Tomcat 为什么要逆置委派？** —— 两个应用依赖同一库的不同版本，必须各自优先加载自己的版本；共享库才下沉到 common 加载器。

## 易错点

- 只答「先给父亲加载」不说动机——安全 + 类唯一性才是「为什么」，漏了等于只背了现象。
- 说「打破就是重写 findClass」——findClass 是委托失败后的查找步骤，真正打破委派要重写 loadClass。
- 不知道 TCCL——SPI 是打破双亲委派的标准案例，答不出 JDBC 驱动加载链路这个模型就白背了。
