## 题目

**场景**：字节 Agent 研发一面，聊到 AI 代码平台的架构，问「测试/沙箱组件的职责」。平台工程题：考的是把「Agent 生成的代码怎么安全地验证」拆成组件职责的能力。

**问**：AI 代码平台中，测试组件和沙箱组件各自承担什么职责？怎么配合？

## 口述答案

> 先给分工定位：**沙箱组件管「安全地跑起来」，测试组件管「跑的结果对不对」**——前者是执行环境，后者是验证逻辑。
>
> **沙箱组件**的职责四条：①**隔离执行**：模型生成的代码不可信，必须在受限环境跑——容器级（独立 namespace/cgroup，限 CPU/内存/进程数）、微虚拟机级（gVisor/Firecracker，内核隔离）按威胁模型选；②**资源与网络管控**：无网或只放行白名单域名（防数据外泄、防挖矿脚本）、限时执行（防死循环挂死资源）、限文件系统写；③**环境供给**：按语言/依赖预置镜像、缓存依赖加速冷启动；④**清理与审计**：一次性环境用完即焚，全程留执行日志供追溯。
>
> **测试组件**的职责三条：①**验证编排**：拿到沙箱的执行结果后跑断言——单元测试、样例用例、回归集，判定通过/失败；对 Agent 场景还有「自动生成测试用例 → 多轮迭代直到通过」的编排；②**结果反馈**：把失败信息（报错栈、断言 diff）结构化回传给模型重写，形成「生成 → 沙箱执行 → 测试判定 → 反馈修复」的闭环；③**质量门禁**：覆盖率阈值、静态扫描，决定代码能不能合入/交付。
>
> 两者的边界一句话：沙箱回答「这段代码**能不能安全执行**」，测试回答「执行结果**符不符合预期**」——测试组件是沙箱的调用方，沙箱是测试组件的执行底座。

## 讲深一层

| 关注点 | 沙箱组件 | 测试组件 |
|---|---|---|
| 回答的问题 | 能不能安全地跑 | 跑出来对不对 |
| 核心手段 | 容器/微虚拟机隔离、限额、断网 | 用例编排、断言、覆盖率 |
| 典型技术 | gVisor、Firecracker、cgroup | pytest/JUnit、覆盖率工具 |
| 失败形态 | 超时/OOM/越权 → 环境层拒绝 | 断言失败 → 业务层反馈 |

**判断技巧**：平台组件题的答法是「职责边界 + 协作链路 + 一个安全考虑」——先分家、再讲两者怎么串成闭环（生成→执行→判定→反馈）、最后主动提隔离等级按威胁模型选，三层齐了就是平台视角。**记忆锚点**：「沙箱管安全地跑，测试管跑得对，闭环靠反馈」。

## 高频追问

1. **为什么容器不够，要微虚拟机沙箱？** —— 容器共享宿主内核，内核漏洞逃逸风险真实存在；对执行不可信代码的场景用 gVisor（拦截系统调用）或 Firecracker（独立轻内核）把攻击面砍到最小。
2. **沙箱冷启动慢怎么办？** —— 镜像分层 + 依赖预热池（热备 Pod 池）、快照恢复（Firecracker snapshot）、按语言分池；目标是把首包延迟压到秒级以内。
3. **测试用例本身谁保证质量？** —— 平台侧维护黄金集 + 代码评审人工抽检；对自动生成的用例做变异测试（mutant 能被杀掉才算有效用例）。

## 易错点

- 把两个组件说成一回事——「跑起来」和「验证对」是两个职责，混答说明没做过平台拆分。
- 只谈测试框架不谈隔离——AI 生成代码的执行安全是这类平台的第一设计约束，漏了它等于没理解场景。
- 忘了闭环反馈——测试结果要结构化回流给模型重试，只说「跑测试」丢掉了 Agent 平台的核心交互。
