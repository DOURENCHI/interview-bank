## 题目

**场景**：后端/基础架构岗必问。面试官问：**MySQL 的四个隔离级别分别解决什么问题？InnoDB 的 MVCC 是怎么实现的？**

## 口述答案

> 四个级别依次是读未提交（RU）、读已提交（RC）、可重复读（RR）、串行化（SERIALIZABLE），分别解决**脏读、不可重复读、幻读**。InnoDB 默认是 RR。
> MVCC 的做法是：每行记录带隐藏的 `trx_id`（最后修改它的事务）和 `roll_pointer`（指向 undo log 里的旧版本），
> 所有旧版本串成一条**版本链**；读的时候生成一个 **ReadView**，里面记着当前活跃事务 id 列表 `m_ids`、最小/最大事务 id，
> 拿行的 `trx_id` 和 ReadView 比：落在已提交区间就可见，落在活跃列表里就顺着版本链往前找。
> RC 和 RR 的差别只在 ReadView 的创建时机：**RC 每条语句新建一次**，所以能看到别人刚提交的；**RR 第一条查询建一次后复用**，所以整个事务看到同一份快照。

## 讲深一层

```text
行记录 ──roll_pointer──> undo log 旧版本 ──> 更旧版本   （版本链）
ReadView = {m_ids(活跃事务), min_trx_id, max_trx_id, creator_trx_id}
可见性：trx_id < min_trx_id        → 已提交，可见
        trx_id >= max_trx_id      → 事务开始后才开的，不可见
        trx_id in m_ids           → 还活着，不可见（顺着链找旧版本）
        其他                      → 可见
```

- **快照读 vs 当前读**：普通 `SELECT` 是快照读，走 MVCC 不加锁；`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是当前读，读最新版本并加锁。
- **幻读怎么处理**：RR 下快照读靠 MVCC 不会看到新插入的行；当前读靠 **next-key lock（记录锁 + 间隙锁）** 锁住区间。两者结合才基本避免幻读，但**不是绝对**——先快照读再当前读仍可能看到新行。
- **undo log 何时清理**：purge 线程判断没有 ReadView 再需要这个版本时才删，长事务会拖住 purge，导致 undo 膨胀。

## 高频追问

1. **RC 和 RR 哪个性能好？** —— RC 每条语句建 ReadView、锁范围小，并发更高，很多互联网公司默认 RC；RR 需要间隙锁，更容易死锁。
2. **RR 完全解决幻读了吗？** —— 没有。快照读靠 MVCC、当前读靠间隙锁，混合场景（先 SELECT 再 UPDATE 不存在的行）仍可能出现。
3. **binlog 三种格式和事务的关系？** —— statement 记录 SQL、row 记录行变更、mixed 自动选；RC 下必须用 row，否则主从不一致。

## 易错点

- 说「RR 完全解决幻读」——只能说基本避免，且要区分快照读/当前读
- 把 MVCC 说成「给每行加锁」——MVCC 的核心是**不加锁读**，靠版本链 + ReadView
- 忘了 undo 版本链，只说「保存多个版本」，讲不清可见性怎么判断
