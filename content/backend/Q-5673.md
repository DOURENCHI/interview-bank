## 题目

**场景**：SHEIN 一面：先问「说说你对 IoC 的理解」，再追「为什么需要 IoC 容器，不用会怎样」。考的是能不能跳出「注解就能注入」的表面，讲出容器解决的工程问题。

**问**：为什么需要 IoC 容器？不用 IoC 的话会遇到什么问题？

## 口述答案

> 先一句话：**IoC 把「对象由谁创建、依赖由谁装配」的控制权从业务代码反转给容器**——没有反转时是类自己 `new UserService(new UserDao(new DataSource(...)))`，反转后类只声明依赖（构造器/@Autowired），装配交给容器。
>
> 不用 IoC 会怎样，对三个痛点：①**解耦**：new 是编译期硬绑定，换实现要改调用方代码——Service 直接 new MySQLDao，换 ES 版本就得改 Service；IoC 面向接口注入，换实现只换配置。②**生命周期与复用**：单例要在哪里 new 才全局一份？连接池、线程池这类重资源谁管关闭？容器统一管创建、初始化、销毁回调、作用域，业务类不用各写一套单例模式。③**可测试性**：类内部写死 new，单测无法替换依赖，只能连真库；构造器注入后测试里传一个 mock 即可。
>
> 再补一层「容器」的价值（为什么不是简单工厂就够了）：对象一多，**依赖图**复杂（A 依赖 B、C，C 又依赖 B）——容器按依赖关系自动解析注入顺序、处理循环依赖、做字段/构造器/方法多方式注入；还有 AOP（事务、日志代理）要作用在容器管理的 Bean 上才有统一入口。所以容器的本质是「**对象的集中注册中心 + 装配引擎 + 生命周期管家**」。

## 讲深一层

| 能力 | 无 IoC 的代价 | 容器如何接 |
|---|---|---|
| 依赖装配 | 类内 new 硬绑定实现 | 按类型/名称自动注入 |
| 生命周期 | 各自写单例/关闭钩子 | 统一 init/destroy 回调、作用域 |
| 可测试性 | mock 进不去 | 构造器注入，测试传 mock |
| 横切能力 | 事务/日志代码散落 | AOP 代理统一织入 |
| 依赖图 | 手工排序 new | 容器拓扑解析、三级缓存 |

**判断技巧**：答「为什么需要 X」类题用「反事实法」——先描述没有它会怎样，再逐条对上它的收益，最后说清「为什么简单方案（工厂）不够」。**记忆锚点**：「解耦、管命、好测，是 IoC 的三笔账」。

## 高频追问

1. **构造器注入和字段注入哪个好？** —— 构造器注入：依赖不可变、必需依赖在创建时就校验、便于单测；字段注入省事但藏依赖、测试要用反射，Spring 官方推荐构造器。
2. **循环依赖 Spring 怎么处理？** —— 单例字段注入靠三级缓存（提前暴露半成品引用）化解；构造器注入的循环依赖无法解决，直接报错——这本身也是构造器注入更健康的佐证。
3. **IoC 和 DI 是一回事吗？** —— IoC 是思想（控制权反转），DI（依赖注入）是它最主流的实现手段；模板回调（如 JdbcTemplate）是另一种 IoC 形式。
4. **容器启动大致做什么？** —— 定位配置 → 解析成 BeanDefinition 注册 → BeanFactoryPostProcessor 加工（占位符替换等）→ 按依赖图实例化注入 → 后置处理器与初始化回调。

## 易错点

- 把 IoC 答成「@Autowired 注解」——注解只是入口，讲不出反转了什么、带来什么收益就停留在操作层。
- 三笔账漏掉可测试性——mock 替换是 IoC 最实用的收益，实习面试常从这里追问。
- 说「容器就是大工厂」就结束——工厂只解决创建，容器还管依赖图解析、生命周期、AOP 织入。
