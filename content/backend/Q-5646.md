## 题目

**背景**：限流方案的架构追问，前面聊完单机令牌桶，面试官把量级抬到百万并发，看是否只会"加个 Redis"。

**问**：Redis + Lua 怎样应对百万级并发限流？

## 口述答案

> 百万并发不能指望 Redis 硬扛，核心是分层削峰加单 key 原子。第一，别让所有请求都到 Redis：网关层先用本地令牌桶或滑动窗口挡掉大部分，本地内存没有网络开销，只有通过本地这层的才进分布式限流。第二，分布式这层用 Lua 把"取窗口、算计数、判断、写回"合成原子操作，避免 GET 再 INCR 的竞态。第三，key 必须分片，按 uid 或接口维度打散，别让单个 key 变成热点。第四，Lua 脚本要短，Redis 执行脚本期间是阻塞的。第五，被限流的请求快速失败，不要重试放大流量。

## 讲深一层

| 方案 | 精度 | 临界问题 | 成本 |
|---|---|---|---|
| 固定窗口 INCR+EXPIRE | 低 | 窗口边界可双倍放行 | 最低 |
| 滑动窗口 ZSet | 高 | 无 | 内存随请求数涨 |
| 分桶计数 | 中高 | 桶粒度误差 | 中 |
| 令牌桶 Lua | 高，可控制突发 | 无 | 中 |

Redis Cluster 下脚本涉及的 key 必须同 slot，用 `{uid}` 做 hashtag，否则直接 CROSSSLOT 报错。

## 高频追问

1. **为什么 Lua 能保证原子？** —— Redis 单线程，脚本整体作为一个命令执行，中间不插入其他客户端请求；但脚本出错不会自动回滚已执行的写
2. **本地限流和分布式限流怎么配合？** —— 本地按"单机配额"挡，分布式按"全局配额"兜底，本地阈值之和略大于全局，避免全局 key 被击穿
3. **Redis 挂了限流怎么办？** —— 降级到本地限流并放行核心流量，或者干脆 fail-open，因为限流的目的是保护系统而不是拦截用户

## 易错点

- 用 GET 再 INCR 两步判断——并发下计数不准，超发就是这么来的
- 所有请求都打同一个 key——单分片热点，扩集群也没用
- 在 Lua 里做复杂计算或循环——阻塞整个 Redis，其他业务请求全部排队
