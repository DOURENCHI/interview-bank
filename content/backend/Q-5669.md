## 题目

**场景**：得物一面并发第一题。两个名词都会背，考的是机制差异（硬件指令 vs 锁）和选型判断，顺带看会不会主动提 ABA 和锁升级。

**问**：CAS 和 synchronized 有什么区别？分别什么时候用？

## 口述答案

> 一句话定位：**CAS 是乐观路线，synchronized 是悲观路线**。CAS 是「比较内存值与期望值，相等才写入新值」的单条 CPU 原子指令（cmpxchg），不阻塞线程，失败就重试或放弃；synchronized 是先拿锁再进临界区，拿不到就阻塞挂起。
>
> 区别看五点：①**底层**：硬件原子指令 vs 对象头 Monitor + 操作系统互斥量；②**冲突处理**：自旋重试 vs 阻塞挂起、唤醒；③**能力面**：CAS 只保证**单变量**的原子读写，synchronized 能保证**一段复合逻辑**的互斥，还顺带解决可见性和可重入；④**开销**：无冲突时 CAS 更快，高冲突下 CAS 自旋空转烧 CPU，锁有挂起/唤醒成本；⑤**附带问题**：CAS 有 ABA（值被改回去看不出来），synchronized 没有。
>
> 选型：读多写少、冲突低、单变量（计数器、状态标志）用 CAS 系（Atomic 类）；临界区长、复合操作、冲突高用 synchronized（JDK 6 之后有锁升级，无竞争时开销很小）。JDK 自己就是混用的范本：ConcurrentHashMap 桶为空用 CAS 插入，有冲突才 synchronized 锁桶首节点。

## 讲深一层

| 维度 | CAS | synchronized |
|---|---|---|
| 底层 | CPU 原子指令（cmpxchg / lock 前缀） | 对象头 Mark Word + Monitor |
| 冲突时 | 自旋重试（占用 CPU） | 阻塞挂起（释放 CPU） |
| 保证范围 | 单变量原子性 | 临界区互斥 + 可见性 + 可重入 |
| 典型问题 | ABA、自旋空转 | 高竞争下重量级锁开销 |
| 代表 API | AtomicInteger、AtomicReference | synchronized 方法/块 |

ABA 一句讲清：值从 A→B→A，CAS 以为没人动过——用版本号解决（AtomicStampedReference；数据库乐观锁的 version 列同理）。锁升级链：无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（互斥量），竞争升级锁才升级。

**判断技巧**：先问「是不是单变量 + 低冲突」，两个都满足才上无锁；复合逻辑（跨多个变量的 check-then-act）别硬凑 CAS，一把锁更清楚。**记忆锚点**：「CAS 赌没人抢，锁是排队进；单变量赌一把，复合逻辑排队走」。

## 高频追问

1. **ABA 怎么解决？** —— 带版本戳的 CAS（AtomicStampedReference），或业务上用单调递增版本号——值可以回退，版本号不会（Q-0624 的版本号方案就是这个思路）。
2. **CAS 自旋长期失败怎么办？** —— 高竞争下换 LongAdder（分段累计降热点）或直接换锁；判断依据是冲突率——冲突率一高，自旋的 CPU 成本反超阻塞。
3. **synchronized 和 ReentrantLock 怎么选？** —— 需要 tryLock/超时/公平锁/多条件才用 ReentrantLock；否则 synchronized 更简洁且 JVM 保证释放，不会漏 unlock。
4. **AtomicInteger 底层怎么用 CAS？** —— 自旋循环：读旧值 → CAS 期望旧值换新值，失败重读重试；高并发下自旋次数暴涨，这正是 LongAdder 分段累计要解决的问题。

## 易错点

- 说「CAS 一定比锁快」——高冲突下自旋空转反而更耗 CPU，快的前提是无冲突。
- 拿 CAS 保护复合逻辑——两个变量的 check-then-act 两次 CAS 拼不出事务，中间态照样可见。
- 不知道锁升级——把 synchronized 一直当重量级锁，等于只了解 JDK 6 之前的它。
