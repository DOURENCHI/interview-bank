## 题目

**背景**：秒杀方案的约束追问，面试官故意禁用 Redis，看候选人是否只会背一套方案。

**问**：秒杀场景如何避免超卖，但不准用 Redis？

## 口述答案

> 数据库本身就能保证，关键是把"判断"和"扣减"合成一条原子语句：`UPDATE stock SET count = count - 1 WHERE goods_id = ? AND count > 0`，看 affected rows 是否为 1，为 0 就是卖完了。InnoDB 会给这行加排他锁，天然串行化，不会出现两个事务都读到 1 再各扣一次。一人一单靠 `(user_id, goods_id)` 唯一索引，重复插入直接失败。再往上优化：把库存拆成多个桶（比如 10 行各 100 件）分散行锁竞争；用版本号乐观锁减少等待；请求先在本地队列预筛再批量提交。代价是吞吐比 Redis 低一个量级，适合中小流量或作为最终兜底。

## 讲深一层

```sql
UPDATE stock_bucket SET cnt = cnt - 1
 WHERE goods_id = ? AND bucket = ? AND cnt > 0;
-- affected_rows = 0 则换桶或售罄
```
桶化的代价是库存不均：某个桶卖完但别的桶还有货，需要"换桶重试"逻辑，或者用中心表做汇总校验。桶数按单行能承受的并发定，8 到 32 个通常够用，再多会让碎片化和换桶逻辑变复杂。

## 高频追问

1. **条件更新和 `SELECT FOR UPDATE` 哪个好？** —— 条件更新只锁一行且语句更短，悲观锁会持锁到事务结束，长事务下更容易堆积
2. **怎么扛更高并发？** —— 分桶降低单行竞争、缩短事务（只做扣减不写大字段）、把非核心逻辑（发券、通知）移出事务
3. **不用 Redis 怎么做限流？** —— 网关本地令牌桶 + Nginx 限流模块，或者数据库计数表（但会成为新瓶颈）

## 易错点

- 先 `SELECT` 查库存再 `UPDATE`——两步之间并发进来就超卖，必须让判断和扣减在同一条语句里
- 事务里塞太多逻辑——行锁持有时间变长，吞吐断崖式下降
- 分桶后不做换桶重试——部分桶售罄会误判整体售罄
