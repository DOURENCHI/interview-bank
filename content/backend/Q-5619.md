## 题目

**背景**：面试官继续追问结果复用：既然清洗和对齐很贵，能不能直接拿原文做缓存键。

**问**：这些清洗和对齐结果想复用，能不能直接用原始文本的哈希作为缓存键？

## 口述答案

> 不够，会串结果。缓存键必须覆盖所有影响输出的输入，而输出不只取决于原文：清洗规则版本变了，同一段原文会得到不同结果；ASR 或对齐模型版本变了，时间戳会变；任务类型不同，比如只要清洗和要清洗加对齐，产物也不一样。另外原文可能有几 MB，先算哈希再查是合理的，但哈希算法要选碰撞可忽略的，用 SHA-256 而不是 MD5。正确做法是组合键：hash(归一化原文 + pipeline 版本 + 模型 id + 参数 + 任务类型)。还有一点，原文微小差异比如多一个空格会导致大面积 miss，所以要先做归一化再进哈希。

## 讲深一层

键结构示例：

```
key = sha256(normalize(raw_text) || pipeline_ver || asr_model_id
             || params_json || task_type)
```

| 遗漏项 | 后果 |
| --- | --- |
| pipeline 版本 | 规则升级后仍命中旧结果 |
| 模型 id | 换模型后时间戳错配 |
| 任务类型 | 半成品被当成品复用 |
| 归一化 | 空格/换行差异导致命中率骤降 |

## 高频追问

1. **为什么不直接用原文当键** —— 太长，Redis key 有实际长度和内存成本，且不便索引
2. **缓存该存哪一层** —— 结果体存对象存储，键和元数据存 Redis，避免大 value 撑爆内存
3. **怎么做失效** —— 缓存条目里记依赖版本，读取时比对，不匹配视为 miss，比批量删更稳

## 易错点

- 只用原文哈希 —— 忽略流水线版本，是这类系统最常见的缓存污染源
- 用 MD5 做键 —— 碰撞在小规模下不致命，但没必要省这点
- 不做归一化 —— 一个空格就 miss，缓存命中率会低到没有意义
