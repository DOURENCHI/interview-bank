## 题目

**场景**：字节日常实习一面 MQ 选型题。考「差异 + 选型依据」而不是罗列功能表：能点出 RocketMQ 的业务功能与 Kafka 的吞吐/生态两条主线，再落一个具体场景判断。

**问**：Kafka 和 RocketMQ 有什么区别？怎么选型？

## 口述答案

> 先定位：两者都是分布式日志型 MQ，底层同为**顺序写磁盘 + 零拷贝 + 批量压缩**，所以单机吞吐都在十万级往上，真正差异在**功能取向和生态**。
>
> **Kafka**：为**日志管道/流计算**而生——配合 Flink/Spark Streaming 是事实标准，生态最厚（Connect、Schema Registry、KRaft 去 zookeeper）；语义上以「高吞吐 + 同分区内有序」为核心，消息**无内置重试/延时队列**，失败要自己处理 offset。**RocketMQ**：为**在线业务**而生——Java 写的、阿里电商场景沉淀：**事务消息**（半消息 + 回查，解决「本地事务和发消息的原子性」）、**延时/定时消息**、**死信队列 + 消费重试**、消息查询轨迹，这些业务刚需 Kafka 都没有或要自建。运维上 RocketMQ 的 NameServer 比 Kafka 早期依赖的 ZooKeeper 轻（KRaft 后此差距缩小）。
>
> 选型一句话：**大数据流处理、日志采集、事件溯源选 Kafka；电商交易、订单驱动、需要事务/延时/重试的业务链路选 RocketMQ**。我们项目里如果订单超时关单，用 RocketMQ 的延时消息一特性就省掉一套定时扫表；纯埋点管道硬上 RocketMQ 反而少了 Flink 生态的顺滑。

## 讲深一层

| 维度 | Kafka | RocketMQ |
|---|---|---|
| 设计取向 | 日志/流管道，吞吐极致 | 在线交易，业务功能全 |
| 事务消息 | 无（Kafka 事务仅限流内原子） | 半消息 + 回查，跨本地事务 |
| 延时消息 | 无 | 支持固定级/任意级 |
| 重试与死信 | 自己管 offset | 内置重试队列 + DLQ |
| 生态 | Flink/Spark/Connect 最厚 | 电商/金融场景组件 |
| 语言/运维 | Scala/Kafka，KRaft 自治 | Java，NameServer 轻量 |

**判断技巧**：选型题公式 =「一句话定位差异 → 两个决定性差异点 → 落到自己项目的场景判据」。这题的决定性差异就两个：**要不要事务/延时消息，要不要流计算生态**。**记忆锚点**：「Kafka 供数（流），RocketMQ 做事（交易）」。

## 高频追问

1. **Kafka 为什么吞吐这么高？** —— 分区并行 + 顺序写 page cache + sendfile 零拷贝 + 批量压缩，把随机写变成流式顺序 IO。
2. **RocketMQ 事务消息流程？** —— 先发 half 消息（消费者不可见）→ 执行本地事务 → commit/rollback；broker 收不到二次确认就回查生产者，最多 N 次——保证「本地事务成功则消息必达」。
3. **消息丢失两边各防什么？** —— Kafka：acks=all + min.insync.replicas + 消费手动提交；RocketMQ：同步刷盘 + 同步复制 + 消费 ACK——都是生产端、存储端、消费端三段设防。

## 易错点

- 把 Kafka Streams 的「事务」当成 RocketMQ 那种事务消息——前者只保证流内原子，不能和数据库事务联动。
- 只背参数不给选型判据——面试官要的是「什么场景选谁」，不是功能清单。
- 说 RocketMQ 吞吐「远低于」Kafka——两者同量级，差异在功能不在吞吐数量级。
