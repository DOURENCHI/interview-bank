## 题目

**背景**：秒杀链路的故障追问，用户投诉"我就点了一次却有两个订单"，面试官要求分析成因和治理手段。

**问**：如果发生了重复下单，可能的原因是什么？怎么解决？

## 口述答案

> 原因大致四类。一，客户端重复提交：连点、超时重试、刷新重放 POST。二，链路重试：RPC 超时重试、MQ 至少一次投递，同一请求到达多次。三，服务端没有幂等键，见到请求就建单。四，并发竞态：两个请求同时查到"未下单"再各自插入。治理分三层：前端按钮置灰加一次性 token；网关用 `SETNX` 或布隆过滤器挡重复；最关键的是数据库唯一索引兜底——用业务幂等号（用户 + 商品 + 活动）建唯一键，插入冲突就查出已有订单返回。核心思路是承认请求会重复到达，把"防重"变成"重复到达也不产生重复结果"。

## 讲深一层

| 层次 | 手段 | 局限 |
|---|---|---|
| 前端 | 置灰、防重 token | 可绕过、刷新失效 |
| 网关 | `SETNX`、布隆过滤器 | 缓存失效即失守 |
| 服务 | 幂等表 + 状态机 | 多一次写 |
| 存储 | 唯一索引 | 最可靠，兜底 |

幂等表要点：`idempotency_key` 唯一，记录"请求指纹 + 处理结果"，重放直接返回首次结果而不是报错。

## 高频追问

1. **唯一索引冲突了返回什么？** —— 查出现有订单号返回成功，而不是抛 500，否则用户看到报错会再点一次
2. **MQ 重复投递怎么幂等？** —— 消费端用消息业务 id 建唯一键或 Redis `SETNX` 去重，处理逻辑本身要做成可重入
3. **超时重试和重复下单怎么区分？** —— 前者是同一幂等号，应该返回同一结果；后者是不同幂等号，属于真实重复购买，得靠业务规则限制

## 易错点

- 只在网关加 `SETNX`——缓存过期或 Redis 抖动就失守，唯一索引不能省
- 把"查询是否已下单再插入"当方案——并发下两个请求都能查到"没有"，这是经典竞态
- 幂等键用 UUID 每次新生成——那等于没有幂等，键必须来自业务（用户 + 商品 + 活动）
