## 题目

**场景**：滴滴一面 Spring 追问链：Spring Boot 自动配置 → 注入注解 → 「注解的实现原理是什么？为什么我加了那个注解之后它就能找到？」——考注解是不是真的只是标签、真正干活的是谁。

**问**：Java 注解的实现原理是什么？为什么加了注解之后，框架就能找到并处理它？

## 口述答案

> 注解本质是一个**继承自 `java.lang.annotation.Annotation` 的特殊接口**，编译后以属性表的形式存在 class 文件里（RuntimeVisibleAnnotations），它本身**不含任何逻辑**——就是一张贴在类、方法、字段上的标签。
>
> 「框架能找到」靠两件事：**@Retention 决定标签活到哪个阶段 + 反射把标签读出来**。只有 Retention 是 RUNTIME 的注解才保留到运行时，框架启动时扫描类路径，对 Class/Method/Field 调 `isAnnotationPresent` / `getAnnotation` 拿到注解信息，然后**执行框架自己的逻辑**：扫描注册、生成代理、依赖注入。所以「加注解就生效」的完整链路是：注解只是数据，反射是眼睛，处理器才是干活的手。
>
> 用 Spring 串一遍：启动时 @ComponentScan 扫描 → 发现 @Component 注解 → 生成 BeanDefinition 注册进容器 → 反射实例化 → @Autowired 由 AutowiredAnnotationBeanPostProcessor 这个后置处理器反射读出并完成注入——每个环节里注解都只是「被读的标记」，逻辑全部在读它的一方。

## 讲深一层

| @Retention | 存活阶段 | 谁在读 | 典型例子 |
|---|---|---|---|
| SOURCE | 只在源码，class 里没有 | 编译器/编译期处理器 | @Override、Lombok @Data |
| CLASS（默认） | 进 class 文件，运行时不可见 | 字节码工具 | 少量底层标记 |
| RUNTIME | 运行时可反射读取 | 框架反射 | @Component、@Autowired、@Transactional |

```java
// 最小复现：自定义注解 + 反射读取
@Retention(RetentionPolicy.RUNTIME)   // 少了这行反射永远读不到
@Target(ElementType.METHOD)
public @interface Schedule { String cron(); }
for (Method m : Task.class.getDeclaredMethods()) {
    Schedule s = m.getAnnotation(Schedule.class);  // 读到标签 → 触发注册逻辑
    if (s != null) registry.register(m, s.cron());
}
```

**判断技巧**：被问「XX 注解怎么生效」，先反问自己**谁在读它**——编译器（SOURCE）、字节码工具（CLASS）、运行时反射（RUNTIME）；答出「读的人」才算答完。**记忆锚点**：「注解是标签，反射是眼睛，处理器是手」。

## 高频追问

1. **Lombok 的 @Data 也是反射读的吗？** —— 不是，SOURCE 级，编译期注解处理器直接改 AST，class 文件里 getter/setter 已经生成，运行时根本不需要注解存在。
2. **反射拿到的注解对象是什么？** —— JDK 为注解接口生成的动态代理实例，统一负责返回成员值；这也是注解成员只能是基本类型/String/Class/枚举/注解/数组的原因。
3. **全类路径扫描慢怎么办？** —— 编译期生成索引（Spring 的 @Index、AutoConfiguration.imports）、缩小 @ComponentScan 范围、Bean 懒加载。

## 易错点

- 自定义注解忘写 `@Retention(RUNTIME)`——class 里有但反射读不到，还以为反射出了问题。
- 说「注解自带功能」——注解从不执行任何代码，一切效果来自读它的那一方。
- 把 @Override 当运行时注解——它是 SOURCE 级，编译器检查完就丢，class 里没有。
