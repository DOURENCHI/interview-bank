## 题目

**背景**：数据库基础题，考察 SQL 调优的方法论。

**问**：MySQL 的 SQL 优化怎么做？

## 口述答案

> 先定位再改，不要凭感觉加索引。用 explain 看执行计划：type 是不是 ALL、key 有没有命中、rows 估算多大、Extra 里有没有 Using filesort 或 Using temporary。常见手段：给 where 和 order by 建联合索引并遵守最左前缀、避免在索引列上做函数运算或隐式类型转换、用覆盖索引减少回表、深分页改成游标、大事务拆小。改完再用 explain 和实际耗时验证。

## 讲深一层

| type | 含义 | 评价 |
|---|---|---|
| const/eq_ref | 主键/唯一 | 好 |
| ref/range | 索引等值/范围 | 可接受 |
| index | 全索引扫描 | 偏差 |
| ALL | 全表扫描 | 需优化 |

深分页：`LIMIT 100000,20` 改为 `WHERE id > last_id ORDER BY id LIMIT 20`。

## 高频追问

1. **加了索引为什么不走？** —— 可能是区分度低、隐式转换、函数包裹列、or 条件或优化器估算代价更高。
2. **联合索引顺序怎么定？** —— 等值条件在前、范围条件在后，兼顾 order by 的最左前缀。
3. **explain 的 rows 准吗？** —— 是估算值，可能偏差很大，必要时用 optimizer trace 或实际执行对比。

## 易错点

- 见慢就加索引，写入变慢且可能重复索引
- 在索引列上用函数，索引直接失效
- 只看 explain 不看真实耗时和数据分布
