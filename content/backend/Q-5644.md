## 题目

**背景**：秒杀系统的开场大题，面试官要求把整条链路讲完整，看候选人是否只做过其中一层。

**问**：请讲一下秒杀系统的全链路，从用户点按钮到订单落库，每一层分别做了什么？

## 口述答案

> 按漏斗讲五层。一，前端：按钮置灰防连点，加验证码或答题削峰，活动页静态化走 CDN。二，接入层：Nginx 限流、缓存静态资源，网关做鉴权和同一 uid 的频控，把刷子挡在外面。三，应用层：请求先打 Redis，用 Lua 原子完成"扣库存 + 一人一单判定"，没通过的直接返回售罄，把九成以上流量拦在 DB 之外。四，异步层：通过的请求投 MQ 削峰，下游按自身消费能力拉取，避免瞬时流量冲垮数据库。五，存储层：消费端建单，`(user_id, goods_id)` 唯一索引防重，事务内完成扣库存、写订单、写流水；超时未支付由定时任务回补。每一层都要假设下一层会挂。

## 讲深一层

| 层 | 主要手段 | 目标 |
|---|---|---|
| 前端 | 置灰、验证码、CDN | 减少无效请求 |
| 接入 | 限流、鉴权、频控 | 挡住刷子 |
| 应用 | Redis 预扣、Lua 原子 | 拦截超量流量 |
| 异步 | MQ 削峰、批量消费 | 保护 DB |
| 存储 | 唯一索引、事务、补偿 | 最终正确 |

真正的容量瓶颈通常不在 Redis 而在 DB 的连接数和行锁，所以队列长度和消费并发要按 DB 的 TPS 反推。

## 高频追问

1. **为什么不在应用层直接扣 DB 库存？** —— 瞬时几千 QPS 会在行锁上排队，连接池打满，整个库被拖死；Redis 预扣是把竞争前移
2. **MQ 积压了怎么办？** —— 先确认消费端是否卡在 DB，再扩消费并发或批量写；盲目扩容可能把 DB 压垮
3. **链路里哪一步最可能不一致？** —— Redis 预扣成功但 MQ 投递失败，需要本地消息表或事务消息保证"预扣"和"投递"最终对齐

## 易错点

- 只讲 Redis 扣库存不讲落库——预扣不是成交，DB 侧的唯一索引和事务才是最终一致性保证
- 说"加机器就能扛"——秒杀瓶颈常在 DB 单行热点和连接数，加应用机器没用
- 漏掉回补和超时取消——库存预扣了但订单没支付，不回补就等于永久少卖
