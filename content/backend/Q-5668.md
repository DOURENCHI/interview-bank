## 题目

**场景**：美团一面，前面聊到 Spring Bean 默认单例作用域，顺势追问「你还用到哪些设计模式」。开放题：考有没有真的在代码里用过，而不是背 23 种名词。

**问**：除了单例，你还在项目里用过哪些设计模式？结合场景各讲一句。

## 口述答案

> 挑 2~3 个、每个按「痛点 → 模式 → 效果」讲透，别报菜名。我的常用组合：
>
> **策略 + 工厂**：计费/推送这类多渠道逻辑，原来一串 if-else 判断渠道码，每次加渠道都要改老代码。抽策略接口、每种渠道一个实现，注册进 Spring 容器按键取——新增渠道只加类不改老代码，改动范围收敛了。
>
> **模板方法**：多个导出/审批流程骨架一样（取数 → 校验 → 生成 → 通知），只是每步实现不同。抽象父类用 final 方法定骨架，子类填步骤——流程一致性有保证，改流程只改一处。
>
> **观察者/事件**：下单成功后要发积分、发通知、同步报表，原来在下单方法里串行调三个服务，耦合重还拖慢主流程。改成发领域事件（Spring Event 或 MQ），下游各自订阅——主流程只管下单，新增下游不动老代码。
>
> 收尾一句观点：模式是应对变化的手段，判断标准是「需求再变时是不是只改一处」，没有这个收益就不值得付抽象成本。

## 讲深一层

| 模式 | 一句话场景 | Java 生态里的影子 |
|---|---|---|
| 策略 | 多渠道计费/推送，按 key 选做法 | Spring 注入 Map<String, 接口> |
| 模板方法 | 流程骨架固定、步骤可变 | JdbcTemplate、Servlet 的 service() |
| 观察者 | 一个动作多个下游、要解耦 | Spring Event、ApplicationListener |
| 建造者 | 多参数配置对象、可选参数多 | Lombok @Builder、Stream.Builder |
| 代理 | 给方法无侵入加日志/事务 | Spring AOP、@Transactional |

**判断技巧**：讲模式必带「痛点 + 效果」两句——缺痛点像背书，缺效果像没用过。**记忆锚点**：「一个场景一个模式；场景讲得动，才算用过」。

## 高频追问

1. **单例有哪几种写法？** —— 枚举最稳（防反射、防序列化破坏），双检锁要 volatile 防指令重排，静态内部类兼顾懒加载和线程安全（Q-1055 有完整对比）。
2. **Spring 的单例 Bean 是设计模式里的单例吗？** —— 不是：是容器级共享实例（一个容器一份），不是类加载器唯一的静态单例，两个容器就有两份。
3. **责任链用过吗？** —— 网关过滤器、Servlet Filter/Interceptor 就是；亮点是顺序控制（@Order）和「任一环节可短路」。

## 易错点

- 报模式名不带场景——立刻露怯，等于没在项目里用过。
- 把「用了 Spring」当「用过模式」却说不出 AOP 是代理、Template 是模板方法——知识是散的。
- 说自己小项目里用满十几种——模式过度是减分项，面试官反而追问哪次是过度设计。
