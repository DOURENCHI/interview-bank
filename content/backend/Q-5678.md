## 题目

**场景**：字节 Agent 研发一面（原题面：是否了解 K8S）。Java 岗被问 K8s，考的是「用过的人」水平：一句话说清它解决什么问题 + 核心组件各自职责，能配一句自己实践更好。

**问**：说说你对 K8s 的理解：它解决什么问题？核心组件有哪些、各自干什么？

## 口述答案

> 一句话定位：**K8s 是容器编排平台，把「一组服务器」抽象成「一个资源池」**——你声明期望状态（这个服务跑 3 个副本、多少 CPU），它持续把实际状态向期望状态收敛。解决的是单机 Docker 之上的问题：**自动调度、故障自愈、弹性伸缩、服务发现与负载均衡、滚动发布回滚**——没有它，几百个容器的放置、重启、扩缩容全靠人盯。
>
> 核心组件分两面。**控制面（大脑）**：kube-apiserver——唯一入口，所有读写走它，认证/鉴权/etcd 存储；etcd——分布式 KV，存集群全部状态；kube-scheduler——决策「新 Pod 放哪个节点」（资源、亲和性、污点）；controller-manager——一组控制器循环「对比期望/实际状态并修正」（副本数、节点故障迁移）。**节点面（手脚）**：kubelet——节点代理，按 PodSpec 拉起并健康检查容器；kube-proxy——维护 Service 的转发规则（iptables/IPVS）；容器运行时（containerd）真正起容器。
>
> 抽象层记四个就够：**Pod**（最小调度单元，一组共享网络/存储的容器）、**Deployment**（管副本数与滚动更新）、**Service**（一组 Pod 的稳定访问入口 + 负载均衡）、**ConfigMap/Secret**（配置与敏感信息注入）。全部是「声明式 API + 控制器收敛」这一个思想的不同粒度。

## 讲深一层

| 组件 | 面 | 一句话职责 |
|---|---|---|
| apiserver | 控制面 | 唯一入口，认证后读写 etcd |
| etcd | 控制面 | 集群状态的唯一真相源 |
| scheduler | 控制面 | 决定 Pod 落到哪个节点 |
| controller-manager | 控制面 | 期望 vs 实际，驱动收敛 |
| kubelet | 节点 | 按 PodSpec 拉起/守护容器 |
| kube-proxy | 节点 | Service 规则转发（iptables/IPVS） |

**判断技巧**：答「是否了解 X」的模板：「一句话定位（解决什么）→ 分层组件（控制面/节点面）→ 一个抽象词收口（声明式 + 调谐循环）」。被追问就往自己场景引——Agent 服务用 Deployment 滚动升级、HPO 按 GPU 弹性扩缩容。**记忆锚点**：「apiserver 是门，etcd 是账本，scheduler 分房，controller 盯梢，kubelet 干活」。

## 高频追问

1. **Pod 和容器什么关系？** —— Pod 是最小调度单元，内含一至多个共享网络/存储/生命周期的容器；sidecar（日志收集、代理）就是同 Pod 的伴生容器。
2. **Service 和 Ingress 的区别？** —— Service 是四层稳定入口（Pod 漂移后 IP 变，Service 提供虚拟 IP + 负载均衡）；Ingress 是七层路由，按域名/路径把外部流量导到不同 Service。
3. **Pod 挂了会发生什么？** —— kubelet 探针失败按重启策略重启；节点级故障由 controller 在别的节点重建——「自愈」就是控制器调谐循环在起作用。

## 易错点

- 只背组件名不说「解决什么问题」——编排价值（自愈/伸缩/滚动发布）才是「理解」二字。
- 把 Docker 和 K8s 说成同类——Docker 是单机运行时，K8s 管跨机集群的调度与编排。
- 组件职责张冠李戴——「scheduler 起容器」（错，kubelet 干活）这类混淆一眼见底。
