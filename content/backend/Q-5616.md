## 题目

**背景**：聊到 Redis 数据结构选型时，面试官拿有序集合的底层实现发问，考的是能不能说出"为什么不用更常见的平衡树"。

**问**：Redis 的 zset 为什么用跳表而不用红黑树？

## 口述答案

> 主要三点。第一是范围查询：zset 的核心操作是 ZRANGE、ZRANGEBYSCORE，跳表底层是有序链表，定位到起点后顺着 level 0 指针线性扫即可，天然适合区间遍历；红黑树做范围查询要中序回溯，指针跳转的局部性差，对 CPU cache 不友好。第二是实现复杂度：跳表插入删除只改指针，不需要旋转和重新染色，代码短、容易证明正确，长期维护的代码库很看重这点。第三是并发友好：跳表是局部修改，便于做细粒度锁甚至无锁；红黑树一次旋转会影响一整片结构。代价是跳表最坏 O(N)、内存略高，但概率极低，Redis 用 p=1/4 控制层数。

## 讲深一层

| 项 | 跳表 | 红黑树 |
| --- | --- | --- |
| 查找/插入/删除 | 期望 O(logN)，最坏 O(N) | 最坏 O(logN) |
| 范围遍历 | O(logN+M)，顺链表 | O(logN+M)，需中序回溯 |
| 实现 | 无旋转，代码短 | 旋转 + 染色，易错 |
| 内存 | 平均 1.33 层指针/节点 | 3 指针 + 1 bit 颜色 |

Redis 的 zskiplist 层数上限 32，节点带 span 字段记录跨越节点数，所以 ZRANK 也能 O(logN)；红黑树不额外维护子树 size 做不到这点。

## 高频追问

1. **为什么不用 B+ 树** —— B+ 树的多叉是为减少磁盘 IO，纯内存场景反而增加节点内查找开销
2. **span 字段的作用** —— 支持 ZRANK/ZREVRANK 按排名访问，这是链表结构本身给不了的
3. **最坏 O(N) 有风险吗** —— 层数随机，整体退化概率可忽略；且 Redis 单线程，不存在并发导致的退化

## 易错点

- 只说"实现简单" —— 这只是第三条理由，范围查询才是 zset 选跳表的主因
- 说跳表查询是严格 O(logN) —— 是期望复杂度，最坏 O(N)，说死会被追打
- 断言"红黑树更省内存" —— 跳表平均 1.33 个指针，红黑树 3 指针加颜色位，结论不一定成立
