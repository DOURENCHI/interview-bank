## 题目

**背景**：Redis 使用的经验题，面试官想确认候选人是否真按访问模式选结构，而不是见到什么用什么。

**问**：Redis 常用的数据结构有哪些？你一般分别在什么场景下使用？

## 口述答案

> 对外五种最常用。String 做缓存对象和计数器，`INCR`/`DECR` 天然原子，适合库存扣减、限流计数、分布式锁的 value。Hash 存对象的多个字段，可以只改一个 field，比整个 JSON 覆盖省带宽，也省序列化。List 做简单队列（`LPUSH` + `BRPOP`）和时间线，但它没有 ack，可靠性要求高就别用。Set 做去重和交并差，比如"一人一单"的 userId 集合、标签圈人。ZSet 做排行榜和延迟队列，score 存时间戳，`ZRANGEBYSCORE` 取到期任务。另外 HyperLogLog 做 UV 估算、Bitmap 做签到、Stream 做带消费组的消息队列。选型看访问模式，不是看数据长什么样。

## 讲深一层

| 结构 | 底层编码 | 典型命令 | 注意 |
|---|---|---|---|
| String | int/embstr/raw | `INCR`、`SETNX` | 上限 512 MB |
| Hash | listpack/hashtable | `HINCRBY` | field 多时转 dict |
| List | quicklist | `LPUSH`+`BRPOP` | 无 ack，会丢 |
| Set | intset/listpack/hashtable | `SADD`、`SINTER` | 大集合运算阻塞 |
| ZSet | listpack/skiplist | `ZADD`、`ZRANGEBYSCORE` | 跳表 O(logN) |

编码阈值：`hash-max-listpack-entries` 默认 128、value 64 字节，超过转 hashtable，内存会明显上涨。选型时先问三件事：要不要按字段更新、要不要排序、要不要去重，答案基本能定结构。

## 高频追问

1. **ZSet 延迟队列怎么保证不丢？** —— `ZRANGEBYSCORE` 后要 `ZREM` 成功才算领取，配合消费失败重入；更强的语义得上 Stream 消费组
2. **大 key 有什么危害？** —— 单次操作阻塞主线程、删除时卡顿、网络带宽突刺，用 `--bigkeys` 或 `MEMORY USAGE` 排查
3. **Set 的 `SINTER` 在百万级集合上能用吗？** —— 会阻塞，改用 `SINTERSTORE` 到临时 key 再分页读，或者放到离线算

## 易错点

- 说 List 可以做可靠队列——`BRPOP` 弹出即删，消费者崩了消息就没了，可靠性场景必须用 Stream 或专业 MQ
- 用 String 存整个对象再全量覆盖——并发下会互相覆盖字段，Hash 的 `HSET` 单字段更新才是对的
- 忽略编码转换——listpack 转 hashtable 后内存可能翻几倍，这是"数据量一上来内存就爆"的常见原因
