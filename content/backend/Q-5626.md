## 题目

**背景**：紧接着 HashMap 的问题，面试官问替代方案内部是怎么做到并发安全的。

**问**：ConcurrentHashMap 的并发安全是怎么做到的？

## 口述答案

> JDK 8 的做法是 CAS 加桶级锁。数组每个桶的首节点就是锁对象：桶为空时用 CAS 直接把新节点放进去，完全不加锁；桶非空时 synchronized 锁住首节点，只锁这一个桶，其他桶的读写不受影响。读操作基本无锁，因为 Node 的 val 和 next 是 volatile 的，保证可见性。计数不用一把锁，用 baseCount 加 CounterCell 数组分散热点，思路和 LongAdder 一样，size 时求和，所以是弱一致。扩容支持多线程协助，已经迁完的桶放一个 ForwardingNode 标记，其他线程遇到就帮忙搬。相比 7 的分段锁，锁粒度从 Segment 降到单个桶，并发度高很多。

## 讲深一层

| | JDK 7 | JDK 8 |
| --- | --- | --- |
| 锁 | Segment 继承 ReentrantLock，默认 16 段 | synchronized 锁桶首节点 + CAS |
| 并发度 | 段数（16） | 桶数（容量） |
| 计数 | 段内 count | baseCount + CounterCell |
| 扩容 | 段内独立 | 多线程协助 transfer |
| size | 遍历段加锁 | sumCount，弱一致 |

`putIfAbsent`、`compute` 这些复合方法也是同一套"桶锁 + CAS"，所以针对单个 key 的复合操作是原子的；但跨多个 key 就不保证，需要自己加锁或用事务性封装。

## 高频追问

1. **size 为什么是弱一致** —— 并发插入时 sumCount 只是个近似值，要精确得自己加锁
2. **key 和 value 能为 null 吗** —— 不能，null 无法区分"不存在"和"值为空"，并发下会二义
3. **computeIfAbsent 有什么坑** —— 映射函数里再操作同一个 map 可能死锁或抛 IllegalStateException

## 易错点

- 说"用分段锁" —— 那是 JDK 7，8 已经是桶级 synchronized
- 认为读也加锁 —— 读靠 volatile 无锁，这是它读性能好的关键
- 说 size 是精确的 —— 是弱一致估计值
