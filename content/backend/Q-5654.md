## 题目

**背景**：消息队列的可靠性追问，面试官先问"消息会不会重复"，再问重复了怎么办。

**问**：消息队列出现重复消费怎么处理？

## 口述答案

> 先承认前提：主流 MQ 只能保证至少一次投递，重复是常态不是异常，所以方案一定在消费端做幂等。四种做法：一，唯一索引，用业务唯一键（订单号加操作类型）建唯一键，重复插入直接冲突；二，幂等表，记录消息 id 或业务 id 的处理状态，处理前先 `INSERT` 抢占，主键冲突即视为已处理；三，状态机，只允许合法迁移，比如订单只能从"待支付"转"已支付"，重复消息因状态不满足而跳过；四，Redis `SETNX` 做短期去重，适合能容忍极小概率漏判的场景。关键点：去重键要来自业务而不是消息 id，因为重投时消息 id 可能变。

## 讲深一层

| 方案 | 适用 | 代价 |
|---|---|---|
| 唯一索引 | 有天然业务键 | 需设计键 |
| 幂等表 | 通用 | 多一次写 + 清理 |
| 状态机 | 有明确状态流转 | 覆盖不全 |
| Redis SETNX | 高频短期去重 | 缓存失效即失守 |

"至少一次投递 + 消费端幂等 = 效果上的恰好一次"，这是工程上唯一可靠的组合，不要指望 MQ 端做到 exactly-once。

## 高频追问

1. **幂等表怎么清理？** —— 按业务保留窗口定期归档或删除，比如只保留 7 天，超出窗口的重复概率可忽略
2. **消息 id 为什么不能做去重键？** —— 重投可能生成新的 id，去重就失效了；要用业务语义上的唯一标识
3. **顺序消息重复了怎么办？** —— 顺序场景更依赖状态机或版本号，`UPDATE ... WHERE version = ?` 保证只应用一次

## 易错点

- 追求 MQ 端 exactly-once——成本和复杂度极高，主流做法仍是消费端幂等
- 用消息 id 去重——重投换 id 就失效，必须用业务键
- 幂等只做一半——检查通过后处理失败，下次重试又被判为"已处理"，要做成"处理成功才落标记"
