## 题目

**问**：软件延时用 for 循环嵌套实现，循环次数是怎么定出来的？有什么弊端？

## 口述答案

> 次数是**实测标定**出来的：固定主频和编译选项，用示波器翻转 GPIO 或 DWT 计数器测一次内层循环的周期数，再用目标延时反推循环次数。
> 弊端很明显：
> · 编译器可能把空循环优化掉，要加 `volatile` 或内联汇编；
> · 主频、Cache、等待周期一变，延时就不准；
> · 中断插进来会拉长实际时间；
> · 全程占着 CPU，低功耗场景浪费电；
> · 换芯片就要重标定。
> 工程上应改用硬件定时器、DWT 周期计数或 RTOS 的 `vTaskDelay`。

## 讲深一层

```c
// 不可靠：可能被优化，且随主频漂移
for (volatile int i = 0; i < 1000; i++);

// 可靠：DWT 周期计数
uint32_t start = DWT->CYCCNT;
while (DWT->CYCCNT - start < us * (SystemCoreClock / 1000000));
```
| 方式 | 精度 | 占 CPU | 可移植 |
|---|---|---|---|
| for 空循环 | 差 | 是 | 差 |
| 定时器 | 高 | 否 | 好 |
| DWT | 高 | 是 | Cortex-M 限定 |

## 高频追问

1. **为什么加 volatile 还可能不准？** —— 只防删除，不防主频和中断影响。
2. **微秒级延时怎么做？** —— DWT 或硬件定时器单次触发。
3. **RTOS 里能用忙等吗？** —— 会阻塞同优先级任务，除非在临界区且极短。

## 易错点

- 直接抄别人的循环次数，主频不同就错。
- 在低功耗场景用忙等，功耗下不来。
