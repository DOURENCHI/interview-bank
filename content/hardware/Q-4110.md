## 题目

**追问**：`configUSE_PREEMPTION` 和 `configUSE_TIME_SLICING` 都设 1，同优先级任务会怎样？

**问**：这两个宏的相互作用是什么？关掉时间片会有什么后果？

## 口述答案

> 两个都开：高优先级任务**立刻抢占**，同优先级任务**按 tick 轮转**（每个 tick 换一次）。
> 关掉 `configUSE_TIME_SLICING`：同优先级任务变成**先进先出**，只有当前任务阻塞/让出才换下一个。好处是减少切换开销，坏处是同优先级的两个死循环任务，第一个会把第二个饿死。

## 讲深一层

| 配置 | 高优先级就绪 | 同优先级 |
|---|---|---|
| 抢占 + 时间片 | 立刻抢占 | 每 tick 轮转 |
| 抢占 + 无时间片 | 立刻抢占 | 先进先出，直到阻塞 |
| 协作 + 时间片 | 不抢占 | 每 tick 轮转（仅当主动 yield 后） |
| 协作 + 无时间片 | 不抢占 | 先进先出 |

```c
// 想减少切换开销（同优先级任务本来就很少同时就绪）
#define configUSE_PREEMPTION    1
#define configUSE_TIME_SLICING  0
```

**时间片关闭的典型用途**：几个同优先级的任务都是"事件驱动"（等信号量才干活），根本不会同时就绪，时间片纯属浪费。

**代价**：一旦有任务长时间不阻塞，同优先级的其他任务就完全没有机会——这类 bug 很难查，因为"平时都是好的"。

## 高频追问

1. **tick 中断还会触发吗？** —— 会，`vTaskDelay` 仍然依赖 tick，只是不再因为时间片而切换。
2. **能运行时改吗？** —— 不能，是编译期宏。
3. **协作式下 `taskYIELD()` 有用吗？** —— 有，主动让出给同优先级任务。

## 易错点

- 关时间片后写同优先级死循环，饿死另一个任务
- 以为关时间片就没有 tick 了
- 把这两个宏和 `configUSE_TICKLESS_IDLE` 搞混
