## 题目

**题目**：两个任务同时对一个 32 位计数器 `counter++`，跑久了结果比预期小。

**问**：竞态条件怎么复现？「撕裂读写」是什么？怎么避免？

## 口述答案

> `counter++` 是**读-改-写三步**，不是原子操作。两个任务交错执行时，可能都读到旧值，各自加一写回，结果只加了 1——这就是**丢失更新**。
> **撕裂读写**指一个 32 位变量被拆成两次 16 位访问（在 8/16 位 MCU 上很常见），读到"一半新一半旧"的值。Cortex-M 上 32 位对齐访问本身是原子的，但读-改-写仍不是。

## 讲深一层

```
时间 →
任务A: 读 counter=5 ────────▶ 写 6
任务B:      读 counter=5 ──────────▶ 写 6
结果：6（应该是 7）
```

| 保护手段 | 关中断 | 禁任务切换 | 开销 | 适用 |
|---|---|---|---|---|
| `taskENTER_CRITICAL` | ✅ | ✅ | 极低 | 极短操作（几条指令） |
| `vTaskSuspendAll` | ❌ | ✅ | 低 | 稍长的操作 |
| 互斥量 | ❌ | ❌（阻塞） | 中 | 有阻塞/较长的临界区 |
| 原子操作 / 信号量 | — | — | 低 | 简单计数 |

```c
// 临界区：几行代码
taskENTER_CRITICAL();
counter++;
taskEXIT_CRITICAL();

// 原子包装（CMSIS）
__disable_irq(); ... __enable_irq();     // 不推荐直接这么写，用宏更可移植
```

**怎么复现**：在两个任务里各加一个 `vTaskDelay(0)` 或 `taskYIELD()` 插到读和写之间，制造交错窗口，问题立刻稳定出现——这是定位竞态最好的手段。

**中断与任务之间的竞态**：必须用临界区（关中断），因为互斥量不能在中断里用。

## 高频追问

1. **临界区里能调用 FreeRTOS API 吗？** —— 大部分不能（会断言），只能做纯计算/赋值。
2. **临界区多久算长？** —— 超过几十微秒就该换方案，否则影响中断响应。
3. **`volatile` 能解决吗？** —— 不能，它只阻止编译器优化，不保证原子性。

## 易错点

- 用 `volatile` 当同步手段
- 临界区里调用 `vTaskDelay` 或 `printf`
- 临界区太长，中断延迟变大
