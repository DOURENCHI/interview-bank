# Q-6163 Linux 的 Buddy（伙伴）内存分配算法是怎么工作的？为什么说它没有外部碎片？

## 口述答案

Buddy 把物理内存按 **2 的幂** 切成块：以 4KB 页为最小单位，每一阶 order 管一种大小——order 0 是 4KB，order 1 是 8KB……Linux 默认 MAX_ORDER=11，最大块 2¹⁰×4KB=**4MB**。每种大小各挂一条**空闲链表**（free_area[11]）。

**分配**：要 n 页，先算出最小能装下的 order，去对应链表找块；找不到就往上一阶找更大的块，拿到后**对半分裂**（一半留下挂链表，一半继续分），直到分裂到目标阶。比如要 1 页但只有 4MB 块：4MB→2×2MB→2×1MB→2×512KB→…→2×4KB，发一块，剩下 10 块各归各阶链表。

**释放**：看「伙伴」在不在。两块互为伙伴 = 大小相同、地址相邻、由同一个块分裂出来。伙伴地址用**异或**算：`buddy = addr XOR (1 << (order + 页大小位))`。伙伴空闲就**合并**成上一阶的块，递归向上，一直合到伙伴不空或到顶为止。

**为什么没有外部碎片**：碎片分两种——外部碎片是「空闲内存总量够、但分散成小块凑不出连续大块」；Buddy 的释放合并规则保证**只要两个伙伴都空闲就必然合并**，空闲块永远是完整的 2 的幂块，不会出现「很多 1 页散块永远拼不成 2 页」的死局。代价是**内部碎片**：要 300KB 只能给你 512KB，多出来的 212KB 浪费——这正是 slab 在它上面解决的问题（小对象用对象池切，见 Q-1557）。

锚点：**分配靠分裂，释放靠找伴，异或算伙伴，合并保连续。**

## 讲深一层

| 设计点 | 决策 | 为什么 |
| --- | --- | --- |
| 块大小 2 的幂 | order 阶链表，大小翻倍 | 伙伴判定只需异或一位；分裂/合并都是 O(1) 移位 |
| 伙伴地址 `addr XOR (1<<order+PAGE_SHIFT)` | 位运算不查表 | 互为伙伴⇔仅该位不同；XOR 翻转这一位即得对方地址 |
| MAX_ORDER=11（4MB） | 上限再大走 CMA/vmalloc | 大块连续物理页稀缺，ARM 上还要处理内存块搬迁 |
| 每阶链表 + 迁移类型 | free_area 按 MIGRATE_* 再分 | 防止不可移动页插在中间挡住大块合并（反碎片化） |
| 零外部碎片、有内部碎片 | 与 slab 分层 | Buddy 管**页框**，slab/kmalloc 管**小对象**（Q-1556） |

## 高频追问

1. **要 5 页怎么办？** —— 向上取整到 8 页（order 3），拿 8 发 8；多出的 3 页是内部碎片，内核尽量用 order 拆分策略减小浪费。
2. **合并为什么必须要求「同一个父块」？** —— 只判相邻还不够：地址相邻但分属不同父块的两块没有共同的上一阶表示，合并会破坏 2 的幂结构；伙伴关系天然编码了父块信息。
3. **伙伴系统在用户态 malloc 里用吗？** —— glibc 的 ptmalloc 用 bins + top chunk 切分，不是经典 buddy；但内核的 kmalloc 底层（slab/slub）下面就是 buddy。
4. **free 的时候怎么知道块大小？** —— 内核用 page 结构的私有字段/阶数记录；用户态 malloc 则在块头存 size。
5. **为什么释放要立即合并，不攒一攒？** —— 立即合并保住「无外部碎片」承诺；代价是抖动（频繁分裂合并），THP/CMA 场景有延迟合并的折中讨论。

## 易错点

- 把「没有外部碎片」说成「没有碎片」——**内部碎片一直都在**，追问立刻露馅。
- 伙伴地址用减法算（`addr ± size`）——那只对「低地址块」成立；XOR 才是双向通用的。
- 说「链表找块是遍历」——每阶链表内任意取一块即可（大小全等），取第一块就是 O(1)。
- 只背「2 的幂」不提 order 分裂链路——面试官下一句「要 1 页只有 4MB 怎么办」就接不住。
