## 题目

**背景**：从 `kmalloc` 的实现追问到 slab，考察是否理解内核分配器的设计动机。

**问**：Linux 的 slab 分配器是为了解决什么问题？它的核心机制是什么？

## 口述答案

> 结论：解决**小对象频繁分配释放的两个成本**：buddy 的最小粒度是页（4KB），分配 64 字节结构体会浪费 98% 的空间；而且每次都要走位图查找、拆分合并、重新初始化。slab 从 buddy 拿整页，切成**同尺寸对象的缓存池**（`kmem_cache`），分配直接从 freelist 取已构造好的对象，释放还回池子。构造/析构只做一次，还保留 cache 热度；配合 per-CPU 缓存，大部分分配路径无需加锁。

## 讲深一层

| 分配器 | 特点 |
|---|---|
| SLAB | 早期实现，队列 + 着色 |
| SLUB | 现在默认，per-CPU freelist，元数据放 page 结构，更简单 |
| SLOB | 嵌入式小内存，极简 first-fit |

```bash
slabtop -o            # 按占用排序看各 cache
cat /proc/slabinfo    # 对象数、每 slab 对象数
```
关键指标：`objsize`、`num_objs`、`active_objs`；`kmem_cache_create()` 可建专用 cache。

## 高频追问

1. **slab 会碎片化吗？** —— 会，部分 slab 半空无法归还；SLUB 有 `slab_min_order` 与碎片整理，`drop_caches` 可回收。
2. **和用户态 malloc 的关系？** —— glibc 的 `malloc` 也用类似的 arena/bins 池化思路，只是不叫 slab。
3. **怎么优化自建 cache？** —— 对齐到 cacheline 避免伪共享，按 NUMA 节点分片，热点对象设 CPU partial。

## 易错点

- 说 slab 解决的是"内存不够"，实际是碎片与分配开销
- 混淆 SLAB/SLUB，答不出当前默认是 SLUB
- 认为 slab 对象归还后物理页立即还给 buddy
