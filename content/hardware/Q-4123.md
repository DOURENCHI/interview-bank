## 题目

**题目**：`configTOTAL_HEAP_SIZE` 是干什么的？为什么不用 C 库的 `malloc` 就够了？

**问**：为什么 FreeRTOS 需要自己的一块堆？

## 口述答案

> 四个原因：**确定性**（分配时间可预测，`heap_1` 甚至没有释放）、**可控性**（不会和 C 库抢内存、不怕碎片策略不可控）、**线程安全**（FreeRTOS 内部会挂起调度器）、**可观测**（能查剩余/历史最小剩余）。
> C 库的 `malloc` 在嵌入式上往往不可重入、碎片策略不透明，还可能因为 `printf` 之类偷偷分配而失败。

## 讲深一层

| 方案 | 能否释放 | 碎片 | 确定性 | 适用 |
|---|---|---|---|---|
| `heap_1` | ❌ | 无 | 最高 | 任务只创建不删除 |
| `heap_2` | ✅ | 有（不合并） | 中 | 已不推荐 |
| `heap_3` | ✅ | 看 C 库 | 低 | 需要和 C 库共用 |
| `heap_4` | ✅ | 有（**会合并**） | 中 | **最常用** |
| `heap_5` | ✅ | 会合并 | 中 | 多块不连续 RAM |

```c
// 运行时观测
size_t free_now  = xPortGetFreeHeapSize();
size_t free_min  = xPortGetMinimumEverFreeHeapSize();   // 历史最低
```

**`heap_4` 为什么最常用**：支持释放且会合并相邻空闲块（减少碎片），实现简单可靠。

**为什么不用 `heap_3`（走 C 库 malloc）**：C 库的 `malloc` 在嵌入式上通常不可重入，而且和 `printf` 抢同一块 heap，出问题很难查。

## 高频追问

1. **堆会碎片化吗？** —— `heap_4` 会合并相邻块，长期运行仍可能碎片；固定大小对象建议用内存池。
2. **能同时用两个堆吗？** —— 不能直接，但可以自己实现 `pvPortMalloc` 包装多区域。
3. **`configTOTAL_HEAP_SIZE` 从哪块内存来？** —— 从 `.bss`（一个大静态数组），所以会占 RAM。

## 易错点

- 只加 `configTOTAL_HEAP_SIZE` 却忘了它会占 RAM
- 用 `heap_2`（不合并，碎片严重）
- 运行时内存不足只看返回值不查剩余量
