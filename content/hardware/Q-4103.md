## 题目

**场景**：一个 Cortex-M3、64 KB RAM 的板子，有人开了 10 个任务，`configMINIMAL_STACK_SIZE` 设 128，编译过了，跑起来 HardFault。

**问**：一个 FreeRTOS 任务占多少 RAM？TCB 加栈怎么算？`usStackDepth` 的单位是什么？

## 口述答案

> 两块：**TCB**（任务控制块，Cortex-M 上约 80–100 字节）加**任务栈**（由 `usStackDepth` 指定）。
> 关键坑是：**`usStackDepth` 的单位是"字"不是"字节"**。Cortex-M 上一字 4 字节，写 128 就是 512 字节。10 个任务就是 10×(100+512) ≈ 6 KB，再加上堆和其他开销。

## 讲深一层

```c
// usStackDepth = 128 → 128 字 = 512 字节
xTaskCreate(task_fn, "adc", 128, NULL, 3, NULL);
```

| 项 | 大小（Cortex-M3/M4） | 说明 |
|---|---|---|
| TCB | 约 80–100 B | 链表节点、优先级、栈顶指针等 |
| 最小栈 | 约 128 B | 只够空任务 |
| 带 `printf` 的栈 | 512 B–1 KB | `printf` 内部吃栈很凶 |
| 浮点任务 | + 额外保存区 | FPU 上下文 |

典型取值参考：

| 任务类型 | 建议栈（字） |
|---|---|
| 空循环/闪灯 | 64–128 |
| 普通业务逻辑 | 128–256 |
| 用了 `printf` / `sprintf` | 256–512 |
| 递归 / 大局部数组 | 单独评估 |

**怎么看实际用量**：`uxTaskGetStackHighWaterMark(handle)` 返回历史最小剩余量（单位字），剩得越少越危险。留 20–30% 余量比较稳。

## 高频追问

1. **为什么单位是字？** —— 栈按 `StackType_t`（通常 32 位）分配，用字更自然；但和"字节"混淆是经典坑。
2. **栈能动态增长吗？** —— 不能，FreeRTOS 栈大小创建后固定。
3. **`configMINIMAL_STACK_SIZE` 是什么？** —— 空闲任务用的栈大小，不是所有任务的默认值。

## 易错点

- 把 `usStackDepth` 当字节数，栈小了 4 倍
- 用 `printf` 却没加大栈
- 只算栈不算 TCB
