## 题目

**场景**：驱动要接一个按键中断，按键与其他设备共用一根 GPIO 中断线。面试官从注册一路问到调度行为。

**问**：request_irq 如何使用？共享中断怎么判断中断来源？什么时候用线程化中断？

## 口述答案

> request_irq(irq, handler, flags, name, dev_id) 注册硬中断处理：irq 来自设备树中断号映射，flags 常用 IRQF_SHARED/IRQF_TRIGGER_*，dev_id 在共享中断时必填且每家不同，用于注销和区分来源。共享中断判断来源：内核把同一 irq 的所有 handler 串成链表，中断来了挨个调用，每个 handler 先读自己设备的状态寄存器确认"是不是我在响"，不是就立刻返回 IRQ_NONE，是才处理并返回 IRQ_HANDLED——一段时间内全是 IRQ_NONE，内核还会认为这条线出了" IRQ flood"并告警。线程化中断：request_threaded_irq(irq, hardirq, thread_fn, ...)，hardirq 里只做"取数据+关中断源"这类不可睡的事，然后唤醒内核线程执行 thread_fn，线程里可以 sleep、用 mutex、走 I2C 读补偿数据——凡是中断处理要碰慢总线（I2C/SPI）或可能耗时不确定的，就该线程化。

## 讲深一层

```c
/* 共享中断注册：dev_id 必须唯一 */
ret = request_irq(client->irq, btn_isr,
                  IRQF_SHARED | IRQF_TRIGGER_FALLING,
                  "btn", client);

/* 线程化中断：上半部极短，重活进线程 */
ret = request_threaded_irq(client->irq, btn_hardirq, btn_thread,
                           IRQF_TRIGGER_FALLING, "btn", client);
```

| 判断点 | 硬中断 handler | 线程化 thread_fn |
|---|---|---|
| 能否 sleep | 绝对不能 | 可以（就是普通内核线程） |
| 典型动作 | 读状态、清中断标志、kfifo 入队 | I2C/SPI 读数据、加锁、上抛 event |
| 调度约束 | 占着中断线，越短越好 | 普通优先级，可被调度 |

判断技巧：**"清中断在硬中断，干活在线程"是线程化中断的固定分工**；硬中断里还敢调 i2c_transfer 就是最典型的错误。

## 高频追问

1. **共享中断里两个设备同时响怎么办？** —— 链表上每个 handler 都会被调一遍，各自查各自的状态寄存器；互不影响，但都处理完这条线才算完。
2. **IRQF_SHARED 的前提是什么？** —— 所有共享方都要声明该标志，且触发方式兼容；电平触发比边沿更适合共享（边沿可能丢事件）。
3. **threaded_irq 的线程优先级能调吗？** —— 能，SCHED_FIFO 可通过 `irq_set_irq_type` 之外的力量（如 cgroup/priority 参数）调整；实时系统里常把关键中断线程提到 RT 优先级。

## 易错点

- 共享中断 handler 不检查来源就直接处理，把别人的中断当自己的
- dev_id 传 NULL 或重复，`free_irq` 时拆错别人
- 硬中断里用 mutex / msleep / 大段内存分配——这些都是睡眠调用，直接 BUG
- 忘了在 handler 里清中断标志，导致中断风暴
