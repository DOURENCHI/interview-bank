## 题目

**场景**：写一个 I2C 传感器的 Linux 驱动，面试官画了两层框：`i2c_driver`（设备驱动）和 `i2c_adapter`（控制器驱动），问这两层各管什么。

**问**：I2C 外设驱动和 I2C 控制器驱动有什么区别？它们如何协作完成一次传输？

## 口述答案

> 外设驱动管"这个器件说什么话"，控制器驱动管"总线怎么把话说出去"。外设驱动（`i2c_driver`）面向具体芯片：定义 of_match 匹配表、probe 里读设备树、创建设备、按芯片手册组寄存器读写序列。控制器驱动（`i2c_adapter`，也叫总线驱动）面向 SoC 上那一个 I2C 控制器外设：实现 `i2c_algorithm` 的 `master_xfer`，把抽象的 i2c_msg 翻译成对控制器寄存器（起始/停止/ACK/DMA）的实际操作。协作方式：外设驱动调 `i2c_transfer(adap->..., msgs)`，内核按设备树挂载关系找到所属 adapter，adapter 的 `master_xfer` 逐条搬 msg 到总线上，时序由控制器硬件完成，外设驱动只管收发回调数据。

## 讲深一层

```c
/* 控制器侧：SoC 厂商实现 */
static const struct i2c_algorithm soc_i2c_algo = {
    .master_xfer   = soc_i2c_master_xfer,   /* 把 i2c_msg 落到寄存器 */
    .functionality = soc_i2c_func,
};

/* 外设侧：芯片驱动只组 msg，不碰寄存器 */
static int sensor_read_reg(struct i2c_client *client, u8 reg, u8 *val)
{
    struct i2c_msg msg = { .addr = client->addr, .flags = 0,
                           .buf = &reg, .len = 1 };
    return i2c_transfer(client->adapter, &msg, 1);
}
```

| 层 | 内核对象 | 谁写 | 关心什么 |
|---|---|---|---|
| 外设驱动 | `struct i2c_driver` + `i2c_client` | 芯片用户/社区 | 芯片手册、寄存器含义、of_match |
| 总线核心 | `i2c-core` | 内核自带 | 匹配、转发、复用 |
| 控制器驱动 | `struct i2c_adapter` + `i2c_algorithm` | SoC 厂商 | 控制器寄存器、时序、FIFO/DMA |

记忆锚点：**外设驱动说"人话"（寄存器语义），控制器驱动说"电平"（总线时序），i2c-core 是翻译官。**

## 高频追问

1. **为什么这么分层？** —— 一套外设驱动能跑在任意 SoC 上（只依赖 adapter 接口），SoC 厂商只需实现一次控制器驱动；不分层就得为每颗芯片×每个平台各写一遍。
2. **设备树里怎么把两者关联起来？** —— 控制器节点（如 `i2c0: i2c@...`）下挂外设子节点，子节点的 `reg = <设备地址>`；probe 时外设的 `client->adapter` 就指向父节点对应的 adapter。
3. **一次 transfer 里控制器驱动具体做什么？** —— 检查 busy、写目标地址到 TX 寄存器、使能并等中断/DMA、处理 ACK/NACK 与 stop 条件，返回 msg 实际搬运的字节数。

## 易错点

- 把控制器驱动当"外设驱动的一种"——两者注册接口都不同（`i2c_register_driver` vs `i2c_add_numbered_adapter`）
- 在外设驱动里直接操作 I2C 控制器寄存器——跨层，换板就废
- 混淆 `i2c_client->addr`（7 位地址）与数据手册写的 8 位读写地址
