## 题目

**追问**：`configCHECK_FOR_STACK_OVERFLOW` 设 2 之后，钩子函数被调用了，怎么找出是谁吃掉了栈？

**问**：任务栈溢出会怎么表现？FreeRTOS 怎么检测？找到之后怎么修？

## 口述答案

> 表现是**随机故障**：HardFault、变量被改、任务跑飞、重启。因为溢出会踩坏相邻内存，位置不固定。
> 检测靠 `configCHECK_FOR_STACK_OVERFLOW`（推荐 2）+ `vApplicationStackOverflowHook`，钩子里能拿到任务名。定位后用 `uxTaskGetStackHighWaterMark` 看历史水位，找出最紧张的那个任务。

## 讲深一层

```c
#define configCHECK_FOR_STACK_OVERFLOW 2

void vApplicationStackOverflowHook(TaskHandle_t xTask, char* pcTaskName) {
    taskDISABLE_INTERRUPTS();
    // 此时来不及 printf（可能也吃栈），直接点灯/死循环
    volatile char* name = pcTaskName;
    (void)name;
    for (;;);
}

// 平时巡检
void stack_report(void) {
    TaskHandle_t hs[16]; UBaseType_t n = 16;
    uxTaskGetSystemState(NULL, 0, &n);           // 先拿任务数
    for (UBaseType_t i = 0; i < n; ++i) { /* 遍历打印水位 */ }
}
```

| 常见吃栈原因 | 修法 |
|---|---|
| `printf` / `sprintf` | 加大栈到 512 字以上，或改轻量输出 |
| 大局部数组 `char buf[512]` | 改成 `static` 或 malloc |
| 递归 | 改迭代 |
| 深层函数调用链 | 精简调用层次 |
| 浮点运算 + FPU 上下文 | 额外预留空间 |

**钩子里的注意事项**：不能再调用可能阻塞或吃栈的 API；最稳的做法是点个 LED 或写一个全局标志然后死循环，让调试器停在那里看调用栈。

## 高频追问

1. **溢出后还能恢复吗？** —— 不能可靠恢复，数据已经被破坏；只能复位。
2. **水位单位是什么？** —— 字（`StackType_t` 个数），Cortex-M 上是 4 字节。
3. **中断用的栈会溢出吗？** —— 会，主栈（MSP）大小在启动文件里配，`printf` 在中断里尤其危险。

## 易错点

- 钩子里调用 `printf`（可能再次溢出/阻塞）
- 只看当前水位不看最小值
- 溢出后试图"继续跑"
