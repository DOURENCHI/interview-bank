## 题目

**背景**：奇瑞嵌入式二面真题。CAN 是车企面试的必修考点，仲裁机制 + 极端场景追问是标准两连。
**问**：CAN 总线仲裁怎么工作？如果节点一直发高优先级报文会有什么影响？

## 口述答案

> CAN 是多主总线，仲裁靠物理层的「线与」完成，不用任何令牌或轮询。所有节点同时发 ID，逐位比较：显性电平 0 会压过隐性电平 1；某节点发出 1 却在总线上回读到 0，就知道有更高优先级的报文在发，立刻退出仲裁转入只收模式，等总线空闲再重发自己的帧。因此 ID 数值越小优先级越高，且仲裁是非破坏性的——赢的报文从头到尾没被打断，不用重传。标准帧 ID 11 位，扩展帧 29 位。如果某节点持续发最高优先级 ID（比如 0x000）：每次仲裁都是它赢，其他节点全部退避，低优先级报文永远排不上——总线被独占，出现饿死，负载率飙高、其它节点的周期报文超时。工程上靠 ID 规划避免：安全类报文给最小区号、周期状态量次之、诊断（0x7xx）压最低；再用 CANoe/candump 统计各 ID 的占比和总线负载率，一般控制在 70%~80% 以下。

## 讲深一层

- 仲裁从 SOF 位开始逐位进行，数据段不参与仲裁；扩展帧与标准帧混发时靠 IDE 位区分，11 位 ID 相同时扩展帧胜出（SRR/IDE 规则），ID 规划时要注意这个坑。
- 「一直发高优先级」的两种恶化路径：合法帧刷屏 → 其他节点饿死、发送超时；若该节点还伴随错误（位错误、ACK 错误），其发送错误计数器 TEC 上升，经历 error active → error passive → bus-off，最坏被隔离出总线。
- CAN FD 的仲裁段速率不变（受环路延迟限制），数据段可以提速并扩到 64 字节，所以「仲裁带宽」仍是瓶颈，ID 规划逻辑不变。

## 高频追问

1. 为什么 ID 小优先级高？——从线与推：ID 逐位比较，先发 0（显性）的把发 1 的压退，数值小的 ID 高位更容易是 0
2. bus-off 后怎么恢复？——检测到 128 次 11 位连续隐性序列后复位错误计数重新加入，软件通常配合复位控制器重初始化
3. 总线负载率怎么算？——按位填充后的帧长度×发送频率求和除以波特率，CANoe 有现成统计

## 易错点

- 说成轮询或令牌仲裁——CAN 是逐位非破坏性仲裁，这是与 CANopen 之上应用层的区分点
- 以为输掉仲裁的节点「发了一半要整帧重传算错误」——仲裁退出是正常机制，不算错误帧，总线空闲后自动重发
- 忽略 0x000 优先级最高这件事——真实项目里诊断 ID 放高优先级会直接把控制报文饿死
