## 题目

**场景**：同事把喂狗放进了 SysTick 中断，理由是"这样肯定不会漏喂"。

**问**：这样做有什么风险？看门狗到底应该在哪里喂？

## 口述答案

> 放中断里喂狗，等于把"系统还活着"的判断交给了**中断**——只要中断还在跑，哪怕主循环死锁、任务饿死、堆被踩坏，狗照样被喂，看门狗就失效了。
> 正确做法是**在能证明系统整体健康的地方喂**：通常在最低优先级的监控任务里，各业务任务周期性地置自己的心跳位，监控任务确认所有心跳都更新过，才喂一次狗。任何一个任务卡死都会导致停喂。
> 不要在中断里喂还有两个原因：喂狗时间点不受调度控制，可能刚好落在窗口看门狗禁止喂的窗口外；调试断点时中断仍在跑，会掩盖问题。

## 讲深一层

```c
void monitor_task(void *arg) {
    const uint32_t all = (1u << TASK_N) - 1;
    for (;;) {
        if ((heartbeat & all) == all) {     // 所有任务都报过到
            heartbeat = 0;
            HAL_IWDG_Refresh(&hiwdg);       // 只在全健康时喂
        }
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}
```

| 喂狗位置 | 能发现的故障 | 风险 |
|---|---|---|
| 中断里 | 几乎发现不了 | 掩盖主循环死锁 |
| 主循环 | 主循环卡死 | 单任务卡死可能漏检 |
| 监控任务 + 心跳 | 任务卡死、调度异常 | 需要设计心跳协议 |
| 窗口看门狗 | 还能发现"跑飞、跑太快" | 喂早了也会复位 |

超时时间取"最长正常周期 × 2~3"；调试时用 DBGMCU 冻结看门狗，别为了调试把狗关死。

## 高频追问

1. **独立看门狗和窗口看门狗差在哪？** —— 独立看门狗用内部 LSI，主时钟挂了也能跑；窗口看门狗由 APB 时钟驱动，还要求喂狗落在窗口内。
2. **低功耗下看门狗还跑吗？** —— 独立看门狗在 Stop/Standby 下仍可运行，唤醒后要重新配置。
3. **喂得太频繁有什么问题？** —— 失去意义，还增加寄存器和总线访问开销。

## 易错点

- 多处都喂（中断 + 主循环），等于变相取消保护。
- 超时设得比最坏执行时间还短，正常业务也被复位。
