## 题目

**场景**：CubeMX 生成的工程里有一堆 `stm32f1xx_hal_*.c`，用户代码被夹在 `/* USER CODE BEGIN */` 之间。

**问**：HAL 库的分层结构是怎样的？业务代码应该写在哪一层？为什么不能改生成的文件？

## 口述答案

> 四层：**寄存器层**（`stm32f1xx.h` 里的结构体定义）、**HAL 驱动层**（`stm32f1xx_hal_gpio.c` 等，操作寄存器）、**中间件**（FreeRTOS/FATFS/USB）、**应用层**（你的业务）。
> 业务代码写在**应用层**（`main.c` 的 USER CODE 区、自己的 `.c` 文件、以及 HAL 回调函数）。CubeMX 重新生成时会覆盖生成区，只保留 USER CODE 区，所以改别处会丢。

## 讲深一层

```
应用层        你的任务、业务逻辑、HAL 回调
   ↑
中间件        FreeRTOS / FATFS / LwIP
   ↑
HAL 驱动层    HAL_GPIO_WritePin / HAL_UART_Transmit
   ↑
寄存器层      GPIOA->BSRR = ...
```

| 层 | 典型文件 | 能不能改 |
|---|---|---|
| 寄存器定义 | `stm32f1xx.h` | ❌ |
| HAL 驱动 | `Drivers/STM32F1xx_HAL_Driver/` | ❌（要改就放 `_user.c`） |
| 中间件 | `Middlewares/` | ❌ |
| 应用 | `Core/Src/main.c` USER CODE | ✅ |
| 自定义驱动 | `Drivers/BSP/` | ✅ |

**HAL 的"回调"是关键设计**：外设中断由 `HAL_xxx_IRQHandler` 统一处理，它内部调用 `HAL_xxx_Callback`（弱函数），你在应用层重定义即可——这样生成代码和用户代码彻底分离。

**绝对不要改 `Drivers/` 下的文件**：换 CubeMX 版本或改配置就会全被覆盖，而且以后没人知道这里被改过。

## 高频追问

1. **USER CODE 区能放多少？** —— 放调用和回调，逻辑多了就拆到自己文件。
2. **想改 HAL 行为怎么办？** —— 用回调、或用 `_user.c` 覆盖弱函数，不要改 HAL 源文件。
3. **能不能不用 HAL？** —— 能，直接用寄存器或 LL 库，性能更好但可移植性差。

## 易错点

- 改 `Drivers/` 下的 HAL 文件
- 业务逻辑全塞 `main.c` 的 while 循环
- 在中断回调里做耗时操作
