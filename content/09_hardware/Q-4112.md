## 题目

**场景**：用 CubeMX 生成 HAL 工程，再挂 FreeRTOS，发现 `HAL_Delay` 变慢或卡死。

**问**：FreeRTOS 的时基为什么常用独立定时器（如 TIM6）而不是 SysTick？

## 口述答案

> 因为 **HAL 库自己也用 SysTick** 做 1 ms 时基（`HAL_Delay`、`HAL_GetTick` 都依赖它）。FreeRTOS 接管 SysTick 中断后，HAL 的时基要么被打断、要么和 FreeRTOS 抢同一个中断，结果就是 `HAL_Delay` 不准确甚至死等。
> 解决办法：**给 HAL 换一个定时器做时基**（TIM6/TIM7），SysTick 留给 FreeRTOS。

## 讲深一层

```c
// main.c 里把 HAL 时基改到 TIM6
HAL_InitTick(TIM6);   // 或在 CubeMX 里把 Timebase Source 设为 TIM6

// stm32f1xx_it.c 里保留 SysTick_Handler 给 FreeRTOS
void SysTick_Handler(void) {
    xPortSysTickHandler();     // FreeRTOS 接管
}
```

| 方案 | HAL 时基 | FreeRTOS tick | 结果 |
|---|---|---|---|
| 都用 SysTick | SysTick | SysTick | ❌ `HAL_Delay` 不准/死锁 |
| HAL 用 TIM6，RTOS 用 SysTick | TIM6 | SysTick | ✅ **推荐** |
| RTOS 用 TIM6，HAL 用 SysTick | SysTick | TIM6 | ✅ 也可以（需改 port 配置） |

**为什么 `HAL_Delay` 会死**：它内部是 `while (uwTick - start < ms)`，`uwTick` 靠 SysTick 中断累加。如果 SysTick 被 FreeRTOS 接管且不再更新 `uwTick`，这个 while 就永远不结束。

**一条纪律**：RTOS 工程里**不要用 `HAL_Delay`**，用 `vTaskDelay`——后者会让出 CPU，前者是空转。

## 高频追问

1. **改了时基还要改什么？** —— 确认 TIM6 的中断优先级低于 `configMAX_SYSCALL_INTERRUPT_PRIORITY`（HAL 时基中断可能调 API）。
2. **`HAL_GetTick` 还能用吗？** —— 能，但值来自 TIM6，和 FreeRTOS 的 tick 不同源。
3. **能不用 HAL 吗？** —— 能，裸用寄存器 + FreeRTOS，就没有这个冲突。

## 易错点

- RTOS 工程里调 `HAL_Delay`，空转 + 时基冲突
- 改了 Timebase 但没改中断优先级
- 以为 `HAL_Delay` 会让出 CPU
