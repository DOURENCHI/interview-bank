## 题目

**背景**：华为三面嵌入式题，前一轮手撕了环形缓冲区，面试官顺势追问数据一致性：中断里写、任务里读，怎么保证数据不乱。考的是并发意识能不能落到 MCU 的真实约束上。
**问**：中断里写、任务里读，怎么保证数据不乱？

## 口述答案

> 这是典型的单生产者（中断）单消费者（任务）场景，我会分四层答。第一层选数据结构：环形缓冲区+FIFO，两边各持一个下标，写侧只推进写指针、读侧只推进读指针，天然把「同时碰同一个变量」减到最少。第二层是下标的并发安全：单字节序系统里，让每个下标只有一个写者，读另一方写入的下标时用原子宽度的对齐读（32 位 MCU 上对齐 32 位读写是原子的）；如果用了 64 位下标或复杂元数据，就要在读侧短暂关中断或用原子操作，防止读到「写了一半」的值。第三层是数据帧本身的一致性：多字节结构体不能让读侧读到写了一半的帧，采用「先写数据、后提交长度」的提交顺序，或双缓冲整帧切换；同时置标志要「先写数据再置位」，读侧「先清标志再取数」，配合编译器屏障防止编译器把写顺序重排。第四层是策略兜底：中断里绝不忙等，缓冲满时按业务选覆盖或丢弃，丢帧要能通过序号/计数检测出来。最后点一句工程终解：FreeRTOS 下直接用队列的 FromISR API，上面这些它都封装好了，自己手写的价值是零拷贝和确定性时延。

## 讲深一层

- volatile 的作用边界：只禁止编译器缓存/重排对该变量的访问，不保证读改写原子、不防总线级乱序——所以 volatile+原子宽度对齐读才成立。
- 提交顺序为什么关键：「数据→长度→标志」的顺序配合读侧校验，能把「读到半帧」变成「读到未提交（跳过）」，错误从脏数据降级为丢帧，可检测。
- 三种临界区方案对比：关中断（最简单、影响实时性、窗口要短）、原子操作（细粒度、依赖硬件）、FreeRTOS 队列（最省心、有拷贝开销和调度延迟）。
- 双缓冲 vs 环形缓冲：帧率固定、整帧处理选双缓冲（切换指针即可）；流式、速率不均选环形缓冲。
- DMA 场景加一条：缓冲区还要处理 Cache 一致性（无效化/回写），这是这一题在带 Cache 的 MCU 上的进阶追问。

## 高频追问

1. 为什么环形缓冲区适合这个场景？——SPSC 下读写指针各只有一个写者，无锁正确性有保障，且天然实现流控
2. 64 位时间戳在中断和任务间共享怎么办？——用原子访问或关中断包裹，或拆成「低位+翻转位」技巧，绝不能裸读写
3. FreeRTOS 队列和手写环形缓冲怎么选？——要阻塞唤醒、多任务分发用队列；要零拷贝、固定时延、ISR 高频小数据用手写缓冲

## 易错点

- 只答「加 volatile」——volatile 不解决读改写原子、半帧和乱序，是最常见的答错姿势
- 在中断里用互斥锁——中断不能睡眠，mutex 直接死机；要用关中断或 FromISR 专用 API
- 忘了提交顺序——先置标志后写数据，读侧就会拿到旧数据配新标志，这种 bug 复现率极低、极难查
