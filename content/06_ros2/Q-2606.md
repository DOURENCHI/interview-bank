## 题目

**背景**：项目从 ROS1 Melodic 迁到 ROS2 Humble，代码结构变化不小。

**问**：ROS2 相对 ROS1 的核心变化有哪些？哪些是「换了实现」，哪些是「换了设计思想」？

## 口述答案

> 最大的变化是**去掉了 Master**。ROS1 靠 `roscore` 集中注册，ROS2 改用 DDS 做分布式发现，节点起来自己就能找到对方。
> 其次是 **QoS**：ROS1 只有 TCP / UDP 两档粗粒度选择，ROS2 可以逐话题指定可靠性、持久性、队列深度，这才让实时感知这类场景变得可控。
> 另外还有生命周期节点、多平台支持、Python 3、ament 与 colcon 构建体系。

## 讲深一层

| 维度 | ROS1 | ROS2 |
|---|---|---|
| 通信中间件 | 自研 TCPROS / UDPROS | DDS（Fast DDS / Cyclone DDS 等） |
| 发现机制 | roscore 集中注册 | 分布式发现（多播 / 单播） |
| QoS | 基本没有 | Reliability / Durability / History / Deadline / Liveliness |
| 节点状态 | 无标准 | Lifecycle Node（未配置→未激活→激活→销毁） |
| 构建 | catkin | ament + colcon |
| 平台 | 主要 Linux | Linux / Windows / macOS / RTOS |
| 实时性 | 弱 | 可配实时执行器、内存池 |

能体现理解深度的一点：去掉 Master 不是纯好处。集中式注册简单可控，分布式发现会带来新问题——跨网段依赖多播，要配 `ROS_STATIC_PEERS` 或 discovery server；`ROS_DOMAIN_ID` 配错就「互相看不见」。这是 ROS2 现场调试的高频故障。

## 高频追问

1. **QoS 不匹配会怎样？** —— 发布者 `BEST_EFFORT`、订阅者要求 `RELIABLE` 时**连不上**，而且不报错，只是收不到数据。这是 ROS2 最坑的问题之一。
2. **生命周期节点解决什么？** —— 让节点有明确状态机，启动顺序可控、故障可恢复，适合量产系统。
3. **DDS 选型有区别吗？** —— 有。Fast DDS 与 Cyclone DDS 在发现行为、内存占用、大消息传输上表现不同，换实现前要实测。

## 易错点

- 只说「ROS2 更快更好」，说不出机制差异
- 忽略 QoS 兼容性这个实际问题
- 把 colcon 和 catkin 当成只是换了条命令
