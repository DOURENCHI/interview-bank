## 题目

**背景**：Agent 工程的安全追问，前面聊到工具调用，面试官抛出权限边界问题：模型能调的工具里有敏感数据接口。

**问**：Tool 能访问敏感数据，但当前用户没有权限，怎么防止越权？

## 口述答案

> 第一原则是权限判定不能交给模型。模型只决定调哪个工具、填什么业务参数，能不能调由服务端执行层裁决。具体三道关。一，身份透传：用户身份从会话上下文带到执行侧，工具不接受模型自报的 userId，否则一句 prompt injection 就能让它冒充别人。二，逐次鉴权：每次调用按"用户—资源—操作"三元组校验，比如查订单必须验证 `order.user_id` 等于当前用户，而不是只校验"他有查询权限"。三，参数收敛：工具签名里不暴露"任意 userId"这种能力，改由服务端从会话注入，模型只能填日期、关键字这类无害参数。再加全量审计日志，越权尝试可追溯。

## 讲深一层

| 防线 | 做法 | 挡住的攻击 |
|---|---|---|
| 身份 | 会话 token 透传，服务端注入 | 模型自报身份 |
| 授权 | 每次调用做对象级鉴权 | 水平越权（查他人订单） |
| 参数 | 白名单 schema，禁自由文本拼接 | 注入、路径穿越 |
| 审计 | 记录 session/tool/args/result | 事后追溯 |

成熟做法是 OAuth 的 on-behalf-of：用用户自己的 token 换下游 token，权限天然收敛到该用户，而不是用服务账号。

## 高频追问

1. **模型被诱导调用越权工具怎么办？** —— 执行层拒绝并返回结构化错误给模型，让它改走澄清路径；同时这条要进告警，说明 prompt 有注入风险
2. **工具很多时怎么减少配置负担？** —— 按角色做工具白名单，再叠加对象级校验；白名单决定"能不能碰"，对象校验决定"能碰哪一条"
3. **怎么做回归测试？** —— 建越权用例集：用 A 用户 token 调 B 的资源，断言必须 403，每次改工具都跑一遍

## 易错点

- 让模型自己判断"这个用户有没有权限"——提示词可以被绕过，权限必须在确定性代码里
- 只做接口级鉴权不做数据级——有查询权限不等于能查任意人的数据，水平越权才是高发漏洞
- 把 userId 作为工具参数暴露给模型——模型可以填任何值，等于把越权入口写进 schema
