## 题目

**背景**：Agent 会话存储的设计题，面试官问的是选型依据，而不是"Redis 快所以用 Redis"。

**问**：多轮对话的上下文怎么存，存 Redis 还是存数据库？

## 口述答案

> 分两层存，不是二选一。热数据放 Redis：最近若干轮原文、当前任务状态、会话锁，特点是读写频繁、要求低延迟、允许丢（丢了能从库重建），设 TTL 比如半小时到几小时。冷数据落库：完整对话记录、结构化任务状态、用户偏好，特点是需要持久化、可审计、可回溯，用于跨会话记忆和问题排查。写入上先写库再写缓存，或异步双写；读时缓存 miss 就从库回填。上下文拼装按预算取：system prompt 加结构化状态加最近几轮加检索到的历史摘要，而不是把全部历史塞进去。Redis 只做加速，不能当唯一存储。

## 讲深一层

| 维度 | Redis | 数据库 |
|---|---|---|
| 延迟 | 亚毫秒 | 毫秒级 |
| 容量 | 受内存限制 | 大 |
| 持久性 | 可丢（看持久化配置） | 强 |
| 查询 | 只能按 key | 可检索、可统计 |

key 设计：`sess:{id}:msgs` 用 List（`LPUSH` + `LRANGE`）或 Stream；`sess:{id}:state` 用 Hash 存结构化槽位，字段级更新。

## 高频追问

1. **Redis 挂了会话会丢吗？** —— 热数据丢了不影响正确性，从库重建即可；关键是结构化状态必须以库为准
2. **历史很长怎么办？** —— 库里存全量，Redis 只留最近 N 轮，更早的做成摘要存库，需要时按需召回
3. **多实例并发写同一会话怎么办？** —— 用会话级锁或按 session id 做一致性哈希路由到固定实例，避免交错覆盖

## 易错点

- 只存 Redis——重启或淘汰就丢上下文，用户会感觉"AI 失忆"
- 只存库——每轮都查库，延迟高且库压力大
- 把结构化状态和对话原文混在一个 blob 里——状态要频繁读写和校验，混存会导致并发覆盖
