## 题目

**背景**：多 Agent 架构里子 Agent 会返回"已完成"之类的结论，面试官追问怎么验证。

**问**：子 Agent 返回的结论，你怎么判断它是对的？

## 口述答案

> 不能只看它说完成了。三层校验：1. 结构校验，返回要符合 schema，关键字段非空、枚举合法。2. 事实验证，结论要带可核对证据，比如工具原始返回、文档 ID 加行号，编排层抽检证据是否支持结论。3. 状态回读，有副作用的操作直接查真实系统状态，不信返回值。LLM-as-judge 只能兜底，不能当唯一依据，它自己也会被骗。

## 讲深一层

| 校验 | 成本 | 能发现 |
|---|---|---|
| schema 校验 | 极低 | 格式错、字段缺失 |
| 证据一致性 | 低 | 编造引用、结论越界 |
| 状态回读 | 一次 IO | 实际未生效 |
| LLM judge | 高 | 语义偏差 |

证据格式建议：`{"claim": "...", "evidence": [{"tool": "...", "raw_id": "..."}]}`，无证据的 claim 直接降级为"未确认"。

## 高频追问

1. **子 Agent 编造了一个看起来合理的订单号？** —— 回读校验，查不到就判失败；所有 ID 必须来自工具返回而非模型生成。
2. **judge 和回读冲突听谁的？** —— 回读优先，它是一手事实；judge 只用于无法回读的主观判断。
3. **怎么衡量这套校验的收益？** —— 统计拦截率和误拦率，以及拦截后人工复核的准确率。

## 易错点

- 用"子 Agent 又说了一遍"当作验证
- 只校验格式不校验事实，格式全对内容全错
- 把 judge 当权威，没意识到它和被测模型同源偏差
