## 题目

**背景**：工具设计聊完后，面试官问到一个较新的概念，看你能不能把它和已有的工具、流程区分开。

**问**：那 Agent Skills 解决的又是什么问题？它和刚才的工具、执行流程怎么配合？

## 口述答案

> 我理解工具和 Skill 是两个层次。工具是"能做什么动作"，是原子的 API，比如查忙闲、建日程；Skill 是"这类任务该怎么做"，是一段可复用的流程知识，可能包含说明文档、脚本和模板。它解决三个问题：领域知识不该全塞进 system prompt，否则上下文膨胀；同一套流程不该每次让模型重新摸索；流程要能被人维护和版本化。配合方式是渐进披露：系统先只给模型 Skill 的名字和一句话描述，判断相关才加载正文，正文里写清什么时候用哪个工具、参数怎么填、失败怎么处理，然后由 runtime 按 Skill 的指令去编排工具调用。

## 讲深一层

| 层次 | 内容 | 加载时机 |
| --- | --- | --- |
| 工具 | 单个 API + JSON schema | 常驻，随请求下发 |
| Skill | 流程说明 + 脚本 + 资源 | 命中描述后才加载正文 |
| 工作流 | 固定编排的执行图 | 编译期确定 |

渐进披露是关键：Skill 数量到几十个时，全部正文进上下文会挤掉真正的内容，只给元数据才能规模化。

## 高频追问

1. **Skill 和 MCP 什么关系** —— MCP 解决工具怎么被发现和调用（协议层），Skill 解决流程知识怎么组织（内容层），可以叠加
2. **Skill 会不会让行为不可控** —— 正文是提示而非强制，关键约束还是要落到工具侧的权限和校验
3. **怎么维护多个 Skill** —— 版本化 + 描述写清适用边界，避免两个 Skill 覆盖同一场景时模型选错

## 易错点

- 把 Skill 说成"就是工具" —— 工具是动作，Skill 是流程知识，混为一谈说明没理解分层
- 认为 Skill 能替代权限控制 —— 它只是提示，安全边界必须在执行侧
- 忽略加载成本 —— 全部 Skill 常驻上下文，和把所有文档塞进 prompt 没区别
