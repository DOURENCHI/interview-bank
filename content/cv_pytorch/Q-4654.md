## 题目

**背景**：上一问聊完 Agent 架构，面试官转向评测：功能正确性之外，还有哪些维度决定这套东西能不能上线。

**问**：Agent 评测除功能正确性外，非功能层面有哪些指标？

## 口述答案

> 我分四组看。一是延迟：TTFT、单步工具耗时、端到端 P50 和 P95，Agent 是多步串行，尾延迟比均值更影响体验。二是成本：单任务 token 数、工具调用次数、折算金额，还要单独看"失败任务花了多少钱"。三是稳定性：同一输入重复跑 k 次的通过率，也就是 pass^k，以及超时率和重试率。四是安全性：越权调用率、prompt injection 成功率、敏感信息泄漏。最后加一个运营指标，人工接管率和用户放弃率，它最贴近真实可用性。功能正确只说明"能做对一次"，这几项才说明"能不能天天跑"。

## 讲深一层

| 指标 | 采集方式 | 判读方式 |
| --- | --- | --- |
| pass@1 vs pass^8 | 同测试集重复采样 | 两者差距大说明方差高、不可靠 |
| P95 端到端 | trace 聚合 | 交互式场景通常要求 10s 内 |
| 单任务成本 | 累计 token×单价 + 工具费 | 要和人工完成成本对比才有意义 |
| 越权率 | 红队用例集 | 高危写操作要求为 0，不设容忍 |

## 高频追问

1. **pass^k 和 pass@k 区别** —— pass@k 是 k 次里对一次，pass^k 是 k 次全对；用户只用一次，所以 Agent 更该看后者
2. **成本怎么归因到单任务** —— trace 里累计每次模型调用的 token，按各自模型单价加权，工具调用单独计费
3. **线上怎么持续评** —— 抽样 + LLM judge + 人工校准；judge 与人工一致率低于 80% 就不能单独作数

## 易错点

- 只答准确率 —— 题目明说"非功能"，答准确率等于没答
- 把 P50 当延迟指标 —— 多步 Agent 的投诉几乎都来自尾延迟
- 忽略失败成本 —— 一个跑飞的任务可能烧掉几十次调用，这笔钱不进账
