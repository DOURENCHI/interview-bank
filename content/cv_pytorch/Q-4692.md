## 题目

**背景**：字节 AI Agent 开发一面的缓存并发题，是缓存击穿的并发版追问。考官要看你能不能把「同 key 合并、跨 key 并行」这两件事同时讲清楚——只答「加锁」会被当场否掉。
**问**：再回到缓存未命中：十个请求同时计算同一份素材，怎样只让其中一个负责计算，又不把不同素材都串行化？

## 口述答案

> 这是缓存击穿的并发形态：同一 key 的请求同时回源。标准解法是单飞 singleflight——以素材 key 为粒度做请求合并：第一个到达的请求负责加载，其余同 key 请求挂起等待同一个结果，加载完成后一起唤醒，十个请求共享一次回源。
> 单进程实现很轻：一个 dict，key 映射到一个占位对象（Event 加结果位加异常位）。第一个请求查 dict 没有就放入未置位的 Event，去执行加载；加载完成写结果、置位 Event、从 dict 摘掉占位；后续请求发现占位就 wait 这个 Event 再读结果。占位用完立刻摘除，dict 的规模天然等于并发中的 key 数，不会膨胀。
> 「不串行化其他素材」的关键在锁的粒度：保护 dict 本身的只是一把微秒级的短临界区锁，真正的计算在锁外按 key 各自并行——不同素材各有各的 Event，互不阻塞。这和「全局大锁包住整个加载」的区别，就是这道题要考的分界线。
> 生产细节有四个，都是事故换来的：一是失败传播——加载方抛异常时必须在 finally 里置位 Event 并把异常传给所有等待方，否则 waiter 永久挂起、线程泄漏；二是等待必须带超时，超时后各自降级；三是微小窗口下仍可能有极少重复加载（占位建立与请求到达的竞态），成本敏感的热点 key 再加一层分布式锁；四是多实例部署时单机合并只能到每实例一次，要严格全局一次就上 Redis 分布式锁加结果写回，但一般场景接受每实例各算一次，复杂度换收益要算账。

## 讲深一层

- Python 标准库没有 singleflight，参照 Go 的 x/sync/singleflight；手写核心结构就是 {key: Event + result + error}，别引入重框架。
- 失败传播是最高发的生产事故点：加载方异常没传给 waiter，wait 的线程集体泄漏——用 Future 把异常原样传给所有等待方，或 finally 置位兜底。
- 惊群余量：占位写入与第一个请求执行之间有竞态窗口，极端情况重复 2-3 次加载；严格去重才需要分布式锁（SETNX 加过期加续期）。
- 和缓存击穿另外两件套的关系：singleflight 解决「过期瞬间的并发回源」，逻辑过期解决「不真删缓存」，后台刷新解决「提前续命」——三者常组合使用。

## 高频追问

1. 负责计算的请求挂了或超时怎么办？——加载方 finally 置位并传异常，waiter 带超时等待，收到异常各自降级（重试、回源或返回旧值）
2. 合并后 dict 会不会无限膨胀？——不会：占位在加载完成即摘除，规模等于并发中的 key 数，天然有界
3. 多进程部署怎么办？——每进程各合并一次，N 个进程最多 N 次回源，一般够用；要全局严格一次就上分布式锁或消息队列按 key 路由到同一消费者

## 易错点

- 张口就「加个锁」——全局锁把不同素材也串行化了，正是题目明确要排除的做法
- 只答单机方案——多实例边界不提，面试官必追问分布式场景
- 占位不清理或异常不传播——前者内存泄漏，后者挂死一批线程，都是真实事故
