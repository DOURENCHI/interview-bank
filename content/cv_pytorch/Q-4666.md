## 题目

**背景**：面试官转向提示词工程，问你在"根据笔记出题"这个任务里提示词是怎么组织的。

**问**：你这个助手会根据笔记出题。提示词一般包含哪些内容？什么时候会加 few-shot 示例？

## 口述答案

> 我一般分五块：角色和目标，说明你是出题助手、题目要考什么；输入数据，也就是笔记正文，通常用分隔符或标签包起来，避免和指令混淆；任务指令，出几道、什么题型、难度分布、覆盖哪些知识点；输出约束，用 JSON schema 固定字段，明确不许编造笔记之外的内容；边界处理，笔记信息不足时怎么办，是少出题还是标注不确定。few-shot 在这几种情况下加：输出结构复杂、光靠 schema 描述模型还是会跑偏；任务边界模糊，比如什么算"好题"说不清；或者 zero-shot 在某一类笔记上稳定失败。但示例占 token 也会带偏风格，一般 1 到 3 个就够。

## 讲深一层

| 该加 few-shot | 不该加 |
| --- | --- |
| 输出格式复杂、字段多 | 格式简单，schema 已能约束 |
| 判定标准模糊（好题/坏题） | 标准可写成明确规则 |
| 某类输入稳定失败 | 失败原因是检索没给到资料 |

经验：加了示例后如果模型开始照抄示例里的答案或题材，说明示例带偏了，要么换更中性的例子，要么减到 1 个。

## 高频追问

1. **示例放前面还是后面** —— 通常放指令之后、真实输入之前；长上下文里靠近输入的位置影响更大
2. **怎么防止模型抄示例** —— 示例用不同题材、不同结构，且不要给完整答案
3. **怎么迭代提示词** —— 建失败样本集，每次改动跑回归，看的是失败类型分布而不是单条效果

## 易错点

- 只答"写清楚要求" —— 没提输出 schema 和边界处理，等于没说工程细节
- 无脑堆 few-shot —— token 成本上升，还会让模型过度模仿示例
- 把笔记和指令混在一起 —— 笔记里的内容可能被当成指令，是注入的入口
