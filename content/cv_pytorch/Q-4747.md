## 题目

**背景**：业务方给了一堆规则，面试官问你怎么把它们落到系统里。

**问**：业务规则怎么融进模型？写进 prompt 还是写进 reward？

## 口述答案

> 按规则性质分三层，而不是二选一。
> · 能用文字说清、需要快速改、要求可解释的 → system prompt 加输出校验；
> · 少量明确示例、希望模型稳定照做 → 进 SFT 数据；
> · 涉及"多个合理答案里偏好哪个"、规则多且要影响生成分布 → 进 reward。
> 硬约束（必须 JSON、不得出现某类词）不要靠 reward，靠受限解码或后置校验，reward 只能提高概率、不能保证。一句话：prompt 管"知不知道"，SFT 管"会不会做"，reward 管"愿不愿意选它"。

## 讲深一层

| 方式 | 生效速度 | 稳定性 | 单条成本 | 适合 |
|---|---|---|---|---|
| prompt | 分钟级 | 中（会被忽略） | 低 | 软约束、话术 |
| SFT | 天级 | 高 | 中 | 固定行为模式 |
| reward | 周级 | 中（易 hacking） | 高 | 偏好排序 |
| 后置校验 | 分钟级 | 最高 | 低 | 硬约束 |

## 高频追问

1. **prompt 里规则太多会怎样？** —— 互相稀释、模型只记住前几条，且 token 成本上升，应压缩成优先级或转成校验。
2. **同一规则能不能既写 prompt 又写 reward？** —— 可以，prompt 保证下限、reward 提升上限，但要注意别双重放大。
3. **规则冲突怎么处理？** —— 显式定义优先级，冲突时以硬约束为准，并把冲突样本收集起来做评测。

## 易错点

- 所有规则一股脑塞进 reward，训完模型行为僵化。
- 只写 prompt 就认为硬约束能 100% 遵守。
- 规则改了不同步评测集，回归时发现不了退化。
