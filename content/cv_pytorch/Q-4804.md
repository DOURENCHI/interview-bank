## 题目

**背景**：面试官问流式输出到底优化了什么，让你区分首字延迟和总耗时。

**问**：项目需要等待模型生成内容，流式输出能解决什么问题？首字延迟和总耗时该怎么区分？

## 口述答案

> 流式解决的是"感知等待"，不是总时长。首 token 一到用户就能开始读，还能中途打断，体验提升明显；总生成时间基本不变，甚至因为分块传输略增。
> TTFT：请求发出到第一个 token 到达，受排队、prefill、网络影响；总耗时 = TTFT + 输出 token 数 / 输出速度。
> 优化方向不同：TTFT 靠缩短 prompt、prefix cache、调度策略；总耗时靠提高 decode 速度、减少输出长度、投机解码。指标要分开报 P50 和 P95。

## 讲深一层

| 指标 | 定义 | 主要影响因素 | 优化手段 |
|---|---|---|---|
| TTFT | 请求→首 token | 排队、prefill、网络 | prefix cache、减 prompt |
| TPOT | 相邻 token 间隔 | decode 速度、batch | 更大 batch、投机解码 |
| 总耗时 | 请求→最后 token | TTFT + N×TPOT | 减输出、并发调度 |

只优化 TTFT 会出现"很快开始、很久才结束"，用户照样等到烦。

## 高频追问

1. **流式会不会增加成本？** —— 不会显著增加，但连接占用更久，并发连接数要按长连接估。
2. **怎么测 TTFT？** —— 在服务端和客户端各埋一个点，区分网络与服务耗时，别只测一端。
3. **输出很长怎么优化？** —— 先控制长度（结构化输出、限制 max_tokens），再谈加速，长度是线性因子。

## 易错点

- 认为流式能降低总耗时，实际只改变了感知。
- 只报平均 TTFT，P95 才是用户抱怨的部分。
- 用流式却不支持中断，用户取消后仍在计费。
