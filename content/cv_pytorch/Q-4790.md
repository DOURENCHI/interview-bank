## 题目

**背景**：团队换了更强的基座模型，面试官问你原来那些提示和编排还要不要。

**问**：如果换了更强的新模型，你怎么判断可以删掉一些提示和编排步骤？

## 口述答案

> 做消融，不要凭感觉删。
> 以当前 pipeline 为 baseline，逐条移除 prompt 片段或编排步骤，在固定 eval set 上比较；先看新模型是否原生覆盖了这些能力（JSON、工具调用、长上下文），再看移除后指标是否在置信区间内不降、失败模式是否可接受。
> 关键区分：平均不降但长尾变差 → 保留；平均降 → 不删。编排步骤很多时候是兜底和可观测点，删了省成本但失去控制。
> 最后用 A/B 在线上验证，而不是只信离线。

## 讲深一层

| 步骤类型 | 删的风险 | 建议 |
|---|---|---|
| 格式约束 | 结构化输出合法率降 | 先换成原生 JSON mode 再删 |
| 分步拆解 | 复杂任务准确率降 | 保留，或只在难任务触发 |
| 重试/校验 | 长尾失败率升 | 保留 |
| 冗余 few-shot | 通常可删 | 优先删 |

## 高频追问

1. **怎么判断是模型变强而不是评测集太简单？** —— 加一批旧模型失败的难例，看新模型是否真的补上。
2. **一次能删多少？** —— 一次一个变量，批量删了出问题无法归因。
3. **删完成本降了但稳定性差了怎么办？** —— 把关键步骤改成条件触发，简单请求走短链路，复杂请求走完整链路。

## 易错点

- 只看平均分，忽略长尾和失败模式的恶化。
- 一次性删掉所有编排，出问题找不到是哪一步。
- 新模型原生支持 JSON 就直接删校验，边界输入照样会破坏格式。
