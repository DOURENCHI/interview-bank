## 题目

**背景**：面试官在聊多 Agent 架构时，追问把编排逻辑从代码里抽出来、单独做成一个 Agent 的代价。

**问**：把编排层单独做成一个 Agent（而不是用代码写死流程），要付出哪些代价？

## 口述答案

> 三方面代价。1. 确定性下降：同样输入可能走不同分支，回归只能靠评测集，写不了单测。2. 延迟和成本翻倍：每一步编排决策都要一次 LLM 调用，多轮 planning 的 token 会叠加。3. 故障定位变难：错误可能出在编排决策、子 Agent 执行或上下文传递，链路一长很难归因。收益是能处理开放式任务、动态选工具。所以常见边界是流程固定用代码，分支不确定才交给模型。

## 讲深一层

| 维度 | 代码编排（workflow） | Agent 编排 |
|---|---|---|
| 单步延迟 | 微秒级 | 0.5–3 s |
| 可复现 | 完全可复现 | 同输入不同轨迹 |
| 长尾覆盖 | 需枚举分支 | 可现场决策 |
| 单测 | 可 mock 断言 | 只能评测集回归 |
| 成本 | 0 | 每步 1–3k token |

经验阈值：分支数 <10 且路径稳定时，Agent 编排的收益基本为负。

## 高频追问

1. **那什么任务值得用 Agent 编排？** —— 步骤数不定、需要根据中间结果决定下一步、工具集经常变；反之固定 SOP 用代码。
2. **怎么降低它的不确定性？** —— 限制可选动作集、给 few-shot 轨迹、temperature 设 0、对关键分支加断言校验。
3. **成本和延迟怎么控？** —— 编排用小模型、子任务并行、缓存重复决策、给总步数上限（如 10 步强制收敛）。

## 易错点

- 只说"灵活"不说代价，像在背优点
- 把"多 Agent"等同于"架构先进"，不讨论是否单 Agent + 工具就够
- 忽略可观测性：没有轨迹日志就无法归因
