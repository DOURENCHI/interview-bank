## 题目

**背景**：vivo Agent 开发一面，跳出日历场景的协议层概念题。structured output 和 function calling 是 Agent 开发里最容易混谈的两个机制——都能让模型输出 JSON、都叫「结构化」，但一个产出数据、一个发起动作。考的是能否讲清「格式合规」和「任务执行」的语义分界。
**问**：模型返回一个符合 Schema 的对象，和发出一次工具调用，有什么区别？两者都能表示成功吗？

## 口述答案

> 本质区别在执行语义。模型返回一个符合 Schema 的对象，是「数据」：它声明「这些内容符合这个格式」——比如一个结构化的会议摘要、一段按字段填好的分析结果。它描述事实或内容，本身不要求系统做任何事。而发出一次工具调用是「动作请求」：它声明「请帮我执行某个函数」，带工具名和参数，框架收到后要真的去调用那个函数、拿到结果、再把结果回填给模型继续推理。前者是「说得对」，后者是「请求做」，一个是内容的容器，一个是控制流的节点。
> 「都能表示成功吗」——不能，两者的「成功」不在一个层面上。Schema 对象合规只说明格式校验通过：字段齐、类型对，这不代表内容正确（时间可能写错、结论可能矛盾），更不代表任务执行成功——它压根没触发任何执行。工具调用的「成功」分两段：调用发起成功（模型输出了合法的调用格式），和执行成功（工具真正跑完并返回了结果，返回值里可能还带着业务失败比如「查询超时」）。所以判断「任务成功」要看的是整条链：格式对 → 工具选中 → 执行完成 → 结果符合预期，任何一层都可能独立失败，把「Schema 校验通过」当成「任务成功」是最典型的错误归因。
> 工程上的分界用法：要模型「产出内容」用结构化输出（约束解码或 JSON Schema 校验加重试）；要模型「驱动流程」用工具调用。两者常配合出现——工具的返回值本身往往就是一个符合 Schema 的结构化对象，回填给模型时格式可控。

## 讲深一层

- 实现机制不同：结构化输出可以用约束解码（在解码层屏蔽不合 Schema 的 token，从生成上保证合法，参考 Q-0883），也可以生成后校验加重试；function calling 是协议层的特殊 token/标记加参数槽，厂商 API 直接支持，框架解析后路由执行。
- 「并行工具调用」的坑：模型一次输出多个工具调用时，彼此可能依赖（第二个调用的参数要用第一个的结果），框架要支持串行回填，盲目并行会产生拿旧参数执行的错序调用。
- 评测口径随之不同：结构化输出测「格式通过率加内容正确率」两个指标；工具调用测「选择正确率、参数正确率、执行成功率」——混成一个「成功率」会掩盖失败发生在哪一层。

## 高频追问

1. Schema 对象「格式对但内容错」怎么办？——加语义校验层：字段间一致性检查、业务规则断言，不合格走重试或降级，格式校验管不住内容
2. 工具调用发起成功但执行失败，模型怎么知道？——框架把执行结果（含错误信息）作为 tool result 回填，模型基于失败信息决定重试、换方案或如实汇报
3. 什么时候用约束解码而不是校验重试？——延迟敏感、Schema 严格（枚举、固定字段）的场景用约束解码一次生成到位；Schema 宽松时校验重试实现更简单

## 易错点

- 说「都是返回 JSON，差不多」——丢掉执行语义这个本质区别，工具调用是控制流节点、会触发真实函数执行，结构化输出只是数据容器
- 答「Schema 合法就代表成功了」——格式、选择、执行、结果四层都可能独立失败，只看格式是最典型的错误归因，面试官就等在这里
- 讲不清「谁执行」——结构化输出没有执行者；工具调用由框架路由到真实函数并把结果回填，这个回填循环（模型→框架→工具→模型）讲不出来就是没用过
