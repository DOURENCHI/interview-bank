## 题目

**背景**：AI 辅助编码的实践题，面试官想听的是遇到反复失败时的工程化处理，而不是"多试几次"。

**问**：如果 vibe coding 始终得不到正确结果，你会怎么办？

## 口述答案

> 先停手，别在同一个方向上继续叠 prompt，那通常是在错误的问题空间里加速。四步。一，缩小问题：把需求拆成最小可验证的子集，先让一件事跑通，而不是一上来要完整功能。二，补信息而不是换措辞：模型答不对多半是缺上下文，把相关代码、报错原文、数据结构、约束贴全，比让它"再想想"有效。三，让它先出方案再写码：要求列出实现思路和会改哪些文件，人先审方案，方案错了写多少代码都白搭。四，自己动手：跑起来看真实报错，二分注释缩小范围。三轮还不行就说明超出它的能力边界，改成自己写核心逻辑、让它写样板代码。

## 讲深一层

| 失败模式 | 典型表现 | 对策 |
|---|---|---|
| 上下文缺失 | 反复用错 API 或字段 | 贴代码和文档 |
| 需求歧义 | 每次实现方向都不同 | 先让它复述需求 |
| 幻觉 API | 调不存在的方法 | 要求给出来源或版本 |
| 跨文件改动 | 改 A 坏 B | 限制改动范围，逐步验证 |

一个有效技巧：让它先写"验收标准"和测试用例，再写实现，把模糊需求变成可判定的目标。

## 高频追问

1. **怎么判断是模型不行还是提示不行？** —— 换个更小的子任务试，如果小子任务能对，说明是任务分解问题；如果连简单任务都错，是模型或上下文问题
2. **要不要换模型？** —— 换模型是最后手段，先排除上下文和任务粒度问题，否则换了还是同样的失败
3. **什么时候该放弃 AI 直接手写？** —— 涉及强约束的并发、内存布局、协议细节时，人工写核心部分、AI 写外围更划算

## 易错点

- 不停换措辞重试——同一上下文下模型大概率重复同样的错，信息不增量就是重复采样
- 一次让它改十几个文件——改动面越大越难定位错误，应当小步提交
- 不看它写的代码就粘贴运行——幻觉 API 和安全漏洞都藏在这里
