## 题目

**背景**：字节跳动 AI Agent 三面的架构收尾题，场景是把「长时间素材分析」（视频理解类，跑几十分钟）封装成 MCP 工具暴露给 Agent。考点是 MCP 协议的任务模型：HTTP 连接是短命的（超时、断线、负载均衡掐连接），而任务是长命的——把两者生命周期绑死，连接一断任务就「消失」，是 Agent 工程最常见的架构事故。考的是异步任务模式和 MCP 具体机制的结合。
**问**：假设把长时间素材分析暴露为 MCP 工具，怎样避免把一个 HTTP 连接的生死当成任务的生死？新版 TypeScript SDK 提供了什么支持？

## 口述答案

> 问题本质是两种生命周期的错配：HTTP 请求-响应模式下，连接断开（客户端超时、网关 100 秒空闲掐断、网络抖动）时服务端通常连带取消正在处理的请求——对毫秒级工具无感，对几十分钟的素材分析就是灾难：任务跟着连接陪葬，Agent 拿到的是错误而非结果。解法是把「任务」从「连接」里解耦出来，做成异步任务模式。
> 标准方案三段式。第一段，提交与受理：MCP 工具收到分析请求后不在当前请求里同步执行，而是立即创建一个任务记录（任务 ID、参数、状态机：pending→running→completed/failed），丢进后台执行器（进程内 worker 池或消息队列），工具调用立刻返回任务 ID 和「进行中」状态——响应秒回，连接可以随时断。第二段，查询与推送：Agent 后续用查询工具轮询任务状态（task_status 工具），或者用 MCP 的通知机制——服务端在任务完成时通过 notification 主动推送结果可用事件。第三段，取回结果：任务完成后结果落对象存储或任务记录里，Agent 按任务 ID 取回，断过的连接重连后照样能拿到。
> 新版 TypeScript SDK（2025 下半年的 spec 更新）把这个模式协议化了，提供 task 支持：工具可以声明自己是长任务，返回任务句柄（task tool result），客户端用 tasks/get、tasks/result 这类方法查询状态和获取结果，任务状态与连接状态解耦，重连后凭任务 ID 恢复上下文——也就是说以前要自己搭的「任务表 + 轮询 + 恢复」三件套，现在协议层内置了。配合 taskTTL（任务结果保留时长）管理任务生命周期，防止任务记录无限堆积。
> 除了协议层方案，还要配一层执行侧的可靠性：任务提交后写入持久化存储（数据库/队列），worker 领任务时用租约（lease）机制防止 worker 挂了任务卡死——租约到期未完成自动回收重派；结果幂等（同一任务 ID 重跑产出一致）；进度上报（任务进度写状态记录，轮询时能看到百分比）让 Agent 能向用户汇报。连接层还有个小优化：即使同步工具，也要把服务端的执行和请求上下文分离（任务丢队列后 handler 立即返回），网关超时配置只影响「等待响应」不影响「任务执行」。

## 讲深一层

- MCP 任务的语义陷阱：tasks/get 查到的是「任务执行状态」，不是「结果内容」——结果可能很大（素材分析产出结构化报告），协议设计是状态元数据走 MCP 消息、大结果走资源（resource）或外部存储引用，别把几十 MB 塞进 tool result；大文件走 URI 引用是通用设计纪律。
- 与 SSE 传输层的关系：MCP 的 streamable HTTP 传输下，服务器可以通过 GET SSE 流推送任务更新通知，客户端断线重连后用 Last-Event-ID 续传——「通知可达性」靠的是 SSE 重放机制，任务状态本身持久化，两层配合才完整。
- 取消语义是配套考点：长任务必须支持取消（用户中途放弃），MCP tasks/cancel 或自定义 cancel 工具要能触达 worker（协作式取消：worker 检查取消标志，中断推理循环释放 GPU）——只做启动不做取消的任务系统，在 Agent 高频试错的使用模式下成本会爆炸。
- 为什么不直接调大超时：把网关/客户端超时调到 60 分钟是脆弱方案——连接占用资源、移动网络必断、负载均衡器不支持；「拉长超时」治标不治本，「异步化」才是因果正确的解法，面试答超时调参不给任务解耦是方向性错误。

## 高频追问

1. Agent 怎么知道该轮询而不是等结果？——工具描述里声明异步语义（描述写明「返回任务 ID，用 task_status 查询」），或 SDK 的任务协议让客户端自动识别任务句柄；工具 schema 的自描述性是 Agent 正确使用长任务的前提
2. 任务 ID 由谁生成、怎么防伪造？——服务端生成（UUID/ULID），查询时校验归属（任务与会话/用户绑定），防止跨会话读取他人任务结果；权限校验在查询入口做，不靠 ID 不可猜测性
3. worker 崩了任务怎么办？——租约超时回收重派，配合任务表状态机（running 且租约过期 → 回收重入队）；重派后要保证幂等（分析任务天然可重跑，有副作用的任务要设计 checkpoint）

## 易错点

- 只答「把超时调大」——方向性错误，长连接占资源且不可靠，任务与连接解耦才是正解；这题就是挖「把连接生死当任务生死」的习惯思维
- 说不出 MCP SDK 的 task 支持——2025 年 spec 已把任务模式协议化（tasks/get、tasks/result、taskTTL），还在答「自己搭任务表+轮询」说明知识停在旧版；协议层能力 + 自建可靠性两层要分开讲
- 忽略取消与幂等——长任务系统没有取消机制和重跑幂等，Agent 试错成本失控；只设计「怎么跑完」不设计「怎么中断、怎么重试」是半成品答案
