## 题目

**题目**：对端发了 3 条 JSON，接收方一次 `recv` 读到了 2 条半。

**问**：TCP 粘包是怎么产生的？怎么解决？

## 口述答案

> 根因是 **TCP 是字节流，没有消息边界**：发送方多次 `send` 的数据可能被合并成一个段，也可能被拆开；接收方的 `recv` 只保证"拿到一些字节"，不保证"拿到一条消息"。
> 所以它不是"粘包 bug"，而是**应用层必须自己划边界**。三种方案：**定长**、**分隔符**、**长度前缀**（最通用）。

## 讲深一层

```c
// 长度前缀：先读 4 字节长度，再读 len 字节
uint32_t len; memcpy(&len, buf, 4); len = ntohl(len);
if (buf.size() < 4 + len) return;          // 半包，等更多
handle(buf.data() + 4, len);
```
| 方案 | 优点 | 缺点 |
|---|---|---|
| 定长 | 简单 | 浪费、不灵活 |
| 分隔符（\n） | 可读 | 内容不能含分隔符 |
| 长度前缀 | **通用** | 要处理长度字段本身的半包 |
- 必须配一个**累积缓冲区**，不能假设一次 `recv` 就是一条消息。
- UDP 没有这个问题（保留边界），但会有丢包和乱序。

## 高频追问

1. **`recv` 返回 0 是什么意思？** —— 对端正常关闭连接。
2. **长度字段本身也可能被拆开吗？** —— 会，所以要先攒够 4 字节。

## 易错点

- 在 `recv` 后直接 `json.loads` 整包
- 不做长度上限校验（恶意长度导致内存爆炸）
