## 题目

**背景**：Linux IO 栈的面试，聊到"写完数据没落盘"的线上事故，面试官要求把 page cache 和回写机制讲清楚。

**问**：page cache、脏页和后台回写大概是什么关系？

## 口述答案

> page cache 是内核拿空闲内存缓存的文件页，读命中就不访问磁盘。写操作默认先改内存里的页并标记为 dirty，这就是 write-back 的"写回之前"状态。脏页不会立刻落盘，由三股力量推动：一是周期性回写线程按 `dirty_expire_centisecs` 把超过时限的脏页刷下去；二是脏页比例超过 `dirty_background_ratio` 时后台异步刷，超过 `dirty_ratio` 时写进程被同步阻塞；三是 `fsync`、`sync` 或内存回收时的强制回写。好处是写合并、随机写变顺序写；代价是掉电会丢未回写的脏页，且脏页堆到阈值会让 write 突然卡住。所以关键数据必须显式 fsync。

## 讲深一层

| 参数（默认） | 值 | 含义 |
|---|---|---|
| `vm.dirty_background_ratio` | 10% | 触发后台异步回写 |
| `vm.dirty_ratio` | 20% | 触发写进程同步回写 |
| `vm.dirty_expire_centisecs` | 3000 | 脏页最长滞留 30s |
| `vm.dirty_writeback_centisecs` | 500 | 回写线程唤醒间隔 5s |

5.x 之后还有 per-bdev 的 wbt 限流，避免单个慢盘拖垮全局回写；`dirty_ratio` 在容器里按 cgroup 内存算，容易误判。

## 高频追问

1. **fsync 一定落盘吗？** —— 只保证到了设备，如果磁盘自身 write cache 没关，数据还在盘上内存里；要 `O_DIRECT` 或关掉盘缓存
2. **为什么大文件拷贝会把系统卡住？** —— 脏页迅速超过 `dirty_ratio`，所有写进程被同步回写阻塞，表现为整机卡顿
3. **mmap 写的页怎么回写？** —— 同样进 page cache 变脏页，靠 `msync` 或周期性回写，掉电一样会丢

## 易错点

- 认为 write 返回就落盘了——只落到 page cache，掉电就丢，这是最经典的误解
- 把 `sync` 当便宜的保险——它会刷全部脏页，可能阻塞数秒，生产上应按文件 fsync
- 忽略磁盘自身缓存——fsync 到盘不等于到介质，企业盘要确认 write cache 策略
