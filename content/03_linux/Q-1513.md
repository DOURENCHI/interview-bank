## 题目

**题目**：服务跑一天内存涨 200 MB，面试官问"你怎么查"。

**问**：内存泄漏怎么排查？valgrind 能看出什么？

## 口述答案

> 分两步：**先定位是否有泄漏**（长时间跑看 RSS 和对象数），**再定位泄漏点**（valgrind / ASan / heaptrack）。
> `valgrind --leak-check=full` 能给出**泄漏字节数 + 分配的调用栈**，直接指到代码行；缺点是程序要跑在 valgrind 下，慢 10–50 倍。

## 讲深一层

```bash
valgrind --leak-check=full --show-leak-kinds=all ./app
```
| 工具 | 优点 | 缺点 |
|---|---|---|
| valgrind memcheck | 精确到调用栈，无侵入编译 | 慢 10–50× |
| ASan（`-fsanitize=address`） | 快（2×），能查越界/UAF | 要重编译 |
| heaptrack / massif | 内存增长趋势 | 需要额外工具 |
| `mtrace` | 轻量 | 只能查 malloc/free |
- valgrind 报 `still reachable` 不一定是泄漏（可能是全局缓存），`definitely lost` 才是。
- C++ 里"泄漏"也可能是**逻辑泄漏**（容器只增不减），工具查不出来。

## 高频追问

1. **`still reachable` 要修吗？** —— 一般不用（程序退出才释放），但要确认不是无上限缓存。
2. **生产环境能跑 valgrind 吗？** —— 一般不能（太慢），用 ASan 灰度或定期快照对比。

## 易错点

- 把 `still reachable` 一律当泄漏
- 只测 1 分钟就下结论
