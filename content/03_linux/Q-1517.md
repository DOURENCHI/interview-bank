## 题目

**题目**：一个数据处理服务，是该用多进程还是多线程？

**问**：什么时候该用多进程，什么时候该用多线程？

## 口述答案

> 看三个维度：**要不要共享状态**（要 → 线程；不要 → 进程）、**能不能容忍崩溃扩散**（不能 → 进程隔离）、**是 CPU 密集还是 I/O 密集**（CPU 密集用进程绕开 GIL/利用多核；I/O 密集用线程或协程省资源）。
> 工程上常见组合：**多进程做隔离 + 每进程内多线程做并发**（Nginx、Redis 都是这个思路）。

## 讲深一层

| 场景 | 推荐 |
|---|---|
| CPU 密集计算 | 多进程 |
| 大量 I/O 等待 | 多线程 / 协程 |
| 共享大缓存 | 多线程（共享内存） |
| 需要故障隔离 | 多进程 |
| 需要频繁创建销毁 | 线程池 |
- 多进程的通信成本高（IPC/序列化），多线程的同步成本高（锁/竞争）。
- 崩溃影响：线程崩溃拖垮整个进程；进程崩溃只影响自己（配合 supervisor 重启）。

## 高频追问

1. **Python 为什么倾向多进程？** —— GIL 让多线程无法并行跑 CPU 密集任务。
2. **怎么选线程数/进程数？** —— CPU 密集≈核数；I/O 密集按并发量放大。

## 易错点

- 用多线程做 CPU 密集计算
- 用多进程共享大量状态（IPC 开销爆炸）
