## 题目

**背景**：存储格式设计的追问，面试官问"重启后怎么知道最后一条记录是写完了还是写了一半"。

**问**：怎么判断一条记录是不是完整写入的？

## 口述答案

> 三个层次配合。一，记录头带 magic、version、length 和 payload 的 CRC：读时先校验 magic，再检查 length 是否在合理范围，最后校验 CRC，任一不符就认为不完整。二，写入顺序：先写 payload 并 fsync，再写"提交标记"或更新长度字段，最后再 fsync；崩溃时没有提交标记的那条直接丢弃，这叫"提交点后置"。三，日志式恢复：记录追加到日志文件，恢复时从头扫描，遇到第一条校验失败的记录就截断到上一条末尾。注意不能假设 4 KB 原子写，扇区通常 512 B，跨扇区的记录必须靠 CRC 加提交标记兜底。

## 讲深一层

```c
struct rec { uint32_t magic, len, crc; uint8_t payload[]; };
// 写: payload -> fsync -> 写头(len/crc) -> fsync
// 读: magic ok && len <= MAX && crc ok 才算有效
```
CRC32C 比 CRC32 快且检错更强；要定位错误位置可以加每 512 B 一个 CRC，或者用带纠错的 ECC。另外 length 必须做上限校验，否则一个被篡改的长度字段会让读取直接越界。

## 高频追问

1. **CRC 够吗，要不要加长度？** —— 必须加，CRC 只保证内容没坏，长度越界会直接读越界内存
2. **为什么不能只靠文件大小？** —— 文件大小更新和内容写入不是原子的，可能出现"大小到了但内容没写"
3. **恢复时遇到坏记录怎么办？** —— 截断到上一条有效记录，并把坏区域标记，后续写入从有效末尾追加，不要试图跳过继续读

## 易错点

- 假设磁盘按 4 KB 原子写——绝大多数设备只保证 512 B 扇区原子，跨扇区仍可能撕裂
- 先写头再写 payload——头里已有长度和 CRC，payload 没写完就被判定为有效，恢复时读到垃圾
- 只用 magic 判断——magic 命中概率不低，必须配长度范围和 CRC 双重校验
