## 题目

**背景**：创建工单草稿这类写接口，用户可能重复点击或客户端重试，面试官追问幂等的落地方式。

**问**：创建工单草稿的写接口怎么保证幂等？只加一个 Redis 锁够不够？

## 口述答案

> 结论：**不够，锁只保证串行，不保证只执行一次**——第一个请求释放锁后，重试照样进来再建一条。正确做法是三层：1. 客户端生成 `request_id` 随请求带上；2. 服务端 `SET idem:{id} PROCESSING NX PX 24h` 抢占，抢不到就查状态，DONE 直接返回上次结果，PROCESSING 返回 409 让客户端轮询；3. 数据库对 `(tenant_id, request_id)` 建唯一索引兜底，冲突时回查原记录返回。Redis 挂了也不会重复。

## 讲深一层

| 层 | 作用 | 失效时 |
|---|---|---|
| Redis SETNX | 挡住绝大部分重复 | 挂掉/丢键 → 穿透 |
| DB 唯一索引 | 最终一致性兜底 | 不会失效 |
| 结果缓存 | 重试返回同一响应 | 回查 DB |

**语义细节**：相同 `request_id` + 不同 body 应返回 409（防参数被改），而不是复用旧结果；TTL 要覆盖客户端最大重试窗口，通常 24h。

## 高频追问

1. **`request_id` 由谁生成？** —— 客户端生成，服务端只校验格式；服务端生成的话重试时会变，失去意义。
2. **异步任务怎么幂等？** —— 投递消息带 `request_id`，消费端用唯一键去重（Redis Set 或 DB 表），并保证"消费 + 落库"同事务或至少一次 + 去重。
3. **更新类接口呢？** —— 用乐观锁版本号或 `If-Match` ETag，天然幂等；DELETE 本身幂等，但返回码要一致。

## 易错点

- 只用分布式锁，锁释放后重复请求照建
- 幂等键放服务端生成，重试即失效
- 唯一索引建了但捕获异常后不返回原结果，用户看到报错又重试
