## 题目

**背景**：中兴二面的调试能力题。GDB 命令人人会背几条，判断点在能不能把「段错误」串成一条完整排查链：编译选项 → core dump 配置 → bt 定位 → 符号缺失怎么办 → 没 core 的嵌入式怎么办。答不出流程只报命令名，等于没用真用过。
**问**：GDB 常用哪些命令？段错误怎么定位？

## 口述答案

> 常用命令按用途分五组。断点：break 文件：行或函数名、tbreak 一次性断点、condition 条件断点（b 42 if i==99）、watch 变量/内存被写时停下（查内存踩踏神器）、info breakpoints 管断点。运行控制：run、next 逐过程、step 逐语句进函数、finish 跑完当前函数、continue、until 跳出循环。查看：print 变量、display 自动显示、info locals/args、bt 全栈回溯、frame N 切到第 N 帧再看局部变量、x/16xw 地址 按十六进制查内存、info registers、disassemble 反汇编。修改：set var x=5 改变量继续跑验证猜想。多线程：info threads、thread N 切线程、thread apply all bt 全部线程各打一份栈。
> 段错误定位流程：第一步编译带 -g -O0 保留调试信息（release 的 -O2 会让断点错位、变量被优化掉）；第二步确认 core dump 开着：ulimit -c unlimited，/proc/sys/kernel/core_pattern 配置落盘路径；第三步崩溃后 gdb ./prog core，bt 看崩溃时的调用栈，frame 切帧查现场变量值，基本能定位到行；第四步如果 bt 全是问号（符号被 strip），用带符号的同版本二进制配 addr2line -e prog 0x地址 还原行号——所以 release 要保留一份 unstripped 副本；没有 core 就直接 gdb 跑，崩溃时 GDB 会停住，照样 bt。
> 根因层面，段错误不只有空指针：野指针（悬垂/未初始化）、数组越界踩坏栈或堆元数据、double free、栈溢出踩到 guard page 都会段错误，所以 bt 定位到的崩溃点常常不是案发现场，要配合 watch 和内存工具（ASan 编译期插桩、Valgrind 离线跑）往前追。
> 嵌入式补充：目标机没有 core dump，替代路线是 fault handler 里把 stacked PC/LR 打印出来配 .map 文件反查（Cortex-M HardFault 取 PSP 里的栈帧寄存器），或用 J-Link/Ozone 在线调试，思路和主机一致：拿到崩溃瞬间的 PC 和调用链。

## 讲深一层

- watch 是硬件断点：调试器用硬件 watchpoint 单元监视地址写入，实时性和主机 GDB 一致；查「谁改了我的全局变量」这类内存踩踏，watch 比 printf 快一个数量级。
- bt 问号的本质：二进制 strip 掉了符号表，运行地址对不上源码行——addr2line 的输入是崩溃 PC 值，喂的是带 -g 的同一次编译产物，版本不对应就还原错。
- 工具分工：内存类 bug（越界/UAF）先上 ASan，它直接报出出错行和分配释放栈，比 GDB 手动追快；GDB 的价值在逻辑类 bug 和无法复现、只能靠 core 的事后分析。

## 高频追问

1. core dump 怎么打开和配置？——ulimit -c unlimited + /proc/sys/kernel/core_pattern；容器里注意挂载落盘路径
2. release 版没符号怎么定位？——保留 unstripped 副本 + addr2line；或者 minidump 只带栈回溯
3. 嵌入式 HardFault 怎么定位？——fault handler 解析 stacked PC/LR + map 文件反查函数；总线错误看 CFSR 寄存器分类型

## 易错点

- 只报命令名不串排查流程——面试官要的是「拿到一个段错误你先做什么」
- 不知道 core dump 要 ulimit 打开——很多环境默认 core size 是 0
- 段错误只答空指针——野指针/越界/栈溢出都算，崩溃点和案发现场分离是关键意识
