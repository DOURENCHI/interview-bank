## 题目

**背景**：拼多多提前批一面后端通用排查题。接口 P99 从 200ms 涨到 5s、同时 CPU 飙升——两个信号同时出现把排查方向收窄到「CPU 在忙什么」。考的是有没有一套从现象到根因的固定动线，而不是东摸一把西摸一把。
**问**：接口平均耗时从 200ms 变成 5s，CPU 也飙升了，怎么排查？

## 口述答案

> 第一步先收窄范围，确认三件事：什么时间开始的（对齐发布记录）、影响面（全接口还是单接口、全实例还是部分实例）、期间有无变更（发版、配置、上游流量、数据量）。耗时涨 25 倍加 CPU 飙升，组合起来基本排除了「纯等待下游慢」（那 CPU 会闲着），指向「CPU 在空转或做无效功」——优先怀疑 GC 风暴、重试风暴、缓存失效引发的计算放大。
> 第二步定位 CPU 去哪了。Linux 上 top -H -p <pid> 找最热的线程号，转十六进制去线程栈里对号——Java 用 jstack 抓栈看热点线程在干什么：是 GC 线程（jstat -gcutil 看 FGC 频率和耗时，Full GC 一秒几次，CPU 就被吃光了）、是业务线程在跑正则/序列化/大循环，还是锁自旋。C++/Go 用 perf top 或 async-profiler 抓火焰图，热点函数一目了然。这一步的目的就是把「CPU 飙升」翻译成「哪个函数在烧 CPU」。
> 第三步按热点分支收口。若是 GC 风暴：查内存——大对象分配、缓存无界膨胀、内存泄漏导致的频繁 Full GC，CPU 和耗时一起涨是它的典型指纹，修复方向是限缓存、拆大对象、修泄漏。若是重试风暴：下游偶发变慢，超时设置过短触发大面积重试，请求量放大几倍把自身 CPU（序列化、连接建立、GC）压垮，恶性循环——修复是退避重试+熔断，把超时调回合理值。若是缓存击穿：热点 key 失效，瞬时大量回源+重建计算（比如大 JSON 反复解析），CPU 被计算吃满——修复是逻辑过期、互斥重建、多级缓存。若是代码热点（正则回溯、低效循环、日志量暴增）：火焰图直接指认，灰度修复验证。
> 验证闭环：修复上线后盯三个指标——P99 回落、GC 频率恢复基线、CPU 降回正常水位，再压测确认容量恢复。

## 讲深一层

- 「CPU 高+耗时高」和「CPU 低+耗时高」是两条完全不同的排查路线：前者查计算侧（GC/热点/重试放大），后者查等待侧（下游慢、锁等待、连接池耗尽）——面试先亮这个二分，条理立刻清晰。
- 重试风暴是生产事故最常见的放大器：下游抖动 30%，超时 100ms+重试 3 次，自身线程池和 CPU 被重试流量打爆，表现为「我们这边 CPU 飙升」但根因在下游——排查时要看下游 P99 和自身重试率曲线是否同步上翘。
- 工具链分层：宏观（top/监控看趋势）→ 线程（top -H/jstack 定位线程）→ 函数（perf/async-profiler 火焰图）→ 代码（对比变更 diff），每层回答「去哪了」，不跳层。

## 高频追问

1. CPU 飙升但火焰图显示都是 GC，下一步？——jmap dump 内存分析大对象直方图（MAT/JProfiler），常见根因是无界缓存、一次性加载全表、Finalize 堆积
2. 没有监控没有 trace 的裸机怎么排查？——top -H + jstack 手工对号，netstat 看连接堆积，tcpdump 抓下游延迟；强调「先有定位工具再谈排查」是监控建设的事后复盘
3. 怎么区分是自身 CPU 不足还是代码热点？——看 CPU 是否已到瓶颈水位（如 90%+）且扩容后指标恢复=容量问题；扩容无效=热点代码，加多少机器都烧

## 易错点

- 上来就说「看日志」——耗时和 CPU 双高的排查主线是「CPU 去哪了」，top -H→线程栈→火焰图这条动线答不出来，说明没真排查过线上问题
- 只答单点根因——面试官给的是开放现象，期望的是分支收口（GC/重试/缓存/热点四条线逐个排除），答死一条等于排查经验只有一次
- 忘了「确认变更」这一步——先对齐发布和数据变更再深挖，是排查的基本纪律，跳过它可能白查半小时
