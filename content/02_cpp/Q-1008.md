## 题目

**背景**：哈希表是 C++/后端两面必考，面试官在「冲突怎么处理」之后一定追问极端退化，考的是知不知道 Java HashMap 树化、HashDoS 加盐这些工程层答案。
**问**：哈希表发生哈希冲突会怎样，那如果是极端场景会退化成 O(n)，怎么优化的？

## 口述答案

> 先说冲突怎么处理，主流两条路。链地址法：每个桶挂一条链表，冲突元素往后串，C++ 的 unordered_map、Java 的 HashMap 都是这条路线，实现简单、删除方便，缺点是链表节点缓存不友好；另一条是开放寻址：冲突了按探测序列找下一个空位，线性探测、平方探测、双重哈希，数据全在数组里缓存友好，但删除要打墓碑、负载因子高了性能塌得快，Python 的 dict 用的就是探测加扰动。极端退化成 O(n) 的本质是所有键挤进同一个桶：要么哈希函数对这批键分布太差，要么更凶险的——哈希函数可预测，攻击者故意构造一堆同桶键把 O(1) 的表打成 O(n)，这就是哈希碰撞 DoS。优化分四层答：第一层，链地址转树，Java 8 的 HashMap 链表长度超过 8 且数组容量达到 64 就把链表换成红黑树，查询从 O(n) 降到 O(log n)，这是最标准的答案；第二层，加固哈希函数，键里掺每进程随机的盐（SipHash 这类 keyed hash），Rust 和 Python 的内置哈希都这么防碰撞攻击；第三层，控负载因子加动态扩容，Redis 的字典还做了渐进式 rehash，把迁移摊到每次操作里避免长停顿；第四层，开放寻址用双重哈希和扰动打散聚集。最后主动补一句加分项：C++ 的 unordered_map 链表并不树化，极端场景照样能退化，高要求场景会换 absl::flat_hash_map 这类实现或自控哈希函数。

## 讲深一层

- Java 树化阈值为什么是 8：负载因子 0.75 下链长服从泊松分布，到 8 的概率约千万分之一，正常数据几乎触发不了，触发即意味着分布异常或攻击；退化回链表阈值是 6，中间留缓冲防频繁互转。
- 扩容为什么取 2 的幂：`hash & (n-1)` 等价取模，且 rehash 时元素要么留原位要么挪「原位+旧容量」，判定只看一个 bit。
- Redis 渐进式 rehash：新旧两张表同时持有，每次增删改查顺手迁一个桶，定时任务批量兜底，把一次性 O(n) 摊平。
- SipHash 的意义：密钥进程级随机，攻击者无法离线预计算碰撞序列，是防 HashDoS 的标准解。

## 高频追问

1. 负载因子一般取多少？——链地址 0.75 左右，Java 超过就翻倍扩容；开放寻址要压到 0.5~0.7，否则探测序列急剧变长
2. unordered_map 为什么不树化？——标准只约束复杂度上界并留实现自由，树化需要元素可比较，而哈希容器只要求 Hash 和 KeyEqual，不一定有 operator<
3. 一致性哈希解决什么？——分布式缓存扩缩容：普通取模在节点数变化时几乎全部键要迁移，一致性哈希用环加虚拟节点把迁移量降到约 1/n

## 易错点

- 只答「拉链法」就停——面试官抛这题就是要听 HashMap 树化和加盐防攻击这两层
- 树化阈值说错——8 树化、6 退回链表、数组容量还要够 64，三个数是一个组合拳
- 声称哈希表查询一定 O(1)——最坏 O(n)，树化后 O(log n)，工程上要按最坏情况设计
