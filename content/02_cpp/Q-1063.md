## 题目

**背景**：腾讯云智二面的 C++ 并发题。它表面问 volatile，实际考三层：DCLP 失败的指令重排机制、volatile 到底管什么不管什么、以及 C++11 之后的正确写法。答到第三层才有区分度。
**问**：volatile 在懒汉单例里有什么用，为什么需要它？

## 口述答案

> 先把场景立起来：懒汉单例的经典写法是双检锁——先判空、加锁、再判空、创建。问题出在 instance = new Singleton() 不是原子动作，编译器（和 CPU）眼里它是三步：分配内存、在内存上构造对象、指针赋值。优化器允许把后两步重排成「先赋指针、再构造」，于是另一个线程在第一次判空时看到指针已经非空，拿去就用，拿到的是一个还没构造完的对象——未初始化字段、崩溃、数据错乱都有可能。
> volatile 在这里的作用是两个：阻止编译器把这条语句和周边内存访问重排，以及阻止把 instance 缓存在寄存器里反复读——保证每次都真实访存。这就是「为什么需要它」的正面答案。
> 但我必须马上说清 volatile 的局限，这是这题真正的考点：volatile 只约束编译器，不管 CPU 的乱序执行和缓存一致性。x86 的内存模型强（TSO），加了 volatile 碰巧能跑；ARM 这类弱内存序架构上依然可能出问题。所以 C++ 的正确做法有两个：一是 std::atomic 声明 instance，默认 seq_cst 内存序把 CPU 重排也挡住；二是干脆用 C++11 起的 Meyers 单例——函数内局部 static，标准保证其初始化线程安全（magic static，编译器生成一次性初始化守卫），手写双检锁根本不需要。结论是分层的：volatile 解决的是「防重排防缓存」的表象问题，但不是完整解；现代 C++ 直接 magic static，问题在语言层面被消灭了。

## 讲深一层

- DCLP 的坑在 C++11 前无解：volatile 不够、锁又退化成每次都锁；C++11 用 atomic 加 acquire/release 语义才算真正修好。
- magic static 的线程安全不是免费的：编译器生成 guard variable 加 __cxa_guard_acquire/release，本质还是一次锁，只是只在首次调用付出代价——知道这个实现细节是加分项。
- volatile 三件事：禁编译器重排、每次强制访存、不提供原子性——「原子性」从来不在它的职责里，混为一谈是概念错误。
- Java 的 DCLP 同样要求 instance 加 volatile（JMM 的 happens-before 规则），跨语言同因不同法，说明这是内存模型层面的通病而非语言缺陷。

## 高频追问

1. volatile 和 atomic 的区别？——volatile 只约束编译器（禁重排、强制访存），无原子性无 CPU 级内存序；atomic 提供原子操作和内存序，两层都挡；多线程标志位用 atomic 不用 volatile
2. 饿汉和懒汉怎么选？——饿汉启动即建无线程问题但可能白建，懒汉省资源但要付线程安全成本；C++11 后用 magic static 的懒汉两全
3. 第一次判空不加锁为什么「看起来没问题」？——恰恰有问题：读到非空但对象半构造，重排场景下就是拿未初始化对象；说「基本没问题」的候选人没理解半初始化

## 易错点

- 只答「防止优化」——说不出「分配、构造、赋值重排成先赋值后构造」的具体场景，等于没答到点上
- 说 volatile 保证原子性——概念错误，这是这题最常见的翻车点
- 不知道 magic static——C++11 之后手写 DCLP 本身就是代码异味，面试官会追问「那正确写法是什么」
