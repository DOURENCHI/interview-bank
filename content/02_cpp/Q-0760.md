## 题目

**题目**：两个线程都要读写同一个 `QVector`，什么时候必须加锁？

**问**：Qt 多线程共享数据，哪些情况必须加锁？`QMutex` 和 `QMutexLocker` 怎么选？

## 口述答案

> 只要**至少一个线程在写**，就必须加锁——包括"一个读一个写"和"两个都写"。多个线程同时**只读**不需要锁。
> `QMutexLocker` 是 RAII 封装：构造加锁、析构解锁，异常或提前 `return` 也能保证解锁。手写 `lock()/unlock()` 一旦漏掉就是死锁。

## 讲深一层

```cpp
class Store {
    mutable QMutex m_;
    QVector<int> data_;
public:
    void append(int x) {
        QMutexLocker lock(&m_);        // ✅ RAII
        data_.append(x);
    }
    QVector<int> snapshot() const {
        QMutexLocker lock(&m_);
        return data_;                  // 拷贝出去，锁外使用
    }
};
```

| 场景 | 需要锁 |
|---|---|
| 多线程只读 | ❌ |
| 一读一写 | ✅ |
| 多写 | ✅ |
| 跨线程传值（信号槽队列连接） | ❌（Qt 会拷贝） |
| 操作 GUI 控件 | ✅ 但更应该"只在主线程操作" |

**更好的思路：别共享**。用信号槽把数据**拷贝**到另一个线程（队列连接自动深拷贝），或者每个线程持有自己的数据，最后合并。锁是最后手段。

**`QReadWriteLock`** 适合"读多写少"：多个读可并发，写独占。但开销比 `QMutex` 大，读操作很短时反而不划算。

## 高频追问

1. **`QMutex` 递归锁是什么？** —— `QMutex::Recursive` 允许同一线程重复加锁（容易掩盖设计问题，慎用）。
2. **`QAtomicInt` 能替代锁吗？** —— 单个计数器可以；多个变量要保持一致就必须用锁。
3. **锁的粒度怎么定？** —— 保护"不变量"，而不是"整个函数"；粒度太粗会串行化。

## 易错点

- 只读也加锁（性能浪费）
- 手写 `lock/unlock`，中途 `return` 忘记解锁
- 在锁内调用可能触发信号槽的代码（死锁风险）
