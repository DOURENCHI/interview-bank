## 题目

**背景**：vivo Agent 开发一面，紧跟着日历预约场景的第一问。考的是把传统对话系统的「NLU 三件套」心智模型和 LLM 时代的 function calling 接起来：三个概念是什么关系、合并到一次模型输出之后边界在哪。判断点在于能否讲清「工具选错」并不因为意图和槽位都对了就消失——工具描述的边界模糊照样会让模型选错函数。
**问**：意图分类、槽位抽取和工具选择有什么联系？前两项都预测对了，工具还可能选错吗？

## 口述答案

> 这三个概念来自传统任务型对话系统的流水线，对应到 Agent 里其实是一件事的三个侧面。意图分类回答「用户要做哪一类事」：是想查日程、建日程还是改日程，它决定候选工具的大类。槽位抽取回答「这件事的参数是什么」：哪一天、几点、多长时间、什么标题，它决定工具调用的实参。工具选择是前面两步的落地：把「意图加槽位」映射到具体的可调用函数上。在 LLM 时代这三步被压缩成一次生成——模型直接输出工具名加参数 JSON——但底层要判断的仍然是这三件事，只是判断者从三个分类器变成了一个模型。
> 前两项都对了，工具仍然可能选错，最常见的三种情况。一是多个工具服务同一个意图：用户说「帮我约个复盘」，可以建日程、也可以发消息邀请对方、还可以创建会议——意图都是「安排时间」，选哪个取决于业务语义，模型如果只看意图就会混淆。二是工具描述的边界写得不清：search_events 和 find_free_time 功能接近，描述里没说清「查具体安排」和「查空闲时段」的分界，模型就按字面相似度选，谁描述得像就选谁。三是槽位对了但分布不同：同一个「查下周」的意图，查忙闲要传时间范围，查详情要传关键词，参数形态一变，模型可能带着旧参数落到错误的工具上。
> 所以工程上的结论是：意图和槽位的准确率不能替代工具选择的准确率，评测要分开测。提升手段主要不是换模型，而是把工具描述写清楚——每个工具说清「什么时候用我、什么时候不该用我」，必要时加 few-shot 示例，这比调 prompt 泛泛地说「仔细选择」有效得多。

## 讲深一层

- 传统流水线（NLU→DST→Policy）里意图和槽位是独立的分类/序列标注模型，错了可以分锅；LLM 合并后三步错误混在一次生成里，排障要靠把失败 case 按「意图错/参数错/工具错」三类拆开统计，否则优化没有靶子。
- 工具选择的本质是「模型对工具描述做语义检索加判断」：工具数量一多（几十个以上），靠把全部描述塞进上下文会撞噪声，工业做法是先按意图/embedding 检索缩小候选集，再让模型在少数候选里选，这其实就是两级的「意图分类」。
- 评测时可以构造「同意图不同工具」的对照集：同一句用户话术，只变一个细节（比如从「看看有空」变成「直接订上」），看模型是否切换到正确工具——这类边界样本比随机采样更能暴露工具描述的缺陷。

## 高频追问

1. 工具太多时怎么办？——先检索后选择的两级方案：向量召回 Top-K 工具描述，模型只在候选内选；或者按业务域分组，第一级先选域
2. 怎么系统性发现「经常选错的工具对」？——统计混淆矩阵：把每次调用的「预期工具/实际工具」落日志，高频错对就是描述要改写的对象
3. 槽位抽取错了怎么兜底？——参数校验层：调工具前做 schema 校验，缺必填槽位就发起澄清提问而不是硬调

## 易错点

- 把三个概念答成三个独立模型各自为政——面试官要的是「传统流水线三步、LLM 一次生成」的演进视角，只背名词不讲联系过不了
- 说「意图槽位都对了工具就一定对」——正确答案恰恰是「不一定」，关键论据是同意图多工具和工具描述模糊，答不出这两条等于没理解 function calling 的失败模式
- 把「工具选错」归因于模型能力不行——主流根因在工具描述质量，改写描述比换模型便宜且有效，这层工程意识是加分项
