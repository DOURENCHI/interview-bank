## 题目

**背景**：美团 AI Agent 一面的系统设计题。考的不是背概念，而是有没有真正想过「Agent 系统的确定性」这个工程问题：相同输入为什么可能得到不同输出，哪些不一致是允许的，哪些必须消灭，分别用什么手段。答成「温度设 0 就一致了」基本暴露没做过生产系统。
**问**：两个 QA 同时输入相同查询，Agent 给出的报告是否一致？

## 口述答案

> 先给结论：默认不保证逐字一致，而且我认为也不应该追求逐字一致——要把「一致」拆成业务真正关心的几个层次，分别对待。第一层是结论性字段一致：报告里的关键判断，比如「这笔退款申请符合规则 X、建议通过」，相同权限、相同数据版本下必须一样。做法是让模型只产出结构化中间结果，最终结论由确定性代码基于规则和数据快照算出来，模型负责理解而非裁决。第二层是证据一致：结论引用的原始证据（检索到的文档块、工具返回）在相同快照下应可复现，所以要固定检索版本、数据快照和工具版本，把它们的指纹记进报告。第三层是文字表达：同样的结论换个措辞完全允许，交付前再由模板渲染成统一格式。追求逐字一致既没必要也做不到——模型采样有随机性，温度 0 只能压采样抖动，压不住上游检索顺序、缓存时效、知识版本这些变化。
> 再说不一致的来源和对策。权限不同看到的数据不同，这不是 bug，按用户隔离；知识库更新了，新查询引用新版本，靠版本号对齐而不是禁更新；并发重复查询，用请求合并或结果缓存，缓存键要覆盖租户权限、归一化查询和策略版本，并且设时效，权限变更立即失效。如果查询涉及外部副作用，那就不是缓存问题而是幂等问题，要用业务幂等键加唯一约束去重，绝不能靠「prompt 相同就当同一次操作」——并发下先查有没有再插入仍有竞态，最终去重必须依赖数据库唯一约束这种原子机制。最后给验收口径：一致性的验收对象是结论和证据，不是措辞。我会做回归对拍——固定一组查询在两个版本上各跑一遍，diff 结论字段和证据指纹，措辞差异白名单化。这样既保住该一致的部分，又不至于为了表面一致把系统做成刚性模板。

## 讲深一层

- 三个「一致性」别混：表达一致（无所谓）、结论一致（必须）、副作用恰好一次（幂等，另一套机制）。先把这三层拆开再谈方案，比直接背缓存高一个档次。
- 缓存键设计：至少含租户/权限范围、归一化后的查询、数据版本、模型与策略版本；权限等价性必须服务端判定，不能信客户端自报的 permission 字段。
- 温度 0 的边界：只消除采样随机性，检索的并发时序、外部数据时效、工具的非确定性（如搜索接口）都还在。
- 请求合并（single-flight）：并发同 key 查询只放行一个在途请求，其余等结果，比事后缓存更省资源；注意 key 设计与权限隔离。
- 幂等键要绑定请求内容摘要：相同作用域、相同键、相同摘要才复用结果；键同摘要不同返回冲突，防止「同键不同意图」互相覆盖。

## 高频追问

1. 为什么不直接温度 0？——只压采样抖动；检索顺序、缓存时效、知识版本、工具非确定性都在，逐字一致既做不到也不该做
2. 缓存命中但权限变了怎么办？——缓存键含权限范围且设 TTL，权限变更事件主动失效；命中后仍按当前权限复核，不能信旧快照
3. 业务就是要逐字一致怎么办？——结论字段由确定性代码产出，文本由模板渲染，模型输出只进中间层；把「一致」收窄到可保证的范围

## 易错点

- 张口就是「温度设 0 就一致」——没碰过生产系统，检索和工具的时序、版本漂移全被忽略
- 把措辞一致当验收标准——为了 diff 全文相等把模型输出锁死成模板，失去 Agent 的意义
- 只谈缓存不谈副作用——有外部写操作的「相同查询」重放是幂等问题，缓存键挡不住重复扣款
