## 题目

**背景**：美团后端一面的诊断题。考的不是背「IO 密集用异步、CPU 密集加机器」，而是有没有一套从现象到结论的排查顺序：先看什么指标、用什么命令区分两种瓶颈、分别往哪个方向治。现场让你描述排查路径，说不出具体指标和工具就是背概念。
**问**：高并发分析：怎么判断是 IO 阻塞还是 CPU 高并发，分别怎么优化？

## 口述答案

> 总原则是先定量、再定位、后动手，别上来就改代码。第一步用系统级指标把两种瓶颈分开：top 看 load 和 CPU，load 高但 CPU idle 也高、iowait 列飙高，大概率是 IO 等待；CPU idle 很低、us/sy 高是真 CPU 瓶颈。vmstat 同理：b 列（阻塞在 IO 的进程数）高是 IO 问题，r 列（等 CPU 的进程数）高是 CPU 问题。第二步落到进程级：CPU 型用 top -H 看哪个线程吃 CPU，再上 perf top 或 arthas profiler 看热点在哪个方法——是死循环、正则回溯、频繁 GC 还是序列化开销；IO 型用 iostat -x 看磁盘 util 和 await，iotop 找进程，再往下分叉：慢 SQL 看慢查询日志、外部调用慢看调用方耗时分布、日志同步刷盘也是常见元凶。还有个高频混淆点：线程数暴涨加大量 WAITING，往往是下游 IO 慢把线程池占满，表象像 CPU 问题，实际是 IO——jstack 看线程在等谁就清楚了。
> 然后分别说优化。IO 阻塞型的核心思路是别让线程干等：同步阻塞调用改异步或线程池隔离；下游慢就上缓存（读）、批量加管道（写）；磁盘慢区分随机和顺序，随机读上缓存，写多异步刷盘合并写；DB 补索引、读写分离；外部 RPC 配超时加熔断防雪崩——不配安全网，一次下游抖动就把线程池耗光变成全站故障。CPU 高并发型的核心思路是少算和分摊：少算——优化热点算法、砍不必要的序列化和日志、GC 调优；分摊——水平扩容加负载均衡，单机内按业务分片并行。特别提醒：CPU 高不一定是业务计算，频繁 full GC、锁自旋都在偷 CPU，先看 GC 日志再谈业务优化。
> 最后是验证闭环：优化后用同样的指标复测——iowait、磁盘 util、线程池队列、GC 频率，压测对比 QPS 和 P99，确认瓶颈真的移走了，而不是感觉上快了。

## 讲深一层

- load 高不等于 CPU 高：load 包含 D 状态（不可中断、等 IO）的任务，iowait 是区分两者的第一分叉指标。
- 排查顺序模板：系统级（top/vmstat/iostat）→ 进程级（top -H/iotop/慢日志）→ 代码级（perf/arthas/线程 dump），每层有明确的分叉判据。
- 线程池打满加大量 WAITING 的锅通常在下游 IO：先看线程在等谁（jstack 看 socket read 或锁），别急着加线程——加线程只会把下游压得更慢。
- GC 是 CPU 型高并发的隐形大户：full GC 频繁时业务线程全被 STW 拖住，优先看 GC 日志。

## 高频追问

1. iowait 高但磁盘 util 不高？——可能是网络 IO 或锁等待被计入 wa，看 ss 连接状态和线程 dump 继续分叉
2. 不让用工具，纯代码层面怎么判断？——看耗时分布：加缓存后 P99 降是 IO 型，算法优化后降是 CPU 型；日志埋点区分耗时在调用前后哪一段
3. CPU 100% 且大量 CLOSE_WAIT？——下游不回包导致连接堆积，是 IO 型问题，查下游健康度和超时配置

## 易错点

- 张口就是「IO 密集用异步、CPU 密集加机器」——没说判据等于不会排查
- load 和 CPU 使用率混为一谈——D 状态任务也算 load，iowait 才是分叉点
- 忽略 GC——把 full GC 的 STW 当业务 CPU 瓶颈去优化算法，白干
- 只优化不验证——不复测指标，瓶颈可能只是被移到了下一跳
