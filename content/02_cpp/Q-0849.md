## 题目

**背景**：网易游戏测试岗，Agent 评测链的主问题（「Agent评测介绍一下」的展开追问）。前面聊了 Agent 系统，面试官落到评测：维度怎么定、标准怎么定。考的是有没有把评测当工程做过——能不能给出分层的维度框架和「自动判 vs 裁判评」的标准设计，而不是背几个指标名词。
**问**：怎么确定评测维度、评分标准？

## 口述答案

> 维度从系统的分层来，每一层测不同的东西，合起来才是完整画像。任务层看结果：任务完成率、最终产出质量、完成一个任务平均多少步多少 token——这是用户真正关心的。过程层看中间步骤：工具选择对不对（该查忙闲却去建日程就是错）、参数抽取对不对、有没有幻觉（编造不存在的日程）、失败后有没有陷入重复循环。安全层看边界：有没有越权执行（没被授权就发了邮件）、破坏性操作有没有护栏拦截、对提示注入的抵抗。交互层看沟通：该澄清的时候有没有澄清（含糊指令下瞎猜执行扣分）、汇报是否如实（部分失败有没有声明）。
> 维度确定之后，评分标准分两条路线走。能用程序判定的一律自动断言：文件是否真的创建了、查询返回的日期对不对、调用的工具名和预期是否一致——这类用单元测试式的 case 集，跑一遍出结果，零主观。无法程序判定的用「评分细则加裁判」：先写 rubric，把「好答案」拆成可核对的条目（如「是否声明了数据边界」「替代方案是否可行」），再用 LLM-as-judge 按条目打分，人工抽检一部分来校准裁判的偏差——裁判模型自己会漂，特别是对长答案的偏好，所以 judge 的结论要定期跟人工对齐。最后是闭环：badcase 按失败层归类（工具选错/参数错/幻觉/越权），统计每类的占比和趋势，评测报告要能直接指导「改哪一层」。

## 讲深一层

- 维度取舍跟着产品形态走：自动化流水线型 Agent（无人在环）安全层权重最高，人机协作型 Agent 交互层（澄清质量、汇报诚实度）权重高——维度权重不是普适的，要按失败成本分布定。
- 过程层评测的工程基础是 trace：每一步的工具调用、参数、返回、模型决策要结构化落盘，没有 trace 的 Agent 评测只能测结果，等于黑盒摸底，定位不了失败层。
- LLM-as-judge 的已知坑：位置偏差（对比评测里偏向某个顺序）、长度偏差（偏爱长答案）、自我偏好——缓解手段是交换顺序评两次、按 rubric 逐条评而非整体打分、定期用人工标注对齐校准。

## 高频追问

1. 「Agent评测」和传统软件测试的区别？——输出不确定：传统测试断言精确输出，Agent 要评「合理区间」，所以标准从断言变成 rubric，这是两者最本质的差异
2. 评测集怎么建？——真实使用日志抽 case 加人工构造边界 case（约束冲突、部分失败、注入攻击），线上发现的新 badcase 定期回灌评测集，防止评测集陈旧
3. 准出条件怎么定？——按层设阈值加红线项：任务完成率达标、安全层零越权（红线，一票否决）、循环失败率低于阈值，发布前全量回归

## 易错点

- 只答「准确率、召回率」——这是分类器指标，Agent 评测的核心在过程层和安全层（工具选择、越权、循环），只说结果指标等于没做过 Agent
- 评分标准只说「用 GPT 打分」——没有 rubric 和人工校准的 judge 不可信，面试官要听到「自动断言优先、judge 按 rubric 逐条评、人工抽检校准」这套组合
- 维度不分层混着说——分层（任务/过程/安全/交互）的价值是 badcase 能定位到层、指导具体修改，混说就失去了评测的工程意义
