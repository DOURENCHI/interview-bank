## 题目

**追问**：既然 Redis 快，**为什么引入 Redis 之后，业务接口响应不一定明显变快？**

## 口述答案

> 缓存不是免费的，引入后链路变成"业务 → Redis → 可能还有 DB"，几个环节会吃掉收益：
> 1. **网络往返**：内网一次 RTT 约 0.5~1ms，如果原来本地查库只要 1ms，收益很小；
> 2. **缓存未命中**：miss 后要回源 DB 再写缓存，比不缓存更慢；
> 3. **序列化开销**：大对象 JSON 序列化/反序列化可能比 SQL 还贵；
> 4. **一致性维护**：更新数据要删缓存/延迟双删，逻辑复杂化后可能引入新的慢路径；
> 5. **缓存异常放大**：穿透/击穿/雪崩时流量直接砸到 DB，反而更慢。
> 结论：**缓存对"读多写少 + 计算重/查询重"的数据才有明显收益**，接入前先量原耗时分布。

## 讲深一层

判定口诀：数据读 QPS 高、原耗时 > 5ms、容忍短暂不一致 → 值得缓存；本地毫秒级查询、强一致要求 → 收益低。

命中率监控：`keyspace_hits / (hits + misses)`，低于 90% 说明 key 设计或过期策略有问题。

## 高频追问

1. **缓存和 DB 不一致怎么办？** —— 先更新 DB 再删缓存（Cache Aside），极端场景延迟双删/订阅 binlog。
2. **为什么是删缓存不是更新缓存？** —— 避免并发写覆盖和写了不读的浪费。

## 易错点

- 回答"加了缓存一定快"——面试官就等着你补不快的条件
- 说出穿透/击穿/雪崩但解释不清区别：穿透=查不存在的数据，击穿=热点 key 过期瞬间，雪崩=大批 key 同时过期
