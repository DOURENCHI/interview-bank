## 题目

**背景**：快手软件研发二面的 MySQL 追问题，紧跟「事务隔离级别」之后。隔离级别是背的，快照读/当前读是理解 MVCC 的试金石：能不能说清普通 SELECT 和加锁读走的不是一条路径、各自在什么时机看什么版本。这题答不清，上一题的 MVCC 就是背的。
**问**：快照读和当前读有什么区别？

## 口述答案

> 一句话定义：快照读读的是 MVCC 版本链里的历史版本，不用加锁；当前读读的是最新已提交的记录本身，必须加锁。普通 SELECT 是快照读：RC 隔离级别下每条语句生成一次 ReadView，RR 下事务第一次查询生成一次后复用，所以 RR 里别的事务提交了我看不到——这正是「可重复读」的实现机制。当前读是所有带锁或修改语义的操作：SELECT FOR UPDATE（排他锁）、SELECT LOCK IN SHARE MODE（共享锁），以及 UPDATE、DELETE、INSERT——它们要修改数据，必须基于最新版本加锁，保证读到的就是马上要改的那一行，不然基于旧快照改会把别人的修改覆盖掉。
> 两者最经典的碰撞场景是幻读：RR 下快照读靠 MVCC 避免幻读，看到的永远是事务开始时的快照；但当前读挡不住——事务 A 先快照读没看到新行，接着 FOR UPDATE 或 UPDATE 走当前读，别的事务刚提交的新行突然就出现了。所以 InnoDB 在当前读时用间隙锁（Next-Key Lock 锁住记录加间隙）防止别的事务往范围内插新行，这是 RR 防幻读的第二道防线。答题时我会主动把「快照读 MVCC 防住、当前读防不住、间隙锁补防」这个三段逻辑讲全，这是考官想听的完整闭环。还有个容易被追问的细节：RR 下先快照读再 FOR UPDATE 为什么能看到新行——因为 FOR UPDATE 走当前读不走快照，ReadView 只对普通 SELECT 生效。

## 讲深一层

- 快照读不是「不加锁随便读」：它沿 undo log 版本链找对当前 ReadView 可见的最新历史版本，RC 与 RR 的差别只在 ReadView 的生成时机。
- 修改语义的操作（UPDATE/DELETE/INSERT）全部是当前读——不是只有带 FOR UPDATE 的 SELECT 才算，漏掉这条是常见盲区。
- RR 下快照读完全无锁（不阻塞别人也不被阻塞），这是高并发读的根源；当前读的加锁范围受隔离级别影响，RC 没有间隙锁。
- 幻读三段论：快照读（MVCC 防住）→ 当前读（防不住）→ 间隙锁（RR 下当前读防住）；RC 两道防线都弱化，所以 RC 下幻读更常见。

## 高频追问

1. 为什么 UPDATE 必须是当前读？——要改的必须是最新值，基于旧快照改会丢失别人的更新；修改语义一律读最新加锁
2. 想让 RR 里的普通 SELECT 也读到最新怎么办？——把它写成 FOR UPDATE 或 LOCK IN SHARE MODE 变当前读，或者提交后重开事务刷新 ReadView
3. 快照读完全不加锁，那历史版本哪来的？——undo log 版本链，更新时旧版本进 undo log，读的时候顺着 roll_pointer 找可见版本

## 易错点

- 说「快照读就是不加锁读最新数据」——读最新是当前读，快照读读的是版本链里对 ReadView 可见的版本
- 不知道 UPDATE/DELETE/INSERT 也是当前读——以为只有 FOR UPDATE 才算
- RR 防幻读只答 MVCC——当前读路径的幻读靠间隙锁，漏这半边是理解不完整
