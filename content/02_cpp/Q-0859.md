## 题目

**背景**：网易游戏测试岗。这岗位日常就是 UI 自动化，面试官从「做过什么」往下挖一层到原理：自动化工具到底怎么操控浏览器。考的是有没有拆过 Selenium/Playwright 的底层协议——答「调 API」过不了关，要答到 WebDriver 协议和 CDP 两条技术路线。
**问**：UI 自动化怎么操控浏览器的？

## 口述答案

> 主流是两条技术路线。第一条是 Selenium 的 WebDriver 协议：测试代码发给一个独立的 driver 进程（每个浏览器厂商按 W3C WebDriver 标准实现，比如 ChromeDriver、GeckoDriver），driver 通过 HTTP 收到指令后，调用浏览器暴露的原生接口（Chrome 是借 DevTools 的底层通道）去执行定位和操作。它是 W3C 标准、跨浏览器兼容最好，但链路长——代码到 driver 再到浏览器，中间多一跳，速度慢一些，能力也被协议框住。
> 第二条是 Playwright 和 Puppeteer 的路线：直接用 CDP（Chrome DevTools Protocol，就是浏览器开发者工具背后的那套调试协议）通过 WebSocket 长连接跟浏览器进程通信，不经过独立 driver。好处是快、能力强：能拦截和 mock 网络请求、开多浏览器上下文、截图录像、抓 console 和 trace。代价是绑定浏览器内核（Playwright 其实三大内核都支持，靠的也是各内核自己的调试协议），不走统一标准。
> 两条路线之上，操作层面是同一套抽象：定位元素（CSS 选择器、XPath、文本定位，现代框架推荐 role-based 的可访问性定位，更稳定更接近用户视角）、执行动作（click、fill、select）、以及等待策略——这是 UI 自动化的命门：脚本和网络渲染在赛跑，现代框架内置自动等待（元素可见可交互才执行动作），替代了老式 sleep 硬等。跟 Agent 结合的形态也顺理成章：把「导航、点击、读取页面」封装成工具给模型调用，页面内容用可访问性树转成文本喂给模型，模型决策下一步操作——这就是当前 Agent 操作浏览器（computer use 类）的基本原理。

## 讲深一层

- 测试视角的两大脆性来源：定位失效（前端改了 DOM 结构，选择器全挂——缓解是优先语义化定位：role、label、测试专属 id，而不是脆弱的层级 XPath）和等待竞态（元素还没渲染完就操作——自动等待解决大部分，但涉及动画和懒加载仍要显式条件等待）。
- Playwright 的 trace 能力是调试利器：一次运行录下每步的截图、DOM 快照、网络请求、console，失败 case 可以逐步回放——测试框架的「可观测性」越来越重要，跟 Agent 评测的 trace 思路同源。
- 游戏测试的特殊性：游戏客户端多是 Canvas/WebGL 渲染，没有 DOM 可定位，UI 自动化通常退到图像识别（模板匹配/OCR）或引擎层接口，这也是为什么游戏测开常问「浏览器自动化」作对照。

## 高频追问

1. Selenium 和 Playwright 怎么选？——老项目兼容多浏览器、团队已有 WebDriver 资产留 Selenium；新项目优先 Playwright：速度快、自动等待、trace、网络 mock，工程效率全面占优
2. 怎么处理动态加载的元素？——显式等待条件（元素出现且可交互）代替固定 sleep；Playwright 自动等待覆盖大部分场景，特殊竞态用 expect-poll 等轮询断言
3. Agent 驱动浏览器和传统脚本自动化的差别？——脚本流程是写死的，Agent 是模型看着页面状态逐步决策：灵活性高但稳定性差，所以 Agent 路线一定要配评测和护栏（操作前校验、失败回滚）

## 易错点

- 只答「调用 Selenium 的 API」——面试官问的就是 API 底下那层，答不出 WebDriver 协议和 CDP 两条路线等于没理解工具原理
- 把 Selenium 和 Playwright 的差异说成「API 好不好用」——本质差异是通信架构（独立 driver 的 HTTP vs 直连的 WebSocket），由此才衍生出速度和能力差异
- 忽略等待策略——UI 自动化一半的 flaky 问题来自等待竞态，只会 sleep 硬等是新手最明显的标志
