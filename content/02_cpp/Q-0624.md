## 题目

**背景**：vivo Agent 开发二面，日程 Agent 场景里的并发一致性题。两个执行者基于同一版本号工作，先后落盘——考的是 CAS（比较并交换）的能力边界：它能防什么、防不了什么。这题考的是并发原语的精确理解，而不是背乐观锁名词。
**问**：两个执行者都读取了版本7。一个先写入版本8，另一个随后也要更新。比较并交换能保证什么，不能保证什么？

## 口述答案

> 先摆机制：CAS 是「比较内存值是否等于期望值，相等才写入新值」的单条原子指令。放在版本号场景里：两个执行者都读到版本 7，A 先提交「7→8」成功；B 随后提交「7→8」时，内存里已经是 8，与期望的 7 不符，CAS 失败。它能保证的第一件事：丢失更新不会静默发生——B 的写入不会覆盖 A 的结果，冲突被显式暴露出来。第二件事：配合版本号（单调递增，不复用），它还能挡住 ABA 问题——如果 A 改完又被改回 7，纯值比较会误判「没人动过」，而版本号 7→8→9 永远回不到 7，B 的失败是真实的。
> 它不能保证的，同样有三层要讲清楚。第一，CAS 不保证 B 成功——失败只是「通知」，B 拿到失败后怎么办（重试、放弃、合并、报给用户）是上层逻辑的事，CAS 本身不解决冲突，只检测冲突。这在日程场景里就是：B 不能悄悄重试覆盖，应该把「版本已变」反馈给上层，让用户重新决策。第二，CAS 只保证单个变量的原子性——如果这次更新要同时改会议时间、与会人、地点三个字段，三个 CAS 拼不出一个事务，中间态可见，跨字段一致性要靠锁或真正的事务机制。第三，CAS 不防逻辑过期——版本号没变但业务事实变了（比如会议被外部系统取消），CAS 照样成功，它只看这个变量的历史，不理解业务语义。
> 所以完整答案是：CAS 保证「检查与写入不可分割」和「基于单调版本号的并发更新检测」，不保证重试策略、不保证多字段事务性、不感知业务级变化。工程对应就是数据库乐观锁的 version 列、Redis 的 WATCH/MULTI、CPU 的 CMPXCHG 指令，共性都是「乐观并发：先干，提交时验证，失败走补偿」。

## 讲深一层

- 版本号 CAS（乐观锁）和值 CAS 的区别就在 ABA：值可能循环复用（库存 7→8→7），版本号单调递增天然免疫 ABA——工程里用 version 列而不是直接比较业务值，本质就是买这份保险。
- Agent 场景的正确姿势是「失败即反馈」：B 检测到版本冲突后，重新拉取最新状态（版本 8），把差异呈现给用户或重新规划，而不是盲目重试旧意图——盲目重试等于把丢失更新换成了意图覆盖。
- 乐观并发 vs 悲观锁的选型：冲突概率低、临界区短（改草稿）用乐观；冲突率高或临界区长（支付扣减）用锁，否则 CAS 自旋在竞争下是 CPU 空转+活锁风险。

## 高频追问

1. ABA 问题具体怎么发生？——线程 1 读到 A，线程 2 把 A 改成 B 再改回 A，线程 1 的 CAS 认为没变过；值复用的场景（内存地址、库存数）会误判，版本号/戳记解决
2. CAS 自旋失败率很高怎么办？——退避（指数 backoff）、改悲观锁、或把冲突串行化（单写入者队列）；判断依据是冲突率，高冲突下乐观锁的 CPU 成本反超锁
3. 数据库里乐观锁 SQL 怎么写？——UPDATE ... SET v=v+1 WHERE id=? AND v=?，affected rows=0 即冲突，业务层重读重试

## 易错点

- 答成「CAS 保证 B 的更新不会丢」——恰恰相反，CAS 保证的是 A 的不被覆盖、B 的被显式拒绝，「不丢」依赖上层重试策略，混淆检测与解决是本题最大的坑
- 不提 ABA——版本号场景里 ABA 被天然规避，但「为什么版本号能防 ABA」（单调递增不复用）要能说出来，这是并发基本功
- 忽略单变量局限——日程改期是多字段操作，三连 CAS 拼不出事务，答不出这层等于没想过真实场景的完整性
