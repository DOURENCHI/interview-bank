## 题目

**背景**：vivo Agent 开发一面，日历场景追问链里的上下文管理题。多轮对话做到一半，面试官问两类信息该各存哪、压缩历史时什么最容易丢——考的是有没有真做过长会话 Agent，知悉「对话历史」和「任务状态」是两种生命周期、两种读写模式的数据。
**问**：对话历史和结构化任务状态各适合存什么？把旧消息压缩成一段摘要，最容易丢哪类信息？

## 口述答案

> 两类数据回答两个不同的问题。对话历史是「过程记录」：用户怎么说的、为什么改主意、语气和偏好、协商的过程，比如「用户先想约周二、后来嫌早改周四」。它的价值在于保留推理依据和语义细节，供模型理解上下文和保持语气一致。结构化任务状态是「当前事实」：草稿对象长什么样、哪些槽位已确认、哪些工具已调用返回了什么、用户的最终决定是什么。它的价值在于机器可直接读写执行——下一次工具调用需要的参数应该从状态里取，而不是从聊天记录里再猜一遍。存的时候要防一个典型错误：同一个事实既在历史里又在状态里且互相矛盾，比如用户在消息里改了时间但状态没更新——原则是状态为准、历史为证，更新状态的动作要由明确的工具调用或确认事件触发。
> 摘要压缩最容易丢的三类信息。一是精确值：具体时间「14:30-15:15」、数量「45 分钟」、编号「Q-0845」——摘要模型天然倾向模糊化成「下午约了半小时左右」，而精确值恰恰是执行参数。二是否定与例外：「周四不行」「别发邮件」——否定词在摘要里很容易被弱化掉，而约束恰恰多数是否定式的。三是指代锚点：用户说「第二个吧」「照旧」，「第二个」指历史里的哪个候选、「照旧」照的哪个旧例，摘要一旦把被指代的条目压掉，后文全部悬空。所以压缩策略要针对性处理：数值、约束、未决事项提取成结构化字段单独保留，摘要只负责叙事部分；被指代的关键候选不压缩。

## 讲深一层

- 实践中的分层结构：system prompt 放不变的业务规则；结构化状态（JSON）放当前任务事实；最近 N 轮原文保留；更早的轮次才压缩。读写频率和生命周期不同，混在一起管理是长会话失控的根源。
- 「未决事项」值得单独一个状态字段：用户提了但还没确认的点（要不要邀请同事、地点定在哪）。摘要最容易把「没谈完的事」压成「已谈完」，Agent 就再也不跟进了。
- 状态更新的一致性：推荐「状态只由工具调用和确认事件驱动更新」——用户嘴里说的改动在确认前进 pending 队列，避免历史与状态打架。

## 高频追问

1. 历史很长全保留不行吗？——成本和噪声双重问题：token 成本线性涨，且旧轮次的过时决定会干扰模型（用户早改了主意，旧话术还在上下文里），所以裁剪不是省钱手段而是正确性手段
2. 压缩由谁做？——通常是另一个模型调用做离线摘要，注意摘要这步本身也会出错，关键事实走结构化提取而不是摘要生成
3. 多轮之后用户指代「照旧」，怎么保证解析对？——被指代的对象在状态里保留稳定 id 和摘要引用，指代解析先查状态再查历史

## 易错点

- 把两类数据说成「一回事、都是上下文」——面试官要听到生命周期和读写模式的不同：历史是过程、状态是事实，混存是长会话 Agent 最常见的架构错误
- 摘要丢什么答「可能丢细节」——太空，要答出三类：精确值、否定约束、指代锚点，最好举「14:30 变下午」「周四不行被压掉」「第二个不知指谁」这种具体例子
- 只讲存不讲一致性——历史和状态会互相矛盾（用户改了消息没更新状态），主动提到「状态为准、事件驱动更新」是实战信号
