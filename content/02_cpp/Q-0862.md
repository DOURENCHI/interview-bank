## 题目

**背景**：网易游戏测试岗，Agent 项目链的架构决策题。候选人讲了自己手搓 Agent 框架，面试官立刻挑战：现成的 codex 加 skill 体系不好用吗，为什么自己写？考的是技术选型的论证能力——「自研」的理由必须落在具体差异点上，答「想自己造轮子练手」在面试语境里是减分项。
**问**：为什么不直接做成 codex+skill，而是手搓框架？

## 口述答案

> 先说清楚选择的前提：我的任务域是收敛的——固定的业务流程、明确的工具集合、可控的输入输出边界。在这个前提下，自研一个小循环框架比套用通用 Agent 产品更合适，理由有四个。
> 第一，上下文组装策略要按业务定制。通用产品内置的上下文管理是通用策略（按轮次压缩、固定窗口），而我的场景需要「结构化任务状态加裁剪后的历史」这种定制组装——状态字段要直接进上下文、关键约束不能被压缩掉，这些控制点通用产品不开放。第二，评测和护栏要埋在确定的位置。我的框架在每一步工具调用前插权限校验、调用后落结构化 trace，评测集可以逐层回放定位失败；闭源产品是个黑盒，行为不可插桩，出了 badcase 只能整体换 prompt 盲调。第三，成本和延迟可控。任务循环简单，自研几十行的 ReAct 循环加几个工具就够，用重型产品要么付费按调用量走、要么拖着一大套用不上的能力。第四，数据与合规边界：业务数据不出内网，接第三方产品要做数据安全评估，自研框架部署在自己环境里，边界清晰。
> 同时要承认反面：通用能力上 codex 这类产品更强——跨仓库改代码、开放式探索任务，它的工具生态和模型协同是成熟产品打磨过的，自己搓不可能短期达到。所以选型判断的核心就一句话：任务是域内收敛的还是开放式的？收敛域内、要评测护栏和上下文控制权，自研小框架；开放通用、追求开箱即用，用成熟产品。skill 的思路（把操作流程封装成可复用单元）两种路线都要，我的框架里同样有等价物。

## 讲深一层

- 「手搓」的实际尺度：不是从零实现模型调用，而是薄薄一层编排——模型 API 加自维护的工具注册表加 ReAct 循环加 trace，几百行量级；真正贵的是评测集和护栏，而这部分无论用不用现成产品都省不掉。
- 通用产品的隐藏成本：行为随版本漂移（产品迭代你的 prompt 可能突然失效）、调试只能靠产物文本、并发和配额受制于平台——「黑盒不可插桩」在出问题排障时是最痛的。
- 何时迁移回现成产品：任务域从收敛变开放（用户开始要求跨系统自由操作）、团队维护框架的人力不够——选型不是一锤子买卖，给面试官讲出「什么信号触发重新选型」是成熟度信号。

## 高频追问

1. 手搓框架踩过什么坑？——工具描述质量决定选择准确率（改描述比改 prompt 有效）、上下文超限要主动裁剪（结构化状态优先保留）、失败重试必须带上限和前提变化——这些都是只有真做过才答得出的细节
2. 自研框架怎么保证不比现成产品差？——拿通用产品的输出当对照组跑评测集，差距项（比如复杂任务规划）可以借助更强模型或引入现成组件补，评测驱动迭代
3. 如果面试官追问「那 skill 是什么角色」？——skill 是把成熟操作流程封装成模型可按需加载的说明书加脚本，降低重复 prompt 成本；自研框架内实现等价机制，两者不冲突

## 易错点

- 理由落在「练手/喜欢自己写」——面试语境里这是没有工程判断的信号，正确答法是列具体差异点：上下文控制权、可插桩评测、成本、数据边界
- 把 codex 一类产品贬得一无是处——通用能力上成熟产品明确更强，敢承认反面并给出分界（收敛域 vs 开放任务）反而体现判断力
- 只讲好处不讲代价——自研的真实成本是评测集建设和长期维护，主动交代这块，防止被追问「维护成本算过吗」时卡壳
