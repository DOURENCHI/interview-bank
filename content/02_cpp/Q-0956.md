## 题目

**追问**：**在 64 位系统下，程序一次性 malloc 很大一块（比如几十 GB），能够申请成功吗？**

## 口述答案

> **大概率"成功"，但成功 ≠ 能用。** malloc 只是登记了一段虚拟地址空间：
> 1. 默认 `overcommit_memory=0`（启发式）下，几十 GB 的申请只要不超过虚拟空间上限就会**返回成功**；
> 2. 真正分配物理页发生在**第一次触碰内存**时（缺页异常逐页分配）；
> 3. 如果物理内存 + swap 不够，内核 OOM killer 会**杀进程**——也就是申请成功、运行中暴毙。
> 所以"能不能申请成功"要分三层：虚拟空间够不够（64 位基本都够）→ overcommit 策略允不允许 → 运行时物理页够不够。

## 讲深一层

```bash
# 复现：申请后先看 VSZ 涨、RSS 不涨；memset 后 RSS 才涨
vm.overcommit_memory=2 时：可提交上限 = swap + RAM×ratio，malloc 直接失败返回 NULL
```

工程含义：大内存规划要按 RSS 算不是按 malloc 算；关键服务可设 `vm.overcommit_memory=2` 换取确定性失败，而不是运行期被 OOM。

## 高频追问

1. **OOM killer 挑谁杀？** —— badness 评分，主要看占 RSS 与 oom_score_adj，可以给关键进程调低分数保护。
2. **怎么提前发现要 OOM？** —— 监控 RSS/swap 与 cgroup limit，接近水位先扩容。

## 易错点

- 把"malloc 返回非 NULL"当成"内存已分配"——只是虚拟地址登记
- 不知道缺页机制，解释不了 VSZ 和 RSS 的差别
