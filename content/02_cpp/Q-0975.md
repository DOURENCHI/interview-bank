## 题目

**场景**：字节 Agent 项目面。面试官：**介绍一下你项目里的 RAG。**

## 口述答案

> 按"为什么需要 → 怎么搭的 → 效果 → 缺陷与改进"四段讲：
> **为什么**：大模型知识有截止时间、且不了解私有文档，直接问会幻觉；RAG 用"先检索、后生成"把答案锚定在真实语料上。
> **怎么搭**：文档清洗 → 分块（按标题/语义切，块间留 overlap）→ 向量化入库（embedding 模型 + 向量库）→ 查询时 query 向量化 → 相似度检索 topK → 重排 → 拼 prompt 交给模型生成，并**要求附引用出处**。
> **效果**：答不上的比例明显下降，答案可溯源。
> **缺陷与改进**：检索质量是天花板——分块不合理会切碎语义，下一步做语义分块和 rerank；对"需要多跳推理"的问题还不够，考虑加 Agentic RAG（先检索再决定是否再检索）。

## 讲深一层

```text
离线：docs → chunk → embed → vector DB
在线：query → embed → topK 检索 → rerank → prompt(上下文+问题) → LLM → 带引用的回答
```

面试官真正想听的：①分块策略和依据 ②向量库选型理由（规模小用 FAISS/内存，大用 Milvus）③怎么量化效果（命中率/人工评审）④失败案例怎么迭代。

## 高频追问

1. **检索不准怎么调？** —— 先看分块（块太大稀释语义，太小缺上下文），再上 rerank，最后换 embedding 模型。
2. **为什么不全量塞 context（长上下文）？** —— 成本、延迟、"中间迷失"效应，检索仍是性价比方案。

## 易错点

- 只讲概念不讲自己项目参数——分块大小、topK、模型名要能脱口而出
- 说不出失败案例，会被认为是"跑通了 demo"级别
