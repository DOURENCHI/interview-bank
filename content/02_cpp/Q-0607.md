## 题目

**场景**：老代码里到处是 `char buf[256]` 和 `strcpy`，改成 `std::string` 后有人担心"性能会不会变差"。

**问**：为什么现代 C++ 优先用 `std::string`？它相对 `char*` 到底多了什么、代价是什么？

## 口述答案

> 多了三样关键能力：**自动管理内存**（RAII，不会忘 `free`）、**自带长度**（`size()` 是 O(1)，不用每次 `strlen`）、**值语义**（可以拷贝、比较、拼接，行为可预测）。
> 代价是每个 `string` 对象有几个字节的额外开销（指针 + 长度 + 容量），短字符串还有 SSO（小字符串优化）的判断成本。但这些开销远小于手写 `char*` 带来的 bug 成本。

## 讲深一层

| 维度 | `char*` | `std::string` |
|---|---|---|
| 内存管理 | 手动 `malloc/free` | RAII 自动 |
| 长度 | `strlen` 每次 O(n) | `size()` O(1) |
| 越界 | 静默写坏内存 | `[]` 不检查，`at()` 抛异常 |
| 二进制安全 | `\0` 截断 | 可存 `\0` |
| 拷贝 | 浅拷贝，易双重释放 | 深拷贝，值语义 |
| 短串 | 一次堆分配 | SSO 存在栈上，无分配 |

```cpp
std::string s = "hello";
s += " world";                 // 自动扩容
s.size();                      // O(1)
s.c_str();                     // 传给 C 接口，只读
s.data();                      // C++17 起可写
```

**SSO 是什么**：多数实现把 15–22 字节以内的字符串直接存在对象内部，不申请堆内存。这就是为什么 `string` 传参时"短串不慢"，也是为什么**跨编译器传 `std::string` 会破坏 ABI**（布局不同）。

## 高频追问

1. **`c_str()` 和 `data()` 区别？** —— C++17 前 `data()` 不保证 `\0` 结尾；C++17 起两者等价。
2. **`string` 和 `string_view` 区别？** —— `string_view` 不拥有内存、不保证 `\0` 结尾，适合只读传参，避免拷贝。
3. **什么时候还该用 `char*`？** —— 与 C 库交互的边界、需要极致控制内存的嵌入式场景。

## 易错点

- 认为 `string` 一定比 `char*` 慢（短串有 SSO）
- 把 `s.c_str()` 的指针存起来，`s` 修改后失效
- 用 `string` 传二进制数据却依赖 `\0` 结尾
