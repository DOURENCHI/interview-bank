## 题目

**题目**：

```cpp
void f() {
    int local = 42;
    std::thread t([&]{ std::cout << local; });
    t.detach();
}   // f 返回，local 销毁
```

**问**：detach 之后线程访问局部变量会发生什么？怎么避免？

## 口述答案

> `local` 在 `f` 返回时销毁，分离的线程再去读它就是**访问已释放的栈内存**——未定义行为，可能打印乱值、可能崩溃，也可能"看起来正常"。
> 避免方法：**按值捕获**（拷贝进 lambda）、**用 `shared_ptr` 保活**、或者干脆不要 `detach`（用 `join`/`jthread`）。

## 讲深一层

```cpp
// ❌ 悬垂
std::thread t([&]{ std::cout << local; }); t.detach();

// ✅ 按值捕获
std::thread t([local]{ std::cout << local; }); t.detach();

// ✅ shared_ptr 保活（对象较大或需要共享时）
auto data = std::make_shared<BigData>();
std::thread t([data]{ use(*data); }); t.detach();
```

| 方案 | 适用 | 代价 |
|---|---|---|
| 按值捕获 | 小数据 | 一次拷贝 |
| `shared_ptr` | 大数据/共享 | 原子引用计数 |
| 不 detach | **首选** | 需要等待 |
| 线程池 + 任务队列 | 大量短任务 | 需要设计 |

**根本问题**：`detach` 把"线程生命周期"和"对象生命周期"解耦了，但**没有提供任何同步机制**。所以一旦涉及外部状态，就必须靠引用计数或值拷贝来保证安全。

**C++20 的替代**：`std::jthread` + `stop_token`，既能协作取消，又保证析构时线程结束。

## 高频追问

1. **`shared_ptr` 保活有什么代价？** —— 每次拷贝原子操作，且延长对象生命周期（可能延迟释放）。
2. **分离线程能访问全局变量吗？** —— 能，但要考虑程序退出时全局对象的析构顺序。
3. **怎么等分离线程结束？** —— 没有标准方法，只能用条件变量/`future` 自己同步——这也是不该 detach 的理由。

## 易错点

- `detach` + `[&]` 捕获局部变量
- 分离线程访问即将析构的全局/静态对象
- 以为 `detach` 后线程会被"托管"
