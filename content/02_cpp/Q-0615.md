## 题目

**场景**：线上程序崩溃，只有 core dump，没有 IDE、没有源码目录，甚至机器只能 SSH。

**问**：有了 IDE 的图形调试，为什么还要会命令行 GDB？

## 口述答案

> 因为**出问题的环境往往没有 IDE**：生产服务器、嵌入式板子、Docker 容器、CI 环境。GDB 是唯一到处都在的工具，而且能处理 core dump——这是 IDE 做不到的（IDE 通常只能调活进程）。
> 还有一点：GDB 可以脚本化，用命令文件批量跑断点和打印，适合复现和自动化。

## 讲深一层

```bash
# 看 core dump
gdb ./myapp core.12345
(gdb) bt                 # 调用栈
(gdb) frame 3            # 切到第 3 帧
(gdb) info locals        # 局部变量
(gdb) p *ptr             # 打印指针指向的内容
(gdb) thread apply all bt  # 所有线程的栈

# 附加到运行中的进程
gdb -p $(pgrep myapp)

# 远程调试（嵌入式）
gdbserver :1234 ./myapp
gdb ./myapp -ex "target remote 192.168.1.10:1234"
```

| 场景 | IDE | GDB |
|---|---|---|
| 本地开发 | 更方便 | 也能用 |
| 生产 / SSH | 通常没有 | ✅ |
| core dump 分析 | 支持有限 | ✅ 标准做法 |
| 嵌入式远程 | 难 | ✅ gdbserver |
| 脚本化批量 | 难 | ✅ `-ex` / `-x` |

## 高频追问

1. **core dump 怎么开？** —— `ulimit -c unlimited`，并确认 `/proc/sys/kernel/core_pattern` 指向的位置。
2. **没有调试符号怎么办？** —— 函数名和行号都没有，只能看汇编和栈回溯；所以发布版要保留符号文件（`RelWithDebInfo` 或单独 `.debug`）。
3. **`bt` 显示 `??` 是什么原因？** —— 缺符号表，或栈已损坏。

## 易错点

- 说"IDE 更方便"就否定 GDB
- 不知道 core dump 需要 `ulimit -c unlimited`
- 发布时把符号全 strip 掉，事故无法定位
