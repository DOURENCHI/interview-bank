## 题目

**现象**：`g++` 编译通过、链接也通过，一运行就报：

```
error while loading shared libraries: libonnxruntime.so.1.16: cannot open shared object file
```

或者更隐蔽：程序启动正常，调用某个函数时抛异常说符号找不到。

**问**：链接能过、运行时找不到符号，问题在哪几层？按什么顺序查？

## 口述答案

> **链接过 ≠ 运行时能找到**。链接阶段找的是"有没有这个符号"，运行时找的是"能不能加载这个 `.so` 文件"。所以分两层查：**先查库文件能不能被找到**（`LD_LIBRARY_PATH`、rpath），**再查符号是否真的存在**（版本不对、被 `strip`、`-fvisibility=hidden` 藏了）。
> 最常见的根因是**版本不匹配**：链接时用的是 1.16 的头文件，运行时加载的是 1.14 的库。

## 讲深一层

```bash
# 1. 看它需要什么、现在找到的是什么
ldd ./app | grep -i onnx
#   libonnxruntime.so.1.16 => not found     ← 找不到

# 2. 看文件系统里有哪些版本
ls -l /usr/lib/x86_64-linux-gnu/libonnxruntime.so*
readelf -d ./app | grep -E 'RPATH|RUNPATH'

# 3. 看符号到底在不在（-D 看动态符号表）
nm -D /opt/ort/lib/libonnxruntime.so | grep OrtCreateSession
c++filt _ZN3Ort...                        # 还原 C++ 修饰名

# 4. 临时指定路径
LD_LIBRARY_PATH=/opt/ort/lib ./app
```

| 层级 | 命令 | 结论 |
|---|---|---|
| 依赖 | `ldd` | `not found` = 路径问题 |
| 搜索路径 | `readelf -d` | 看 RPATH/RUNPATH |
| 符号存在性 | `nm -D` | 没有 = 版本不符或被隐藏 |
| 符号名 | `c++filt` | 区分 C++ 修饰名和 `extern "C"` |

**两种隐性问题**：
1. **`-fvisibility=hidden`**：符号存在于 `.so` 里但不导出，`nm -D` 看不到，链接时也会失败。
2. **ABI 不匹配**：库和调用方对同一个类的内存布局理解不同，符号找得到但行为错乱——这在混用不同编译器（GCC vs MSVC）时必然发生。

## 高频追问

1. **`LD_LIBRARY_PATH` 和 rpath 谁优先？** —— 一般 `LD_LIBRARY_PATH` 优先于 RUNPATH（但 DT_RPATH 更早）；生产环境更推荐写 rpath。
2. **`undefined reference` 和 `cannot open shared object` 区别？** —— 前者是链接期（找不到符号），后者是运行期（找不到文件）。
3. **为什么调试版能跑、发布版不能？** —— 可能链接了不同的库路径，或发布版 strip 掉了依赖信息。

## 易错点

- 只查 `ldd` 不查 `nm -D`，路径对了但版本不对时卡住
- 用 `LD_LIBRARY_PATH` 长期兜底，掩盖了打包问题
- 混用 GCC 和 MSVC 编译的库
