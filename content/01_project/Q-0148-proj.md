## 题目

**场景**：面试官看到项目只有 240 行，会怀疑"这算工程吗"。

**问**：工程化体现在哪？

## 口述答案

**要点**

- 工程化不看行数，看**流程是否完整**：需求拆解 → 编码 → 编译调试 → 写测试 → 文档 → 版本管理。
- 具体证据：公开仓库有 README（含用法和功能清单）、有明确的编译命令、退出码有文档、Git 有意义的提交历史。
- 反面例子：代码 2000 行但只有一个 `initial commit`、没有 README、跑不起来——那才不叫工程。

## 讲深一层

可验证的工程化清单：

| 项 | 本项目的做法 |
|---|---|
| 构建 | 一条 `g++ -std=c++17` 命令，无外部依赖 |
| 用法 | README 写清参数形式和示例 |
| 错误处理 | 退出码区分错误类型 |
| 文档 | 项目说明书含口述稿与 20 问 |
| 版本管理 | Git，提交按功能粒度 |
| 可复现 | 环境写清（Ubuntu 22.04 / g++ 11.4 / C++17） |

「可复现」这条最容易被忽略：**面试官拿到你的仓库，能不能在 10 分钟内跑起来**，这是个硬指标。

## 高频追问

1. **提交粒度怎么算合适？** —— 一个提交做一件事，message 说清"做了什么"而不是"改了代码"。
2. **为什么没写单元测试？** —— 诚实说：命令行工具靠 shell 脚本验证，没有引入测试框架。这是可以改进的点。
3. **CI 呢？** —— 没做。规模小，本地编译够了；但如果要展示工程能力，加一个 GitHub Actions 跑编译是低成本的加分项。

## 易错点

- ❌ 硬说"麻雀虽小五脏俱全" —— 空话
- ❌ 回避"没测试" —— 应承认并给出改进方向
- ✅ 用"可复现"这个标准来论证，而不是行数
