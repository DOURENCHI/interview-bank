## 题目

**场景**：同一个检测节点有两版：**v1 在图像回调里直接推理**，**v2 回调只把 `shared_ptr` 塞进单槽邮箱，由 worker 线程慢慢算**。

**实测**（fake_camera 30 fps，跑 60 秒）：

| 指标 | v1 | v2 |
|---|---|---|
| `infer_ms_p50` | ≈3 ms | ≈3 ms |
| `serve_ms_p50` | ≈5 ms | ≈5 ms |
| `fps` | ≈30 | ≈30 |
| `transport_ms_p99` | 较高 | 更低 |

**问**：加线程并没有让推理变快，那 v2 的意义是什么？这个对比该得出什么结论？

## 口述答案

> 结论是反直觉的：**v2 不降低端到端延迟，因为瓶颈在推理本身——只有一张卡，一次只能算一帧，加线程不会让它算得更快。**
> v2 真正做的是**把积压从 DDS 队列挪到自己的邮箱里**。v1 里推理期间新帧堆在 DDS 队列（depth=1，只留最新），丢帧发生在中间件里，你看不见；v2 里回调立刻返回，新帧覆盖旧帧，丢在自己邮箱里，**丢哪一帧、丢了多少、要不要记日志，全部可控**。
> 所以正确的说法不是「v2 更快」，而是「v2 用丢帧位置换来了控制权」。

## 讲深一层

```cpp
// v2：回调只做一件事——覆盖式投递，立刻返回
void onImage(const sensor_msgs::msg::Image::SharedPtr msg) {
  std::lock_guard<std::mutex> lk(m_);
  if (mailbox_) ++dropped_overrun_;      // 上一帧还没算完，记一次丢弃
  mailbox_ = msg;                        // 单槽覆盖，永远只有最新一帧
  cv_.notify_one();
}

void workerLoop() {
  while (rclcpp::ok()) {
    sensor_msgs::msg::Image::SharedPtr job;
    {
      std::unique_lock<std::mutex> lk(m_);
      cv_.wait(lk, [&] { return mailbox_ || !rclcpp::ok(); });
      job = std::move(mailbox_);
    }
    if (job) detect(*job);               // 慢活在这里，不阻塞回调
  }
}
```

为什么要**单槽**而不是队列：
- 队列会让延迟累积（越排越久），而实时感知只要最新帧；
- 单槽天然实现了「丢弃旧帧」，语义清晰；
- 丢帧计数落在自己的代码里，能上报、能告警。

| 对比项 | v1（回调内推理） | v2（worker + 单槽） |
|---|---|---|
| 端到端延迟 | 取决于推理 | 几乎相同 |
| 回调是否被阻塞 | 是 | 否 |
| 丢帧发生位置 | DDS 队列（不可见） | 应用层（可计数） |
| `transport_ms_p99` | 较高 | 更低 |
| 实现复杂度 | 低 | 需要锁 + 条件变量 |

**这个对比里最该讲的一句话**：如果 v2 的 `infer_ms` 比 v1 快，说明你测的不是同一件事——大概率是两次跑之间 GPU 降频了。只有交替跑同一时刻的数据才有可比性。

## 高频追问

1. **什么时候 v2 真能降低延迟？** —— 当瓶颈不是推理而是 I/O 或预处理时，并行化才有效；纯 GPU 推理瓶颈下，加线程只改丢帧位置。
2. **能不能多开几个 worker 提高吞吐？** —— GPU 上并发推理反而会互相抢占，通常是串行更稳；CPU 多线程 EP 才有收益。
3. **丢帧怎么上报？** —— 项目里 `dropped_overrun_` 有计数但没写进 `LatencyReport`，这是已知缺口，加上字段才能做端到端观测。

## 易错点

- 断言「加线程一定更快」，看到延迟没降就说代码有问题
- 用队列而不是单槽，延迟越跑越大
- 两次跑不在同一时刻，把 GPU 降频当成加速比
