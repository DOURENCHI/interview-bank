## 题目

**场景**：一个检测节点订阅相机话题，处理完把结果画在窗口上。现在画面能出来，但延迟大约 200 ms，而且颜色偏了。

**问**：一张图从相机到屏幕，中间经过哪几步？每一步最容易出什么问题？

## 口述答案

> 大致五步：**驱动采集 → 序列化发布 → DDS 传输 → 反序列化加 `cv_bridge` 转 `cv::Mat` → 处理并显示**。
> 延迟通常出在传输和队列（深队列积压旧帧），颜色偏多半是**编码格式没对上**：相机发的是 `bgr8`，代码按 `rgb8` 解释，红蓝就换了。`cv_bridge` 的 `encoding` 参数必须和实际一致，不能想当然。

## 讲深一层

```cpp
void onImage(const sensor_msgs::msg::Image::SharedPtr msg) {
  cv_bridge::CvImagePtr cv_ptr;
  try {
    cv_ptr = cv_bridge::toCvCopy(msg, sensor_msgs::image_encodings::BGR8);
  } catch (const cv_bridge::Exception &e) {
    RCLCPP_ERROR(node->get_logger(), "cv_bridge: %s", e.what());
    return;
  }
  cv::Mat img = cv_ptr->image;   // 注意：toCvCopy 是深拷贝
  detect(img);
}
```

| 步骤 | 常见问题 | 现象 |
|---|---|---|
| 采集 | 曝光过长、驱动掉帧 | 帧率低于设定 |
| 序列化 | 编码未指定或写错 | 颜色通道错乱 |
| 传输 | 深队列 + 可靠传输 | 延迟持续增长 |
| 转换 | `toCvShare` 与 `toCvCopy` 混用 | 悬垂指针或多余拷贝 |
| 显示 | 每帧 `imshow` + `waitKey(1)` | GUI 线程成为瓶颈 |

**`toCvShare` 和 `toCvCopy` 的区别**：前者零拷贝但返回的对象只在消息存活期间有效，一旦把 `cv::Mat` 存下来跨帧使用就会悬垂；后者安全但有拷贝开销。要"既不拷贝又安全"，得自己管理消息生命周期。

延迟排查最有效的一招：在回调里打 `node->now() - msg->header.stamp`，这就是端到端延迟；大于预期就查队列深度和 QoS。

## 高频追问

1. **为什么延迟会一直涨？** —— 队列越积越多。把订阅 QoS 改成 `BEST_EFFORT` + `depth=1`，只处理最新帧。
2. **`imshow` 能放在回调里吗？** —— 能跑但危险，GUI 事件循环和 ROS 执行器会互相卡；工程上一般单独线程或换 rviz / Web 显示。
3. **共享内存能省多少？** —— 大图传输用零拷贝（intra-process 或 loaned message）能省掉序列化和两次内存拷贝，1080p 下收益明显。

## 易错点

- `encoding` 写错导致红蓝互换，还去查模型
- 用 `toCvShare` 后把 Mat 存起来，出现随机花屏
- 深队列 + 可靠传输，延迟越跑越大
