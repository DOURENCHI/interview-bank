## 题目

**背景**：流式输出到一半网络断了，用户看到半句话，面试官问怎么处理。

**问**：网络抖动导致端上已经生成了半句就断了，你怎么保证体验和一致性？

## 口述答案

> 结论：**把"已生成到哪"变成可恢复的状态，而不是依赖连接本身**。1. 每个 SSE event 带自增 id 或字符 offset，重连时带 `Last-Event-ID`，服务端从 offset 续写或重放缓冲；2. 同一 `request_id` 保证不重复生成、不重复计费，命中缓存直接回放；3. 端上保留已渲染文本，按 offset 拼接去重；4. 超时分两层：首 token 超时和 token 间隔超时，别用总时长；5. 兜底 UI 保留半句 + 重试，重试是续写不是从头。

## 讲深一层

```http
event: delta
id: 137
data: {"text":"...","offset":137}
```
| 断点 | 处理 |
|---|---|
| 首 token 前 | 重试整个请求 |
| 生成中 | 带 offset 续写 |
| 生成完未收完 | 拉取完整结果缓存 |

服务端要按 token 缓冲输出，保留最近 N 秒的窗口，否则断线后无法续写。

## 高频追问

1. **服务端怎么支持从 offset 续写？** —— 生成时缓冲输出；超出窗口就返回已完成的完整文本，而不是续写。
2. **重试会不会产生两份不同结果？** —— 同一 request_id + 固定 seed/温度可复现；否则只能返回缓存的首份结果。
3. **弱网下要不要降级成非流式？** —— 可以，连续失败 2 次后改为一次性返回，牺牲首字体验换成功率。

## 易错点

- 断线后从头重生成，用户看到重复内容且计费翻倍
- 只设总超时，长回答被误杀
- 服务端不缓存，客户端想续也续不上
