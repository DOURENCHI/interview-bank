## 题目

**背景**：平台把训好的大模型包装成对外服务，面试官问接口怎么设计。
**问**：推理服务的对外接口应该怎么设计？要考虑哪些点？

## 口述答案

> 按"协议—语义—工程"三层说。**协议**：内部同步链路用 gRPC（低延迟、强 schema），对外 REST 更通用；LLM 类生成接口必须支持**流式输出**（SSE/WebSocket），用户要的是逐 token 吐出而不是等 30 秒一次返回。**语义**：请求带模型版本号（灰度和回滚的基础）、温度等采样参数显式声明默认值；响应带 request_id 方便追踪。**工程**：长请求做**异步化**——提交任务返回 task_id，客户端轮询或回调，避免 HTTP 超时；接口幂等（同 request_id 重复提交不重复计费）；限流按租户配额；错误用结构化错误码而不是裸 500。最后一条平台视角的要点：**批处理是服务端内部的事**，对客户端暴露的应该是"一次请求一个结果"的简单语义，动态 batch 在服务内部攒，客户端无感。

## 讲深一层

```
POST /v1/completions      → 同步，SSE 流式
POST /v1/tasks            → 异步提交 → task_id
GET  /v1/tasks/{id}       → 状态/结果
错误体: {"code": "...", "message": "...", "request_id": "..."}
```
- 版本放 URL 还是 header？——大版本 URL 便于网关路由，小版本 header
- 幂等键：客户端生成 request_id，服务端去重窗口内复用结果

## 高频追问

1. 流式输出断线怎么办？——续传靠 task_id 拉取已生成部分
2. 灰度怎么做？——按流量比例路由到不同版本实例

## 易错点

- 只答"REST + JSON"，流式和异步两个必考点都漏
- 把动态 batch 说成客户端行为
