## 题目

**场景**：车端部署岗核心认知题。服务器上跑得好好的模型，搬到车上不是「慢一点」的问题，是整层约束都换了。

**问**：车端 SoC（如 NVIDIA Orin）和数据中心 GPU（A100/H100）差在哪？直接搬模型会撞上什么墙？

## 口述答案

> 五个维度，一个比一个硬：
>
> ①**算力的口径不同**——GPU 标 TFLOPS（FP16/BF16），车端标 INT8 TOPS，且是「GPU+DLA+CPU」混合算力，DLA 只吃支持算子列表里的结构，标称峰值和可用算力差距很大；②**内存带宽差一个量级**——A100 是 80GB HBM、约 2TB/s，Orin 是 32-64GB LPDDR5、约 205GB/s，大模型车端推理的瓶颈通常在带宽不在算力；③**功耗预算**——机房单卡 300-700W 有风冷液冷，车模整个域控只给十几到几十瓦，频率、并发、batch 全要按功耗墙收缩；④**软件栈**——车端是 DriveOS/QNX 安全分区 + 精简的 CUDA/TensorRT，动态 shape、新算子、自定义 kernel 的支持远不如服务器灵活，升级还要过 OTA/功能安全流程；⑤**可靠性与实时性**——车规温度范围（-40~85°C）、看门狗、ASIL 功能安全分区，GPU 上「偶尔超时重跑」的宽容在车上不存在——**帧周期是硬截止期**。
>
> 所以搬模型的正确姿势是整套压缩链路：**量化（INT8 校准）+ 算子融合 + 裁剪/蒸馏 + 静态 shape + 流水线重叠（预处理/推理/后处理三级）**，敏感算子留 FP16、高频小算子下沉 DLA。一句话定位：**服务器在吞吐预算下做峰值，车端在功耗预算下做实时**。

## 讲深一层

| 维度 | 服务器 GPU (A100 级) | 车端 SoC (Orin 级) |
|---|---|---|
| 算力口径 | FP16/BF16 TFLOPS | INT8 TOPS + DLA 固定算子 |
| 内存 | 80GB HBM ~2TB/s | 32-64GB LPDDR5 ~205GB/s |
| 功耗 | 300-700W/卡 | 域控 15-60W 总预算 |
| 软件栈 | 完整 CUDA 生态 | DriveOS/QNX + 精简 TensorRT |
| 时效约束 | 吞吐优先，可排队 | 帧级硬截止期，抖动即事故 |

**判断技巧**：答对比题别报参数清单，报「约束→策略」：功耗墙→量化+降频设计；带宽墙→小模型+融合+带宽友好数据排布；实时墙→静态 shape+流水线+超时兜底。**记忆锚点**：「服务器拼吞吐，车端拼省电还准时」。

## 高频追问

1. **为什么车端 INT8 指标有水分？** —— TOPS 是乘加阵列峰值；实际受带宽、算子支持度、DLA 占比限制，可用算力常只有标称的几分之一，评估要用实测整帧延迟。
2. **大模型上车现在靠什么？** —— 小参数量 + KV cache 量化 + 投机解码/蒸馏，本质还是把带宽和功耗需求压进车端预算；端到端 VLA 走的也是「剪到车端养得起」的路线。
3. **DLA 和 GPU 怎么分工？** —— 常驻骨干（卷积类、量化友好的）下沉 DLA 省电，动态控制流/不支持的算子回 GPU；图要按 DLA 算子列表切分，切不好来回拷贝反而变慢。
4. **车端要不要 batch？** —— 传感器数据是流式的，批不起来；靠多路相机/多帧微批和流水线并行把利用率顶上去，而不是靠大 batch。

## 易错点

- 只比 TOPS/TFLOPS 数字——口径不同（INT8 vs FP16、峰值 vs 可用），比了等于没比。
- 忘了内存带宽——车端推理第一瓶颈常常是带宽不是算力。
- 漏掉软件栈差异——「TensorRT 都一样」是错的，车端版本功能面窄、流程重。
- 不提实时性语义——帧周期是截止期，不是「跑快点」的软目标。
