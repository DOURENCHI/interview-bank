## 题目

**背景**：自回归生成需要缓存历史 K/V 避免重复计算，端上内存紧张。

**问**：KV Cache 具体存什么、占多少内存？端侧怎么省？

## 口述答案

> 结论：**每层缓存该层历史 token 的 Key 和 Value**，形状 `[batch, n_kv_head, seq_len, head_dim]`，通常 fp16。每 token 字节 = `2 × 层数 × n_kv_head × head_dim × 字节宽`。例：32 层、GQA 8 个 KV head、head_dim 128 → `2×32×8×128×2 = 128KB/token`，4K 上下文就是 512MB，端上很难承受。省法：GQA/MQA 减 head、KV 量化到 int8/int4、滑窗、淘汰（H2O、保留 attention sink）、PagedAttention 减碎片、前缀共享。

## 讲深一层

| 手段 | 典型收益 | 代价 |
|---|---|---|
| GQA 8→1 | KV 降 8× | 质量略降 |
| KV int8 | 降 2× | 需校准 |
| 滑窗 512 | 与长度解耦 | 丢远距离 |
| 前缀共享 | 省 system 部分 | 需 hash 匹配 |

```python
per_token = 2 * layers * n_kv_head * head_dim * dtype_bytes
total = per_token * seq_len * batch
```

## 高频追问

1. **为什么只缓存 K/V 不缓存 Q？** —— Q 只用于当前步，历史 Q 不再参与计算；K/V 要被所有后续 token attend。
2. **滑窗会不会丢信息？** —— 会，长文档问答会失效；折中是"滑窗 + 少量全局 token（sink）"。
3. **端上还能 offload 吗？** —— 可以，冷 KV 换到闪存，但随机读写延迟高，只适合超长上下文的低频场景。

## 易错点

- 按 `n_head` 而不是 `n_kv_head` 估算，GQA 下高估数倍
- 忽略 batch 维度，多并发时内存爆掉
- 量化 KV 后不校准，长上下文 PPL 明显上升
