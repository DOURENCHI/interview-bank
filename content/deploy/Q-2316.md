## 题目

**背景**：多轮对话每轮都重新 prefill 全部历史，首 token 延迟很高，面试官问怎么复用。

**问**：多轮对话怎么复用上一轮的 KV Cache？需要满足什么前提，端上内存不够怎么办？

## 口述答案

> 结论：**保留完整 prefix 的 KV，新一轮只 prefill 新增 token**，首 token 延迟能降一个数量级。前提是 prefix **逐 token 完全一致**：system prompt、历史消息、角色标记、模板里的空格换行，任何一处变化都会失效重建。工程上用 prefix cache（vLLM APC、TensorRT-LLM 的 KV reuse）按序列哈希匹配，session 绑定 slot，LRU 淘汰。端上只留最近 N 轮 KV，更早的做摘要重写，但重写会失效 cache，要成批做。

## 讲深一层

```text
turn1: [S][U1][A1]              → 缓存 KV(1)
turn2: [S][U1][A1][U2]          → 命中前 3 段，只算 U2
turn3: [S][U1][A1][U2][A2][U3]  → 继续追加
若中途改写 system → 全失效
```
| 策略 | 命中率 | 内存 |
|---|---|---|
| 全量保留 | 高 | 随轮数线性涨 |
| 最近 N 轮 | 中 | 有界 |
| 摘要 + 最近 N 轮 | 中 | 有界，需重建 |

## 高频追问

1. **多用户并发怎么管理 slot？** —— 按 session id 绑定，空闲超时回收；容量不足时按 LRU 淘汰最久未用的 prefix。
2. **怎么判断 cache 命中了？** —— 统计 `prefix_cache_hit_tokens / total_prompt_tokens`，命中率骤降通常意味着模板被改了。
3. **跨请求能复用吗？** —— 相同 system prompt 的请求可共享前缀，这是多租户场景最大的收益点。

## 易错点

- 每轮重新拼接模板导致空格差异，cache 全不命中
- 保留 KV 但没算进显存预算，并发一高就 OOM
- 摘要重写后忘了让 cache 失效，输出错乱
