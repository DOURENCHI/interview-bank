## 题目

**背景**：快手 AI 应用开发岗二面的线上问题排查题（备考笔记帖，题面完整按 11-23 前例保留）。这题的精妙处在约束条件：「线上成功率下降而离线评测未变」——排除了「模型变差」这个直觉答案，逼你找「线上与离线的差异面」。考点是系统化排查框架：先验证指标本身可信，再按差异维度分桶定位，最后归因到变更。与库内 Q-4650（分层排查）、Q-0674（性能突降排查）、Q-4649（评测方法陷阱）互补，本题是 Agent 场景专用版。
**问**：线上 Agent 成功率下降而离线评测未变时，按什么顺序排查？

## 口述答案

> 先点破题眼：离线评测未变说明「模型在评测集上的能力没变」，那问题大概率出在「线上环境与评测环境的差异面」——排查框架就是沿着这个差异面找，而不是盲目重训模型。
> 第一步，验证指标可信（最容易跳过但最重要）：线上成功率是按什么统计的？先看是不是口径/埋点变了（比如新版客户端把「用户主动取消」也算进失败）、是不是流量结构变了（新接入一个难度极高的场景、促销期涌入长尾用户）。如果分母构成变了，成功率下降可能是「假下降」——离线当然不变。这一步的产出是「真实的、可比的失败样本集」。
> 第二步，分桶对比定位失败面：拿第一步的失败样本按维度分桶——按时间（何时开始跌，对齐变更时间线）、按场景/意图（哪类任务失败率涨）、按地域/客户端版本/用户群、按链路环节（失败发生在检索、工具调用、生成还是解析）。成功的离线评测覆盖不到的那一桶就是嫌疑区。典型发现：失败集中在「新上线的某个工具」或「某类长尾查询」。
> 第三步，检查环境差异面（重点嫌疑）：一是上游依赖——模型版本/温度参数/提示词版本是否被偷偷变更（线上灰度的配置漂移）、检索索引是否更新过（语料变了导致检索质量下降）、外部 API 是否改版或限流；二是数据分布漂移——线上真实 query 分布与评测集分布偏离（评测集太旧，覆盖不了新出现的需求形态）；三是并发与资源——超时率上涨、排队延迟导致截断。逐项与离线评测的环境 diff，找出「线上有而评测没有」的变量。
> 第四步，归因验证与修复：对头号嫌疑做受控实验——回滚该变更（回滚提示词版本/检索索引/模型版本）看成功率是否回升，或用失败样本回放复现；确认根因后修复并把这些失败样本补进评测集（评测集要随线上分布演化，否则「离线未变」会一再失真）。最后闭环：加监控告警（分桶成功率+变更关联），防止同类问题潜伏。
> 收尾一句方法论：这题的本质是「评测集不再代表线上分布」或「环境变量 diff」，答案骨架永远是——先信指标、再分桶、再 diff 环境、实验归因，而不是「模型不行了重训」。

## 讲深一层

- 「离线评测未变」有两种可能的真相：一是线上问题确实与模型能力无关（环境/分布差异），二是评测集本身过时已不能代表线上——第二种意味着离线评测的「未变」是失真的「未变」，这是本题最深的陷阱；所以排查终点常常是「更新评测集」而不是「修 bug」。
- 时间对齐是排查的第一工具：成功率下跌曲线的起点对齐变更时间线（发布/配置/索引/上游 API），大多数 Agent 事故在时间轴上都能对上一次变更——先做时间对齐再做复杂分析。
- 分桶的意义是把「成功率下降」这个笼统信号拆成可归因的具体信号：整体 95%→88% 看不出原因，但「工具调用类任务 98%→70%、纯对话类不变」立刻指向工具链路——排查效率的差别全在分桶维度设计。
- 数据漂移的工程对策：线上 query 抽样聚类监控新意图比例（漂移告警）、评测集滚动更新（按月把真实失败样本转评测用例）、影子评测（线上流量抽样跑当前版本与基线版本双跑对比）——把「离线与线上同步」做成机制而不是靠人记。
- 与 SRE 方法论的映射：这题就是 Agent 版的 SRE 排查——先看 dashboards 口径、再按 label 分桶、再 diff 近期 change（changelog 驱动）、再 A/B 回滚验证；面试里点破这个同构，体现的是工程素养迁移。

## 高频追问

1. 为什么不能直接怀疑模型变差？——模型权重没动的话能力不会突变；「离线评测未变」直接支持这一点；先找环境差异再怀疑模型
2. 失败样本怎么抽样才不偏？——按分桶维度分层抽样保证各桶覆盖，随机抽样会把长尾桶抽空；同时保留完整链路日志（含中间产物）供回放
3. 怎么判断是检索质量降了还是生成质量降了？——失败样本里看中间产物：检索命中了吗（召回/相关性）、工具返回对吗、生成是否偏离事实——分段评测定位环节
4. 评测集多久更新一次？——随线上分布滚动更新（月级），重大功能上线前把新增场景补进评测；评测集是活资产不是一次性资产
5. 灰度配置漂移怎么防？——配置变更纳入发布流程与审计（版本可查可回滚）、线上实际生效配置定期对账、关键配置告警——配置漂移是「离线未变线上变」的头号来源

## 易错点

- 第一直觉就是「模型退化，重训/换模型」——题面「离线未变」已经排除了这条路径，顺着直觉答说明没读懂约束条件
- 跳过指标可信验证直接归因——埋点口径变更和流量结构变化造成的「假下降」是高频真实事故，不先验证就排查是本末倒置
- 只答「看看日志」没有分桶框架——笼统排查在面试里等于没有方法论；分桶+时间对齐+环境 diff 三件套才是完整骨架
- 忘了「更新评测集」这个闭环——排查完成后把失败样本转评测用例，否则下轮漂移还会失真；说出这层说明理解评测是活的
