## 题目

**场景**：多轮 RAG 对话。用户第一轮问"TensorRT 和 ONNX Runtime 部署有什么区别"，第二轮追问"**那第二种呢？**"——这四个字直接送去检索什么都查不到。

**问**：多轮追问时，检索 Query 怎么改写？

## 口述答案

> 追问的本质问题是**指代和省略**——"第二种"依赖上一轮才成立。改写就是把"依赖上下文的口语 query"还原成"独立可检索的完整 query"。三种手段按成本递增：
>
> ①**规则拼接**：上一轮 query 里的实体 + 本轮增量（"ONNX Runtime 部署有什么区别"），便宜但只处理得了简单指代；
> ②**LLM 改写**：带最近 N 轮历史的 rewrite prompt，要求输出"不需要任何上下文也能看懂"的独立问题（"ONNX Runtime 在模型部署上和 TensorRT 的区别是什么"），主力方案；
> ③**多查询扩展**：改写后再拆成 2-3 个不同角度的子查询并行召回并合并，对抗"一次改写写偏"。
>
> 两条红线：**改写要保真**——不能把用户没问的东西加进 query（会召回到"相关但答非所问"的内容）；**要有兜底**——改写失败或超时，用原始 query 直查，宁可召回差也不能不召回。

## 讲深一层

历史窗口怎么给改写模型（工程细节决定成败）：

| 策略 | 做法 | 坑 |
|---|---|---|
| 近 N 轮 | 固定带最近 2-3 轮 | 指代对象在更早轮次时改写错 |
| 指代感知 | 检测到指代词时回溯到"最近一次出现该实体的轮次" | 实现稍复杂，准 |
| 全量历史 | 全带上 | token 贵，远轮噪声干扰改写 |

链式指代是累积误差的来源：第一轮说 A，第二轮"那 B 呢"，第三轮"**它俩**的区别"——改写必须一次还原全部指代链，逐轮拼接会错上加错。所以改写输入是"原始历史"，输出是"完整独立问题"，而不是在前一轮改写结果上继续叠。

**判断技巧**：验证改写质量的土办法——把改写后的 query 单独拿给不了解对话的人看，能不能猜出用户在问什么；猜不出就是没改写干净。

**记忆锚点**：「**改写的验收标准：脱离对话仍可独立检索**」。

## 高频追问

1. **怎么评估改写模块？** —— 端到端：同一评测集，对比"原始 query 直查"与"改写后查询"的召回命中率提升；保真性：人工抽检改写是否夹带未问内容；两者要一起看，只优化召回会鼓励改写模型自由发挥。
2. **改写用大模型还是小模型？** —— 任务简单（指代消解），微调过的 1-3B 小模型够用且延迟低；用大模型做改写在多轮高 QPS 场景成本不划算。
3. **追问之外还有什么要改写的场景？** —— 口语转检索语言（"为啥我部署完显存爆了"→"模型部署显存溢出 原因"）、中英混合实体归一、一个意图拆多查询。

## 易错点

- 只用规则拼接：处理不了"它俩""刚才那个"这类跨实体指代。
- 改写 prompt 给了全量历史：噪声多、token 贵，还可能把旧话题混进来。
- 改写结果直接替换原 query 进答案引用：答案里引用的是改写后的问题，用户觉得"我没问这个"。
