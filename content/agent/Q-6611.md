## 题目

**背景**：字节抖音电商 AI Agent 开发一面的第一问。这题不是背「多 Agent 的好处」，而是考判断力：能不能给出「什么时候单 Agent 够用、什么时候必须拆」的决策依据，以及「编排层用 Agent」这个反直觉设计背后的理由。答成「三级 Agent 就是主控+编排+执行三层」的名词罗列是及格线，讲出拆分阈值和约束手段才是区分度。
**问**：三级 Agent 是否必要？编排层为什么也要用 Agent？

## 口述答案

> 先给结论：三级 Agent 不是标配，是系统复杂度越过阈值后的产物。能不拆就不拆——单 Agent + 工具循环能扛住（工具十几个以内、上下文装得下、流程基本线性）的场景，拆成三级只会引入额外的交接损耗、延迟和错误放大点。
> 什么时候必须拆，四个信号：一是工具爆炸——几十个工具的 schema 塞进一个系统提示，选择精度被稀释、上下文被占满，按领域拆成多个子 Agent、每个只挂自己领域的工具；二是阶段间知识隔离——比如「意图澄清→检索→生成→审核」每个阶段的 prompt 策略、模型选择完全不同，混在一个上下文里互相干扰；三是要并行——多数据源同时检索、多文档同时摘要，单 Agent 只能串行等；四是权限与上下文最小化——子 Agent 只拿它那个任务需要的上下文和工具权限，隔离脏数据也隔离敏感信息。
> 编排层为什么用 Agent 而不是硬编码工作流：编排层要做的决策——这个任务拆成几步、每步给谁、结果怎么合并、失败了重试还是换路线——本质依赖对任务内容的理解，是动态的，静态 DAG 枚举不完。用 Agent 做编排，就是把「理解任务并规划」交给 LLM，把「路由、合并、重试」封装成编排 Agent 的工具。但必须点破约束：编排 Agent 的决策空间要收紧——子 Agent 白名单、步数/预算上限、终止条件、每步产出过 schema 校验——否则编排层一个误判会被下层所有 Agent 放大。
> 工程上的实际折中：确定性强的主干用硬编码状态机（LangGraph 的图 + 条件边就是这个思路），真正需要动态判断的分支点才交给编排 Agent 决策。「全 Agent」和「全硬编码」都是错的，答案是按不确定性比例混合。

## 讲深一层

- 错误放大机制：三级链条里每级的准确率相乘，编排层选错子 Agent 一次，子 Agent 再执行得再好也是白费——所以编排层的决策日志、可回放、可降级到默认路由，是生产系统的刚需。
- 编排 Agent 与子 Agent 的模型分层：编排用强模型（决策贵、频率低），执行用小模型（调用频繁、任务窄）——成本大头在执行层，这个分层是成本控制的核心手段。
- 上下文预算视角：三级 Agent 的每一级都是一个独立的上下文窗口，编排层不搬运子 Agent 的中间过程、只收结构化结果——这就是上下文隔离红利，反过来也是交接设计的难点（下一问）。
- 什么时候不要编排层：任务模式固定、分支可枚举（如固定的 ETL 流、固定报表生成），直接写工作流，Agent 编排纯属浪费延迟和 token。

## 高频追问

1. 编排 Agent 用什么模型？——决策频率低但质量要求高，用强模型；执行层用小模型跑量，成本分层
2. 编排出错怎么兜底？——白名单路由 + 步数上限 + 失败降级到默认子 Agent + 结构化错误向上抛而不是死循环重试
3. 单 Agent 什么时候反而更好？——工具少、任务单一、上下文装得下：拆分带来的交接损耗和延迟超过收益
4. 怎么评测三级 Agent 系统？——分端评测：编排决策准确率（路由对不对）、子 Agent 任务完成率、端到端成功率，不能只看最终结果

## 易错点

- 把「三级」当标准答案背——先说「不必要，是复杂度阈值产物」再给拆分信号，这个顺序本身就是答案的一部分
- 编排层理由只说「灵活」——要落到「动态决策无法静态枚举」这个本质，再补约束手段，否则像没做过系统
- 只讲架构不讲失败模式——错误放大、交接丢信息、成本翻倍，主动讲出来才是工程视角
- 混淆多 Agent 与多轮对话——多 Agent 是多个独立上下文的协作结构，不是一段对话里多问几轮
