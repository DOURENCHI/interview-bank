## 题目

**场景**：一个 AI 代码平台（或 Agent 平台）服务多条产品线、多个租户。共享同一个 LLM 服务、同一套向量库、同一批沙箱。用户 A 的代码、知识库、对话历史绝不能被用户 B 看到。

**问**：多产品线、多用户之间的数据隔离怎么做？

## 口述答案

> 按"数据流经的每一站"分层做，**每一站都带租户上下文**：
> ①**存储层**：物理隔离（独立库/独立集群）或逻辑隔离（共享库 + 租户 id 列 + 行级权限）。默认逻辑隔离起步，强合规客户上物理隔离。所有表、对象存储路径、向量库 collection 都带租户前缀/字段。
> ②**检索层**（Agent 系统最容易漏的）：向量检索的 query **强制拼接租户过滤器**——不是靠 prompt 约定，而是检索接口签名里租户 id 是必填参数，缺了直接报错；共享 collection 用 metadata 过滤，或干脆按租户分 collection。
> ③**运行层**：沙箱/代码执行按租户（至少按会话）分实例，用完即毁；文件系统、网络出口不共享。
> ④**推理层**：共享 LLM 实例时，隔离靠"请求级上下文"——每次请求的上下文只由服务端按租户组装，**绝不在服务端跨请求拼上下文**；对话历史按租户+会话存，鉴权后加载。
> ⑤**日志与可观测**：日志也带租户隔离——运营人员查日志也走权限，否则隔离在日志里漏光。
>
> 一条铁律：**默认拒绝**——任何查询缺失租户上下文时应该失败，而不是"不过滤全量返回"。

## 讲深一层

| 层 | 隔离单位 | 常见事故 |
|---|---|---|
| 存储 | 租户 id / 独立库 | 对象存储路径拼接漏租户前缀 |
| 检索 | collection / metadata filter | 向量库过滤参数可选→忘传就跨库 |
| 运行 | 容器/进程 | 沙箱复用残留文件 |
| 推理 | 请求级上下文 | 服务端全局缓存串了会话 |
| 日志 | 租户字段 + 权限 | 排障日志全租户可查 |

验证隔离不是"测功能"而是"测越权"：专设**跨租户攻击用例**（用户 A 的 token 去读 B 的资源、检索 A 的知识库、访问 A 的沙箱文件），CI 里常驻。Agent 系统额外要测：prompt 注入能否诱导模型引用另一个租户注入过的内容（共享知识库的间接注入）。

**判断技巧**：答平台隔离题，最后一定落到"默认拒绝 + 越权测试用例"——机制讲得再多，没有验证手段都等于没做。

**记忆锚点**：「**数据流过的每一站都查票；检票员缺席（缺租户上下文）就停车，不放行**」。

## 高频追问

1. **物理隔离和逻辑隔离怎么选？** —— 成本与合规的权衡：逻辑隔离成本低、运维简单，靠机制保证；物理隔离给强合规/大客户，故障域和信任域都独立。通常"默认逻辑 + 大客户物理"双轨。
2. **共享 LLM 实例，怎么防上下文串台？** —— LLM 是无状态的，串台只会发生在"服务端自己维护的会话状态/缓存"里：会话状态按 (租户, 会话 id) 键控，缓存 key 带租户哈希，prompt 拼接由租户感知的网关统一做。
3. **审计怎么做？** —— 所有跨租户边界的数据访问（读/检索/执行）留审计日志：谁、租户、资源、动作、时间；审计日志本身只增不删。

## 易错点

- 只做存储隔离：检索层忘加过滤器，一个 API 调用跨租户召回。
- 靠 prompt 或前端传租户 id：租户上下文必须来自服务端鉴权结果，不来自请求参数。
- 隔离做了但没越权测试：机制腐化无从发现。
