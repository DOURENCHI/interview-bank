## 题目

**背景**：美团后端 Agent 开发一面的第二问（备考笔记帖，题单形态，仿 11-21 快手帖前例保留）。这题考 Agent 工程化落地能力：能否把「实施约束」从一句「提示词里写清楚」展开成一套工程体系——约束的本质是 LLM 输出不可靠，要把「模型可能做错的空间」用工程手段收窄到「做错了也不出事故」。与库内 Q-1031（工具级约束三层）、Q-6611（编排层约束收紧）互补，本题是系统级总览。
**问**：Agent 开发过程中怎样实施约束？

## 口述答案

> 先给定位：约束的前提认知是模型输出是采样出来的、不可靠也不可信，所以约束的目的不是「让模型不犯错」，而是「模型犯错时系统不出事故」。实施按执行时序分三层：事前收窄空间、事中拦截执行、事后审计兜底。
> 事前（进入模型之前）：一是工具白名单与最小权限——Agent 只挂这个任务需要的工具，敏感工具（写库、支付、删除）单独标记；二是权限前置——需要授权的操作先拿用户确认或校验令牌，绝不替用户编造资源 ID 和参数（这是幻觉事故的高发点）；三是参数 schema——每个工具的参数用 JSON Schema 声明类型、枚举、范围，模型输出先过 schema 校验再进执行；四是系统提示里的硬规则写成明确否定式（「绝不执行删除类操作」「绝不输出密钥」）——但要清楚提示词是最弱的一层，只能当第一道不能当唯一一道。
> 事中（执行过程中）：一是沙箱——代码执行、文件操作放进容器/沙箱，限网络、限文件系统、限时长；二是步数与预算上限——max steps、token 预算、单步超时，防死循环和成本失控；三是每步再校验——工具参数运行时再验一次（不信任上一环节），输出格式用结构化输出或约束解码保证可解析；四是分级人工确认——读操作自动执行、写操作确认后执行、不可逆操作（删数据、对外付款）强确认，这就是 human-in-the-loop 的分级设计。
> 事后（结果落地之后）：一是结果校验——schema 校验加业务规则校验（金额上限、路径白名单、时间范围）；二是全量审计日志——每步的模型输出与工具调用可回放可追溯，出事故能定位到步；三是可回滚——写操作设计成可补偿的事务，失败能退回；四是评测兜底——上线前用约束类对抗用例（越权、提示注入、资源耗尽、死循环）做回归，把约束当功能来测。
> 收尾点题：这是纵深防御——提示词最弱、schema 与白名单中等、沙箱和权限系统最强；任何单层都能被绕过，多层叠加后「模型犯的错」到不了「系统的事故」。后端场景还有一层：Agent 调用的内部服务本身要有鉴权、幂等、限流，约束一半做在 Agent 侧、一半做在工具侧。

## 讲深一层

- 强度谱系要能排序：提示词约束 < 结构化输出/schema < 工具白名单 < 沙箱隔离 < 账号权限系统——前两层是「劝」，后三层是「拦」；面试里主动说出这个排序，是把「做过系统」和「看过文章」区分开的关键。
- 提示词约束为什么必然可绕：提示注入（间接注入藏在检索内容里）、长上下文稀释（规则在第 3 条，第 80 轮对话后注意力衰减）、采样波动——三条任何一条都足以击穿，所以「提示词写清楚」只配当第一道。
- 成本也是约束对象：步数上限、token 预算、超时既是安全约束（防死循环）也是成本约束（防失控账单），生产事故里成本失控占比不比逻辑错误低；预算到顶要优雅终止并汇报进度，不是抛异常。
- 分级确认的工程细节：确认不是「每次都问」（用户会疲劳然后无脑点同意，形同虚设），而是按风险分级——只读自动、可逆写批量确认、不可逆单独强确认；确认载荷要给足上下文（做什么、影响范围、可拒绝），否则确认变成走过场。
- 与编排层约束的关系：多 Agent 系统里本题的三层要再叠加编排层约束（子 Agent 白名单、步数预算、产出 schema 校验，见 Q-6611）——编排层一个误判会被下层所有 Agent 放大，所以编排层的决策空间收紧是优先级最高的约束点。

## 高频追问

1. 提示词里写清楚约束为什么不够？——软约束，注入、上下文稀释、采样波动都能绕过；只能当纵深防御的第一层，硬约束必须落在执行侧
2. 约束和灵活性怎么平衡？——不做一刀切禁止，用白名单加分级确认；把「放开某个约束」做成显式授权动作（可审计），而不是改提示词
3. 怎么验证约束真的生效？——约束类对抗用例进评测回归（越权、注入、死循环、成本超标），线上靠审计日志抽检；约束是功能，要像功能一样被测试
4. 步数上限设多少合适？——按任务类型定预算：简单查询 3~5 步、复杂任务 15~30 步，到顶优雅终止并汇报已完成部分，不是直接报错
5. Agent 执行写操作失败了一半怎么办？——写操作按可补偿事务设计（先落草稿/影子写入，确认后提交），配合审计日志定位未完成步骤，重试前先做幂等去重

## 易错点

- 只答「提示词里写清楚约束就行」——面试官想听工程手段；提示词是最弱一层，这个认知本身就是答案的一部分
- 约束全部落在模型侧——执行侧（沙箱、权限、运行时校验）才是硬约束，模型侧手段全是软的
- 混淆「约束」与「错误处理」——约束是事前收窄空间，错误处理是事后恢复，两者都要但层次不同，混着说显得没做过系统
- 漏掉成本与步数约束——生产 Agent 事故一半是死循环和账单失控，预算上限是必答题
- 确认机制设计成「每步都问」——用户疲劳后无脑放行，确认形同虚设；要讲出风险分级
