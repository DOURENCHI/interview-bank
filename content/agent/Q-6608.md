## 题目

**场景**：Agent 通过 MCP 接入外部工具与数据源。大部分交互是 Agent 发请求、Server 回结果；但有些场景 Server 需要主动说话——长任务的进度、资源变更的通知。

**问**：MCP 的消息回调是怎么做的？请求-响应之外，Server 怎么主动推？

## 口述答案

> 先分两种通信形态：
> ①**请求-响应**（早期只有这种）：Agent 发 tool call 请求，Server 回结果，**单向拉**——JSON-RPC 的 request/response，覆盖"问一句答一句"的工具调用。它的局限：Server 在两次请求之间是"哑"的，长任务只能靠 Agent 反复轮询。
> ②**通知/回调**（协议扩展出来的主动推送）：MCP 定义了 **notification 消息**——Server 不需要配对请求就能发出单向消息，典型如 `notifications/resources/updated`（订阅的资源变了）、进度通知（长任务的百分比）、日志通知。客户端对感兴趣的资源**先订阅**，变更时 Server 主动推，Agent 侧的消息循环收到后决定是否触发新一轮推理。
>
> 工程上回调进 Agent 要过三道处理：**排队**（回调不能打断正在进行的 LLM 推理，先进队列，下轮决策时消费）、**去重合并**（同一资源连续变更合并成一条）、**幂等**（通知可能重复送达，处理逻辑按 (资源 id, 版本号) 幂等）。

## 讲深一层

| 形态 | 方向 | 典型消息 | 适用 |
|---|---|---|---|
| 请求-响应 | Agent→Server→Agent | tools/call、resources/read | 一步一答的工具调用 |
| 通知 | Server→Agent 单向 | resources/updated、进度、日志 | 长任务进度、数据变更 |
| 订阅 | Agent 订阅→Server 推 | resources/subscribe | 只关心特定资源的变更 |

传输层承载：stdio（本机子进程）、SSE / Streamable HTTP（远程）。远程场景下"Server 主动推"依赖连接的长保持——连接断了通知就丢，所以重要状态变化要支持**重连后拉取快照**（通知只做"催看"，真相以重新 read 为准）。

**判断技巧**：答这题的关键是点破"通知是催办不是数据"——收到通知后重新拉取资源拿到一致快照，而不是把通知内容本身当数据源，这一句能体现分布式系统的基本功。

**记忆锚点**：「**请求-响应是问答，通知是敲门；门敲了，还是开门看实物**」。

## 高频追问

1. **通知丢了或乱了怎么办？** —— 通知带序号/版本号，Agent 侧检测空洞就触发一次主动 read；处理幂等，重复通知无害。
2. **和 WebSocket 推送什么关系？** —— MCP 不自己造传输层，通知跑在所选 transport（stdio/SSE/Streamable HTTP）之上；对比 WebSocket：MCP 是协议语义层，关心的是"什么消息、什么时机"，传输是可替换的。
3. **回调触发 LLM 重新推理的时机怎么定？** —— 不能每条通知都触发（成本失控）：合并去重后按优先级分档，关键事件（用户消息、任务失败）立即触发，普通变更攒到下一轮决策一并消费。

## 易错点

- 把通知内容当数据用：通知到达与 read 之间数据可能又变了，不一致。
- 回调直接打断正在进行的推理：上下文错乱，必须排队。
- 长任务用轮询硬扛：轮询间隔与延迟/成本的平衡比通知机制差得多，但要知道轮询是兜底（Server 不支持推送时）。
