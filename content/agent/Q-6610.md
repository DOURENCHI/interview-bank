## 题目

**场景**：Agent 通过 function calling 驱动一批工具（搜索、代码执行、数据库查询、文件读写）。

**问**：工具调用有哪几种模式？你们的 Agent 用的是什么模式、为什么？

## 口述答案

> function calling 的调用形态按"谁决定调用序列"分三档：
> ①**单步调用**：模型一次输出一个工具调用，系统执行、回填结果、模型继续——最基础形态，ReAct 循环的原子操作。
> ②**并行调用（parallel tool calls）**：模型一次输出多个互不依赖的调用（"查 A 的价格 + 查 B 的库存"），系统并发执行、一次性回填——省轮次和延迟，前提是调用间无依赖。
> ③**串行依赖链**：后一个调用需要前一个的结果（"先查用户 id，再拿 id 查订单"），模型根据回填结果发下一发，本质是单步调用的循环。
>
> 再往上按"确定性"分两种编排哲学：**模型自主决策**（ReAct/自主模式：模型自己挑工具、自己定顺序，灵活但不确定）和**代码编排 + LLM 填槽**（Workflow 模式：调用序列由代码写死，LLM 只负责填参数/分类，确定可控）。生产系统大多混合：**主流程用 Workflow 保证确定性，开放探索环节放开给模型自主调用**。
>
> 我们的选择逻辑一句话：**错误代价高的路径用 Workflow，探索性路径用自主调用，边界处加校验**。

## 讲深一层

| 模式 | 确定性 | 延迟 | 适用 | 失控风险 |
|---|---|---|---|---|
| 单步 | 低 | 高（多轮往返） | 通用 | 步数失控 |
| 并行 | 低 | 低 | 无依赖批量查询 | 副作用并发 |
| 依赖链 | 中 | 中 | 多表查询类任务 | 链条中途错 |
| Workflow | 高 | 看流程 | 支付/下单等强确定业务 | 死板 |

工具多了模型会选错，工程对策：**按场景分组注入**（本轮任务相关的工具才进 prompt）、**工具描述写清适用条件与反例**、工具集大到上百个时做 **RAG over tools**（先检索相关工具再注入）。

**判断技巧**：面试官问"你们用什么模式"是在要具体经验——答案必须带一个"为什么不用另一种"的理由，只报名词不加分。

**记忆锚点**：「**按依赖关系选形态，按错误代价选编排；工具太多先分组**」。

## 高频追问

1. **并行调用的副作用怎么管？** —— 并行只给只读/幂等操作；有副作用的调用（写库、发消息）串行或加锁，并在工具描述里声明副作用等级。
2. **工具调用失败怎么办？** —— 错误信息结构化回喂模型让它决策（重试/换工具/放弃并告知），比框架层无脑重试好；但网络类瞬时错误在框架层直接重试，不浪费一次模型推理。
3. **模型硬要调不该调的工具怎么办？** —— 权限在执行层卡，不在 prompt 层卡：工具按会话权限白名单过滤注入，执行前再校验一次参数合法性（防注入出的畸形参数）。

## 易错点

- 无依赖的调用还串行跑：白多几轮往返，延迟翻倍。
- 副作用操作放进并行批次：执行顺序不保证，业务写坏。
- 工具列表全量注入每一轮：token 膨胀 + 选择准确率下降。
