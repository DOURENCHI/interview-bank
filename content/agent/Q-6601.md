## 题目

**场景**：设计一个 Agent，LLM 要驱动工具完成多步任务。

**问**：ReAct 和 Plan-Execute-Replan 两种模式的区别是什么？各自适合什么任务？

## 口述答案

> 区别在"什么时候做决策"：**ReAct 是每一步现场决策**——LLM 走一步"想→调工具→看结果→再想"，没有全局计划，边走边定；**Plan-Execute-Replan 是先决策一次、执行中修正**——先让 LLM 产出完整计划（步骤列表或任务 DAG），执行器逐步跑，只有失败或环境变化时才触发 Replan 重新规划。
>
> 适用任务：**ReAct 适合探索型任务**——路径未知、工具少、步数少，比如"查一下这个仓库的 license 再决定怎么引用"，边看边定反而高效。**Plan-Execute-Replan 适合长链路、可并行、成本敏感的任务**——比如"调研 20 个竞品并出对比报告"，先出计划可以并行执行、上下文也更省（执行器不用每次背着全部历史）。
>
> 各自的失败模式正好互补：ReAct 没有全局视图，**一步走偏后面全偏**；Plan 的计划会**过时**——环境变了还在埋头执行旧计划，所以 Replan 的触发条件是这类系统的命门。

## 讲深一层

| 维度 | ReAct | Plan-Execute-Replan |
|---|---|---|
| 决策粒度 | 每步一次 LLM 决策 | 计划一次 + 执行时逐步 |
| 上下文成本 | 每步都带全部历史，长任务 token 膨胀 | 执行器只带当前步骤上下文，省 |
| 纠错方式 | 观察到异常后下一步自纠 | 失败/偏差触发 Replan |
| 并行性 | 难（串行思考链） | 计划里无依赖步骤可并行 |
| 典型失败 | 局部最优、绕圈、跑偏 | 计划过时、过度规划（计划比任务复杂） |

Replan 触发条件（工程上的关键设计）：关键工具调用失败且重试无效、前置步骤结果与计划假设不符、用户目标中途变更、执行超时。Replan 不是全量重来——保留已完成步骤的结论，只重排剩余部分。

**判断技巧**：面试追问"你选哪种"时，先反问任务特征（步数、确定性、是否可并行），再给选择——直接背答案会显得没做过系统。

**记忆锚点**：「**ReAct 走一步看一步；Plan-Execute 先画路线图，Replan 是图过时就重画**」。

## 高频追问

1. **两者能不能结合？** —— 常见混合架构：Planner 出粗计划，Executor 执行单个步骤时内部用 ReAct（步骤内仍要探索）；这样兼得全局视图和局部灵活。
2. **计划用什么表示？** —— 结构化 JSON 步骤列表（每步：目标/工具/依赖/验收标准），依赖关系决定并行与 Replan 的波及范围；自然语言计划不好机读。
3. **怎么判断该 Replan 而不是重试？** —— 区分"执行错误"（重试）与"计划假设错误"（Replan）：结果虽然失败但符合预期形态→重试；结果揭示前置假设不成立→Replan。

## 易错点

- 把 ReAct 说成"不需要规划"——它每步的思考就是微型规划，只是不持久化、不全局。
- Plan-Execute 不做 Replan——那就退化成一次性脚本，环境一变就废。
- 长任务还用纯 ReAct——历史全量进上下文，token 成本和注意力分散双输。
