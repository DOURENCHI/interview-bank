## 题目

**背景**：快手 AI 应用开发岗二面的 Agent 工程题（备考笔记帖，题面完整按 11-23 前例保留）。Checkpoint（检查点/断点恢复）是 Agent 从 demo 走向生产的关键能力：长任务跑几十步，进程崩溃、超时、人工接管后怎么从中间状态续跑？考点是「状态建模」——能说清必须持久化哪些状态、为什么这些不可省，以及恢复时如何重建上下文。与库内 Q-6612（主子 Agent 上下文交接）、Q-0839（对话历史 vs 结构化状态）形成序列：那两题讲「传什么给下一个 Agent」，本题讲「怎么存、怎么恢复」。
**问**：Checkpoint 需要保存什么状态，才能让下一个 Agent 继续工作？

## 口述答案

> 先给定位：Checkpoint 的目标不是「存个文件」，而是让恢复后的 Agent 不需要重跑已完成步骤、也不会带着错误假设继续——所以保存的是「足以重建执行现场的完整最小状态集」。可以按五类展开。
> 第一类任务级状态：任务目标（原始需求与验收标准）、任务计划（步骤列表/依赖图）、当前进度指针（哪步完成、哪步进行中、哪步失败）——这是恢复的骨架，缺了它 Agent 不知道自己干到哪了。
> 第二类对话与上下文状态：完整的对话历史或其结构化摘要、关键的用户决策与澄清（比如用户明确说过「不要用方案 B」）、当前推理的中间结论——恢复时 Agent 要能「想起来」为什么走到这一步，否则会重新质疑已确定的决策。注意这里摘要可能丢字段，关键约束要原文存。
> 第三类工具与外部副作用账本：已经调用过哪些工具、参数是什么、返回了什么（尤其是创建了哪些外部资源——发的邮件、建的工单、写的文件 ID）。这类最容易被漏：恢复后如果不知道「邮件已发过」，重跑就会重复执行副作用——所以副作用要记录成可查询的账本，配合幂等键防重复执行。
> 第四类环境与版本状态：当时用的模型版本、工具版本、配置参数、提示词版本——恢复后环境漂移会让「同样的输入产生不同行为」，版本元数据让恢复可复现、可审计。
> 第五类数据快照引用：中间产物（检索结果、生成的草稿、下载的文件）不一定要全量入 checkpoint（体积大），但要存引用与校验（路径/哈希），保证恢复时能取回或识别失效。
> 收尾回答「下一个 Agent 继续工作」：恢复流程是——加载五类状态→校验外部副作用账本（对账：已做的标记完成）→按任务计划指针定位下一步→重建上下文（历史+摘要+关键决策原文）→从断点步骤继续执行。一个成熟实现还要定期打快照（每步或每 N 步）、checkpoint 带版本号支持回滚到更早的检查点。

## 讲深一层

- 与 Q-6612 的分工要说清：那题讲「主 Agent 把任务交给子 Agent 时传什么」（任务契约：目标+约束+已有成果），本题讲「同一任务跨时间恢复存什么」；共同点是「状态建模」，差异是交接是横向快照、checkpoint 是纵向存档——面试里主动点破两题关系显得体系完整。
- 「最小状态集」的工程权衡：全量存对话历史恢复保真但体积大、成本高；只存摘要恢复快但可能丢关键细节——成熟做法是分层（结构化状态全存+对话按需摘要+关键决策原文保留），这正是 Q-0839 讲的三类丢失问题的落地点。
- 幂等是 checkpoint 的安全网：恢复后从断点重试，如果上一步其实执行了一半（工具调用发出但响应没记到），重复执行就是事故——所以副作用设计成幂等（幂等键/条件写/check-then-act），账本+幂等双保险。
- 版本元数据容易被当成凑数，实际是审计刚需：生产事故里「恢复后行为变了」最常见根因就是模型/提示词版本漂移——存版本才能回答「为什么上次能跑这次不行」。
- 与工作流引擎的类比：LangGraph 的 checkpointer（thread 级持久化）、Temporal 的 workflow state——面试提一句「这本质是工作流引擎的持久化模型套到 Agent 上」，展示的是工程迁移能力。

## 高频追问

1. 对话历史太长 checkpoint 存不下怎么办？——结构化状态全存、历史做摘要、关键决策与用户约束保留原文；摘要丢字段的问题靠「关键项白名单」兜底
2. 恢复后发现外部世界变了怎么办？——对账：副作用账本逐条核实（资源还在吗、状态对吗），失效的重新执行、完成的跳过；这就是为什么账本要存资源 ID 与状态
3. checkpoint 多久打一次？——每步打成本高但丢失窗口为零；按步/按时间/按风险事件（外部副作用前必打）混合；有外部副作用的步骤前打点是关键规则
4. 能不能回滚到几个 checkpoint 之前？——可以，checkpoint 带版本与父子关系（链式），回滚到早版本重新执行；注意外部副作用不可回滚的部分要人工介入
5. 和数据库事务有什么相似？——同样是「状态+日志+恢复」模型：checkpoint 是持久化状态、副作用账本是 redo/undo log、对账是崩溃恢复——把这个类比讲出来是加分项

## 易错点

- 只答「存聊天记录和任务摘要」——漏掉副作用账本（最关键）与环境版本元数据；题面本身就是从这层卡住的（考生的第一反应就是这两样），面试官想听的是完整的五类
- 不区分「对话历史」与「结构化任务状态」——两者角色不同（上下文 vs 进度指针），混为一谈会导致恢复后「知道聊过什么但不知道干到哪」
- 忽略幂等与重复执行风险——恢复语义必然包含「断点附近可能重复」，没有幂等设计的 checkpoint 方案是纸面方案
- 把 checkpoint 说成存档没有恢复流程——面试官追问「怎么恢复」时要说清加载→对账→定位→重建上下文→续跑五步
