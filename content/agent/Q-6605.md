## 题目

**场景**：长对话 Agent，第 1 轮用户说"必须用 Python 3.9、不能用外部依赖、输出要能直接进 CI"。对话 40 轮后触发上下文压缩，模型开始 pip install、写出 Py3.12 语法——用户的核心需求被压缩弄丢了。

**问**：怎么避免 Context 压缩之后，模型忘记用户之前提出的重要需求？

## 口述答案

> 先讲透病因：压缩本质是**有损压缩**，而用户的约束性需求恰恰是最容易被压掉的信息——它只在第 1 轮说过一次、占字数少、和后面热闹的工具输出比"存在感"低。摘要模型天然偏向保留"发生了什么"，丢掉"被要求了什么"。
>
> 所以解法的核心是**把"需求"从"历史"里拆出来单独管理**，不让它参与压缩：
> ①**需求钉扎**：对话开始或需求出现时，把约束提炼成结构化"任务卡"（目标/硬约束/偏好），固定放在每次请求的 system 区——它不是历史，是不参与压缩的常驻层；
> ②**分层压缩**：历史按"近 N 轮原文保真 + 更早的摘要 + 任务卡常驻"三层组织，压缩只作用于中间层；
> ③**按类别配额压缩**：摘要时明确指示"约束与指令必须逐字保留，工具输出可以丢"，把压缩的损失定向到可损失的信息上；
> ④**压缩后校验**：压缩完成时检查任务卡里的每条约束是否还能在上下文中找到，找不到就回填——压缩也要有单元测试。
>
> 配套：关键约束在长对话里**周期性复述**一次（把"很远的信息"变"很近的信息"），以及约束变化时同步更新任务卡。

## 讲深一层

信息分三类，压缩策略不同（这也是"压缩后消息丢失"类问题通用解法）：

| 信息类别 | 例子 | 压缩策略 |
|---|---|---|
| 指令/约束 | "必须用 Py3.9" | 钉扎常驻，永不压缩 |
| 事实/结论 | "用户环境是 CUDA 12" | 进长期记忆/任务卡，可回查 |
| 过程/中间 | 工具原始输出、试错轨迹 | 可摘要、可丢弃 |

第三条（事实进长期记忆）补齐了钉扎管不到的情况：约束会演化、事实会增多，靠"常驻任务卡 + 会话状态存储"双载体，模型随时可以"查"而不必"记"。

**判断技巧**：答这类题先给病因（有损压缩 + 需求信息密度高存在感低），再给方案——上来就报方案，面试官不知道你是不是真理解为什么会丢。

**记忆锚点**：「**需求不是历史，是常驻的合同；压缩历史，不压合同**」。

## 高频追问

1. **怎么自动判断哪些话该"钉扎"？** —— 规则打底（祈使句/含"必须/不要/只能"）+ 轻量意图分类；不确定的进"候选约束"让用户确认一次。宁可多钉，钉错了顶多多占几十 token。
2. **压缩什么时候触发？** —— token 阈值（如 70%）触发，且在"任务边界"处切（一轮完整问答后），不在工具调用半途切；避免压缩打断执行中的状态。
3. **怎么验证方案有效？** —— 构造"长对话需求保持率"测试集：40 轮闲聊+工具调用中埋 3 条约束，测最终回答对约束的遵守率；没这个测试集，压缩策略改动全凭感觉。

## 易错点

- 指望摘要 prompt 里加一句"保留用户需求"就够了：软指令对摘要模型约束力有限，约束照丢，必须结构化钉扎。
- 压缩触发在工具调用中间：执行状态和压缩后上下文对不上，行为错乱。
- 只处理"需求丢失"，不管"事实丢失"：用户改过 3 次口径，模型还按第 1 次执行。
