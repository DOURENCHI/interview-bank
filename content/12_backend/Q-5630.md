## 题目

**背景**：面试官问到分库分表中间件的选型，重点不是会用，而是为什么要用、代价是什么。

**问**：我们为什么要使用 ShardingSphere？分库分表的痛点在哪？

## 口述答案

> 解决的是单库单表撑不住的问题。数据量上到千万级以后，B+ 树层高增加，查询和写入都变慢；单库的连接数、IOPS、磁盘容量都有硬上限；大表做 DDL 锁表时间不可控，备份恢复也慢。ShardingSphere 在 JDBC 层做透明分片，SQL 进来解析、改写、路由到多个库表，再归并结果，业务代码基本不用改；除了分片还提供读写分离、分布式事务、数据加密和影子库压测。但代价必须说清：跨分片 JOIN 和分布式事务很难，聚合排序分页要在内存归并，全局唯一 ID 要另做方案，运维复杂度明显上升。所以不到瓶颈不拆。

## 讲深一层

| 能力 | 说明 |
| --- | --- |
| 分片 | 分库分表、读写分离 |
| 路由 | 解析 SQL，按分片键选库表 |
| 改写与归并 | 补列、改表名、内存排序聚合 |
| 分布式事务 | XA 或柔性事务 |
| 其他 | 数据加密、影子库、弹性迁移 |

单表经验阈值：MySQL 单表 2000 万行左右开始明显劣化，但要结合行宽和查询模式看，不是绝对线。

## 高频追问

1. **分片键怎么选** —— 选查询必带、分布均匀的字段；选错会导致大量跨片查询，分片反而更慢
2. **跨分片分页怎么优化** —— 禁止深分页，用游标或二次查询（先取 id 再回表）
3. **为什么不直接用代理模式** —— 代理少改代码但多一跳网络和运维节点，JDBC 模式性能更好但和语言绑定

## 易错点

- 把分库分表当银弹 —— 它把单机问题换成了分布式问题，事务和 JOIN 的代价常常更高
- 分片键选用户 id 却又按时间范围查 —— 广播到所有分片，等于没分
- 忽略全局 ID —— 自增主键在多库下会冲突，要提前设计雪花或号段
