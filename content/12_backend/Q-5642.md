## 题目

**背景**：秒杀系统的核心追问，面试官已经从缓存一致性问到具体方案，现在要落到"怎么在 Redis 里保证不超卖且一人一单"。

**问**：如果用 Redis 作为秒杀订单系统的缓存，怎么保证不超卖、并且做到一人一单？

## 口述答案

> 超卖靠"原子扣减 + 结果判定"，不能先 GET 再 DECR，那是典型的 check-then-act。库存预热进 Redis 后，用 Lua 脚本把"判库存 > 0、扣减、写用户标记"合成一次原子执行，`DECR` 后若小于 0 就 `INCR` 回滚并返回失败。一人一单用同一段脚本里的 `SISMEMBER` 判重，或用 `SET order:uid:goods NX EX`，过期时间覆盖整个活动周期。但 Redis 只是"资格预扣"，最终要靠数据库兜底：`(user_id, goods_id)` 建唯一索引，重复插入直接失败；异步下单再加超时未支付回补库存。

## 讲深一层

```lua
if redis.call('SISMEMBER', KEYS[1], ARGV[1]) == 1 then return -1 end
local s = tonumber(redis.call('GET', KEYS[2]))
if s <= 0 then return 0 end
redis.call('DECR', KEYS[2]); redis.call('SADD', KEYS[1], ARGV[1])
return 1
```
集群模式下 KEYS 必须落在同一 slot，用 `{goodsId}` 做 hashtag，否则脚本直接报 CROSSSLOT。脚本内所有判断必须在同一次执行里完成，任何"客户端再读一次"的逻辑都会重新引入竞态；返回码要能区分售罄、重复下单、成功三种，前端才能给出不同提示。

## 高频追问

1. **Lua 为什么能保证原子？** —— Redis 单线程执行命令，脚本整体作为一个命令串行跑，中间不会插入其他客户端请求；但它不保证"失败自动回滚"，异常前的写已生效，要自己写补偿
2. **Redis 挂了怎么办？** —— 主从切换可能丢预扣，靠 DB 唯一索引和库存字段的条件更新（`UPDATE ... SET stock=stock-1 WHERE stock>0`）做最终裁决
3. **回补库存怎么防重复？** —— 回补也走幂等：订单状态机只能从"待支付"转"已取消"，用条件更新 `WHERE status=0` 保证只回补一次

## 易错点

- 用 `GET` 判库存再 `DECR`——两步之间并发进来就超卖，必须脚本或 `DECR` 后判负回滚
- 只靠 Redis 不设 DB 唯一索引——Redis 宕机、主从延迟、脚本重试都会漏，数据库是最后一道闸
- 一人一单的 key 不设过期——活动结束后 key 永久堆积，内存被历史数据吃掉
