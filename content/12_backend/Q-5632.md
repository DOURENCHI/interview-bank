## 题目

**背景**：面试官给了一个开放的设计题：事件流持续写入，要能随时查某个用户某类行为的次数。

**问**：用户一系列事件，生产环境下如何设计一个可用的接口，随意获取一个用户的某种行为的次数？

## 口述答案

> 写读两条路径分开设计。写入侧先做幂等，事件带 event_id，用 Redis SETNX 去重，TTL 覆盖业务窗口，避免重投导致多算；然后 INCR 计数键，键设计成 `cnt:{behavior}:{uid}:{yyyyMMdd}`，同时把明细丢进 Kafka 异步落库。读侧查单日直接读 Redis，miss 回落预聚合表；查区间查按天或按小时的 rollup 表，绝不在明细表上做 count(*)。只要 UV 不要精确值时用 HyperLogLog，误差约 0.81%，内存固定。还要处理两个坑：热点用户会让单个 key 变成大 key，按 uid 哈希拆片；计数键必须设过期，不然无限增长。

## 讲深一层

| 需求 | 方案 | 代价 |
| --- | --- | --- |
| 精确日计数 | Redis INCR + 异步落库 | 大 key 风险 |
| 区间查询 | 预聚合 rollup 表 | 有分钟级延迟 |
| UV 近似 | HyperLogLog | 误差约 0.81% |
| 事件去重 | SETNX / 布隆过滤器 | 布隆有假阳性，不能删 |

读多写少时可以在 Redis 前再挂一层本地缓存，但要接受秒级的过期延迟，别用在强一致场景。

## 高频追问

1. **大 key 怎么拆** —— 按 uid 取模拆成 N 个 key，读时求和；或者热点用户单独走明细表
2. **跨天怎么算** —— 按事件发生时间归属日期，不要按写入时间，否则补数据会串天
3. **怎么保证不丢** —— 先写 Kafka 再更新计数，或者计数失败可重放，别让 Redis 成为唯一真相

## 易错点

- 直接对明细表 count(*) —— 数据量一大就拖垮库，这是最常见的错误答案
- 不做幂等 —— 上游重投会把次数算多，且很难事后修正
- 计数 key 不设 TTL —— 内存无限增长，最后 OOM
