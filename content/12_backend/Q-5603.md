## 题目

**场景**：列表页翻到很后面就超时。面试官问：**`LIMIT 1000000, 20` 为什么慢？有哪几种优化方式？**

## 口述答案

> 慢的原因是**偏移量要真实扫描**：MySQL 先按顺序取出 1000020 行（如果走二级索引还要逐行回表），再丢掉前 100 万行，只返回 20 行。翻得越深越慢，成本是 O(offset)。
> 优化有四种：
> 一是**延迟关联**，先用覆盖索引查出主键 `SELECT id FROM t ORDER BY id LIMIT 1000000,20`，再拿这 20 个 id 回表；
> 二是**游标分页**，记住上一页最后一个 id，改成 `WHERE id > last_id ORDER BY id LIMIT 20`，成本变 O(1)；
> 三是**业务限制最大页数**（大部分用户不会翻到 5 万页）；
> 四是**覆盖索引**减少回表，或者用 ES/宽表专门做深翻页。

## 讲深一层

```sql
-- 慢：扫 1000020 行 + 回表
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- 快 1：延迟关联（覆盖索引先拿主键，再回表 20 次）
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) t ON o.id = t.id;

-- 快 2：游标分页（要求排序键稳定且唯一）
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20;
```

- 游标分页的代价：**不能跳页**（只能上一页/下一页），且排序键必须唯一稳定，否则会漏行/重复。
- 延迟关联为什么快：子查询只在二级索引上扫，不需要回表，最后只回表 20 次。

## 高频追问

1. **为什么不能直接 `LIMIT` 加索引就完事？** —— 索引只解决排序，不解决「要数过前面 N 行」这个偏移成本。
2. **`ORDER BY` 字段没索引会怎样？** —— 全表扫 + filesort，深分页会更慢，`EXPLAIN` 里能看到 `Using filesort`。
3. **搜索引擎方案怎么选？** —— 深翻页 + 复杂过滤交给 ES，MySQL 只存详情；代价是数据同步与一致性。

## 易错点

- 只说「加索引」，没有解释偏移量本身要扫
- 用游标分页却不要求排序键唯一，导致翻页丢数据
- 忘记 `ORDER BY` 和 `LIMIT` 的排序稳定性问题
