## 题目

**背景**：限流算法的手写题，面试官要求不只讲思想，还要能写出无定时器的高效实现。

**问**：如何手写一个令牌桶算法？

## 口述答案

> 核心是"按速率补令牌，取到才放行，桶满则丢弃新令牌"。实现上不要起定时器，用惰性计算：状态只有 `tokens` 和 `last_refill` 两个字段，每次请求先算距上次过了多久，应补 `elapsed × rate` 个，取 `min(capacity, tokens + 补充)`，再判断是否够一个，够就扣减放行。这样单次判断 O(1)，没有后台线程，空闲时也不消耗资源。并发下必须保护 `(tokens, last_refill)` 这个二元组的更新，可以用互斥锁，也可以 CAS 循环重试；分布式版本用 Redis 的 Lua 把读、算、写合成原子操作。三个参数：`rate` 是稳态 QPS，`capacity` 是允许的突发量。

## 讲深一层

```cpp
bool allow() {
  auto now = steady_clock::now();
  lock_guard lk(m_);
  double add = duration<double>(now - last_).count() * rate_;
  tokens_ = min(capacity_, tokens_ + add);
  last_ = now;
  if (tokens_ >= 1) { tokens_ -= 1; return true; }
  return false;
}
```
时间必须用单调时钟，`system_clock` 被 NTP 回拨会让 `elapsed` 变负，令牌被倒扣。CAS 版本要把时间戳和令牌数一起更新，否则两个线程各算各的补充量会重复发令牌；锁粒度到单个限流 key 即可，不必全局一把锁。

## 高频追问

1. **令牌桶和漏桶的区别？** —— 令牌桶允许突发（桶里有存货），漏桶强制匀速输出；削峰用漏桶，允许 burst 用令牌桶
2. **capacity 怎么定？** —— 等于能容忍的瞬时突发量，配太大起不到限流作用，配太小则正常波动就被拒
3. **分布式怎么保证公平？** —— Redis + Lua 做单 key 原子更新，key 按用户或接口维度拆，注意别让单 key 成为热点

## 易错点

- 用定时器每秒补令牌——精度差、线程多、空闲时白跑，惰性计算才是标准做法
- 用系统时间算间隔——时钟回拨会导致令牌数异常，必须单调时钟
- 只限 QPS 不限并发——限流管的是速率，线程池和信号量管的是并发数，两者要分开
