## 题目

**背景**：上一轮说用参数哈希做幂等键，面试官指出参数里有个时间戳字段每次都变。

**问**：参数哈希里带了时间戳字段，每次调用哈希都不一样，幂等键就失效了，怎么解决？

## 口述答案

> 不能对全量参数做哈希，要先做语义归一化。剔除不影响副作用的字段：时间戳、trace_id、request_id、随机 nonce，以及顺序无关数组的排列差异；只保留业务主键、金额、目标对象这些真正决定结果的字段。更稳的是用白名单而不是黑名单，新增字段不会悄悄破坏幂等。最彻底的做法是幂等键由调用方按业务语义生成，比如业务单号加操作类型，而不是从参数推导。

## 讲深一层

```python
KEY_FIELDS = ["order_id", "action", "amount", "target_user"]
def idem_key(p):
    norm = {k: p[k] for k in KEY_FIELDS if k in p}
    return hashlib.sha256(
        json.dumps(norm, sort_keys=True, ensure_ascii=False).encode()
    ).hexdigest()
```
坑：金额浮点精度（用分为单位的整数）、字符串大小写、空值 null 与缺省的区分。

## 高频追问

1. **白名单漏了新业务字段怎么办？** —— 新字段上线时强制评审幂等键字段集，加集成测试断言"改该字段键必须变"。
2. **同一请求重放但参数合法变化（比如改金额）？** —— 键应该变，这是两次不同业务；但要防止用改参数绕过限额。
3. **幂等键存哪？** —— Redis SETNX 短期去重 + DB 唯一索引长期兜底，两级都要有。

## 易错点

- 用 `hash(所有参数)` 图省事，加个时间戳就全废
- 用黑名单排除字段，新字段默认参与哈希
- 忽略 JSON 序列化顺序，同一对象哈希出不同值
