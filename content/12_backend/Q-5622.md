## 题目

**背景**：缓存复用聊到并发更新，面试官构造了一个"算得慢、源数据变得快"的时序，问你怎么防脏写。

**问**：如果计算期间原始资料从 v1 更新成 v2，刚算完的旧结果会不会重新污染缓存？你怎样避免？

## 口述答案

> 会，这是一个典型的丢失更新。时序是：读到 v1 开始计算，期间源更新成 v2，计算完成把基于 v1 的结果写回缓存，后面所有请求都命中这个旧结果。避免的核心是让缓存条目带上依赖的源版本，并且写回必须是条件写。具体三层：键里带源内容的 hash，v1 和 v2 天然是两个键，不会互相覆盖；写回前用 Lua 做 CAS，比对当前源版本还是 v1 才允许写，否则直接丢弃；读取时也校验条目里的 source_version 和当前版本，不一致当 miss 处理。版本号用单调递增的字段，不要用时间戳，时钟回拨会出错。

## 讲深一层

写回的条件写示意（Lua 保证原子）：

```lua
if redis.call('GET', src_ver_key) == expected_ver then
  redis.call('SET', result_key, val, 'EX', ttl)
  return 1
end
return 0   -- 源已更新，丢弃这次结果
```

| 手段 | 防的是 |
| --- | --- |
| 键含 content hash | 不同版本互相覆盖 |
| 写回 CAS | 旧结果覆盖新结果 |
| 读时校验版本 | 已存在的脏条目被使用 |

## 高频追问

1. **为什么不干脆算完就删缓存** —— 删了下次还要重算，长任务成本高；CAS 能保留有效结果
2. **同 key 并发重复计算怎么防** —— singleflight 合并，同一键同时只有一个在算，其余等结果
3. **版本号用什么** —— DB 的 version 字段或全局递增序列，别用 `updated_at`，精度和回拨都不可靠

## 易错点

- 只在写完后删缓存 —— 删的是新结果，旧结果早就写进去了
- 用时间戳做版本比较 —— 时钟回拨或同秒并发会判错
- 认为 CAS 能覆盖所有情况 —— 源版本更新和 CAS 之间仍有窗口，要靠读时校验兜底
