## 题目

**背景**：华为嵌入式软件开发岗二面的 C 基础题（一面基础题密集段的典型题型）。考点分两层：「区别」考 API 语义精度——能不能说清两个最常用拷贝函数的终止条件与适用对象差异；「隐患」考安全意识——缓冲区溢出是 C/C++ 安全问题的头号来源，嵌入式岗（内存受限、无 MMU 保护的场景多）尤其看重。只答「strcpy 遇 \0 停、memcpy 按长度拷」是第一层，讲出三个隐患与工程替代方案才算完整。
**问**：strcpy 和 memcpy 有什么区别？strcpy 有什么隐患？

## 口述答案

> 一句话定位：strcpy 复制的是「以 \0 结尾的字符串」，从 src 逐字节拷到 dst，遇到源串的 \0 把它一起拷过去然后停；memcpy 复制的是「n 字节的内存块」，精确拷调用方给的长度，内容是什么、有没有 \0 一概不关心，也不补 \0。
> 区别展开三个维度。第一，终止条件不同：strcpy 的结束由源串内容决定（运行时才确定的 \0 位置），memcpy 的结束由调用方显式给定（n 参数，编译期就能审查）；第二，适用对象不同：strcpy 只能用于 C 字符串，拷二进制数据时中间的 \0 会被当成结尾截断，memcpy 对任意内存（结构体、数组、二进制流、含 \0 的数据）都成立；第三，出错模型相同但都危险：两者都返回 dst 首地址、都没有错误码返回，出问题不是报错而是未定义行为。
> strcpy 的隐患有三个。一是无边界检查导致缓冲区溢出：strcpy 不知道 dst 有多大——数组传参退化成指针，长度信息在函数内不可得，源串比目标缓冲区长就直接写穿，覆盖栈上相邻数据甚至返回地址，这是历史上最经典的漏洞形态；二是 \0 依赖：如果源缓冲是当二进制数据用的、中间没有 \0，strcpy 会一直读越界直到碰巧撞上一个 \0，读多远、写多远都不可控；三是内存重叠未定义：src 与 dst 有重叠时 strcpy 行为未定义（读写交错可能先把 \0 覆盖掉），memcpy 标准同样禁止重叠——重叠场景必须用 memmove，它按地址方向决定拷贝顺序来保证正确。
> 工程上怎么防：优先用带边界的版本——C11 的 strcpy_s/memcpy_s（目标大小作为参数传入，越界可拦截）、strncpy（注意它有一个著名的坑：len 用满时不补 \0，后续读串照样越界，必须手动补）、或者 snprintf(dst, sizeof(dst), "%s", src) 拷字符串最稳；C++ 里直接 std::string 和 std::copy，让容器管边界，不留裸指针拷贝。

## 讲深一层

- 三个隐患的共同根源是一个语言设计事实：C 的字符串长度不是类型信息而是运行时约定（数 \0），且数组传参退化为指针丢失长度——所以「库函数帮你查边界」在 C 里先天做不到，边界责任永远在使用者一侧，这也是 strcpy_s 系列要把 dst 大小显式传进去的原因。
- strncpy 的补 \0 语义要能说准：源串长度 < n 时补 \0 到 n，源串长度 ≥ n 时一个 \0 都不补——「用它就安全」是常见误解，不补 \0 的 strncpy 比strcpy 更隐蔽。
- memmove 与 memcpy 的唯一区别就是重叠处理：memmove 多一次方向判断（可能走逐字节反向拷贝的慢路径），无重叠时两者性能相同——「总是用 memmove 换安全」在性能敏感的热循环里是有代价的，正确做法是保证不重叠时用 memcpy、不确定时用 memmove。
- 嵌入式语境的加分点：无 MMU 的 MCU 上栈溢出写穿没有段页保护兜底，溢出就是直接改写相邻变量或栈帧，所以裸机 C 代码里strcpy 类函数在多数团队的编码规范里是禁用项（MISRA C 也限制），静态检查工具（如 cppcheck 的 bufferAccessOutOfBounds）会直接标红。

## 高频追问

1. strncpy 为什么说它也不安全？——len 用满时不补 \0，拷完的目标串没有终结符，后续 strlen/strcpy 会继续越界；正确用法是手动 dst[n-1]='\0' 或改用 snprintf
2. memcpy 和 memmove 怎么选？——确认不重叠用 memcpy（快），有任何重叠可能用 memmove；重叠时 memcpy 是未定义行为不是「结果可能不对」
3. strcpy_s 相比 strcpy 多了什么？——dstMax 参数让函数能查边界，越界时返回错误并可触发约束处理函数，把未定义行为变成可检测错误
4. 为什么 C 标准不让 strcpy 返回错误码？——历史包袱（K&R 时代签名固定）+ C 哲学「不 为不需要的检查付运行时开销」；改签名会破坏所有存量调用，所以标准委员会走 Annex K 新增安全版本而不是改旧函数

## 易错点

- 只答「一个遇 \0 停一个按长度拷」就停——这是背书不是理解，隐患三个（无边界/\0 依赖/重叠 UB）至少要展开两个
- 说「memcpy 更安全所以都 用 memcpy」——memcpy 同样不查 dst 边界，n 给错照样溢出；安全性来自「长度是显式参数」这一点，不是函数本身
- 忘了重叠问题或把重叠说成「结果不确定」——标准措辞是未定义行为（UB），编译器可以据此做任意优化，后果不可预测
- 不知道任何工程替代方案——strcpy_s/strncpy 的 \0 坑/snprintf/std::string，至少要给出一条，否则像没写过防御性 C 代码
