## 题目

**背景**：多实例部署下需要跨进程互斥，候选人说"用 Redis 加个锁就行"。

**问**：用 Redis 实现分布式锁的标准做法是什么？它会遇到哪些失效场景？

## 口述答案

> 结论：**加锁用一条 `SET key token NX PX ttl`，释放用 Lua 比对 token 再删**，不能先 GET 再 DEL。三个坑：1. **锁过期但业务没跑完**，互斥失效，需要 watchdog 续期；2. **主从异步复制丢锁**，从节点升主后锁不存在，用 fencing token（单调版本号）让存储侧拒绝旧版本写，RedLock 本身也有争议；3. **不可重入**，同线程再次加锁会自锁，需要重入计数。

## 讲深一层

```lua
-- 释放：比对 token，避免删掉别人的锁
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else return 0 end
```
| 失效场景 | 缓解 |
|---|---|
| 业务超时 | watchdog 续期 / 长任务拆分 |
| 主从切换 | fencing token、`WAIT` 同步副本 |
| 客户端 GC 停顿 | 租约 + 版本号校验 |
| 锁被误删 | Lua 比对唯一 token |

## 高频追问

1. **为什么不能 `SETNX` + `EXPIRE` 两条命令？** —— 中间崩溃会留下永不过期的锁；`SET ... NX PX` 是原子的。
2. **RedLock 的问题是什么？** —— 依赖各节点时钟不大幅漂移，且网络分区下仍可能双持锁；Kleppmann 的批评核心是"锁不能提供绝对安全，需要 fencing"。
3. **有没有更简单的方案？** —— 能用数据库唯一索引/行锁/乐观版本号解决的，就别引入分布式锁。

## 易错点

- 用 `DEL` 直接释放，删掉别人续期后的锁
- TTL 拍脑袋设 30 秒，长任务必翻车
- 把锁当成"只执行一次"的保证，忽略它只保证串行
