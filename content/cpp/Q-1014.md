## 题目

**背景**：Agent 岗 2025-2026 年的高频新题，考协议层次感——三个名字天天见，但能把「能力/应用-工具协议/Agent 间协议」三个层次讲清的人不多。
**问**：MCP、Function Call、A2A 怎么区分？接过哪些 MCP 服务，自己手写的话要做哪些事？

## 口述答案

> 三个东西在协议栈里的层次不一样。Function Call 是模型侧的能力：开发者给模型一份工具的 JSON Schema 描述，模型判断该用工具时输出结构化调用请求，执行在应用层完成、结果回填给模型继续推理——它是「模型和你的应用之间」的调用约定，OpenAI、Anthropic 的格式各不相同。MCP 是 Anthropic 开放的应用层协议，标准化「应用怎么接工具和数据源」：宿主应用当 MCP 客户端，每个工具或数据源包成一个 MCP 服务器，走 JSON-RPC 通信，统一暴露 tools（可调用工具）、resources（可读资源）、prompts 三类能力，传输走 stdio 或 HTTP——它解决的是 M 个应用对 N 个工具原本要 M×N 次定制集成的组合爆炸，现在各自实现一次就是 M+N。A2A 是 Google 主推的 Agent 间协作协议：每个 Agent 用 Agent Card 自描述能力，任务以标准生命周期在 Agent 之间委托和汇报，解决跨厂商、跨框架的 Agent 互操作。关系串成一句话：模型用 Function Call 决定调工具，工具通过 MCP 标准化接入，Agent 之间用 A2A 协作——MCP 的工具最终仍靠模型的 Function Call 能力触发。生态里常见的 MCP 服务有文件系统、GitHub、数据库、浏览器自动化（Playwright）、搜索这几类，官方和社区都有现成 server。自己手写 MCP server 要做的事：选传输（本地进程 stdio 最简单）、实现 JSON-RPC 2.0 消息层、处理 initialize 握手做协议版本和能力协商、响应 tools/list 返回每个工具的名字描述和 inputSchema、实现 tools/call 执行并按约定返回内容与错误码；生产上直接用官方 SDK，Python 里一个 @mcp.tool() 装饰器就能把函数暴露成工具，协议细节 SDK 全包。

## 讲深一层

- 协议栈一张图：`模型 ↔(Function Call 约定)↔ 应用 ↔(MCP)↔ 工具服务器`；`Agent ↔(A2A)↔ Agent`——Function Call 严格说是模型输出格式约定，不是独立协议。
- MCP 核心报文序列：initialize（版本/能力协商）→ tools/list → tools/call，JSON-RPC 2.0；2025 年传输层从 HTTP+SSE 演进为 Streamable HTTP。
- A2A 关键对象：Agent Card（托管在 /.well-known/agent.json，发现与能力自描述）、Task（submitted→working→completed/failed 的任务状态机）。
- 手写 server 的头号坑：stdio 模式下日志绝不能打到 stdout——会污染 JSON-RPC 协议流导致客户端解析失败，日志一律走 stderr。
- 工具的 name、description、inputSchema 本质是写给模型的提示词：描述含糊，模型就选错工具、传错参数。

## 高频追问

1. MCP 和 Function Call 谁取代谁？——不冲突也不取代：Function Call 是模型「决定调什么」的机制，MCP 是工具「怎么接进来」的标准，MCP 工具注册后仍以 Function Call 形式喂给模型
2. 什么时候需要 A2A 而不是 MCP？——单 Agent 接工具用 MCP 就够；跨厂商、跨框架把独立 Agent 组队委托任务才是 A2A 的场景
3. stdio 和 HTTP 传输怎么选？——本地工具（文件、脚本）用 stdio 简单安全；远程共享服务、多客户端复用用 HTTP，还要考虑鉴权

## 易错点

- 把 MCP 说成模型的新能力——MCP 完全在应用层，模型感知到的仍只是普通 Function Call 的工具列表
- 三者并列成三种同类协议——层次不同：模型能力（FC）、应用-工具协议（MCP）、Agent-Agent 协议（A2A），混为一谈是最大扣分点
- 手写 server 跳过 initialize 握手——客户端第一步就是版本和能力协商，直接 tools/list 会被断连
