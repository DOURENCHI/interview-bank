## 题目

**面试官问**：为什么类的成员变量要设成私有？全 public 不是更方便吗？

**问**：封装到底解决了什么问题？它和「getter/setter 一大坨」是同一件事吗？

## 口述答案

> 封装解决的是**不变量维护**：类的成员之间有约束（比如"余额不能为负""起止下标必须有序"），如果外部能直接改，这些约束随时可能被破坏，而且出错点离现场很远。
> 但封装**不等于给每个成员配 getter/setter**。如果只是机械地加 `getX/setX`，等于把 public 成员换了个写法，约束仍然没被保护。

## 讲深一层

```cpp
// ❌ 假封装
class Account {
public:
    double balance;                 // 谁都能改成负数
};
class Account2 {
    double balance_;
public:
    double get() const { return balance_; }
    void set(double v) { balance_ = v; }   // 照样能设负数
};

// ✅ 真封装：接口表达业务规则
class Account3 {
    double balance_ = 0;
public:
    double balance() const { return balance_; }
    bool withdraw(double v) {
        if (v <= 0 || v > balance_) return false;
        balance_ -= v; return true;
    }
};
```

| 层次 | 表现 |
|---|---|
| 无封装 | 成员全 public |
| 假封装 | private + 机械 getter/setter |
| 真封装 | 只暴露**操作**，不暴露**状态修改** |

**判断标准**：接口应该是"你能对它做什么"，而不是"它有哪些字段"。`withdraw()` 比 `setBalance()` 表达了更多约束。

**代价**：过度封装会导致接口膨胀、样板代码多。工程上按"有没有不变量要保护"来决定，不是一律 private。

## 高频追问

1. **所有成员都必须 private 吗？** —— 不必。纯数据聚合（struct）可以全 public，只要没有不变量。
2. **`friend` 会破坏封装吗？** —— 会削弱，但它把"允许访问"显式写在类里，比全 public 可控。
3. **什么时候用 struct？** —— 只做数据聚合、没有约束、不需要接口时。

## 易错点

- 认为"加了 getter/setter 就是封装"
- 把 `struct` 和 `class` 的区别理解成"有没有封装"
- 过度封装，接口爆炸
