## 题目

**背景**：字节跳动 AI Agent 三面的分布式一致性场景题。上下文是草稿同步类功能（类似多端文档草稿）：客户端产生草稿 v2、v3 两个版本，请求乱序到达服务端，v3 先到、v2 后到。识别重复靠幂等键能解决（库内 Q-0663 已覆盖），这题考的是下一层：乱序问题——同一实体的多个版本到达顺序错了怎么办。Agent/后端岗都在考，考的是有没有真做过多端同步。
**问**：消息重复可以识别，但顺序乱了怎么办？比如同一草稿先后产生 v2 和 v3，v2 结果却更晚回来？

## 口述答案

> 先定性质：乱序的处理原则是「识别顺序 + 拒绝过期」，核心机制是版本号比较——服务端给每个草稿维护当前已接受的最大版本号，消息带上产生时的版本号，到达时比较：消息版本号大于当前版本号才接受并更新，小于等于则判定为过期消息，丢弃或返回冲突。v3 先到把版本推进到 3，v2 再到时 2 < 3，直接拒绝，草稿不会被旧版本覆盖。这个模式和 TCP 的序列号、数据库的 MVCC 版本链、Git 的 commit 链是同一个思想：用单调递增的版本号给事件定全序。
> 版本号从哪来有讲究。最简单是服务端单点发号：每次写入原子递增，天然单调，但客户端离线时拿不到号。多端并发编辑场景（同一草稿两个端各自产生 v3）版本号会撞，这时两层处理：第一层，版本号相同的冲突对「先到先得 + 后到返回 409 冲突」，客户端感知冲突后基于服务端最新版本重做（乐观锁语义，类似 HTTP If-Match）；第二层，如果业务要求合并而不是二选一（草稿场景两边改动都要保留），要上 CRDT 或 OT 这类多端合并算法——Google Docs 的 OT、Figma 的 CRDT 都是为「无中心仲裁的并发编辑」设计的，它们能保证各端按不同顺序收到相同操作集，最终收敛到同一状态。
> 工程上还要处理三个细节。一是版本号的持久化与原子性：版本比较和更新必须在一个原子操作里完成（数据库的 UPDATE WHERE version = old_version 或 Redis Lua），否则并发请求会双双通过比较造成覆盖。二是乱序窗口的存在期：请求超时重试是乱序的主要来源，客户端重试旧请求前应携带最新版本号，服务端靠版本号兜底，不依赖网络保序。三是消费侧的顺序语义：如果草稿更新还要扇出到搜索索引、推荐特征等下游，要么下游按版本号做同样的过滤，要么上游用分区（按草稿 ID 分区）保证同一实体走同一条队列保序——Kafka 同分区内有序就是这个原理。
> 最后补充答案边界的判断：如果业务只是「保存最新草稿」，版本号比较就够了，CRDT 是杀鸡用牛刀；只有「多端并发编辑且都要保留」才需要合并算法。面试先给最简可行方案再谈升级路径，比上来就堆 CRDT 术语更可信。

## 讲深一层

- 版本号全序的适用前提是「写入方对该实体的版本演化有共识」：单用户多端或服务端发号都满足；完全对等的多写方（如协同编辑）无法预先统一版本号，才需要向量时钟（能检测并发但不能定序）或 CRDT（数学上保证收敛）——三级工具按冲突容忍度递进选用。
- 数据库层的对应物：乐观锁（version 列 + UPDATE WHERE version=N）就是消息层版本号比较的关系型实现；面试能把「消息乱序处理」和「数据库乐观锁」接上，说明理解的是同一个并发控制原理而非孤立技巧。
- 幂等与乱序是正交的两个问题但常被一起考：幂等键解决「同一条消息到达多次」（去重），版本号解决「多条消息到达顺序错」（定序）；生产代码通常一个表里同时做（唯一键去重 + 版本列拒旧），设计时分开想、实现时一起落。
- Agent 场景的变体：Agent 的工具调用结果、多轮对话状态同步同样会遇到乱序回包（并行工具调用完成顺序不定），解法相同——每个状态更新带轮次/步骤序号，落盘前比较拒绝过期更新，这个迁移能力是大模型应用岗的加分答法。

## 高频追问

1. 版本号撞了（两个 v3）怎么办？——先按「先到先得、后到 409」仲裁，客户端带最新版本重试；业务要求保留双方改动再上 CRDT/OT；大多数业务场景二选一就够，先简后繁
2. 为什么不用时间戳定序？——多机时钟不可信，NTP 有毫秒级误差且可能回拨，两个端的「先后」用物理时间判不准；逻辑时钟（版本号/Lamport 时间戳）才是可靠全序，物理时间只能做辅助排序
3. 下游消费怎么保序？——按实体 ID 分区（同一草稿的消息进同一队列分区，分区内天然有序），或下游同样做版本号过滤；跨分区无顺序保证是所有消息队列的通识

## 易错点

- 只答「用消息队列就有序」——MQ 只保证分区内有序，跨分区、重试、多生产者都会乱序；把保序责任全推给中间件暴露没处理过真实乱序
- 忽略「比较与更新要原子」——版本号检查通过后写入前被并发请求插队，旧版本照样覆盖；不说原子性（乐观锁 SQL 或 Lua）等于方案有并发漏洞
- 上来就 CRDT——草稿保存类需求版本号就够，CRDT 复杂度高且合并语义不一定是业务想要的；不问业务语义直接上重武器是典型的过度设计信号
