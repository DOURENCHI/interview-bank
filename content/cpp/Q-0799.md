## 题目

**背景**：百度 Apollo 车载软件三面的体系结构题——多核 cache 一致性（MESI）与对写代码的影响。考点三层：协议本身（四状态与迁移触发）、实现机制（总线嗅探/目录）、工程影响（伪共享、内存屏障需求、volatile 的真实边界）。这是多核嵌入式/自动驾驶域控（多核 SoC）岗位的高频题，答出「协议 + 影响」两层才算完整；只背四状态名不谈代码影响，会被第二问直接打穿。
**问**：多核之间怎么保证 cache 一致性，对你写代码有什么影响？

## 口述答案

> 先讲问题为什么存在：每个核有私有 L1/L2 cache，同一内存行可能在多核 cache 里各有一份副本；核 A 写了它的副本，核 B 读自己那份旧副本就出错——硬件必须让所有核看到一致的值，这就是 cache 一致性问题。
> 主流答案是 MESI 协议。每个 cache 行四个状态：Modified（本核改过，内存里是旧的，其他核没有有效副本）、Exclusive（只有本核缓存且与内存一致）、Shared（多核都有且与内存一致）、Invalid（失效不可用）。工作方式是总线嗅探：核 A 要写一个 Shared 状态的行时，发 Invalid 消息，其他核嗅探到后把自己的副本置 Invalid 并回应，A 才升级为 Modified 独占写入——写操作通过「先失效别人」保证任何时刻只有一个核能写同一行。写回时机上，Modified 行被其他核读时要先写回内存再降级 Shared。
> 对写代码的影响是面试的胜负手，说四条。第一，volatile 不解决一致性问题——MESI 保证的是硬件层面的单变量最终一致，volatile 解决的是编译器优化（不缓存到寄存器），多线程的逻辑正确性（如「读-改-写」原子性）MESI 管不了，还是要原子指令/锁。第二，伪共享（false sharing）是性能杀手：两个无关变量在同一 64 字节 cache 行上，两核各写各的也会互相失效对方副本，行在核间弹跳，性能可差一个量级；对策是关键写变量按 cache line 对齐/隔离（alignas(64) 或填充）。第三，MESI 只保证单变量的可见性顺序，多变量的顺序语义需要内存屏障——store buffer/invalid queue 让写不是立即全局可见（缓冲旁路了嗅探），所以 x86 有较强的 TSO 模型、ARM 是弱内存模型，跨核标志位配对必须用屏障或 C++ 的 memory_order（acquire/release）。第四，DMA 外设数据不走核 cache，要显式 invalidate/clean（嵌入式司机题，CAN DMA 收包先 invalidate cache 才能读到新数据）。

## 讲深一层

- MESI 的性能痛点是写共享数据：Shared→Modified 要广播失效并等应答，写一个被多核读的热变量比写私有变量慢得多——这是「共享可变状态是并发性能敌人」的硬件根源，设计上尽量私有化数据再合并结果。
- store buffer 解释了屏障为什么必要：核把写先放进 store buffer 就继续跑（避免等应答），其他核暂时看不到；x86 的 TSO 模型只允许 store-load 重排、ARM 弱模型四种都允许——同一份无同步代码在 ARM 域控上比 x86 更容易翻车，跨平台并发代码必须走标准内存模型而不是踩平台运气。
- 伪共享的定位方法：perf c2c 或 cachemiss 事件直接定位跨核行争用；多线程计数器数组、并发的标志位结构体是高发区——「代码没改却慢了，换核数反而更慢」的经典症状。
- 目录协议与嗅探的取舍：核少（≤16）嗅探广播可接受，核多（服务器/大 SoC）用目录（snoop filter）减少广播；车载域控 8 核 A78 仍是嗅探为主，知道扩展性问题即可。
- 与锁的关系：mutex/unlock 内含屏障与原子交换（MESI 层面的独占获取），锁保护的是逻辑临界区；「volatile + 忙等」既缺原子性又缺顺序性，两个维度都要靠同步原语——这是把 volatile、MESI、屏障三者关系说圆的关键。

## 高频追问

1. MESI 四个状态迁移各在什么时候发生？——写 Shared 行：广播 Invalid 自己升 M；读别人 M 的行：对方先写回内存双方降 S；自己 M 被别人读：写回降 S；嗅探到失效：自己降 I
2. volatile 和 MESI 分别解决什么？——volatile 挡编译器寄存器缓存（语言层可见性），MESI 挡多核私有 cache 旧值（硬件层一致性）；逻辑原子性与跨变量顺序两者都不管
3. 什么是伪共享，怎么修？——无关变量同 cache 行导致行在核间弹跳；按 64 字节对齐隔离或填充，用 perf c2c 验证
4. 为什么还需要内存屏障？——store buffer/invalid queue 让写延迟全局可见，MESI 的「最终一致」不含顺序保证；acquire/release 或显式屏障建立跨变量的先后关系
5. DMA 和 cache 一致性怎么处理？——DMA 不经过核 cache，收包前 invalidate 该区域、发包前 clean；或用一致 DMA 内存（coherent pool/CMA）

## 易错点

- 把 volatile 说成「保证多核一致性」——MESI 是硬件层、volatile 是编译器层、原子性是第三件事，三者混为一谈是多核题最常见翻车点
- 只背四状态名不迁移条件——面试官追问「Shared 状态怎么变成 Modified」考的就是嗅探广播机制，背不出过程等于没懂
- 不知道伪共享——写代码影响这一问的默认考点，「知道 MESI 但不知道 false sharing」等于只看过协议图没写过并发代码
- 忽略 ARM 与 x86 内存模型差异——车载域控是 ARM，弱内存模型下屏障要求更严格，答出这层说明真做过跨核开发
