## 题目

**场景**：禾望电气嵌入式面经的驱动段：ioctl 收到用户态传来的一个指针，内核能不能直接用；另一家未注名公司也从「用户态程序和内核驱动怎么交互」问到了数据怎么安全跨界。

**问**：用户态传来的指针，内核能直接解引用吗？正确的做法是什么？

## 口述答案

> **不能，这是内核安全的底线**。用户态传进来的只是一个虚拟地址值：它可能指向未映射页、可能已被换出、也可能是**恶意构造的内核地址**——直接解引用等于把内核的读写权交给用户任意支配：踩坏地址就 oops，32 位下用户地址能落进内核空间更是提权漏洞。而且用户页随时可能被另一线程 munmap，时序完全不可控。
>
> 正确路径是 **copy_from_user / copy_to_user**（简单类型用 get_user/put_user）：内部先用 **access_ok** 检查地址范围在用户空间内，再把访问包进**异常表（extable）**——真踩到未映射页时走缺页处理，把失败转成「返回未拷贝的字节数」而不是内核崩溃；缺页时可能睡眠换页进来。所以注意两点：**返回值是「剩余未拷贝字节数」，0 才是成功**；copy 类函数可能睡眠，**自旋锁/中断上下文里不能调**。
>
> 全景：用户态和内核交换数据，小数据走 read/write，控制命令走 ioctl（结构体 copy_from_user），大块数据走 mmap（内核缓冲直接映射给用户，零拷贝），异步通知走 netlink/procfs/sysfs。共同原则：**跨界数据必须经内核检查和搬运，不裸奔**。

## 讲深一层

```c
ssize_t my_read(struct file *f, char __user *ubuf, size_t n, loff_t *ppos)
{
    if (*ppos >= sizeof(msg))
        return 0;                              /* 读到文件尾 */
    n = min(n, sizeof(msg) - (size_t)*ppos);
    if (copy_to_user(ubuf, msg + *ppos, n))    /* 返回未拷贝字节数，非 0 即失败 */
        return -EFAULT;
    *ppos += n;
    return n;                                  /* 返回实际拷贝字节数 */
}
```

**判断技巧**：答「能不能直接用」要给三层——地址不可信（用户构造）、页不可靠（随时缺页/被换出）、机制怎么兜底（access_ok + 异常表 + 缺页处理）。**记忆锚点**：「用户指针只是个数值；跨界搬运只能 copy_from_user，返回 0 才算成」。

## 高频追问

1. **copy_from_user 为什么不能在中断里用？** —— 缺页处理可能睡眠（换页/IO），中断上下文禁止睡眠；中断里先把数据存内核缓冲，再由下半部/工作队列转给用户。
2. **access_ok 检查过了就安全吗？** —— 不够。它只验「范围在用户空间内」，不保证页已映射；真正的兜底是异常表 + 缺页机制，两个机制缺一不可。
3. **SMAP 是干什么的？** —— CPU 硬件特性，禁止内核态直接访问用户页，误用裸指针直接 fault——硬件层面强制你走 copy 类函数。
4. **mmap 方式和 copy 方式怎么选？** —— 大流量低拷贝选 mmap/DMABUF（一帧图像多拷一次都嫌贵）；小配置、命令用 ioctl + copy_from_user，简单可控。

## 易错点

- 把 copy_from_user 返回值当 -1/错误码——它返回未拷贝字节数，非 0 即失败。
- 在自旋锁临界区里调 copy_from_user——可能睡眠，有死锁风险。
- 只做 access_ok 检查就放心用——检查不等于搬运，缺页还得异常表兜底。
- 把内核缓冲地址直接写回用户结构体——内核地址泄露，用户态也用不了。
