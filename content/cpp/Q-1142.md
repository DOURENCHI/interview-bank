## 题目

**背景**：拼多多软件研发二面的网络基础题。原帖题面因防屏蔽把 HTTPS/HTTP 拆成了乱码字，此处已还原。考的不是「HTTPS 更安全」一句空话，而是能不能列出它在 HTTP 之上具体多做了哪几件事：TLS 握手、证书验证、混合加密、完整性校验，外加默认端口与代理行为差异。答得全且有序，说明真懂 TLS 的分层结构。
**问**：HTTPS 相比 HTTP 具体多做了哪些事情？

## 口述答案

> 我按一次请求的生命周期把「多做的事」串起来。第一件：建连阶段多了一次 TLS 握手——TCP 三次握手之后，客户端和服务端还要协商 TLS 版本和密码套件、交换密钥材料；TLS 1.2 要两个 RTT，TLS 1.3 压到一个 RTT，还能靠会话复用（session ticket/PSK）进一步省往返。第二件：服务端要证明自己——下发证书，客户端验证信任链（证书是不是受信 CA 逐级签发）、域名匹配、有效期、吊销状态（CRL/OCSP）；没有这一步，加密只是把密文加密给了中间人，认证是加密有意义的前提。第三件：数据传输改用混合加密——握手阶段用非对称算法（RSA 或 ECDHE）协商出对称会话密钥，之后的应用数据全部用对称加密（AES-GCM 这类）收发；只用非对称太慢扛不住流量，只用对称又没法安全地把密钥送到对方手里，所以是「非对称换密钥、对称传数据」。用 ECDHE 还有前向安全：每次会话的密钥由临时参数算出，服务器私钥将来泄露也解不开历史流量。第四件：完整性校验——每条记录带认证标签（MAC/AEAD），内容被篡改、乱序、重放都会校验失败直接断连。这四件加起来，防窃听、防篡改、防冒充三个目标才凑齐。
> 再补两个工程差异：默认端口从 80 变 443；代理和 CDN 看不到明文只能按域名（SNI）转发，缓存行为也变了——所以 HTTP 迁 HTTPS 要配 HSTS、301 和证书自动续期（ACME 这类），这些是实际干活真会碰的。

## 讲深一层

- 「非对称换密钥、对称传数据」是 HTTPS 骨架；ECDHE 与 RSA 密钥交换的本质区别是前向安全——RSA 私钥泄露可解历史流量，ECDHE 不能。
- 证书验证四要素：信任链、域名、有效期、吊销状态；很多客户端 SDK 默认不校验证书，这是真实漏洞高发点——「HTTPS 就安全」只对浏览器成立。
- TLS 1.3 关键变化：握手 1-RTT、0-RTT 复用（有重放风险，只用于幂等请求）、删掉 RSA 静态密钥交换和一批弱套件。
- 中间人仍能看到 SNI（域名）和 IP，流量分析没死；ECH（加密 SNI）是后续演进方向——「HTTPS 等于完全不可见」是误解。

## 高频追问

1. 为什么不全程非对称加密？——慢一到两个数量级，会话全程做非对称运算服务器扛不住；对称快但密钥分发需要非对称护航
2. 中间人伪造证书会怎样？——信任链验证失败直接报错拦截；用户点「继续访问」等于自己放弃认证
3. TLS 握手的往返能省吗？——会话复用（session ticket）、TLS 1.3 的 PSK/0-RTT、QUIC 把 TLS 1.3 内嵌进建连实现 1-RTT 起流

## 易错点

- 只答「HTTPS 是加密的 HTTP」——没拆出握手/证书/混合加密/完整性四件事，是背标语不是懂原理
- 说「HTTPS 用非对称加密传输数据」——非对称只在握手换密钥时用，数据全是对称加密
- 漏了证书验证——只加密不认证，等于把密钥当面交给中间人
- 被追问「TLS 握手几次往返」答不上——1.2 是 2-RTT、1.3 是 1-RTT，这是基本功
