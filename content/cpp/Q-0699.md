## 题目

**现象**：一个模板相关的编译错误，终端刷出 300 行，第一行是 `In file included from /usr/include/c++/11/vector:66`，真正的原因埋在中间。

**问**：g++ 的报错信息该怎么读？怎么快速定位真正的错误？

## 口述答案

> **从下往上读**。真正的原因在最后几行的 `error:` 之后，前面的 `In file included from`、`required from`、`In instantiation of` 都是**上下文链**，告诉你"这个错误是怎么被引出来的"。
> 先搜 `error:` 关键字跳过所有 `note:` 和模板展开噪音，是最快的办法。

## 讲深一层

```bash
g++ main.cpp 2>&1 | grep -n "error:" | head        # 只看错误行
g++ main.cpp -fmax-errors=3                        # 限制错误数，先修前三
g++ main.cpp -ftemplate-backtrace-limit=0          # 模板展开链全打印（默认截断）
g++ -E main.cpp | less                             # 看预处理结果
```

典型结构：
```
In file included from a.h:1,
                 from main.cpp:2:      ← 包含链
/usr/include/.../vector:66: note: ...  ← 库内部触发
main.cpp:10:5: error: no matching function for call to 'f(int)'   ← 真正的错误
main.cpp:10:5: note: candidate: 'void f(std::string)'             ← 候选说明
```

| 关键词 | 含义 | 优先级 |
|---|---|---|
| `error:` | 真正的错误 | **先看这个** |
| `note:` | 补充说明（候选函数、模板参数） | 次看 |
| `In file included from` | 包含链 | 可忽略 |
| `required from` | 模板实例化链 | 追到自己的代码为止 |

**模板错误的读法**：从 `required from` 链里找**最后一个指向你自己代码的行**，那才是问题所在，再往下的 `note:` 解释为什么不行。

**减少噪音的手段**：C++20 concepts 能让错误在调用点就报清楚；拆小模板、少嵌套也能显著改善。

## 高频追问

1. **`-fmax-errors` 有什么用？** —— 一个错误可能引发几十个连锁错误，限制数量能先看根因。
2. **`-fsyntax-only` 呢？** —— 只做语法检查不生成代码，改代码时验证快。
3. **链接错误怎么读？** —— `undefined reference to 'xxx'` 是符号缺失，看 `c++filt` 还原后的名字，查库路径和顺序。

## 易错点

- 从第一行开始读，被模板展开淹没
- 看到库头文件就以为库有问题
- 不区分 `error:` 和 `note:`，把候选说明当成错误
