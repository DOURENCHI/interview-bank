## 题目

**场景**：业务跑了一年，核心表上了千万行，运营反馈列表页越翻越慢，要给出系统性的优化方案。

**问**：数据库数据越来越多查询变慢，如何优化查询速度？

## 口述答案

> 第一步永远是**定位**：开慢查询日志抓 Top SQL，`EXPLAIN` 看执行计划——重点看 type 是不是 ALL（全表扫）、扫描行数 rows、有没有用上索引。大部分慢查询到这一步就现形了。
> 然后是最常见的三板斧：一是**建对索引**——给 WHERE、ORDER BY、JOIN 列建，联合索引注意**最左前缀**，尽量**覆盖索引**免回表；二是**改写 SQL**——不写 `SELECT *`、深分页别用大 OFFSET（改游标或延迟关联）；三是**加缓存**——热点结果放 Redis，注意失效策略。
> 索引和改写都到顶了再动架构：**读写分离**、**冷热分离/归档**、**分库分表**，必要时反范式冗余减少 JOIN。顺序不能反——先 SQL 后架构，架构改造成本高得多。

## 讲深一层

```text
排查链: 慢日志 → EXPLAIN 看 type/rows/key
  type=ALL 全表扫 · Using filesort 排序未走索引 · rows 大命中少 区分度低
索引失效: 列上函数/运算 · 隐式类型转换 · 前导% LIKE · OR 混无索引列
深分页: LIMIT 1000000,10 → WHERE id > 上次最大id LIMIT 10 (游标式)
```

| 手段 | 成本 | 适用 |
|---|---|---|
| 建索引/覆盖索引 | 低 | 首选，见效最快 |
| SQL 改写 | 低 | 深分页、SELECT * |
| 缓存 | 中 | 读多写少的热点 |
| 分库分表/归档 | 高 | 单表数据量到千万级以上 |

**判断技巧**：先 EXPLAIN 再动手——九成慢查询是「没走索引」或「回表太多」；区分度太低的列（如性别）建索引意义不大，别无脑加。

## 高频追问

1. **索引为什么快？** —— B+ 树把全表 O(N) 变成树查找 O(logN)，叶子层还能顺序读磁盘页。
2. **为什么深分页慢？** —— OFFSET 要扫过并丢弃前 N 行；用游标（记录上次最大 id）或先查 id 再关联。
3. **索引是不是越多越好？** —— 不是，每个索引都拖慢写入并占空间，按查询模式建。

## 易错点

- 上来就说加索引，不做 EXPLAIN 定位
- 联合索引把区分度低的列放最前，违反最左前缀
- 只优化读不考虑写放大——索引是有代价的
- 深分页靠 OFFSET 硬翻页
