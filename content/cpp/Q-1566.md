## 题目

**场景**：原力灵机嵌入式面经的第一问：芯片手册里外设寄存器地址是 0x4002xxxx 这样的物理地址，为什么内核代码不能直接拿来读，一定要先 ioremap——考的是 MMU 和设备内存映射的理解。

**问**：ioremap 解决什么问题？为什么内核不能直接解引用外设寄存器的物理地址？

## 口述答案

> **根因是 MMU**：内核态和用户态一样跑在虚拟地址上，代码里写的地址都是虚拟地址；而外设寄存器住在**物理地址空间**（芯片手册里的 0x4002_0000 之类）。**不建映射直接解引用，访问的是一个毫不相干的虚拟地址**——要么踩到别的内存，要么缺页触发 oops。`ioremap(phys, size)` 向内核申请页表映射，把这段物理地址映射成**内核虚拟地址**返回，之后才能通过返回值访问寄存器。
>
> 访问方式有讲究：不要拿到指针就 `*p = x`。**用 readl/writel（及 readb/writeb）这类访问器**——它们自带 volatile 防止编译器优化掉访问、带内存屏障保证先后顺序、处理端序；现代驱动配合 `__iomem` 注解，让 sparse 静态检查帮你抓「裸解引用」。
>
> **映射页的 Cache 属性必须是 nocache（设备内存）**：寄存器的值由硬件随时改，走 Cache 会读到过期数据，写也可能被合并、延迟发出——这对「读清标志位」「先写数据再置使能」这类时序敏感操作是致命的。ioremap 默认就按 device/uncached 属性建映射，别自己画蛇添足开 Cache。

## 讲深一层

```c
void __iomem *base = ioremap(0x40020000, 0x1000);
if (!base)
    return -ENOMEM;                    /* 映射可能失败，必须判空 */

u32 val = readl(base + REG_STATUS);    /* 带 volatile/屏障语义的访问器 */
writel(val | BIT(0), base + REG_CTRL);
iounmap(base);                         /* 卸载时释放映射 */
```

| 错误做法 | 后果 |
|---|---|
| `*(u32 *)0x40020000` 直接读 | 解引用的是无关虚拟地址，踩内存或 oops |
| 映射后用 `*p` 裸读写 | 编译器重排/合并，Cache 读到脏值 |
| 把映射后的内核地址传给用户态 | 内核地址泄露，用户态也访问不了 |

**记忆锚点**：「MMU 开着，手册地址是物理的；ioremap 换回内核虚拟地址，readl/writel 带屏障，映射天然 nocache」。

## 高频追问

1. **ioremap 和 mmap 的区别？** —— 都建虚拟→物理映射，但 ioremap 在内核空间映射设备内存（uncached），mmap 主要在用户空间映射文件/匿名内存（cached）；字符设备的 mmap 实现里常内部调 io_remap_pfn_range 把寄存器暴露给用户态。
2. **为什么必须检查返回值？** —— ioremap 可能失败（参数非法/映射区耗尽）返回 NULL，直接解引用就是空指针 oops。
3. **devm_ioremap_resource 好在哪？** —— devm 资源管理版：probe 里一次拿到 reg 资源 + 映射，remove 或 probe 失败时自动 iounmap，防忘释放。
4. **读写寄存器为什么需要屏障？** —— CPU 与总线可能乱序合并写；readl/writel 内置屏障，保证「先写配置寄存器再置使能位」这类顺序不被打乱。

## 易错点

- 把芯片手册的物理地址直接强转指针用——MMU 开着，那是误闯虚拟地址空间。
- ioremap 后用 `*p` 裸读写——绕过访问器丢了屏障和 volatile，偶发玄学问题。
- 想给寄存器映射「开 Cache 提速」——设备内存必须 nocache，开了读脏数据。
- iounmap 忘调或时机错——映射泄漏，驱动反复 probe 就崩。
