# Q-1570 Linux 的文件描述符（fd）是什么？和 FILE* 有什么区别？

## 口述答案

**fd 是「进程打开文件表」的下标**，一个小非负整数——不是指针，是数组索引。进程每 open 一个文件，内核在它的**文件描述符表**里从 0 开始找**最小空位**放表项，把这个下标返回给用户。所有系统调用（read/write/close/epoll）都拿这个整数当句柄。

三层结构要能画出来：
```
进程A fd表          系统打开文件表            inode
[0] ──┐
[1] ──┼──> entry(偏移量/标志/引用计数) ──> 文件
[2] ──┘        ↑
进程B fd表 ────┘  （fork/dup 让不同 fd 指向同一 entry，共享偏移量）
```
- **fd 表**：每进程私有，下标即 fd；
- **打开文件表**：系统级，存**当前偏移量**和状态标志——同一 entry 的两个 fd **共享读写位置**；
- **inode**：真正的文件。

**0/1/2** 是约定俗成的 stdin/stdout/stderr，进程一创建就由 shell 接好。

**fd vs FILE\***：fd 是**系统调用层**的裸句柄（int，无缓冲，每次 read 都是真实系统调用）；`FILE*` 是 **C 标准库**在 fd 外面包的**带缓冲流**（结构体里有缓冲区、错误标志、位置指针），fwrite 攒够缓冲才 write。混用时记得 fflush，否则顺序错乱。

**锚点：fd 是下标不是指针，0/1/2 生而就有，FILE* 是带缓冲的包装。**

## 讲深一层

| 问题 | 答案 | 为什么 |
| --- | --- | --- |
| 为什么新 fd 总是最小空位 | 内核线性找第一个空槽 | 这正是**重定向的原理**：close(1) 后 open 文件 → 拿到 1 → printf 全进文件；dup2 就是在做这件事 |
| fork 后 fd 怎么样 | 子进程**复制 fd 表**，指向同一打开文件表项 | 父子共享偏移量——这是 Q-1506 里「fork 后日志不乱」的底层 |
| ulimit -n 是什么 | 每进程 fd 数量上限（历史默认 1024） | 超了 open 返回 EMFILE；长跑服务/高并发必调 |
| fd 泄漏 | open/accept 后忘 close | 长跑进程 fd 涨满，之后所有 open 失败——「跑几天就挂」的经典原因 |
| 查看进程 fd | `ls /proc/<pid>/fd` | 排查泄漏第一现场；socket/pipe/eventfd 都占 fd |

## 高频追问

1. **socket 是 fd 吗？** —— 是。Linux「一切皆文件」的落地就是 socket/pipe/eventfd/signalfd 都统一占 fd，所以 epoll 能统一监听所有 I/O（Q-1201）。
2. **dup 和 dup2 干嘛的？** —— 复制 fd 到指定槽位（原子重定向）；CGI/守护进程接管 stdio 的标准手法。
3. **write(1, ...) 和 printf 输出顺序为什么会乱？** —— printf 走 FILE* 缓冲（攒着），write 直达内核；不 fflush 时两个通道的「时间线」不同步。重定向到文件时 stdio 变全缓冲，顺序差异更明显。
4. **fd 和文件偏移量的关系？** —— 偏移量在**打开文件表项**里，不在 fd 里也不在 inode 里：两个 fd 指同一 entry 则共享偏移；各自 open 同一文件则各有一个 entry、偏移独立。
5. **一次进程最多多少 fd？怎么改？** —— 软限 `ulimit -n`（shell 里改）/setrlimit，硬限 /proc/sys/fs/file-max；生产环境把 nofile 提到 10 万级很常见。

## 易错点

- 说「fd 是指向文件的指针」——它是**下标**；指针说法在追问「fork 后会怎样」时立刻露馅。
- 以为每个 fd 独立偏移量——共享的是 entry；这正是「共享偏移」追问的区分点。
- FILE* 和 fd 混用不 fflush，输出顺序错乱后怀疑「内核丢数据」。
- 忘了 0/1/2 已被占用——测试代码里 close(1) 后 printf 消失，还以为缓冲问题。
