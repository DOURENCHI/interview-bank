## 题目

**场景**：并发入门必考题，但「背模板」和「懂原理」在两个追问上当场分层：为什么 while？notify 在锁内还是锁外？

**问**：mutex + 条件变量 + 队列实现生产者-消费者，写出骨架，并解释 while 判断和 notify 位置的原因。

## 口述答案

> 骨架四件套：**互斥锁护队列、两个条件变量（不满/不空）、wait 前用 while 判条件、改完状态再 notify**。
>
> **while 而不是 if，三个理由**：①**虚假唤醒**——底层 futex/wakeup 允许无 notify 也醒，if 直接往下走就把空队列当有货用了；②**唤醒 ≠ 条件成立**——notify 只说「条件可能变了」，从醒到重新拿锁之间，别的消费者可能已经把最后一个元素拿走，条件又被改回去了；③**广播竞争**——notify_all 唤醒 N 个线程，名额只有一个，输家必须回 while 继续等。一句话：**条件变量不保存条件，醒来必须重新查**。
>
> **notify 位置**：正确性上锁内锁外都对（wait 返回时本来就要重新竞争锁）；性能上**锁外 notify 更好**——锁内 notify 会让刚醒的线程立刻在锁上阻塞，白做一次「叫醒又按住」（hurry up and wait）。但**退出场景例外**：必须先置停止标志（锁内）再 notify，保证等待方一定能看到标志。
>
> **wait 的原子性**：`cv.wait(lock, pred)` 等价于 `while(!pred) wait(lock)`——wait 内部「解锁 + 挂起」是原子的，不存在「检查完条件、还没挂起就被 notify、唤醒信号丢失」的窗口；这个丢失唤醒问题正是自己用 flag 轮询写不出来的原因。

## 讲深一层

```cpp
std::mutex mtx;
std::condition_variable cv_not_full, cv_not_empty;
std::queue<int> q;
const size_t CAP = 16;
bool stopped = false;

void producer(int v) {
    std::unique_lock lk(mtx);
    cv_not_full.wait(lk, [] { return q.size() < CAP || stopped; });
    if (stopped) return;
    q.push(v);
    lk.unlock();                  // 锁外 notify：被唤醒者不必立刻再阻塞
    cv_not_empty.notify_one();
}

int consumer() {
    std::unique_lock lk(mtx);
    cv_not_empty.wait(lk, [] { return !q.empty() || stopped; });
    if (q.empty()) return -1;     // stopped 且队列空
    int v = q.front(); q.pop();
    lk.unlock();
    cv_not_full.notify_one();
    return v;
}
```

| 写法 | 后果 |
|---|---|
| `if` 判条件 | 虚假唤醒/竞争失败后直接操作非法状态 |
| 只用一个 cv | 生产者消费者互相当醒，吞吐抖动，还容易漏醒 |
| 锁内 notify | 正确但被唤醒者立刻撞锁，白白排队 |
| wait 不带谓词手写 | 漏写循环=丢唤醒窗口，谓词版最稳 |

**判断技巧**：写完骨架主动报三个设计点（while、双 cv、锁外 notify）再让面试官挑，比被动追问体面。**记忆锚点**：「条件不保存，醒来再查一遍；叫人下锁外叫，散伙先立牌」。

## 高频追问

1. **notify_one 还是 notify_all？** —— 单名额配对用 one；状态变化影响所有人（如停止、容量变大）用 all；拿不准用 all，代价是无谓唤醒。
2. **和信号量（semaphore）实现的差别？** —— 信号量把「名额计数」做进原语（C++20 `counting_semaphore`），队列空/满各一个信号量即可，不用手写谓词；条件变量更通用，但条件逻辑要自己维护。
3. **生产者和消费者是多个时还有什么坑？** —— 唤醒风暴（惊群）：广播后大量线程抢一个名额；高并发场景改用每线程本地队列 + 批量窃取，或内存池化减少锁竞争。
4. **C++20 有什么改进？** —— `condition_variable_any` 配 `stop_token` 支持协作取消；`jthread` 析构自动 join，退出语义比手写标志位干净。

## 易错点

- 用 if 判条件——虚假唤醒当场翻车，这是本题第一杀。
- 一个条件变量管两个方向——漏唤醒和惊群都来了。
- notify 忘了在状态变更之后——先 notify 后改状态等于白叫。
- 退出流程不置标志只 notify——等待方醒来条件仍不满足，永远等下去。
