## 题目

**背景**：字节火山引擎后端一面的工程实践题。它比「内存泄漏怎么排查」多了一个后置环节——**解决后怎么复测**，这是区分「看过工具文档」与「真修过线上泄漏」的分水岭：前者答到 Valgrind/pprof 就停，后者能讲出修复验证的完整闭环（同场景回归、长稳、工具复验、监控兜底）。排查部分与库内 Q-0635（泄漏产生机理）互补：那卡讲「为什么泄」，这卡讲「怎么定位、怎么修、怎么证明修好了」。
**问**：讲讲内存泄漏的解决？解决后怎么复测？

## 口述答案

> 按「确认—定位—修复—复测」四段讲。先说**确认与定位**：泄漏的典型症状是进程 RSS 单调上涨、GC 后不回落（托管语言）、最终 OOM；确认泄漏后定位分语言取工具——C/C++ 用 AddressSanitizer（编译期插桩，退出时 LeakSanitizer 直接报泄漏栈）或 Valgrind memcheck（无需重编译，慢但准），长跑服务配堆快照 diff；Go 用 pprof 的 heap profile——间隔几分钟抓两份做 diff，看哪类对象只增不减，再顺着 retained-by 引用链找谁攥着不放，goroutine 泄漏（阻塞在没消费的 channel/锁）用 goroutine profile 看 goroutine 数是否只涨不跌；Java 用 jmap dump + MAT 看 GC Roots 到泄漏对象的引用链。
> 然后**修复**，按根因分类落刀：忘了释放/配对删除（补释放路径，特别是不抛异常路径与早返回路径也要释放——RAII/defer 是结构性解法）；引用被无意攥住（全局 map 缓存只增不删——加 TTL 或 LRU 淘汰；监听器/回调注册后未注销——补注销；Go 里 goroutine 引用外层对象导致对象集滞留）；循环引用（C++ 智能指针 shared_ptr 互指改 weak_ptr 打破环）；持有无界集合（切片/map 持续 append 不清理——定容量+淘汰）。修完单点先在预发验证泄漏曲线趋平。
> 关键是第三段**复测**，这是题眼，要讲成完整闭环：第一，同场景回归——用修复前能稳定复现泄漏的压测脚本/操作序列原样重跑，对比内存曲线：修复前线性上涨、修复后应稳态波动（有涨有落、GC 后回落）；第二，长稳测试——泄漏是低速率慢性病，短压测可能测不出，按比历史泄漏周期更长的时间长跑（如 7×24 小时），盯 RSS/GC 后基线是否漂移；第三，工具复验——ASan/Valgrind 重跑确认泄漏报告清零，pprof 两份快照 diff 归零，用量化证据代替「感觉不涨了」；第四，边界与副作用——修复不能引入新问题：性能回归（ASan 开销大，只在测试构建开）、补上泄漏场景的单元测试防复发；第五，上线兜底——内存水位监控与告警（RSS 阈值/容器 OOMKilled 计数），万一没修干净能在生产第一时间发现。收尾点题：泄漏修复的完整性=复现脚本+量化曲线+工具清零+防复发测试，四样齐了才叫解决。

## 讲深一层

- 「复测证明修好」的核心方法论是**对照实验**：同一复现脚本、同一压测强度、修复前后各跑一轮，画出两条内存曲线并排放——只说「修好了不涨了」是零信息，说「修复前每小时涨 80MB、修复后 24 小时基线漂移 <5MB」才是工程结论。
- Go 泄漏最常见的真凶是 goroutine 泄漏而非堆泄漏：goroutine 阻塞在无人消费的 channel 或未释放的锁上，它引用的对象集全部滞留——pprof goroutine 数曲线只涨不跌是一眼诊断指标；面 Go 岗位必带这条。
- 缓存类泄漏的正确修法是**有界化**而不是「定时清空」：TTL/LRU 让缓存有界且命中热数据；定时全清会造成周期性延迟毛刺——两种方案的性能差异能讲清是加分项。
- ASan 与 Valgrind 的取舍：ASan 插桩快 10~20 倍且报栈精确，但要重编译、只能抓它构建内的进程；Valgrind 零改码但慢 10~50 倍，适合短脚本与回归集；线上长跑泄漏用「堆快照 diff+监控」而非常驻插桩。
- 复测的隐藏收益是**留下复现资产**：能稳定复现泄漏的压测脚本沉淀进回归集，CI 里定期跑内存断言（峰值阈值/增长斜率）——泄漏从「事故」变「回归项」，这是团队级最佳实践。

## 高频追问

1. RSS 涨但 pprof heap diff 正常，什么情况？——堆外内存：CGO/系统调用占的内存、goroutine 栈扩张、mmap 大块——heap profile 只看 Go 堆；换 debug.FreeOSMemory 验证、看 runtime.MemStats 的 Sys、排查 cgo 泄漏
2. 泄漏在第三方库怎么办？——先升级/查 issue，确认为库内问题则包装隔离（限流+定期重启容器兜底）+ 上游提 PR；生产可先加周期性滚动重启止损
3. 容器里内存 OOM 但宿主机看进程不大？——容器 memory limit 含 page cache 与内核态占用；cgroup 统计口径与 RSS 不同；用 container memory working set 指标对齐 limit 再排查
4. 修复后内存曲线稳态但比泄漏前基线高，正常吗？——正常：修复后缓存/池回到设计水位（TTL 内的合法驻留）；判断标准是「有界且不随时间增长」，不是回到绝对低点
5. Go 的 GOGC/GOMEMLIMIT 对泄漏排查有什么用？——GOMEMLIMIT 限制堆上限让泄漏更快暴露（提前 OOM 而非慢性上涨）；GOGC 调大换更低 GC 频率会掩盖泄漏速率，排查期间保持默认参数

## 易错点

- 只答工具名不答复测——题眼在后半段；只讲 Valgrind/pprof 就停，面试官会追问「怎么证明修好了」，答不上来前功尽弃
- 复测只说「跑了没问题」——没有对照（修复前曲线）、没有时长（长稳）、没有量化（漂移阈值）的验证等于没测；要讲成对照实验
- Go 岗位只讲 C++ 工具链——字节后端 Go 为主，pprof/goroutine 泄漏是主考面，Valgrind 只是背景知识；工具选型要贴岗位语言
- 把「重启兜底」当修复——定期重启是止损不是解决，能说清「重启只是生产止血，根因修复+复测闭环才是解决」体现工程成熟度
