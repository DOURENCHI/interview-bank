## 题目

**背景**：性能优化相关的面试，聊到某段代码"逻辑没问题但就是慢"，面试官顺着问怎么确认是不是缓存层面的问题。

**问**：Cache miss 是什么意思？怎么判断一个程序是不是存在比较明显的 Cache 问题？

## 口述答案

> Cache miss 指 CPU 要访问的数据不在 L1/L2/L3，只能去内存甚至更远取，延迟从几个 cycle 涨到上百 cycle。分三类：compulsory（首次访问必然 miss）、capacity（工作集超过缓存容量）、conflict（多个热点地址映射到同一 set 互相挤）。判断上先量化再定位：`perf stat -e cache-references,cache-misses,LLC-load-misses` 看 miss 率和 IPC，IPC 低而 LLC miss 高基本可以确认；再用 `perf record` 找热点函数，`perf c2c` 查伪共享，Valgrind cachegrind 做逐行模拟。代码特征上，大数组按列遍历、链表随机跳转、多线程写同一 cache line 都是高发模式。

## 讲深一层

| 层级 | 典型延迟 | 容量量级 |
|---|---|---|
| L1 | 4–5 cycle | 32–64 KB |
| L2 | 12–20 cycle | 256 KB–2 MB |
| L3 | 40–75 cycle | 8–64 MB |
| DRAM | 200–300 cycle | GB 级 |

经验阈值：L1 miss rate 一般在个位数百分比，L2 通常 <5%，LLC 超过 10% 且 IPC < 1 就值得查。cache line 通常 64 B，跨行访问和伪共享都按这个粒度算代价。另一个常被忽略的点是 TLB miss 会和 cache miss 叠加，大页同时缓解两者。

## 高频追问

1. **怎么缓解 capacity miss？** —— 分块（blocking/tiling）把工作集压到缓存容量内，矩阵乘的 6 层循环分块是经典例子
2. **伪共享怎么发现和解决？** —— `perf c2c` 看 HITM 次数；解决靠 padding 到 cache line 或 `alignas(64)`，C++17 可用 `hardware_destructive_interference_size`
3. **miss 率低就一定快吗？** —— 不一定，还要看指令数、分支预测失败率和内存带宽，miss 只是其中一环

## 易错点

- 把 cache miss 等同于"内存不够"——它和容量、映射冲突、访问模式都有关，加内存往往没用
- 只看平均延迟不看 P99——偶发毛刺常来自 NUMA 远端访问或 THP 缺页，平均值会被掩盖
- 拿 `gettimeofday` 做微基准——时钟精度和噪声都比 cache 差异大，要用 `rdtsc` 或重复多次取中位数
