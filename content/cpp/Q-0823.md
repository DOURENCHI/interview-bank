## 题目

**背景**：美团 AI Agent 一面的追问题（紧跟着参数补全问的）。考的是「歧义消解」这个具体场景：检索出多个候选资源时，系统该自动挑一个还是问用户，边界画在哪。答「选置信度最高的」就掉坑了——概率不是授权。
**问**：残缺信息无法唯一确定资源，系统如何选择？

## 口述答案

> 我的原则是：先用硬约束缩小集合，再谈选择，选不动就问，绝不编造。第一步限定范围：先按租户、项目、环境、资源类型、时间这些硬条件过滤，把候选集压到权限可见、语义合法的范围内。这一步是安全边界，必须在语义排序之前做——否则语义搜索可能把无权访问的资源排到第一，候选列表本身就是一次越权泄露。第二步解析与排序：对候选做名称匹配、别名匹配或语义排序，排序只解决「优先展示谁」，不解决「是不是它」。第三步分情况处理：过滤后只剩一个候选，也不能直接用，还要检查它满足明确约束、证据充分（状态正常、版本正确）；剩多个合理候选，把最少但足以区分的信息列出来——资源 ID、所属项目、环境、更新时间——让用户选，展示的是「可区分性」而不是倾倒全部细节；零候选就明确说缺什么条件，绝不生成一个看起来像真的虚构 ID，这是操作类 Agent 最危险的行为之一。
> 第四步确认后绑定：用户选定后绑定不可变资源 ID 和版本号，执行前再查一次状态与权限，防止「确认时是 A、执行时被删了或换了 B」的竞态，必要时用条件更新或乐观锁兜底。对删除、支付、生产变更这类操作，语义相近永远不能作为自动选取依据。如果业务明确允许自动选择，比如「当前绑定工作区内唯一同名只读资源」，那必须是业务白纸黑字定下的解析规则，系统记录规则和匹配依据，而不是模型临场发挥。

## 讲深一层

- 「排序第一 ≠ 唯一正确」：top-1 是检索指标不是业务授权；把 rerank 分数当选择依据是把推荐系统的思路错搬进操作类 Agent。
- 权限前置：过滤必须在语义检索之前（至少在展示之前），否则候选列表本身就是越权信息泄露。
- 绑定不可变 ID 而非名字：名字会重复、会被改；执行前二次校验（状态、权限、版本）用条件更新/乐观锁兜底竞态。
- 虚构 ID 是幻觉的工程级危害：宁说「没找到」也不编造，宁可停也不猜——这是操作类 Agent 的底线设计。
- 确认信息的最小充分集：给用户看的候选信息要「足够区分」而非「全部信息」，3~5 个区分字段通常够，信息过载等于没问。

## 高频追问

1. 用户不想被频繁打断怎么办？——把「允许自动选」写成显式业务配置（作用域 + 条件），规则外的仍要问；规则由业务定，不是模型猜
2. 两个候选语义分数几乎一样怎么办？——分数接近说明区分度不足，恰恰是应该问用户的信号，不是掷硬币的授权
3. 自动选择错了怎么兜底？——操作前二次校验 + 高危必确认 + 全程 trace 记录匹配依据，错了能回放定位到哪条规则哪一步

## 易错点

- 「选置信度最高的那个」——把语言模型概率当业务授权，两个同名环境这类语义相近资源会直接选错
- 权限过滤放在语义检索之后——候选列表泄露无权资源，本身就是安全事故
- 找不到就编一个 ID——幻觉进操作链路是事故级 bug，正确行为是明确报缺
