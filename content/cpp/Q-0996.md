## 题目

**背景**：华为三面存储系列的压轴题，从「fsync 保证了什么」一路追问到「掉电后数据在不在」，考的是对 write→page cache→磁盘→介质这条链路的完整理解，答「fsync 就是写磁盘」是不够的。
**问**：fsync 到底保证了什么，突然掉电还能不能保证数据在？

## 口述答案

> fsync(fd) 的契约是：把该文件在内核页缓存中的脏页连同相关元数据强制刷到存储设备，设备确认写入完成后才返回——所以 fsync 返回成功代表数据已交给持久介质，而普通 write 返回只代表进了页缓存，进程崩溃不丢但掉电会丢。掉电后数据在不在，要分两种情况说：fsync 已返回的数据，理论上有保障——但注意这个「理论」依赖设备本身诚实，消费级 SSD/USB 盘的板载缓存可能没电容保护，掉电瞬间缓存里的数据照样丢，企业级设备才承诺掉电安全，这是工程上真实踩过的坑；没来得及 fsync 的数据，掉电即丢，没有任何保证。还要说清 fsync 不管什么：只管这一个 fd 对应文件，别的文件要各自 fsync；不提供原子性，多文件、多偏移的多次写不会因为一次 fsync 变成事务。所以日志型系统（数据库 WAL、文件系统 journal）的固定套路是：先写日志并 fsync，再改数据——日志先持久化，崩溃后才有东西可恢复。

## 讲深一层

- 写路径四层：应用 buffer → 内核 page cache → 磁盘 write cache → NAND/盘片；fsync 负责把前两层推到「设备确认」，最后一层靠硬件。
- fsync vs fdatasync：fdatasync 不强制刷 mtime/size 等元数据（除非 size 变了），日志追加场景省一次元数据落盘，更快。
- O_DSYNC/O_SYNC 是每次 write 自动 sync，语义等价但省系统调用；批量写场景手动 fsync 反而可控。
- 掉电测试怎么做：不能真手拔电源，用可编程电源控制器切断供电 + 事后校验数据完整性，工业上叫 power-fail test。
- 「fsync 返回了但设备骗人」的现实案例：某些消费级 SSD 掉电丢缓存但返回成功，所以关键系统要选有掉电保护的盘并在上电后做日志重放校验。

## 高频追问

1. fdatasync 和 fsync 的区别？——fdatasync 跳过非必要元数据（mtime 等），只保证数据可取回；文件大小变化时仍会刷元数据
2. 为什么数据库都先写 WAL？——日志先把「要做什么」持久化，数据页哪怕写一半损坏，重放日志也能恢复；顺序只有这一种是对的
3. 没有掉电保护的设备怎么办？——上层用日志+校验和+上电重放做软保障，或直接换企业级硬件；fsync 的语义本身救不了骗人的设备

## 易错点

- 把 write 返回成功当成已持久化——只进了页缓存，掉电必丢
- 忽略磁盘自身缓存——fsync 只保证到「设备确认」，设备内部缓存是否真落介质由硬件决定
- 以为 fsync 提供原子性/跨文件一致性——它只保证单文件数据的持久化时点，事务语义要上层自己建
