## 题目

**背景**：美团 AI Agent 一面的架构权衡题。考的是「为什么把能力做成 CLI 而不是让模型直接调库/现场写脚本」——本质是接口契约化 vs 自由生成的权衡。容易答成「方便啊」就没了，要讲出可复用、可测试、可靠性边界三层理由和代价。
**问**：为什么要把 skill/工具执行流程封装成 CLI，这种方案有什么好处？

## 口述答案

> 先说动机：把工具执行流程封装成 CLI，本质是把「能力」做成稳定的机器接口，把「怎么用」的智能留给上层。好处我总结三层。第一层是可复用：同一个 CLI 能同时服务开发者终端、CI 流水线、Skill 和 Agent——人能跑，程序能跑，模型也能跑，不必为每个入口各写一套调用逻辑；而且 CLI 在没有聊天上下文的情况下也能复现一次操作，这对排障和自动化都关键。第二层是可测试、可约束：CLI 的输入输出是明确契约——子命令、参数 schema、结构化输出、退出码、错误分类。我可以对它写真正的自动化测试，覆盖参数错误、无权限、超时、重复提交这些分支；而「让模型现场写一段脚本」每次生成都是新的，测试无从谈起。第三层是可靠性边界：CLI 内部封装鉴权、参数校验、超时、幂等和错误归一化，模型只需要提出「意图 + 参数」，不用也不允许它自己拼命令行、解释自由文本日志——模型猜错的爆炸半径被限制在接口校验层，错了会在边界被拦下。
> 代价也要主动讲，这是加分项：CLI 相比直接调库多了进程启动、序列化、环境安装和版本管理成本；服务化场景下高并发持续交互用 API、队列或 MCP 工具接口可能更合适，所以同一业务服务可以同时提供多种适配器，不必层层转发。还有两句容易漏的：封装本身不带来安全——可执行能力仍要白名单限制，凭据不能进命令行参数和日志；判断要不要封装，看它是否降低接入与排障成本，而不是目录里多了一个命令就高级了。

## 讲深一层

- Skill 与 CLI 的分工：Skill 描述「何时用、按什么步骤用、如何验收」，CLI 承担确定性执行；方法在文档里，执行在代码里，两层独立演进。
- stdout/stderr 协议：结构化结果走 stdout 给机器消费，日志走 stderr 给人看，长任务返回 run_id 供轮询——这是 CLI 作为机器接口的最低要求。
- 退出码语义要区分「命令失败」与「业务失败」：status 查到一个 FAILED 任务，命令本身成功（退出码 0），任务状态在 JSON 里；上层 Agent 靠这个区分重试策略。
- 安全细节：调用外部程序用参数数组不拼字符串，避免 shell 注入；凭据走环境注入或凭据存储，不进 argv 不进日志。
- 演进路径：脚本 → CLI → 服务 + MCP 工具；何时升级取决于并发、调用方多样性和权限集中化需求，不必一步到位。

## 高频追问

1. 为什么不直接让 Agent 写 Python 调库？——每次生成都是新代码，无法测试、无法审计、错误路径不可控；CLI 是一次写好、长期复用的受控接口
2. CLI 和 MCP 工具什么关系？——MCP 是协议层，可以把 CLI 包装成 MCP 工具暴露给宿主；一个是进程契约一个是协议契约，不冲突
3. 参数复杂时 CLI 不好用怎么办？——支持结构化输入（JSON 文件/stdin），参数 schema 版本化，复杂对象不硬塞命令行 flag

## 易错点

- 只答「方便、灵活」——说不出可复用/可测试/可靠性边界三层，等于没做过工程化封装
- 把密钥写进命令行参数——argv 在进程列表和日志里裸奔，凭据必须环境注入或凭据存储
- 认为 CLI 封装 = 安全——封装只是收敛了调用面，鉴权、白名单、幂等还是要单独做
